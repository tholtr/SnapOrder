## 附录 D：第四轮问题处理核对记录

| 原编号 | 原问题 | 处理情况 |
|---|---|---|
| R10 | 消费幂等 Key 的 24 小时 TTL 与共享 Redis 的 512MB / `noeviction` 预算冲突 | 已处理：采用方案 C，取消运行时幂等，去重下沉到离线统计 |

**R10 问题回顾**：原设计用 `SETNX risk:event:dedupe:{requestId}:{operationType}` 做消费幂等，TTL 24 小时。这是风控模块中唯一一个以小时计 TTL、且基数随事件量（而非活跃用户数）增长的 Key，量级无上界——100 条/秒下 24 小时约 1.3–1.7GB，而风控与抢单共用 512MB / `noeviction` 的同一 Redis 实例，键被撑满会连带影响抢单 Lua 写入。这是第一轮 C6 在幂等 Key 上的复发。

**定稿方案（方案 C）**：消费端不做运行时幂等、不写任何幂等 Key；每次消费只写 `risk_event_processed`（`REVIEW` 额外写 `risk_review_pending`）结构化日志。重投递只产生重复日志，不产生重复业务状态。去重职责下沉到离线统计：脚本按日志中的 `requestId + operationType` 去重后再计算指标，`risk_event_duplicate_total` 由该步骤得出。

**选择理由**：消费端不落表、不动资金、不碰抢单名额，全部产出物是结构化日志，重复一条日志的代价远低于在共享 Redis 上维护一个无上界基数幂等 Key 的风险。观测数据按 at-least-once 处理、在查询端去重，与该模块「结构化日志承载指标」的既有取向一致，且不新增表、不新增中间件。

> **P9.4 设计期已重新定位这条待办**（2026-09-11）：「在代码里显式声明」做不到。本仓库用的 `org.apache.rocketmq.client.apis.consumer.PushConsumerBuilder` **没有** `setRetryPolicy` 方法（`javap` 逐方法核对；同名方法只存在于 shaded 的 OpenTelemetry 包里，不是这个类型）。`RetryPolicy` 真正在 `org.apache.rocketmq.client.java.retry`，且只能由服务端随消费组下发（`inheritBackoff(apache.rocketmq.v2.RetryPolicy)`）。所以落点从「消费者构造代码」改为 **`docker/init-mq.sh` 的 `updateSubGroup`**，并且只能一组一组地配。`mqadmin getConsumerConfig` 回读现状：`retryMaxTimes = 16`、`groupRetryPolicy = GroupRetryPolicy{type=CUSTOMIZED, exponentialRetryPolicy=null, customizedRetryPolicy=null}`——**声明了 CUSTOMIZED 但两个 body 都是 null**，即当前的 16 次重投没有任何退避曲线。P9.4 只消掉风控自己那个新组（决策 D11），其余四个组不在本阶段范围内。
