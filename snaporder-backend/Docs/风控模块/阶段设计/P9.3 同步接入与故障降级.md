# P9.3 设计：同步接入、Shadow 与故障降级

> 依据文档：`风控反作弊实现蓝图.md`（§3.7、§3.8、§3.10）
>
> 目标：把 P9.2 交付的风控预检接入抢单用例，并证明**风控自身的故障不会破坏既有抢单正确性**。
>
> 状态：设计中。
>
> **本文档只写设计。** 实现期被推翻的初稿结论与实测硬约束一律记在 `实现期发现.md`，正文只在必要处放一行指针。

---

## 1. 本阶段边界

**做**：`GrabErrandUseCase` 内的风控调用、同步顺序约束、共享总 deadline、`fail-open` / `fail-closed`、`RiskContext` 在用例内的组装、`requestId` 在两条链路上的口径统一、降级下的并发正确性验证。

**不做**：不修改抢单 Lua、不修改 MySQL CAS、不修改 Sentinel 规则、不改变任务状态机、不新增中间件、不实现 MQ 事件（P9.4）、不做压测报告与离线指标（P9.5）。

**一个必须提前说明的范围细节**：本阶段**不承诺共享 Redis 完全不可用时抢单仍成功**（实施计划 §7.4）。风控与抢单共用同一个 Redis 实例，整个实例宕机时抢单自己也活不了——把它算作「风控可独立降级」是把两件事混为一谈。本阶段验证的是**风控路径自身的异常**：Lua 报错、键类型错误、预算耗尽。

## 2. 已拍板的决策

| 编号 | 决策 | 落实位置 |
|---|---|---|
| D1 | 接入点固定在 `grab()` 内、`GrabRateLimiterPort` 之后、信用校验之前 | §6.1 |
| D2 | 用例**不为「风控关闭」开分支**：关闭与 `SHADOW` 都落到 `denied()==false` | §6.1 |
| D3 | `Command` 增加两个可空 `String` 承载设备与 IP，`RiskContext` 在用例内组装 | §6.2 |
| D4 | `requestId` 全程**只解析一次**，controller 优先取 request attribute | §6.3 |
| D5 | deadline 做成**协作式**（每步前检查余额），**不改端口签名**（覆盖 P9.2 的 D11） | §3.3、§5.1 |
| D6 | 在途命令的上界是 Redis 客户端自身的 `commandTimeout`，本阶段**不收紧** | §4.3 |
| D7 | `fail-open` **只**作用于「预算耗尽且决策仍为 `PASS`」这一种结果 | §5.2 |
| D8 | `fail-open=false` 时拒绝，新增 `ErrorCode.RISK_UNAVAILABLE` | §5.3、§5.4 |
| D9 | `DegradeReason` 追加 `DEADLINE_EXCEEDED`，**只能追加在末尾** | §3.2 |
| D10 | 运行策略收成一个 `RiskPolicy` 领域 bean（覆盖 P9.2 §4.3 的 `@Value` 决定） | §3.1、§4.2 |
| D11 | `deadline-ms=0` 是**合法值**，语义为「强制走降级路径」 | §7.1 |
| D12 | 降级次数**不引入进程内计数器**，由 `risk_decision` 行承载 | §8.3 |

各决策的具体影响：

**D1 —— 接入点是顺序的落点。** 实施计划 §7.2 的同步顺序是「请求上下文 → Sentinel → 风控预检 → 信用分/在途任务校验 → Redis Lua → MySQL CAS」。前两项已经在 `grab()` 里：请求上下文的解析在拦截器里（P9.1），`GrabRateLimiterPort.tryPass` 是 `grab()` 的第一行。风控因此插在这一行之后、`creditRepository.scoreOf` 之前——**是一次纯粹的插入，不动任何既有语句**。

有一处措辞要校准：实施计划与蓝图都写「Sentinel 先于风控」，而当前默认配置下被装配的 `GrabRateLimiterPort` 实现是 `LocalGrabRateLimiterAdapter`（`SentinelGrabRateLimiterAdapter` 带 `@ConditionalOnProperty("dash.grab.limit.type=sentinel")`，两个 yaml 都没开）。**这不影响本阶段的结论**：本阶段要守的是「L1 在风控之前」这个**顺序**，而顺序由 `grab()` 的语句顺序保证，与哪一个实现被装配无关；换哪个实现是 P7 的事，本阶段不动。

**D2 —— 用例里没有「风控关闭」分支。** 风控关闭时恢复接入前行为（实施计划 §7.2）这条要求，不靠一个 `if (riskEnabled)` 实现，而是靠 `RiskPreCheckUseCase` 第 0 步返回 `PASS`。理由是旁路分支的代价：任何一个写着 `if (!enabled) { 跳过风控 }` 的地方，都是将来某个配置读错、某个 bean 没注入时**静默绕过风控**的入口。让「关闭」只表现为「预检自己返回 `PASS`」，则接入点对开关完全无感知，绕过的可能性在结构上消失。

代价是关闭状态下每次抢单多一次 `preCheck` 调用（第 0 步就返回，只有一次分支判断与一行日志）。这个代价是可接受的，而且那行日志正是 §3.10 要求的「关闭期间」的观测依据。

**D3 —— 上下文在用例内组装。** P9.1 的 `RiskRequest` 明确写了分工：「由知道 `errandId` 的一方（P9.3 的抢单用例）组装 `RiskContext`」（`实现期发现.md` F-8）。本阶段照办。`RiskRequest` 在 `dash-presentation`，`dash-application` 编译期看不见它，所以 `Command` 只能收扁平字段。见 §6.2，那里同时说明为什么另有一条路（`Command` 直接收 `RiskContext`）不选。

**D4 —— `requestId` 只能有一个值。** 这是一条**缺陷修复**，不是设计偏好：见 §6.3。

**D5 —— 协作式 deadline。** P9.2 的 D11 预判「P9.3 要改端口签名与相关测试」。读完两边的代码之后**这个预判不成立**，理由写在 §3.3：适配器拿到 deadline 也只能在**发起调用前**检查余额，而这与用例在调用前检查完全等价——两者都无法中断一条已在途的命令。既然如此，改三个端口、三个适配器、两个测试类的代价换不来任何额外的保证。**这是对 P9.2 D11 的显式偏离。**

**D6 —— 在途命令的上界不在本阶段手里。** 既然不收紧客户端超时（§4.3），就要如实说明：`deadline-ms` 是**协作式预算**，不是硬上界。任何声称「风控预检一定在 10ms 内返回」的说法都是错的，本文档 §4.3 给出的是**实测到的**真实上界。

**D7 —— `fail-open` 的作用域。** 这是全阶段最容易写错的一条。蓝图 §3.8 那张表里既有「风控 Lua 报错 → 记录原因并按配置放行」，也有「黑名单查询失败 → 记录降级并跳过快速拦截」，而表下面紧跟着一句「**降级不等于放行**」。两处必须分开读：

| 情形 | 性质 | 是否受 `fail-open` 管辖 |
|---|---|---|
| 某个端口抛异常 | **局部**：少一个证据，其余证据仍在 | ❌ 由「降级不是放行」处理——决策照常得出 |
| 预算耗尽 | **整体**：预检没能履行「10ms 内给结论」这个契约 | ✅ 这是 `fail-open` 唯一的作用点 |

写成「任何降级都按 `fail-open` 处理」会把一次 Redis 抖动放大成整次预检作废，而那正是 §3.8 用一整段否掉的读法。写成「`fail-open` 完全不起作用」则 `fail-open` 成了死配置项（本模块反复点名的 F-5 那一类）。**`fail-open` 只 gate 一种结果：预算耗尽后决策仍然算不出任何东西。**

**D8 —— `fail-closed` 要真的实现。** 蓝图 §3.10 与实施计划 §3 的配置块里都列着 `fail-open`，而两个 yaml 里都没有它——P9.1 落了两个 key、P9.2 落了两个，剩下 `fail-open` 与 `deadline-ms` 至今没落地。绑定一个配置项却不让它生效，就是一个死配置项；而 `fail-open: false` 是一个**能把全站抢单变成不可用**的开关，恰恰是最不能「看着像配上了其实没接」的一个。

默认仍是 `true`（蓝图 §3.10），`false` 只在本阶段定义的那一种结果上生效：超时且没有任何证据挡得住 → 拒绝。

**D9 —— 追加在末尾。** `DegradeReason` 的**声明序就是日志里 `degradeReasons` 的顺序**（P9.2 §3.4），`RiskDecisionLogTest` 逐字断言整行。插在中间会改变既有顺序、可能让已绿的用例变红——而那是**正确**的红，因为顺序是给离线脚本的跨系统契约的一部分。新增第 6 个值放在末尾，既有的五个一个字都不动。

**D10 —— 运行策略收成一个值对象。** P9.2 §4.3 把 `enabled` 定成 `@Value`，理由是「它不是领域概念，做成第三个 `RiskMode` 值会把关闭和只观察混成一个轴」——这条理由仍然成立，本阶段不推翻它。但它**没有否定一个独立的策略值对象**：追加 `fail-open` 与 `deadline-ms` 之后，用例构造器要背 8 个参数，而 `RiskProperties` 这个类存在的理由原文就是「若沿用 `@Value`，`RedisRiskFeatureAdapter` 的构造函数要背 9～10 个参数」。同一个理由在同一个模块里应当给出同一个结论。

于是：`RiskPolicy(enabled, mode, failOpen, deadlineMs)` 作为领域值对象，由 `RiskConfig` 出 bean，`RiskMode` 那个独立 bean 随之撤销（它是 `RiskPolicy` 的一部分）。**这覆盖 P9.2 §4.3 与 F-17 的实现期决定**，需要同步改设计文档 §5.1 的 `enabled` 段落——见 §4.2 的同步清单。

顺带一处收口：`RiskContextInterceptor` 的 `enabled` 也从 `@Value` 改成注入 `RiskPolicy`。**这一条是可单独砍掉的**（砍掉不影响 D10 其余部分），保留它的理由是它顺手消掉 F-17 记的那个隐患——「同一个 `dash.risk.enabled` 有两个默认值，必须人工保持一致」。收口之后，这个开关在全仓只剩 `RiskProperties` 一个默认值来源。

**D11 —— `deadline-ms=0` 是合法值。** 它的语义是「预算从第一毫秒起就不够」，于是第 1~4 步的采集全部跳过、决策退化为「所有证据为 0」、随后由 `fail-open` 决定放行还是拒绝。这让**降级路径有了一个纯配置的、确定性的触发方式**——本阶段的降级并发验证（§8.2）与将来的故障演练都会用到它。

因此启动期校验只拒**负数**，不拒 0。这条要写进文档，否则后人会顺手把 0 当成非法值拒掉，而降级演练的开关随之消失。

**D12 —— 不加计数器。** 实施计划 §7.2 要求「记录降级原因和次数」。`risk_decision` 行里的 `degraded` / `degradeReasons` 已经同时承载了原因与次数（离线按行计数即可），而蓝图 §3.10 明确「本轮使用结构化日志承载指标，不新增 Micrometer」。再加一个进程内计数器会立刻引出「怎么导出」「进程重启怎么算」「和离线口径以谁为准」三个新问题，且与 P9.5 的指标口径重复。**降级次数的唯一定义在离线统计里，本阶段只保证日志行数据完整。**

## 3. 领域层设计（`dash-domain`）

### 3.1 `RiskPolicy`

`com.campusdash.domain.risk.model` 新增：

```text
RiskPolicy(boolean enabled, RiskMode mode, boolean failOpen, int deadlineMs)
```

**为什么它是领域类型而不是配置类的嵌套**：消费它的 `RiskPreCheckUseCase` 在 `dash-application`，看不见 `dash-infrastructure`——本阶段四个字段全部要过河，所以它必须落在两边都看得见的模块里。这与 `RiskRules` / `RiskMode` 同一条理由（P9.2 §4.3），不是新增的模式。

**`enabled` 与 `mode` 放在同一个对象里，会不会把 D2 要分开的两件事混起来？** 不会。P9.2 §4.3 拒绝的是把 `enabled=false` **做成第三个 `RiskMode` 值**——那会让「关闭」与「只观察」在类型上无法区分。`RiskPolicy` 是两个**正交字段**，`enabled=false` 与 `mode=SHADOW` 在值域上仍然分得开，调用面也仍然完全不同（前者一个端口都不碰）。P9.2 §5.1 那张三态对照表一个字都不用改。

**`RiskPolicy` 不做取值校验。** `deadlineMs` 的唯一生产者是 `RiskConfig`，而它的来源 `RiskProperties` 会在绑定期拒掉负数（§4.1）。值对象层再判一次就是第二处默认值/边界，正是 F-17 记下的那类隐患。手工构造的负数会表现为「预算立即耗尽」，即降级方向，不会崩溃。

### 3.2 `DegradeReason` 追加 `DEADLINE_EXCEEDED`

```text
DEADLINE_EXCEEDED      预检的共享总预算耗尽，后续采集被跳过
```

**追加在末尾**（D9），既有五个值的顺序与语义一个字不动。它的语义边界要说准：

- 它记的是**预算**的耗尽，不是某一次调用的失败。某个端口抛异常仍然记各自的原因（`USER_WINDOW_FAILED` 等）——两者可以同时出现在一次决策里，而它们的处置确实不同：前者只是少了这个维度的证据，后者是连「去要证据」的动作都没发生。
- **一次决策里它只出现一次**。首次发现预算耗尽时记入，此后所有采集类端口一律不再调用（用一个粘住的布尔，而不是每一步各判各记）——同一事实在 `degradeReasons` 里重复四遍是噪声，不是信息。
- 它**不影响 `riskScore` 与 `action`**（`withDegradeReasons` 的既有性质）：预算耗尽只是让决策在更少的证据上做出，不是另开一条裁决路径。

### 3.3 端口**不变**（覆盖 P9.2 的 D11）

`RiskFeaturePort` / `RiskBlacklistPort` / `RiskLimitPort` 三个端口的签名、三个适配器的实现、`RiskPreCheckIT` 与 `RiskPreCheckUseCaseTest` 里的 fake 端口**全部不动**。

P9.2 的 D11 预判本阶段要改端口签名。当时的推理是「10ms 预算贯穿四次 Redis 调用，这个信息得传下去」。读到实现层之后，这个推理断了：

```text
适配器拿到 deadline 之后能做的事 = 在发起调用之前检查余额
用例拿到 deadline 之后能做的事 = 在发起调用之前检查余额
```

**两者是同一个动作。** 端口签名多一个参数，换不来任何额外的保证——因为无论谁检查，检查都发生在**调用之前**，而检查通过之后那条命令走多久，两端都管不着（那是 §4.3 的事）。既然等价，就选代价小的那个：不动端口，不动适配器，不动两个测试类里的 fake。

**这不等于「剩余时间」这个语义被丢掉了**，它被落在用例的检查点上（§5.1）：每一步之前问「还有余额吗」，没有就跳过这一步。差别只在粒度——用例按**步骤**（4 个）检查，而不是按**命令**。本阶段的每个步骤恰好一次 Redis 往返，两个粒度在当前实现下重合。

**`RiskDeadline` 也就不带 `remainingMs()` 这类数值接口**：它没有消费者，而 P9.1 已经明确反对过「给端口加一个只为打日志存在的参数」。它对外只有 `expired()` 一个查询。

## 4. 基础设施层设计（`dash-infrastructure`）

### 4.1 `RiskProperties` 补两项

```text
boolean failOpen     @DefaultValue("true")
int     deadlineMs   @DefaultValue("10")
```

四项启动期校验里新增一条：

| 校验 | 不校验的后果 |
|---|---|
| `deadlineMs >= 0` | 负数会让预算从第一毫秒起就是负数，**每一次预检都降级**。配 `fail-open=false` 时这就是「全站抢单不可用」，而它在配置里看起来只是「把超时配小了一点」。**0 必须放行**（D11）。 |

`deadlineMs` 与 Redis 客户端超时的关系（预算大于客户端超时时预算没有意义）**不做校验**：`RiskProperties` 看不见 `spring.data.redis.timeout`，为它引入一次跨配置项的耦合不值当；这条关系写进 §4.3 的说明，由运维自己保证。

### 4.2 `RiskConfig` 装配改造

```text
[删除] RiskMode  riskMode(RiskProperties p)
[新增] RiskPolicy riskPolicy(RiskProperties p)   // enabled + mode + failOpen + deadlineMs
```

`RiskRules` 与 `DeviceHasher` 两个 bean 不变。

`RiskPolicy` 的四个字段是四个不同类型/含义的位置参数，顺序写错编译器不报错——沿用 `RiskConfigTest` 已经确立的手法：**用一组两两不等的值逐个字段断言**（P9.1 的 F-5）。

**同步清单**（D10 覆盖了两个既有决定，不改文档就是让文档说谎）：

| 落点 | 改动 |
|---|---|
| 本文档 §3.1 | `RiskPolicy` 的理由 |
| P9.2 设计 §4.3 末段 | 加一行指针：`enabled` 的 `@Value` 决定已被 P9.3 的 `RiskPolicy` 覆盖 |
| P9.2 设计 §5.1「`enabled` 从哪来」段 | 同上 |
| `实现期发现.md` F-17 | 补一行后续：该结论在 P9.3 被推翻，及推翻的理由 |

**P9.2 的设计文档只加指针、不改结论文字**：设计文档写的是「当时为什么那样定」，改掉它等于抹掉 F-17 的来龙去脉——那份推理在 `fail-open` 上仍然成立，被推翻的只是「做不成领域 bean」这一步。

### 4.3 在途命令的真实上界（D6）

**已核实的实现事实**：Spring Boot 3.5.8 的 `LettuceConnectionConfiguration.createBuilder` 把 `spring.data.redis.timeout` 直接绑成 Lettuce 的 `commandTimeout`

```text
builder.commandTimeout(properties.getTimeout())
```

两个 yaml 里这一项都是 `2000ms`。因此：

```text
一条已经在途的 Redis 命令，最坏在 2000ms 后抛 RedisCommandTimeoutException（RuntimeException）。
```

这正是蓝图 §3.8 表格里「不等待全局 2000ms」所指的那个 2000ms——它**本来就存在**，是共享 Redis 客户端的超时，不是风控引入的。

于是本阶段能给的保证与不能给的保证，要分开写：

| | 保证 | 依据 |
|---|---|---|
| ✅ | 预算耗尽后**不再发起**任何新的风控命令 | 用例的检查点（§5.1） |
| ✅ | 预算耗尽后**不再等待**剩余步骤 | 同上，直接跳过 |
| ✅ | 单条命令卡住最多拖 2000ms，不是 Lettuce 默认的 60s | 上面这条已核实的事实 |
| ❌ | 预检整体一定在 10ms 内返回 | 做不到 |

**为什么不新建一个 `commandTimeout=10ms` 的风控专用连接池**：那会把「风控与抢单复用同一个 Redis 客户端」这条前提拆成两套超时，抢单 Lua 与风控脚本的行为从此可以在同一台 Redis 上不一致；而且第二套连接池自身是一个新的资源与新的故障面（连接数、`maxclients`、池耗尽时抛的异常类型都不同）。实施计划 §2 的「复用已有 Redis」与 §7.4 的「不承诺共享 Redis 完全不可用时抢单仍成功」都指向同一个方向：**Redis 是共用的，超时也应当是共用的**。

要不要收紧这个 2000ms，留到 P9.5——那时它要连同 Sentinel、请求级 2000ms 预算和压测读数一起看，在这里单独调一个客户端的全局超时是盲调。

日志里不新增任何字段来承载这件事（P9.2 的 D8 已经把格式定为跨系统契约）：预算耗尽表现为 `degraded=true degradeReasons=DEADLINE_EXCEEDED`，`decisionLatencyMs` 会如实反映当时花了多久——**它变大的那一侧正是这条上界的实测证据**。

## 5. 应用层设计（`dash-application`）

### 5.1 `RiskDeadline`

包私有（`com.campusdash.application.risk`，与 `LogField` 同处），**不进领域层**：它不是领域概念，只是编排内部的执行预算。

```text
RiskDeadline.after(long budgetMs)       // 生产用，时钟取 System::nanoTime
boolean expired()
```

测试需要一个**能推进的假时钟**（要构造「第 1 步花掉了预算、第 3 步发现耗尽」这种中途耗尽的场景，靠 `sleep` 会抖），所以内部持一个 `LongSupplier`，另有一个包私有构造器接假时钟。假时钟由用例的 fake 端口持有：端口方法被调用时把时钟推进过去，于是「哪一步之后耗尽」完全确定。

`expired()` 用 `System.nanoTime()` 做减法的符号判断，不做毫秒换算——预算是 10ms 量级，纳秒到毫秒的整除会把「剩下 0.9ms」和「已经超了 0.1ms」压成同一个数。

### 5.2 `RiskPreCheckUseCase`：检查点与第 8 步

P9.2 的七步顺序一个字不动，插入的是**检查点**与**出口**：

```text
0. !enabled                  -> 直接返回 PASS，不做任何 I/O（不变）
── 构造 RiskDeadline ──
1. ENFORCE 读限频键           ┐
2. 查三类黑名单               │ 每一步之前问一次「还有余额吗」；
3. 采集用户窗口               │ 没有则记一次 DEADLINE_EXCEEDED 并跳过该步，
4. 采集设备/IP 维度           ┘ 此后所有采集类端口一律不再调用
5. RiskRules.evaluate        -> 决策（不变）
6. ENFORCE 且 action==LIMIT  -> 写限频键（**不受检查点管辖**，见下）
7. 写决策日志行               ->（该行照常携带 DEADLINE_EXCEEDED，不变）
8. 整体不可用判定             -> 新增
```

**第 6 步为什么不进 deadline 的门。** 检查点管的是**采集证据**，而第 6 步是**执行已经做出的决定**。若预算在决策产出前耗尽、决策又恰好是 `LIMIT`，跳过写入会造成一个很坏的组合：请求被拒了（用户受到了惩罚），但限频键不存在（惩罚的依据没有了）——下一次请求立刻到来、窗口里计数照旧越线、于是再判一次 `LIMIT`，冷却永远不会发生。日志里会持续出现 `action=LIMIT` 而**冷却一次都没生效过**。让这一步写入，`LIMIT` 的语义才是完整的：这一次拒绝 + 接下来冷却一段。

**第 8 步**（D7 的唯一作用点）：

```text
if (enforce && !policy.failOpen() && budgetExhausted && decision.action() == PASS)
        -> 本次预检标记为「不可用」
```

三个条件缺一不可，每个都有对应的反向用例：

| 条件 | 去掉它的后果 |
|---|---|
| `enforce` | `SHADOW` 下会开始拒绝请求——而 `SHADOW` 的定义是不拦截 |
| `!failOpen` | `fail-open=true`（默认）时仍然拦截，等于把默认配置改成 fail-closed |
| `budgetExhausted` | 一次普通的局部降级（比如黑名单查询失败）就会拒绝整次请求 |
| `decision.action() == PASS` | **预算耗尽但证据已经足够 `BLOCK` 时会被改判放行**——这是「降级不是放行」在 deadline 语境下的同一条不变式，必须有独立用例守住 |

**日志与拦截结果会不一致，这是故意的**：被第 8 步改写为拒绝的那一次，`risk_decision` 行里仍然是 `action=PASS`。因为那**就是**决策的真实内容——决策是分数的纯函数，它没变；变的是「这次决策算不算数」。两者都能从同一行读出来（`degraded=true degradeReasons=DEADLINE_EXCEEDED action=PASS` 加上调用方的结果码），而为了对齐两者去给日志加字段，等于动一份已经冻结的跨系统契约（P9.2 的 D8）。

`decisionLatencyMs` 的计时范围不变（用例入口到决策完成或降级结束），第 8 步不计入——它不做任何 I/O。

### 5.3 `RiskPreCheckResult`：第三态

```text
RiskPreCheckResult(RiskDecision decision, boolean enforced, boolean unavailable)

    RiskAction effectiveAction()   // 不变：enforced ? decision.action() : PASS
    boolean    denied()            // 新增：调用方唯一需要读的东西
    ErrorCode  errorCode()         // 新增一个分支：unavailable -> RISK_UNAVAILABLE
```

紧凑构造器加一条不变式：`unavailable` 为真时 `enforced` 必须为真，且 `decision.action()` 必须为 `PASS`。前者由第 8 步的 `enforce` 条件保证，后者由同一行的 `action == PASS` 条件保证——写进构造器是因为**这两个条件是两个 if 的两半，将来改一处就会静默漂移**。

**`denied()` 是调用方唯一要读的东西**，这是本节存在的理由。P9.2 说「P9.3 只需要读 `effectiveAction()`，不必再判一次模式」，那句话在本阶段之前成立、现在不成立了：第三态让 `effectiveAction()==PASS` 不再蕴含「放行」。调用点若继续写 `effectiveAction() != PASS`，`fail-open=false` 就会**静默失效**——拒绝被漏掉，而这正是 `fail-open=false` 唯一要做的事。

```java
public boolean denied() {
    return unavailable || effectiveAction() != RiskAction.PASS;
}
```

`denied()` 与 `errorCode() != OK` 在当前实现下等价，但保留前者是因为调用方要表达的是「这条请求要不要拒」，而不是「有没有错误码」——后者将来多一个非拒绝性质的码就会静默失效（P9.2 对 `errorCode()` 用穷尽 `switch` 的取舍是同一个思路：让新增的档位在那里**编译不过**）。

### 5.4 错误码

`ErrorCode` 新增一个：

```text
RISK_UNAVAILABLE   "风控服务暂不可用，请稍后再试"
```

不与三个既有风控码合并：那三个说的是「**你**被判成了什么」（限频 / 审核 / 封禁，都是对行为的判定，用户换个人就没事），这一个说的是「**风控自己**没给出结论」。运维侧的意义也完全不同——出现 `RISK_UNAVAILABLE` 说明要去看 Redis 与预算配置，而不是去看用户行为。混成一个码，P9.5 就分不出「拦对了多少人」和「有多少次根本没拦住」。

## 6. 抢单链路接入

### 6.1 接入点与顺序

```java
public Result grab(Command cmd) {
    // L1：热点任务限流。放在所有下游调用之前（P7，不动）
    if (!rateLimiter.tryPass(cmd.errandId(), cmd.runnerId())) { ... }

    // L1.5：风控预检（蓝图 §3.7：Sentinel 之后、信用校验之前）。
    // 拒绝即返回：不进信用校验、不进抢单 Redis、不进 CAS。
    RiskPreCheckResult risk = riskPreCheck.preCheck(new RiskContext(
            cmd.runnerId(), cmd.errandId(), cmd.requestId(), cmd.deviceId(), cmd.clientIp()));
    if (risk.denied()) {
        return Result.failed(risk.errorCode(), null);
    }

    // L2：资格前置校验（原样不动）
    ...
}
```

四个细节：

1. **`userId` 取 `cmd.runnerId()`，不取上下文里的。** 注入的 `Command` 未必来自 HTTP（测试与将来的内部调用直接构造），而此时「被操作的身份」是 `runnerId`。用 `runnerId` 构造，则「风控看的用户」与「抢单的用户」**在类型上不可能不是同一个**；用外部传进来的 userId 则是两处各自维护、靠约定相等。
2. **被风控拒绝的请求不进候选队列。** `enqueueCandidate` 只在「抢输了」时调用，被风控拒绝不是抢输了——把这些人放进候选队列，等于让风控拦下的账号继续占有流转机会。
3. **返回 `Result.failed(code, null)`**，与既有的失败形态一致（`rank` 为 `null`）。不改 `Result` 的形状。
4. **`preCheck` 抛异常不在这里兜底。** 端口异常已在 `RiskPreCheckUseCase` 内部逐条转成降级原因，第 8 步之外没有能抛出来的路径；在这里再套一层 try-catch 会造出一个「用例层不知道的降级语义」，两处对「什么算降级」的判断迟早分叉。这条由单测钉住：fake 端口抛异常时 `grab()` 不抛、照常走完。

### 6.2 `Command` 的扩展与 PII

```text
Command(long errandId, long runnerId, String requestId, int creditScore,
        String deviceId, String clientIp)

Command(errandId, runnerId, requestId)                  // 保留
Command(errandId, runnerId, requestId, creditScore)     // 保留
```

两个便捷构造器**必须保留**：全仓有 27 处 `new GrabErrandUseCase.Command(...)`，其中大部分在 IT 里，它们是「原有抢单正确性测试」的组成部分，改签名去逼它们逐个改，等于把一次接入变成一次覆盖面很广的重构。既有调用点传 `null`、`null`，风控仍然照跑——只是设备与 IP 两个维度缺失（`RiskContext` 的紧凑构造器会把空白归一成 `null`，下游跳过对应维度）。

**这会把原始设备标识与原始 IP 带进 `dash-application`**，代价必须写在明处（P9.1 的 D1：原始值只应在解析层与哈希层之间短暂存在）。两条约束随之成立：

- **`Command` 必须覆写 `toString()`**，输出里不含 `deviceId` / `clientIp`。`Command` 是个到处传的 record，默认 `toString()` 会把这两个字段原样打出来，而 `GrabErrandUseCase` 的 catch 块里已经有一条 `log.warn`——今天它只打 `errandId` / `runnerId`，但「今天恰好没打」不是约束。覆写是 3 行代码换一条**结构上**的保证。
- `Record` 的 `equals` / `hashCode` 仍包含这两个字段。这是对的：它们确实是这次调用身份的一部分，去掉会制造两个「相等」但风控结果不同的 `Command`。

**为什么不让 `Command` 直接收一个 `RiskContext`**（另一条看起来更干净的路）：`RiskContext` 自带 `errandId`，与 `Command.errandId` 成为两个可能不一致的字段，而它们不一致时没有任何地方会报错——风控按 A 任务判、抢单按 B 任务抢。`Command` 收两个扁平字符串则没有这个缝。

### 6.3 `requestId` 只能解析一次（缺陷修复）

**现状**：

```text
RiskContextResolver.requestIdOf(头部)
    -> 空白或缺失时返回 UUID.randomUUID().toString()

ErrandController.grab      调一次  -> 进 Command          -> 抢单幂等键 errand:idem:{requestId}
RiskContextInterceptor     调一次  -> 进 RiskRequest     -> RiskContext -> 风控窗口去重成员
```

**两次调用，两个 UUID。** 预存缺陷 D-2 的修复统一了**函数**（`ErrandController` 不再自己判空，改调同一个 `requestIdOf`），但没有统一**取值**——同一个空白头，两个调用点各生成一个。

**为什么今天无害、P9.3 之后有害**：`requestId` 是两条链路之间的**关联键**。P9.4 的风险事件靠它标识「哪一次业务操作」，P9.5 的离线统计「按 `requestId + operationType` 去重」。接入之后，对于**不发 `X-Request-Id` 头的客户端**，`risk_decision` 行里的 `requestId` 与 `errand:idem:` 键里的那个值不是同一个字符串——于是「这条风控决策对应哪一次抢单」在数据上无法回答。而按实施计划 §9.4 的说明，本轮前端不发这个头，**等于对全部真实流量都断了这条关联**。

**修法**：`requestId` 只在一处产生，另一处复用它。

```java
@PostMapping("/{errandId}/grab")
public Result<...> grab(@PathVariable long errandId,
                        @RequestAttribute(value = RiskRequest.ATTR, required = false) RiskRequest risk,
                        @RequestHeader(value = REQUEST_ID_HEADER, required = false) String requestId) {
    var cmd = new GrabErrandUseCase.Command(
            errandId, CurrentUser.get(),
            risk != null ? risk.requestId() : RiskContextResolver.requestIdOf(requestId),
            60,                                // creditScore，P5 起被忽略，原样保留
            risk != null ? risk.deviceId()  : null,
            risk != null ? risk.clientIp()  : null);
    ...
}
```

- **优先取 attribute**：拦截器已经把「这次请求是哪个请求」算过一次，且它同时是风控链路用的那个值。复用它是唯一能保证两条链路同值的做法。
- **attribute 缺失时才回退到 `requestIdOf`**：拦截器在三种情况下不写 attribute——风控总开关关闭、该路径没有已认证用户、解析抛异常（它记一条 warn 后放行，`RiskContextInterceptor.preHandle` 的三个 return 分支）。前两种情况下风控链路根本不存在（不会产生 `risk_decision` 行），第三种已经被记了 warn。回退分支只为「拦住 500」而存在，不改变任何一条已生效链路的口径。
- **两条链路仍然共用 `requestIdOf` 这一个函数**（D-2 的成果不丢），只是不再各调一次。

**回归锁**：`RequestIdIdempotencyIT`（4 例，真实 HTTP）必须原样通过——它锁的正是「空白头下的幂等行为」。另加一条**新的**、只有本阶段才可能有意义的断言（§8.2）：同一次请求里，风控窗口 ZSet 的去重成员与抢单幂等键指向**同一个** `requestId`。

## 7. 配置落地

### 7.1 新增配置项

```yaml
dash:
  risk:
    deadline-ms: 10        # 新增：预检的共享总预算
    fail-open: true        # 新增：预算耗尽且无证据时是否放行
```

两项蓝图 §3.10 的配置示例里本来就有，P9.1/P9.2 只是没落（那时用不上）。

`deadline-ms` 的注释必须写清三件事：它是**协作式**预算（不是硬上界）；**0 是合法值**，语义是「强制走降级路径」（故障演练与降级验证用）；启动期拒负数（D11）。

`fail-open` 的注释必须写清：默认 `true`；改成 `false` 之后，风控超时会变成**拒绝请求**，是能把全站抢单变成不可用的开关；以及它只在「预算耗尽且无证据」这一种结果上生效（D7）。

### 7.2 校验与顺序

沿用 P9.2 §6.2 的落点与顺序：**先改测试 yaml 建好启动基线，再动代码**（`预存缺陷与坑.md` K-1）——测试 yaml 是整体替换而不是合并，反过来做会被一串启动失败淹没。

## 8. 测试策略

### 8.1 单元测试（无中间件依赖）

沿用仓库约定：纯 JUnit 5 + `@DisplayName` 中文场景名，不用 Mockito，需要的协作者手写 fake（fake 记录每一次调用，于是「这一步有没有发生」从注释里的声明变成可断言的事实）。

| 目标 | 要覆盖的性质 |
|---|---|
| `RiskDeadline` | `after(0)` 立即过期；假时钟推进后 `expired()` 翻转；**未耗尽时不受假时钟以外的影响** |
| `RiskPreCheckUseCase` —— **预算耗尽** | 耗尽后**四个采集端口一个都没被调用**（journal 断言，不是只看结果码）；决策照常完成并写日志行 |
| `RiskPreCheckUseCase` —— **中途耗尽** | 假时钟让第 1 步花掉预算：第 1 步的端口被调用、第 3、4 步的没有，且 `budgetExhausted` 与「第一步是否成功」无关 |
| `DEADLINE_EXCEEDED` 只记一次 | 中途耗尽后 `degradeReasons` 里它**恰好出现一次**，不是四次 |
| **降级不是放行**（deadline 版） | 预算耗尽但黑名单已经返回 `BLOCK` → 决策仍是 `BLOCK`，第 8 步不改判 |
| **第 6 步不受预算管辖** | 预算耗尽、`action==LIMIT`（由已采集到的证据得出）→ 限频键**仍然被写** |
| `fail-open=true`（默认） | 预算耗尽 + `PASS` → `denied()` 为 false、`errorCode()==OK` |
| **`fail-open=false`** | 预算耗尽 + `PASS` + `ENFORCE` → `denied()` 为 true、`errorCode()==RISK_UNAVAILABLE` |
| `fail-open=false` + `SHADOW` | 仍然放行——`SHADOW` 的定义不能被一个降级开关改写 |
| `fail-open=false` + 局部降级 | 某端口抛异常（非预算耗尽）→ **照常放行**，`fail-open` 不该在这里生效（D7 的回归锁） |
| `RiskPreCheckResult` | `denied()` 的三种状态；`unavailable` → `enforced` 的不变式；`errorCode()` 含 `RISK_UNAVAILABLE`；紧凑构造器拒绝「unavailable 且 action 非 PASS」 |
| `GrabErrandUseCase` —— **拒绝后零后续调用** | 风控拒绝 → 返回风控码，且信用仓储、`GrabSlotPort`、`TransactionalStep` **三个计数器全为 0**（对齐既有的限流用例手法） |
| `GrabErrandUseCase` —— 放行 | 风控放行 → 原有链路逐步照常走完 |
| `GrabErrandUseCase` —— 关闭 | `enabled=false` 时行为与接入前一致（同一条断言序列） |
| `GrabErrandUseCase` —— 异常不外溢 | fake 端口抛异常时 `grab()` 不抛、照常返回（§6.1 第 4 点） |
| `Command` | `toString()` **不含** `deviceId` / `clientIp`（PII 的回归锁）；两个便捷构造器把两个字段置 `null` |
| `RiskProperties` | `deadlineMs` 负数被拒、**0 放行**（D11 的回归锁） |
| `RiskConfig` | `RiskPolicy` 四个字段**两两取不同的值**后逐个断言（沿用 `RiskRules` 同一手法，见 §4.2） |

### 8.2 集成测试

**`RiskGrabLinkIT`** —— 三条链路各自的独立 `@Nested` 上下文（与 `AuthModeIT` 同型：外层不挂 `@SpringBootTest`，每个 `@Nested` 自带 properties）。`ENFORCE` 那个额外用 `webEnvironment = RANDOM_PORT`：D4 的回归锁必须走真实 HTTP，`requestId` 的解析缺陷整个活在 controller 与拦截器之间，直接调用例会绕过它。

| 上下文 | 性质 | 用例设计 |
|---|---|---|
| `ENFORCE` | **高频用户在抢单 Redis 之前被拦** | 同一用户对同一任务连发 `shortThreshold + 1` 次（次数由配置推导，不写死）。前几次按正常结果返回，最后一次必须是 `RISK_LIMITED`。**「没进后续链路」的判据是 `errand:idem:{requestId}` 不存在**——幂等键由 `grab.lua` 写入，它不存在就说明 Lua 从未执行；这比对名额数或 `grab_record` 更直接 |
| `ENFORCE` | **黑名单用户不进入后续链路** | 写入用户黑名单键后抢单 → `RISK_BLOCKED`，且同样断言幂等键不存在；收尾删键（黑名单键没有 TTL，共享测试库不能留垃圾） |
| `ENFORCE` | **键盘类型错误只降级不拦** | 把 `RiskKeys.deviceCluster(hash)` 手工建成**字符串**：`risk_cluster.lua` 的 `SADD` 报 `WRONGTYPE` → 适配器抛 → 记 `CLUSTER_FAILED` → **抢单照常成功**。这是蓝图 §3.8「键类型错误只适用于特征采集」那句话的直接证据（黑名单查询用 `EXISTS`，对类型不敏感，没有这条路径） |
| `ENFORCE` | **两条链路的 `requestId` 同值**（D4 的回归锁） | **刻意不带 `X-Request-Id` 头**走真实 HTTP 抢单，再从 `errand:idem:{errandId}:*` 里取出服务端生成的那个值，断言 `risk:win:{userId}:10s` 这个 ZSet 的成员里有它。**必须是空白头**：带上显式头时新旧代码本来就同值（P9.3 之前也是），测不出任何东西；而按实施计划 §9.4，本轮前端根本不发这个头，也就是这条分支覆盖的正是全部真实流量。幂等那一半仍由 `RequestIdIdempotencyIT` 守着 |
| `SHADOW` | **不改变业务结果** | 同一设备上 `lowThreshold + 1` 个账号，**各抢自己的单名额任务**（不是多名额任务，原因见 `预存缺陷与坑.md` D-4），断言**每一次都成功抢到**、设备集合确实越线、且 `risk_decision` 行确实算出了非 `PASS` 的动作。**三条缺一不可**：没有第三条，「SHADOW 全放行」与「风控关掉」在行为上无法区分；没有第二条，第三条就没有来源 |
| `ENFORCE` + `fail-open=false` + `deadline-ms=0` | **按配置降级** | 每个抢单请求都被 `RISK_UNAVAILABLE` 拒绝，且**不产生任何 `risk:win:*` 键**（键集合差集）——第二条是「降级真的发生了」的反证，没有它，用例可能只是把请求拦在了别处 |

**`RiskDegradeConcurrencyIT`** —— 单独一个类、单独一个上下文（`deadline-ms=0` + `fail-open=true`）：**降级时 2000 并发抢 1 个名额，成功 1 个、零超卖**，骨架复用 `GrabConcurrencyIT`（虚拟线程 + `BenchRun` 登记 + verify SQL）。

同样必须断言**降级确实发生了**：测试期间不产生任何 `risk:win:*` 键。少了这一条，这个用例就退化成 `GrabConcurrencyIT` 的复制品——它证明的是「风控降级时抢单仍然正确」，而**风控没有降级**的世界里它同样会全绿。

判据还要再补一条**反证**：单看「零新增」可能是「压根没人走到 preCheck」造成的。所以同时断言**抢中者的用户窗口键不存在**——他确实走完了整条链路，他的键本该存在。没有这条，前一条在风控完全没接上的世界里也会全绿。

**「没进入后续链路」的判据为什么不写成 mock 计数**：IT 里没有 mock（全仓无该依赖），而 `errand:idem:` 键是**由被测链路自己写下的**痕迹，比任何外部观测都硬。它与「§8.1 的计数器断言」是互补的：单测证明调用面，IT 证明落点。

**降级路径不全进 IT**：`USER_WINDOW_FAILED` 等四类端口异常仍由 §8.1 的 fake 覆盖（P9.2 §7.2 已确立）。IT 只加**一个**真实可诱发的故障——键类型错误，因为它不需要 mock 也不需要断连，`SET` 一个字符串即可。

**`SHADOW` 上下文把 `deadline-ms` 从默认 10 放宽到 1000**，这是**必须的**，不是为了让用例更容易过。本上下文要断言的是「设备集合真的攒到了阈值之上」，而集合写入在 10ms 预算下是尽力而为的：实测新 Spring 上下文的**第一个**请求耗时 15ms（连接池冷启动），整段采集被跳过，集合少一个成员，断言随之失败——那次失败与 `SHADOW` 的语义毫无关系。预算行为有专门的用例（`ZeroBudgetFailClosed` 与 `RiskDegradeConcurrencyIT`），不该在这里被顺带检验。详见 `实现期发现.md` F-19。

**IT 不登记 `BenchRun` 的判定沿用 P9.2 §7.2**：`RiskGrabLinkIT` 只读 Redis 与既有业务表、不写新的压测记录，与 `AuthModeIT` 一致；`RiskDegradeConcurrencyIT` **要登记**（它跑了 2000 并发、有超卖校验，与 `GrabConcurrencyIT` 同一性质）。

### 8.3 不做什么

- **不做 `SHADOW → ENFORCE` 灰度切换的自动化**：蓝图 §3.10 说 SHADOW 是「先观察一段真实流量再切」，那个「一段」是运维用配置决定的。本阶段只保证两个模式各自的行为被断言过。
- **不加降级计数器**（D12）。
- **不验证「整个 Redis 宕机」**：实施计划 §7.4 已排除。
- **不重复验证 P9.2 的决策逻辑**：阈值、档位、黑名单语义全部由 P9.2 的用例守着，本阶段一个字不改。

## 10. 验收标准

| 验收项（实施计划 §7.3） | 判定方式 |
|---|---|
| 正常抢单链路无回归 | 完整 `mvn test` 全绿（**看总用例数与 `Skipped`，不是失败数**，见 K-2） |
| **高频用户在抢单 Redis 前被拦截** | `RiskGrabLinkIT`：突发请求的最后一次返回 `RISK_LIMITED`，且 `errand:idem:{requestId}` 不存在 |
| **黑名单用户不进入后续抢单链路** | `RiskGrabLinkIT`：`RISK_BLOCKED` + 幂等键不存在 |
| **风控拒绝后无信用、Redis、DB 后续调用** | 单测：三个计数器全为 0；IT：幂等键不存在（两者互补） |
| `SHADOW` 模式不改变业务结果 | `RiskGrabLinkIT` 的 `SHADOW` 上下文：全部成功，与 `ENFORCE` 上下文形成对照 |
| **风控异常时接口按配置降级** | `fail-open=true`：`RiskDegradeConcurrencyIT` 全部放行；`fail-open=false`：`RiskGrabLinkIT` 全部 `RISK_UNAVAILABLE`。**两侧都要有**——只测一侧证明不了「按配置」 |
| **降级时 2000 并发抢 1 个名额仍成功 1 个且零超卖** | `RiskDegradeConcurrencyIT`（复用 `GrabConcurrencyIT` 的 verify SQL） |
| 原有抢单正确性测试全部通过 | `GrabConcurrencyIT` / `SettlementIT` / `TimeoutTransferIT` / `CreditIT` / 两个缓存 IT 原样通过 |
| 键类型错误只降级不拦 | `RiskGrabLinkIT`：设备键被建成字符串 → 抢单照常成功 |
| `fail-open` 只作用于预算耗尽（D7 的回归锁） | 单测两条：局部降级 + `fail-open=false` → **仍放行**；预算耗尽 + 证据已够 `BLOCK` → **仍 `BLOCK`** |
| 第 6 步不受预算管辖 | 单测：预算耗尽 + `LIMIT` → 限频键仍被写入 |
| `deadline-ms=0` 合法且语义为强制降级 | `RiskProperties` 单测放行 0、拒负数；两个 IT 上下文实际使用它 |
| 两条链路的 `requestId` 同值（D4 的回归锁） | `RiskGrabLinkIT`：ZSet 成员与 `errand:idem:` 键指向同一个值 + `RequestIdIdempotencyIT` 原样通过 |
| `Command.toString()` 不含 PII | 单测逐字断言 |
| 新增风控 Domain 类型通过 ArchUnit 分层约束 | `ArchitectureRuleTest` 自动纳入 |
| 原有测试全部通过 | 完整 `mvn test` 全绿 |

**验收时必须如实记录的两条限制**：

1. **10ms 不是硬上界**（§4.3）。预算耗尽后不再发起新命令，但一条已在途的命令由共享 Redis 客户端的 `commandTimeout`（当前 2000ms）兜底。文档与结论里不得出现「预检一定在 10ms 内返回」这类说法。
2. **不承诺共享 Redis 完全不可用时抢单仍成功**（实施计划 §7.4）。风控与抢单共用一个实例，本阶段验证的只是风控路径自身的异常。
