# P9.4 设计：异步事件与消费去重口径

> 依据文档：`风控反作弊实现蓝图.md`（§3.9、§4、§5.3）
>
> 目标：把风险行为记录**移出同步主链路**，并把「重复投递怎么办」这件事一次性定死到离线下游。
>
> 状态：设计中。
>
> **本文档只写设计。** 实现期被推翻的初稿结论与实测硬约束一律记在 `实现期发现.md`，正文只在必要处放一行指针。

---

## 1. 本阶段边界

**做**：风险事件的触发判据与载荷、时间窗聚合（四个闸门键）、异步发送与失败记录、消费端处理与日志行、离线去重脚本、`docker/init-mq.sh` 的新 topic 与消费组、以及那条悬了很久的**消费重试窗口**。

**不做**：不改抢单 Lua / MySQL CAS / Sentinel / 任务状态机；不改资金、超时、通知四个既有 topic；不给另外四个消费组补重试策略；不新增中间件与服务进程；不做压测报告与指标报告（P9.5）。

**一条必须先说清的范围细节**：本阶段交付的**唯一**一处「真连 broker」的自动化验证是 `RiskEventIT`。在此之前，全仓 27 个 IT **无一例外**都写着 `dash.mq.enabled=false`——测试 yaml 的注释把「集成测试不依赖外部 broker」写成了明确的设计意图（`预存缺陷与坑.md` K-1）。本阶段要动它，就得说清为什么值得：蓝图 §5.3 的第一条验收是「风险事件正常发送和消费」，这条在**没有 broker 的世界里无法被证伪**——一个把 `sendAsync` 写反了、body 拼错了、topic 名打错了的实现，用假 producer 的单测照样全绿。所以本阶段**只开一个类**（`RiskEventIT`），并且给它加独立的中间件守卫（§8.2）。

各决策的具体影响：

**D1 —— 命名法。** 仓库既有的四个 topic 全是 `errand-*`（`errand-confirm-timeout` / `errand-auto-settle` / `errand-fund-event` / `errand-cache-evict`），既有消费组全是 `dash-*-consumer`（`dash-timeout-consumer` / `dash-autosettle-consumer` / `dash-fund-event-consumer` / `dash-cache-evict-consumer`）。照抄：`errand-risk-event` + `dash-risk-event-consumer`。

**topic 做成常量、组名做成配置**这条不对称是照 `CacheEvictConsumer` 的先例来的：topic 是**代码两侧必须一致**的名字（生产者与消费者各写一份字面量，漂移了就是「发了没人收」且不报错），所以由端口提供唯一常量；组名是**部署期**的东西（同 topic 多组是常态，`errand-fund-event` 已经有两个组），必须能在不改代码的前提下另起一个。

**D2 —— 判据只写一遍。** 实施计划 §8.2 的触发集合是「`LIMIT/REVIEW/BLOCK`、黑名单命中、风控降级」。黑名单命中的动作恒为 `BLOCK`，所以这个集合并起来就是 `action != PASS || degraded`。写成 `RiskDecision` 上的方法而不是在两个调用点各写一遍 `if`：本阶段至少有两个地方要用它（决策时判断要不要分配 `eventId`、投递时判断要不要入队），两处一旦漂移，症状是「分配了 id 却没发」或「发了事件却没有 id」——**两种都不报错**。

**D3 —— `eventId` 在决策时分配。** 这是本阶段唯一一处对既有已交付签名的改动，也是 P9.3 自己预告过的：`RiskDecisionLog` 里那个恒为 `-` 的 `eventId=` 字段，注释原文写着「等 P9.4 真有 eventId 时，『给它一个来源』这件事会表现为改签名，编译器会把所有调用点找出来」。

为什么不改成「发送时才生成」：那样 `risk_decision` 行的 `eventId=` 会**永远**是 `-`。一条冻结契约里的永久空字段，就是本模块反复点名的死配置项——看起来接上了，实际没有。而按 D3，两行共用同一个 id，于是「分配了事件号但最终没上 MQ」变成**可统计的**（决策行有 id、`risk_event_publish` 行说 `SUPPRESSED`/`DROPPED`），而不是看不见的。抑制率的口径因此是完整的：分母来自决策行，分子来自投递行。

**D4 —— 聚合键不带时间桶。** 蓝图 §3.9 的键名示例是：

```text
risk:event:gate:limit:{userId}:{10sBucket}
```

本阶段落地为不带第二段的形式，窗口靠 TTL 表达：

```text
risk:event:gate:limit:{userId}
```

三步都是 `SET key 1 NX EX <窗口秒>`。**为什么不能是带桶的形式**：

1. **桶会在窗口边界上泄漏。** 桶名把时间切成 `[0,10)`、`[10,20)` 这样的格子，于是 `t=9.9s` 与 `t=10.1s` 两次事件落在两个桶里、**各自都抢到了键**——同一用户 0.2 秒内上了两条 MQ，而规则写的是「10 秒内最多 1 条」。`SET NX EX` 的语义是「距上一次发送满 N 秒才允许下一次」，与规则逐字对应，没有边界。
2. **桶名必须在调用点算出来**，而 `RiskKeys` 是**纯名字构造器**（它自己的类注释：「风控 Redis 键的唯一构造入口」）。把时间计算塞进去，等于让一个键名工具同时承担时钟职责——然后单测要么依赖真实时钟，要么给键名类注入一个假时钟。

花括号保留（`{userId}`、`{instanceId}`），与 `limitKey` 同型：蓝图与实施计划逐字写着这个形状，运维会照着 `redis-cli` 敲；键名与文档不一致的后果，`RiskKeys.limitKey` 的注释已经写过一次了。

**D5 —— 窗口不做配置。** 蓝图 §3.9 的表格把四个窗口定死为 10/60/60/10 秒，它们是**语义值**（「同一用户 10 秒最多一条」就是这个规则本身），不是运维旋钮。做成四个配置项会立刻引出四个新默认值，以及「文档写 10、yaml 写 30」这类没人能发现的漂移。写成领域常量之后，改窗口等于改语义，必须同时改设计文档——这正是我们想要的摩擦。

代价是 IT 不能靠「把窗口配成 1 秒」来加速，因此 §8.2 的聚合用例**不等待窗口过期**，改断言键的 TTL（见 §8.1）。

**D6 —— 聚合判断与发送整体离开请求线程。** 蓝图 §3.9 只说「使用 `sendAsync`，不能阻塞抢单主链路」。`sendAsync` 本身已经异步，但**闸门判断是一次 Redis 往返**，而风控与抢单共用同一个 Redis 实例；`实现期发现.md` F-19 实测过饱和时单次往返是 **15ms** 量级。把这次往返留在请求线程上，等于给抢单链路加一段**不受 `deadline-ms` 管辖**的延迟——P9.3 刚把预检做成协作式预算，这里反手在预算之外接一段不可控的 I/O，是把上一阶段的结论原地推翻。

还有一个更硬的理由：RocketMQ 客户端**首次向某个 topic 发送时要查路由**，那是同步的网络往返。`sendAsync` 不保证这一步也异步。放在请求线程上，第一个风险事件会给某一次抢单凭空加上一次未实测过的延迟尖峰。

于是：请求线程只做一次 `offer`（失败即 `DROPPED`），其余全部在执行器线程上。

**D7 —— 闸门按动作优先定档。** 一次决策可以同时是「`LIMIT`」和「降级」（比如黑名单查询挂了、但用户窗口已经越线）。闸门只能用一个，取 `action != PASS` 的那一个：动作型事件的证据价值高于降级通告，**如果反过来**——降级键抢到了、`LIMIT` 键没抢到——被抑制的恰好是攻击信号，抑制掉的是我们要看的东西，方向完全反了。

**D8 —— 闸门失败仍然发送。** 聚合是**保护 MQ 的手段**，不是「要不要记录」的判断。Redis 抛异常时抑制掉事件，等于在最需要证据的时刻（Redis 出问题往往伴随流量异常）把证据丢掉。多几条 MQ 只是成本，丢证据是能力缺失。

反方向的风险（有人靠打死 Redis 来放大 MQ）不成立：风控与抢单共用一个 Redis，Redis 挂了抢单本身就挂了，没有流量可供放大。

**D9 —— 队列满要留痕。** 队列有界是必须的（broker 挂掉时不能无限吃内存），但「有界」必然意味着丢弃。丢弃本身可以接受（蓝图 §3.9 定的是 best-effort），**静默丢弃不可以**——否则 P9.5 的报告里「事件数比预期少」会变成一个无法归因的现象。所以队列满时请求线程记一条 `result=DROPPED`。

**D10 —— 格式非法不重试。** 一条字段缺失、数字解析不了的消息，重投 16 次之后仍然是同一条消息。让它走完重试链只会把重试队列堵住、并且在 P9.5 的「无长期堆积」验收上制造一个假问题。所以：**格式非法 → 记日志 + `SUCCESS`**（丢弃），**处理异常 → `FAILURE`**（重投）。两者的区别是「这条消息永远好不了」与「这次处理失败了，下次可能成功」。

**D11 —— 重试窗口只能声明在服务端。** `风控模块设计问题清单.md` 附录 D 那条待办写着「本项目所有 `PushConsumer` 均未配置 `setRetryPolicy` / `maxDeliveryAttempts`」。**这条待办在代码侧无法完成**——本阶段实地核实了 `rocketmq-client-java 5.2.0` 的公开 API：

- `PushConsumerBuilder` 的**全部**公开方法里没有 `setRetryPolicy`（已用 `javap` 逐个方法确认）；
- 全 jar 范围内 `setRetryPolicy` 只出现在 shaded 的 OpenTelemetry 类里；
- `RetryPolicy` 接口确实存在，但在 `org.apache.rocketmq.client.java.retry` 包下，且它的 `inheritBackoff(apache.rocketmq.v2.RetryPolicy)` 签名说明了它是**从服务端下发**的。

也就是说：这条待办的落点是消费组的服务端配置，不是代码。`mqadmin updateSubGroup` 提供两个开关——`-r/--retryMaxTimes` 与 `-p/--groupRetryPolicy`（JSON，形如 `{"type":"EXPONENTIAL","exponentialRetryPolicy":{"initial":1000,"max":10000,"multiplier":2}}`）。现状（`getConsumerConfig` 回读）是：

```text
retryMaxTimes     = 16
groupRetryPolicy  = GroupRetryPolicy{type=CUSTOMIZED, exponentialRetryPolicy=null, customizedRetryPolicy=null}
```

**`type=CUSTOMIZED` 而两个 body 都是 `null`**——一个「声明了但没有内容」的状态，正是这条待办要消掉的东西。本阶段只消掉**风控自己的组**（§6.4），另外四个组的重试次数不去动：它们承载的是资金与超时语义，把 16 次改成 3 次可能丢一次超时流转，那是 P3/P5 的领域，风控阶段不该有意见。

**D12 —— 消费端完全不落状态。** 蓝图 §3.9 已定，这里补一条实现期的理由：消费端**连 Redis 都不写**。风控与抢单共用一个 Redis，而幂等键的基数是**没有上界**的（每个 `requestId` 一个），一旦被撑满会连带影响抢单 Lua 的写入——蓝图 §3.9 原文就是为了避开这一点才把去重下沉到离线。这条在实现上表现为：`RiskEventProcessor` 的依赖里**没有** `StringRedisTemplate`，也不会有 `JdbcTemplate`。给它的构造函数加一个存储依赖，就是这条决策被破坏的第一现场。

**D13 —— 日志字段值的空白中性化。** `LogField.safe` 目前只替换 ISO 控制字符（CR/LF/Tab），**不处理空格**。而 `requestId` 来自客户端的 `X-Request-Id` 头，是一个可以带空格的自由文本。于是下面这个头：

```text
X-Request-Id: x action=BLOCK
```

会产生这样一行：

```text
risk_decision userId=1 ... requestId=x action=BLOCK action=PASS ...
```

离线脚本按空格切分取 `action` 时，读到的是**客户端写进去的值**。这不是「日志难看」，而是**指标可被外部输入伪造**——而 P9.5 的整个报告都建立在这些行上。本阶段要给四个新日志行接上同一个 `LogField.safe`，也就是把这条通路**复制**一份，所以顺手把闸门补上：空格一并替换为 `_`（控制字符的处理不变）。

**范围的最终形态**（实现期定档，见 §4.4）：挡的不是「空格」两个字面字符，而是 `isISOControl` / `isWhitespace` / `isSpaceChar` 三个谓词的并集——第二类里 `U+2028`/`U+2029` 能造出整行、第三类里 `U+00A0` 一类能多切出一个字段，两种失效方式都得堵，而真正无害的 `U+200B`（ZWSP）两个都不挡。

**这一条是对既有已交付行为的改动**（`risk_feature` / `risk_decision` 两行的输出会变，仅限值里本来含空格的行）。`LogField` 自己的注释说过「Tomcat 会拒绝含裸 CR/LF 的请求头，所以这道闸平时用不上」——同样的论证在空格上不成立，Tomcat 不拒绝含空格的请求头。所以本阶段**一起改**（已拍板）。它影响 `LogField` 的两条既有格式锁单测（§8.1 的第三行），**单独砍掉也不影响其余任何部分**——这是它当初能作为独立选项摆出来的原因。

**D14 —— 消费行不写 `consumedAt`。** `occurredAt`（事件自己的时间）必须写，因为它是事件载荷的一部分、也是 `lagMs` 的计算基准。但消费时刻**不再单独写一个字段**：日志行自身的时间戳就是消费时刻，再写一个 `consumedAt` 等于引入两个可以互相矛盾的时间源，而离线脚本该信哪个并没有答案。`lagMs` 是两者的差，它的存在已经证明「消费时刻被记下来了」。

## 3. 领域层设计（`dash-domain`）

### 3.1 `RiskOperationType`

`com.campusdash.domain.risk.model` 新增一个枚举，本轮**只有一个值** `GRAB`。

为什么只有一个值还要做成枚举：蓝图 §3.9 要求 `requestId + operationType` 共同标识一次业务操作，这个组合之所以需要两个字段，正是因为「同一个 requestId 可能对应多类操作」是设计允许的未来。做成枚举（而不是字符串常量）买到三件事：日志与载荷里只会出现枚举名（不含空白，天然不可伪造）、离线脚本的取值范围是封闭的、新增操作类型必须改代码（于是必须被评审看见）。**声明序即日志顺序**的既有约定同样适用：新值只能追加在末尾。

### 3.2 `RiskEventGateType`

```text
LIMIT(10)  REVIEW(60)  BLOCK(60)  DEGRADED(10)     // 括号内为窗口秒数
```

窗口值是蓝图 §3.9 那张表（D5：不做配置）。做成枚举而不是四个常量，是为了让「键名段」与「窗口」**同源**：键名里的 `limit`/`review`/`block`/`degraded` 由枚举名小写得到，TTL 由枚举字段给出，两者不可能漂移。将来加第五类闸门时，`RiskKeys` 的 `switch` 会因不穷尽而编译失败。

`windowSeconds()` 之外不提供别的访问器——特别**不提供**把枚举映射成 `DegradeReason` 的方法：`DEGRADED` 是一个闸门，不是一个降级原因，本轮的降级原因可以是五个值中的任何一个。把两者混成一个轴，正是 P9.2 拒绝过的那个错误。

### 3.3 `RiskEvent`

```text
RiskEvent(String eventId, String requestId, RiskOperationType operationType,
          long errandId, long runnerId, RiskOutcome outcome, RiskAction decisionAction,
          boolean degraded, List<DegradeReason> degradeReasons, long occurredAt)
```

一个与 `RiskDecision` 平行的值对象，紧凑构造器负责把载荷的不变式收在一处：`eventId`/`requestId` 非空白、`degradeReasons` 为 `null` 时收成空列表、`degraded == false` 时 `degradeReasons` 必须为空（与 `RiskDecision` 的同类约束同向）。

**为什么单独一个类而不是复用 `RiskDecision`**：`RiskDecision` 是规则层的输出，它不知道 `eventId`、`operationType`、`occurredAt` 这三样东西——那些是「这次业务操作」的属性，不是「这次决策」的属性。硬塞进去会让规则层背上它不需要的概念（P9.2 的 F-14 已经为同一类问题否掉过一次签名扩展）。`RiskEvent` 是应用层把两边拼起来的产物。

`RiskOutcome` 是新增的两值枚举 `PASSED` / `DENIED`（= 蓝图载荷里的 `outcome`）。**如实说明**：本轮它与 `decisionAction` 之间可由 `decisionAction == PASS` 推出，是一个冗余字段。保留它的理由有两条——它在蓝图 §3.9 的载荷字段表里是冻结的；以及它把「挡不挡」与「挡在哪一档」分成两个轴，将来调整档位分值表时（`LIMIT` 的分数线从 30 挪到 40 之类）离线口径不需要跟着动。

### 3.4 `RiskDecision.producesEvent()`

```java
public boolean producesEvent()   // == action != PASS || degraded
```

D2 说的那个唯一判据。加在 `RiskDecision` 上而不是某个工具类里：它是**关于一次决策**的性质，读起来就是 `decision.producesEvent()`。

### 3.5 `RiskEventPort`

`com.campusdash.domain.risk.ports` 新增：

```java
public interface RiskEventPort {
    String TOPIC_RISK_EVENT = "errand-risk-event";   // D1
    void publish(RiskEvent event);
}
```

三个设计点：

1. **`publish` 不返回任何东西、也不抛领域异常。** 它必须能在任何情况下立即返回（蓝图：不能阻塞抢单主链路），失败由适配器自己记日志。返回 `boolean` 会诱使调用方写 `if (!published)` 分支，而那正是 blueprint 要避开的「异步异常影响同步结果」。
2. **端口不暴露 topic。** topic 常量放在端口上是为了给**实现方与消费方**同一个字面量，不是给调用方的参数——调用方说「发一条风险事件」，它不该有机会说「发到哪个 topic」。
3. **端口不带 deadline / 不参与 `RiskDeadline` 预算。** 它在决策**之后**被调用，已经在预算的作用域之外了。给它一个 deadline 参数会让人以为它受预算管辖，而它真正需要的保证是「立刻返回」（由 D6 的执行器提供）。

## 4. 基础设施层设计（`dash-infrastructure`）

### 4.1 `RiskKeys` 新增四个闸门键

```java
public static String eventGate(RiskEventGateType type, long userId)    // LIMIT/REVIEW/BLOCK
public static String eventGate(RiskEventGateType type, String instanceId)  // DEGRADED
```

产出 `risk:event:gate:{limit|review|block}:{userId}` 与 `risk:event:gate:degraded:{instanceId}`（D4）。

**两个重载而不是一个 `Object` 参数**：主体是 `long`（用户）还是 `String`（实例）由闸门类型决定，`Object` 会把「给 `LIMIT` 传实例名」这种错误从编译期挪到运行期。

`instanceId` 复用 `requireHash` 的**校验精神**但不复用它的正则：它要求 32 位十六进制，而实例名是 `[A-Za-z0-9._-]+`。校验必须做，理由是 D4 保留的那对花括号——`{` 是 Redis Cluster 的 hash tag 分隔符，实例名里一旦混进 `}`，键的 hash tag 会**静默变成另一个字符串**，两个实例的键可能撞到一起（也可能不撞，取决于名字），而这类问题只在 Cluster 下才现形。非法值直接抛 `IllegalArgumentException`，与 `requireHash` 一致。

**基数与 TTL**：这是本阶段唯一新增到共享 Redis 的键。三类用户键的基数上界是「**活跃用户数 × 1**」、降级键是「**实例数**」，且每个键都在 10/60 秒后自己消失——与蓝图 §3.9 拒绝「运行期幂等键」时给出的理由（基数无上界）不是同一类东西，这一点必须在评审时讲清楚，否则会被当成同一个错误。

### 4.2 `RedisRiskEventGate`

```java
@Component
public class RedisRiskEventGate {
    boolean tryAcquire(RiskEventGateType type, String subject);   // true = 抢到，可以发
}
```

实现就是 `redis.opsForValue().setIfAbsent(key, "1", Duration.ofSeconds(type.windowSeconds()))`。三个细节：

1. **值仍是常量 `"1"`**，照 `RedisRiskLimitAdapter` 的先例——闸门只回答「键在不在」，把时间写进值里就多出一个「谁负责读」的悬案。
2. **`setIfAbsent` 返回 `null` 时抛 `IllegalStateException`**，照 `RedisRiskLimitAdapter.isLimited` 的先例（该处注释已说明：普通调用拿不到 `null`，拿到说明调用方式变了）。
3. **失败语义与限频键相反**：这里抛出去的异常会被适配器捕获并转成「仍然发送」（D8）。适配器**不做**这个转换——它是策略，属于调用方（与 `RiskLimitPort` 的既有分工一致）。

### 4.3 `RiskEventPublishLog` 与 `RiskEventConsumeLog`

四条日志行，按生产侧/消费侧拆成两个类（照 `RiskDecisionLog` / `RiskFeatureLog` 的一类一线族的先例）。字段 camelCase、空格分隔、空值渲染 `-`、集合按枚举声明序以 `|` 连接——与既有两条行完全一致。

**生产侧（`RiskEventPublishLog`）**：

```text
risk_event_publish eventId=... requestId=... operationType=GRAB errandId=... runnerId=...
                   decisionAction=LIMIT degraded=false gateType=LIMIT result=SENT

risk_event_publish_failed eventId=... topic=errand-risk-event error=<异常类名>
```

`result` 的四个取值收在 `RiskEventPublishResult` 枚举里（`com.campusdash.infrastructure.risk`），声明顺序即下面这个表的顺序，枚举名原样渲染进日志行——它就是 §8.3 脚本要匹配的字面量：

| 值 | 含义 | 离线映射 |
|---|---|---|
| `SENT` | 闸门放行，已交给 `sendAsync` | `risk_event_publish_total` |
| `SUPPRESSED` | 被时间窗聚合抑制（含聚合开关关闭时的**不发**——不存在这种情形，见下） | `risk_event_suppressed_total` |
| `SENT_GATE_FAILED` | 聚合判断本身失败，仍然发送（D8） | `risk_event_publish_total` + 降级指标 |
| `DROPPED` | 执行器队列满，未入队（D9） | `risk_event_dropped_total` |

**`SENT` 的含义到此为止——不是「已投递」**（见 §10 的同一句）：它到没到 broker 由 `risk_event_publish_failed` 的**缺席**间接说明，而缺席不是证明。

**为什么不设 `SENT_UNGATED`（聚合开关关闭）**：实施计划 §9.4 定的是「同一攻击流量、同一配置时长下跑两次」的**对照实验**，两次运行各自有一整份日志，开关状态由运行本身确定。为它多造一个状态值，只会让「这个值算不算发送成功」多出一个需要判断的分支。

`risk_event_publish_failed` 是**独立一行**而不是 `risk_event_publish` 的第五个 `result` 值：发送失败是在 `CompletableFuture` 的回调里才知道的，与前面那行的产生时刻隔着一次网络往返。把它并进去只有两种做法——要么把 `risk_event_publish` 也推迟到回调里写（那样 `SUPPRESSED` 与 `DROPPED` 这两类根本不会回调的事件就没法记了），要么让它承载一个「还不知道」的值。两种都比多一行差。

**消费侧（`RiskEventConsumeLog`）**：

```text
risk_event_processed eventId=... requestId=... operationType=GRAB errandId=... runnerId=...
                     outcome=DENIED decisionAction=LIMIT degraded=false degradeReasons=-
                     occurredAt=1757600000000 lagMs=42 deliveryAttempt=1

risk_review_pending eventId=... requestId=... operationType=GRAB errandId=... runnerId=...
                    occurredAt=1757600000000
```

`occurredAt` 用 **epoch 毫秒**（照 `TimeoutTraceLogger.tsEpochMs` 的先例，JSON 载荷里也是同一个值），不用 ISO 字符串：离线脚本拿它直接做减法，不需要解析时区。

`risk_review_pending` 只带「去查这一单需要的最小集合」。**它不重复 `decisionAction`**——这条行的存在本身就意味着 `REVIEW`，写上是个恒为常量的字段；手工审核入口要的是 `eventId` 与 `errandId`，其余可以从 `risk_event_processed` 行取。

**四条行都必须有 `format(...)` 纯函数 + 逐字格式锁单测**（照 `RiskDecisionLogTest` / `RiskFeatureLogTest` 的手法：整行文本断言 + 字段顺序游标）。`TimeoutTraceLogger` 是唯一没有格式锁的行，而它的消费方（`analyze_s5_trace.py`）只能靠字符串标记定位——P9.4 的离线脚本要在**四条行**上做统计，没有格式锁就等于把契约交给运气。

### 4.4 `RocketMqRiskEventAdapter`

实现 `RiskEventPort`，`@Component` + `@ConditionalOnProperty(name = "dash.mq.enabled", havingValue = "true")`（与 `RocketMqConfig` 同构）。

**执行器（D6、D9）**：

```text
ThreadPoolExecutor(1, 1, 0, MILLISECONDS, new ArrayBlockingQueue<>(4096), 命名为 risk-event-pub 的守护线程)
```

- **单线程**：线程上只做「组包 → 闸门 SETNX → `sendAsync`」三件事，而 `sendAsync` 本身不等待网络。并发在这里没有收益，只会让抑制判断的调用顺序变得不可预测（单线程下同一用户的连续事件天然有序，日志更好读）。
- **`AbortPolicy` + 捕获 `RejectedExecutionException`** → 记 `DROPPED`。不用 `CallerRunsPolicy`：那会把「队列满」这件异步侧的拥塞，变成请求线程上一次同步的 SSH 往返，恰好抵消 D6。
- **守护线程 + `@PreDestroy` 里 `shutdown()`**：不 `awaitTermination`。理由：抢单进程关停时不该为风险事件多等；队列里没发出去的事件会丢，这是 best-effort 的边界，写进 §10 的限制。

**`publish(RiskEvent)` 的实现步骤**：先按 D2 判据早退（理论上调用方已经判过，适配器再判一次是**防御性**的——但这里保留它，因为「误调用导致凭空发事件」的代价远高于一次布尔判断）→ `offer` 到执行器 → 失败即记 `DROPPED` 并返回。

**执行器线程上的流程**：闸门定档（D7）→ 若 `aggregationEnabled` 为假则跳过闸门直接发 → 否则 `tryAcquire`；抢到发、没抢到记 `SUPPRESSED`、抛异常记 `SENT_GATE_FAILED` 后照发（D8）→ `producer.sendAsync(message)` → `.whenComplete(...)` 里失败记 `risk_event_publish_failed`。

**消息组包**用的是既有的 `ClientServiceProvider.newMessageBuilder()`，与 `RocketMqDelayMessageAdapter` 同型，`setTopic(RiskEventPort.TOPIC_RISK_EVENT)`、`setKeys(eventId)`（消息键 = `eventId`，控制台上可按它直查）。

**载荷是手写 JSON 字符串拼接，不引 JSON 库**——沿用仓库的既有取舍（`TimeoutTraceLogger` 手拼、五个消费者手写 `extractLong`）。字段顺序与 §3.3 的声明序一致，**顺序即契约**（消费者的解析与离线脚本都按位置无关、按名字取，但顺序固定能让日志与消息体肉眼可比）。

**`requestId` 必须做 JSON 转义**，这是载荷里**唯一**由客户端控制的字段。不转义的后果不是「格式难看」：客户端发一个

```text
X-Request-Id: x","decisionAction":"BLOCK
```

就能在事件里**多插一个字段**，而消费端与离线脚本都按名字取值——一次伪造的字段会直接进指标。转义规则只需覆盖 JSON 字符串内必须转义的三个字符（`"`、`\`、控制字符），不引库。这与 D13 是同一类问题在两个载体（日志行、JSON 载荷）上的两次出现。

### 4.5 `NoopRiskEventAdapter` 与装配

`dash.mq.enabled=false` 时装配空实现（`@ConditionalOnProperty(..., havingValue = "false", matchIfMissing = true)`），与既有的 `NoopDelayMessageAdapter` / `NoopCacheEvictAdapter` / `NoopFundEventAdapter` 三兄弟同型，位置也放一起（`com.campusdash.infrastructure.config`）。

**空实现里什么都不做**（不记日志、不计数）。理由：测试 yaml 的 `dash.mq.enabled=false` 意味着**几乎全部 IT** 都在用这个实现，任何一行日志都会变成噪音；而「MQ 关闭」这件事本身已经有配置可查。

`RocketMqConfig` 不需要新 bean：生产者复用既有的 `timeoutProducer` 吗？**不。** 那是个泛型 `Producer`（构建时**刻意**没调 `setTopics`，注释写明「预绑定会让 topic 不存在时直接启动失败」），复用它意味着风险事件的发送失败会与超时消息的发送互相影响失败计数与重试观测。**给风险事件单独一个 `Producer` bean**：一个 topic 一个 producer 是仓库既有的做法（`RocketMqFundEventAdapter` 就为事务消息单独建了一个）。

**`LogField.safe` 的补丁（D13）**：改动落在 `isNeutralized` 一个方法上（快慢两条路径都调它，所以只改一处）。补一条回归用例（值 `a b` → `a_b`），并**逐字断言既有两行中一条含空格值的输出**，把这次改动钉住。

**净化范围最终是三个谓词的并集（实现期补上第三类，2026-09-11 拍板）**：`isISOControl` 管 CR/LF/Tab，`isWhitespace` 管 ASCII 空格与 `U+2028`/`U+2029`/`U+3000`，再加 `isSpaceChar` 管 `U+00A0`（NBSP）/`U+2007`（FIGURE SPACE）/`U+202F`（NNBSP）。

第三类是实现期实测补上的：它们**不**是换行（`isWhitespace` 对它们为 false，所以曾从两个条件中间穿过去），但 Python 的 `str.split()` 认它们是分隔符——`X-Request-Id: x<NBSP>action=BLOCK` 照样能多切出一个字段，与 D13 要堵的是同一件事。选 `isSpaceChar` 而不是「把 Unicode 空白全挡上」，是因为它对真正切不开的 `U+200B`（ZWSP）为 false，不会把造不出危害的字符也一并换掉。三类各自的失效方式与实测表见 `实现期发现.md` 的 F-21。

**`LogField` 搬家（实现期定档）**：它原先是 `dash-application/.../risk/` 的**包私有**类，而 D13 要把这道闸接到四条新行上——`risk_event_publish` 的产生点在 `dash-infrastructure`，`dash-domain` 之外什么都看不见（pom 层面看不见，不是 ArchUnit 拦的）。三个使用方里有一个够不着的。落点选了**下沉到 `dash-shared` 并改为 `public`**：不新增任何模块边，且 `dash-shared` 已经住着同类的横切工具（`SnowflakeIdGenerator`），比放进 `dash-domain`（定位是业务规则与领域模型）语义上准确。搬家的代价是 main 侧两处 import，加 `dash-shared` 里一个新的 `LogFieldTest`——那边验**净化器本身**（快慢两条路径、U+2028/U+2029、纯空白值），既有两行那边继续验**调用路径**，两者不重复。

## 5. 应用层设计（`dash-application`）

### 5.1 `RiskDecisionLog` 的 `eventId` 落地

`format` / `emit` 增加一个 `String eventId` 参数，`EVENT_ID_NOT_WIRED` 常量删除（D3）。

`RiskDecisionLogTest` 的两条用例随之改写：原来的 `eventIdIsAlwaysPlaceholder` 变成「判据成立时是分配到的值」「判据不成立时是 `-`」。**字段名与顺序一个字不改**——这是冻结契约的边界，字数、位置、总数都不动。

### 5.2 `RiskPreCheckUseCase` 分配 `eventId`

在构造 `RiskDecision` 之后、写决策日志之前：若 `decision.producesEvent()` 则生成一个 `UUID.randomUUID().toString()`，否则为 `null`。

**生成方式是 UUID 而不是雪花 ID**：仓库里雪花 ID 的使用者是 `SnowflakeIdGenerator`（worker 侧），而这里在 app 侧、且**不要求有序**（`occurredAt` 已经给了时间序）。UUID 的既有先例是 `RiskContextResolver` 给缺失的 `requestId` 生成的那一个。为它引一个跨进程的 id 生成器（还要 `worker-id` 配置）是纯粹的负担。

### 5.3 `RiskPreCheckResult` 携带 `eventId`

`RiskPreCheckResult` 增加一个可空 `String eventId`，随决策一起交回调用方。

**为什么不让 `RiskPreCheckUseCase` 自己投递**：投递需要 `operationType`，而「这次预检属于哪类业务操作」是**调用方**的知识。让预检去接收 `operationType` 就等于把「预检」这个能力的签名绑死在「它只服务抢单」上——而 `RiskPreCheckUseCase` 目前对业务类型一无所知，这个无知是它最好的性质。

于是分工是：**预检负责「这次决策有没有事件号」（它知道判据），用例负责「把事件组装出来并投出去」（它知道业务操作）**。同一判据（`producesEvent()`）在两侧都被调用，实现只有一处（D2）。

### 5.4 `GrabErrandUseCase` 组装并投递

在 `preCheck` 返回之后、`denied()` 分支**之前**插入一处投递（单一调用点，覆盖全部触发情形）：

```java
if (result.producesEvent()) {
    riskEventPort.publish(RiskEvent.of(result, RiskOperationType.GRAB, requestId, errandId, userId, clock));
}
```

`outcome` 由 `result.denied()` 决定（`DENIED`/`PASSED`），`occurredAt` 取当前毫秒。**在 `denied()` 分支之前**而不是在各返回点上分别调用：`grab()` 有多个返回点，散布式调用迟早会漏掉一个，而漏掉的症状是「某个动作不发事件」——静默、且只在离线统计里表现为「少了一点」。

构造器增加第 15 个参数 `RiskEventPort`。P9.3 已经把 `GrabErrandUseCaseTest` 收敛成共用 `Fixture`，所以这个改动在测试侧只有一处。

**时钟**：`RiskEvent.of` 接受一个 `long occurredAt` 参数而不是在内部调 `System.currentTimeMillis()`，用例提供一个 `LongSupplier`（默认 `System::currentTimeMillis`）。理由与 `RiskDeadline` 留假时钟接缝相同：`occurredAt`/`lagMs` 是要被断言的量，没有接缝就只能断言「大于 0」。

## 6. 消费侧设计（`dash-worker`）

### 6.1 载荷解析

`RiskEventPayload`（`dash-worker/.../worker/`）：把消息体解析成一个小 record，只含消费端真正要的字段。

**不复制第五份 `extractLong`。** 仓库里五个消费者各自有一份**私有静态** `extractLong`，且实现有细微差异（`CacheEvictConsumer` 不处理负数、`FundEventPushConsumer` 空值返回 0、`AutoSettleConsumer` 跳过前导空白与引号）——同一个工具的五份手抄本已经漂移了。本阶段的载荷还要解析**字符串**字段（`eventId`/`requestId`/`operationType`，而 `extractLong` 只管数字），再抄一份只会把漂移面积扩大。

所以：新写一个 `RiskEventPayload.parse(String json)`，字段提取与 **JSON 反转义**（对应 §4.4 的转义）收在它内部，配独立单测。**既有五份一个字不动**——它们的行为已经和五个消费者的语义绑在一起，本阶段没有立场去动（§8.3）。

解析失败（字段缺失、数字非法、引号不配）抛 `IllegalArgumentException`，由处理器转成 D10 的「格式非法」路径。

### 6.2 `RiskEventProcessor`

```java
@Component
public class RiskEventProcessor {
    ConsumeResult process(String body, int deliveryAttempt);
}
```

流程（蓝图 §3.9 的四步，逐条对应）：

1. `RiskEventPayload.parse(body)`；
2. 写 `risk_event_processed`（`lagMs = now - occurredAt`，负数按 `0` 记并保留原值——时钟漂移不是拒绝一条日志的理由）；
3. `decisionAction == REVIEW` 时**额外**写 `risk_review_pending`；
4. 捕获 `IllegalArgumentException` → 记 `risk_event_invalid` 行 + `SUCCESS`（D10）；其余异常 → `FAILURE`。

**这个类的构造器里没有 `StringRedisTemplate`、没有 `JdbcTemplate`、没有 `RiskProperties`**——这是 D12 在代码上的形态。它的依赖只有日志行与时钟。

`risk_event_invalid` 是第五条行，只带 `error` 与 `deliveryAttempt`，**不打印原始 body**：body 里有 `requestId`，而原始 body 的转义/长度都不受控，往日志里塞一段外部文本正是 D13 要堵的那类通路。要排查内容，用 topic 上的消息键去控制台查。

### 6.3 `RiskEventConsumer`

照既有四个消费者的形态逐项对齐：`@Component` + `@ConditionalOnProperty(dash.mq.enabled=true)`、`@PostConstruct start()` 里 `provider.newPushConsumerBuilder()...build()`、`@PreDestroy stop()` 里 `close()`、`setClientConfiguration(configuration)`、`setSubscriptionExpressions(Map.of(RiskEventPort.TOPIC_RISK_EVENT, new FilterExpression("*", FilterExpressionType.TAG)))`、`setMessageListener(view -> processor.process(utf8(view.getBody()), view.getDeliveryAttempt()))`。

组名走 `@Value("${dash.mq.group.risk-event:dash-risk-event-consumer}")`（D1）。body 用 `StandardCharsets.UTF_8.decode(view.getBody()).toString()`。

`setConsumptionThreadCount` **不设**（用客户端默认）：风险消费是「解析 + 写日志」，没有 I/O 等待，加线程只会让 `risk_event_processed` 行的相对顺序更乱。`TimeoutTransferConsumer` 需要 32 个线程是因为它每条消息都要跨进程调用。

### 6.4 重试窗口：声明在消费组上（D11）

`docker/init-mq.sh` 新增：

```bash
# 普通类型 topic（不带 -a；DELAY/TRANSACTION 才需要声明 message.type）
admin "updateTopic -n $NAMESRV -c $CLUSTER -t errand-risk-event"
admin "updateSubGroup -n $NAMESRV -c $CLUSTER -g dash-risk-event-consumer \
       -r 3 -p '{"type":"EXPONENTIAL","exponentialRetryPolicy":{"initial":1000,"max":10000,"multiplier":2}}'"
# IT 专用消费组（RiskEventIT 在测试 JVM 里手建消费者用它）
admin "updateSubGroup -n $NAMESRV -c $CLUSTER -g dash-risk-event-it"
```

取值理由：风险消费端只写日志，**一条失败 3 次的消息几乎必然是格式非法或 worker 整体不可用**。初值 1 秒、倍增、上限 10 秒，三次重投在 10 秒内走完；而默认的 16 次会在 worker 停机时堆出一条要十几分钟才排空的重试队列，让 P9.5 的「无长期堆积」验收多出一个与风控无关的观察对象。

**`-r` 的语义（最大重试次数还是最大投递次数）本设计不预设**，实现时必须用 `getConsumerConfig` 回读确认，并把回读结果记进归档——`updateSubGroup` 的成功输出只有一行 `tail -1`，不确认就等于没配。

**IT 专用消费组写进生产初始化脚本**是一个刻意的选择：`RiskEventIT` 需要一个不与应用/worker 争抢消息的组，而它的名字如果只活在测试代码里，就成了一个「在别人机器上跑才失败」的隐藏依赖（`预存缺陷与坑.md` K-2 那一类）。

## 7. 配置落地

### 7.1 新增配置项

```yaml
dash:
  risk:
    event-aggregation-enabled: true    # 新增：时间窗聚合总开关（P9.5 对照实验的自变量）
    instance-id: ${HOSTNAME:unknown}   # 新增：降级闸门键的主体
```

`event-aggregation-enabled` 在蓝图 §3.10 与实施计划 §3 的配置块里本来就有，P9.1–P9.3 只是没落（那时没有事件可聚合）。它的注释必须写清两件事：**关掉它不改变任何同步决策**（蓝图 §3.9「聚合不得改变同步风险决策结果」），以及它只影响「有几条上了 MQ」。

`instance-id` **没有 `@DefaultValue`**，两个 yaml 各写一次：主配置 `instance-id: ${HOSTNAME:unknown}`（容器里 `HOSTNAME` 天然存在），测试 yaml `instance-id: it-instance`（**写死一个可预测的字面量**，这样 IT 能直接算出降级闸门键名去断言 TTL）。缺失时绑定期失败——这是刻意的，与 K-1 的建议一致（先改测试 yaml 建好启动基线，再动代码）。

**`dash-worker` 的 yaml 一个字都不动**（即 `src/main/resources/application.yaml`，方案的取舍见 §8.4，已定方案 A）。理由是三条叠起来：

- topic 是端口常量、消费组走 `@Value("${dash.mq.group.risk-event:dash-risk-event-consumer}")`——与 worker 里那四个消费者**同一种写法**（已逐个核对：`CacheEvictConsumer`、`FundEventConsumer`、`AutoSettleConsumer`、`TimeoutTransferConsumer` 全都带 `:` 默认值），所以缺 key 不是启动失败；
- 方案 A 让 worker 根本不绑 `RiskProperties`，本阶段新增的两个 key（`event-aggregation-enabled` / `instance-id`）都只在 app 进程里成立；
- `RiskEventProcessor` 按 D12 的构造器形态**没有** `RiskProperties` 依赖，`RiskEventConsumer` 只接 topic、group、processor 三个东西。

这一段不是假设：设计期的现场实验已经实测到 worker 启动失败，见 `预存缺陷与坑.md` D-5。**注意 `src/test/resources/application.yaml` 是另一回事**——那份要新建、且必须整份抄自上面这个文件（K-1 的整文件替换，见 §8.2）。

### 7.2 校验与顺序

沿用 K-1：**先改测试 yaml，再动代码**。`event-aggregation-enabled` 有默认值、`instance-id` 没有——后者是这次唯一会在启动期报错的项，所以它必须第一个进 yaml。

### 8.1 单元测试（无中间件依赖）

| 目标 | 要覆盖的性质 |

| `RiskDecision.producesEvent()` | 四个动作 × `degraded` 两态的**全枚举**；`PASS` 且未降级为假（这条是「普通 PASS 不发事件」的实现形态） |

| `RiskEventGateType` | 四个窗口值（10/60/60/10）逐个断言——**这是语义值，必须钉死**，不能只断言「大于 0」 |

| `RiskEventConsumeLog` | 两条行的逐字格式 + 顺序游标；`degradeReasons` 空集渲染 `-`、非空按声明序 `|` 连接 |
| `LogField.safe`（D13） | 三类字符 → `_`：控制字符（原有行为不变）、`isWhitespace`（ASCII 空格 + `U+2028`/`U+2029`/`U+3000`）、`isSpaceChar`（`U+00A0`/`U+2007`/`U+202F`）；**反面样本** `U+200B`（ZWSP）不被换掉；既有两条行的含空格值输出被**逐字断言** |
| `RiskEventPayload` | 正常载荷往返（含转义过的 `requestId`）；缺字段/数字非法/引号不配三种非法输入被拒；**转义回归锁**：`"x\":\"decisionAction\":\"BLOCK"` 解析后 `requestId` 是那一整串、而不是多出一个字段 |
| `RiskEventProcessor` | 四条路径：正常 → 1 条 `processed`；`REVIEW` → 额外 1 条 `review_pending`；**同一条 body 喂两次 → 两行日志、零次存储调用**（蓝图 §5.3 的「重投递只产生重复日志」）；格式非法 → `risk_event_invalid` + `SUCCESS`；处理异常 → `FAILURE` |
| `RiskEventProcessor` 的依赖 | 断言它的构造函数里**没有**存储类依赖（D12 的结构性回归锁：`StringRedisTemplate`/`JdbcTemplate` 不在构造器参数里，用反射检查） |
| `RocketMqRiskEventAdapter` | 手写假 `Producer`（`org.apache.rocketmq.client.apis.producer.Producer`，7 个方法）+ 假闸门：聚合关闭 → 每次都发；聚合开启 → 同用户第二次 `SUPPRESSED` 且**未调用** `sendAsync`；闸门抛异常 → `SENT_GATE_FAILED` 且**仍调用**了 `sendAsync`；`sendAsync` 返回失败 future → `publish_failed` 行；队列满 → `DROPPED` 且**未**入队 |
| `GrabErrandUseCase` | 判据成立 → 恰好一次 `publish`，事件字段逐个断言；判据不成立 → **零次调用**；投递抛异常 → 抢单结果不受影响（对齐 P9.3 已有的「异常不外溢」用例） |
| `GrabErrandUseCase` 的 `outcome` | `denied()` 为真 → `DENIED`；`degraded` 但放行 → `PASSED` 且 `degraded=true` |
| `RiskPreCheckUseCase` | 判据成立时分配了非空 `eventId`；不成立时为 `null`；`occurredAt` 用假时钟 |
| `RiskConfig` | `event-aggregation-enabled` 与 `instance-id` 的 bean 装配（沿用「两两取不同值」的既有手法） |

**手写假 `Producer` 的代价要说在前面**：`Producer` 有 7 个方法，其中 5 个（两个同步 `send`、`beginTransaction`、两个 `recallMessage*`）在这个假实现里只会抛 `UnsupportedOperationException`。这是仓库「不用 Mockito、手写 fake」的既有代价，不是新增的——但它意味着**这个假实现必须尽量薄**：不要在它里面记录调用流水之外的东西。

### 8.2 集成测试

**`RiskEventIT`** —— 全仓第一个、也是本阶段唯一一个开着 MQ 的测试（两个嵌套上下文，都 `dash.mq.enabled=true`）。

**它在 `dash-bootstrap` 里（包 `com.campusdash.it`），靠「两个真进程」验往返。** 设计初稿写的是「它必须住在 `dash-worker`」，理由是这个模块边界：消费者类在 `dash-worker` 的 `com.campusdash.worker` 包下，而 `dash-bootstrap` 的 pom 只依赖 `dash-presentation` + `dash-infrastructure`、**不依赖 `dash-worker`**。**那个理由是成立的**（下面「为什么不只看测试 JVM」一节保留它），但结论下早了：不必把用例搬去一个连 HTTP 脚手架都没有的模块——把 worker 当**子进程**拉起来，bootstrap 里就能同时握住两端。

三个观测面，缺一条都有假绿的余地：

| 观测面 | 是谁写的 | 承载什么判据 |
|---|---|---|
| 测试 JVM 的内存 `LogCapture` | 真 Spring 上下文（HTTP + `GrabErrandUseCase` + 真 `RocketMqRiskEventAdapter`） | `risk_event_publish` 行的字段（动作、`result`、`gateType`）；HTTP 响应里的幂等键 → `requestId` 同值 |
| 观察者 `PushConsumer`（组 `dash-risk-event-it`，测试 JVM 里手建，照 `dash-bench` 的 `DelayMessageProbe` 同型） | broker | 载荷逐字段；**这份载荷是「消息真的过了一遍 broker」的唯一证据**——本地打完日志而没发出去（`local_message` 那次事故）它抓不到，日志更抓不到 |
| 子进程的日志文件 | `java -jar dash-worker/target/dash-worker-*.jar`，真 `WorkerApplication` | `risk_event_processed` 行（消费者真的执行过） |

**跨进程的全部证据是一个 `eventId`**：发布行与消费行里必须是同一个值。两行分属两个进程、两个日志文件，谁也不能替谁说话。这与 §8.3 的离线口径是配套的——那份脚本正是按这三类行做统计的。

**为什么不只看测试 JVM**：bootstrap 的上下文里根本没有 `RiskEventConsumer`（不在它的扫描路径里），所以「消息被消费了」这件事在测试 JVM 内**没有观测面**。写成「测试 JVM 收到消息 = 消费成功」的用例是假绿——收到消息只证明 broker 上有，不证明消费者跑过。子进程写下的 `risk_event_processed` 行才承载后者。D-5 能躲过四个阶段（`dash-worker` 至今没有任何 `@SpringBootTest`）是同一个盲区；那个口子由 **0c** 的 `WorkerApplicationContextTest` 堵（它钉的是**装配**，不需要 broker），**不由本用例堵**——两者是两件事。

**子进程只覆盖一个配置项：数据源指向隔离库 `campus_dash_worker_it`**（`--spring.datasource.url=...`）。其余全部走**生产 yaml**——这与既有 27 个 IT 的处境正好相反（那些 IT 关着 MQ、按测试 yaml 装配）。按生产配置跑意味着下面四件事都真的会发生：

- **五个 `@Scheduled` 任务启动即跑第一次**。它们都写成 `fixedDelayString` / `cron` 而**没有一个带 `initialDelay`**，所以放大 `dash.timeout.scan-interval-ms` 这类配置层防御是无效的：间隔只推迟第二次，第一次在进程启动的瞬间就执行。0c 用的 `NoScheduling`（`@TestConfiguration` 里换一个永不触发的 `TaskScheduler`）**管不到子进程**——它只对同 JVM 的上下文生效。所以本用例唯一的防线是**库隔离**：子进程改的东西落在 `campus_dash_worker_it`，共享 IT 库不受影响。实测扣掉 `RiskGrabLinkIT` 用户信用分、导致**下一轮** IT 报 `CREDIT_TOO_LOW` 的那次事故，就是「真 worker 写共享库」的现场（`实现期发现.md` F-20，本阶段的 F-30 记的是它的隔离结论）。
- **worker 的四个消费者会一起连 broker**（超时流转、自动结算、资金、缓存失效），外加 `FundEventPushConsumer`：它在 `dash-infrastructure.realtime`，不在方案 A 的排除范围内，订阅 `errand-fund-event`、组 `dash-fund-event-push`，该组不在 `init-mq.sh` 里、靠 broker 自动建组。**这是既有行为**（生产 app 进程默认就是这个状态），不是本阶段引入的；写在这里是为了将来这条用例在别处变红时，有人知道多出来的那几个消费者是谁。
- **它同时是「真 worker 会不会污染共享 IT 库」这件事的自动化证据**：子进程被钉在隔离库上，所以它跑的调度、结算、信用扣减全落在别处。**但 Redis 隔离不了**：6380 只有一份，子进程与测试 JVM 共用。本用例涉及的键都带用户/实例前缀且用例自己 `purgeUser` / `purgeEventGates` 清过，但那**不是隔离，是互不重叠**——边界写在这里，免得将来有人以为子进程碰不到自己的键。
- **隔离库不自动创建**：用例检测不到它，就整类跳过并打印创建配方（`CREATE DATABASE` + `docker exec -i dash-mysql mysql ... < docker/init.sql`）。自动建库会把「忘了建库」变成一条静默的、发生在别处的假绿。

```java
// dash-bootstrap 测试源里既有的 MiddlewareAvailable，本阶段给它加了第三个探测。
Assumptions.assumeTrue(MiddlewareAvailable.check() && MiddlewareAvailable.mqReachable(), "...");
```

`MiddlewareAvailable.mqReachable()` 探 `127.0.0.1:8081`（gRPC proxy 端口），与 MySQL/Redis 两个探测同型。**不探 9876**：应用连的是 8081，探 nameserver 会得到一个「9876 通但应用连不上」的假绿。**只有 `RiskEventIT` 需要它**——`WorkerApplicationContextTest` 走 `dash.mq.enabled=false`，不碰 broker，守卫只探 MySQL/Redis。

**原计划的 `WorkerMiddleware` 已取消**：它存在的唯一理由是「用例住在 worker，而 `MiddlewareAvailable` 是 bootstrap 测试源里的包级私有类、跨模块看不见」。用例搬回 bootstrap 之后这个问题不存在了，再添一个同型的类就是重复。

**除了中间件，本类独有两道前置**，各自对应一类「跑不起来却看起来像失败」：

- **worker 的 jar 必须存在且不过期**：子进程跑的是 `dash-worker/target/dash-worker-*.jar`，不是测试类路径。jar 缺失、或比 `src/main`/pom 旧 → 跳过并给出「先 `mvn -pl dash-worker -am package -DskipTests`」的提示。少了这条，用例会拿**上一次打包的** worker 去跑，通过与否取决于谁什么时候打过包。
- **隔离库必须存在**（见上）。这两条都不满足时**跳过而不是失败**——它们描述的是环境没准备好，不是被测行为有问题。

**worker 的上下文测试不可能不依赖中间件**：`RedissonConfig` 是无条件 `@Configuration`，它的工厂方法**在建 bean 时就连接**。把 redis 指向死端口做对照实验，上下文刷新直接失败在 `RedisConnectionException`。所以这个上下文测试与其余 IT 同处境——中间件没起就整类跳过（`Assumptions`），而不是变红。

| 用例（嵌套类） | 性质 |
|---|---|
| **端到端往返**（`ProcessToProcess`） | ① 同一个用户连抢到**越线**为止（`shortThreshold + 1` 次），只有最后一次非 PASS、才发事件；② 断言投递行恰好 1 条 `result=SENT`，字段逐个比对（`operationType` / `errandId` / `runnerId` / `decisionAction` / `degraded`）；③ 子进程日志里出现**同一 `eventId`** 的 `risk_event_processed` 行，两行其余字段自洽（D3 的回归锁）；④ broker 上的载荷逐字段比对——这一份才是「消息真的过了一遍 broker」的独立证据 |
| **聚合真的抑制**（`ProcessToProcess`） | 同一个用户在同一 10 秒窗内触发 N 次 `LIMIT` → 投递行里恰好 1 条 `SENT` + 其余 `SUPPRESSED`（抑制行的 `gateType=LIMIT` 指向聚合闸门，不是别的闸门），且**观察者只收到 1 条消息**。不需要等窗口过期（D5），也不需要断言时序 |
| **`requestId` 同值 + 降级放行**（`DegradedOverHttp`） | 不带 `X-Request-Id` 头走真实 HTTP（`RANDOM_PORT`），从服务端的幂等键取回生成值，断言它就是载荷里的 `requestId`（P9.3 D4 的跨阶段约束在本阶段的落点）。这个上下文同时用 `deadline-ms=0` + `fail-open=true` 逼出**降级放行**：`decisionAction=PASS`、`degraded=true`、`degradeReasons=DEADLINE_EXCEEDED`——而 PASS 只在降级时才发事件，正好把 `producesEvent()` 的第二个分支也拿到真链路上验一遍 |

**三条用例都靠「等第 N 条」而不是「数一次」。** 投递行在 `risk-event-pub` 线程上异步写，`grab()` 返回时它**还没落盘**——实测第 2 条 `SUPPRESSED` 行比断言晚 1~2ms 出现。所以断言写成「等到第 2 条（本用例不该出现的那条）或者超时」，超时也返回手里已有的行，由断言带着现场报错（`LogCapture.awaitLines`）。这不是测试洁癖：先跑出来的那次失败**看起来就是聚合失效**，而它其实只是抓晚了。

**不做的三件事**（避免 IT 越铺越大）：

- **不测消费端重投**：重投需要真实触发一次消费失败，而按 D10 格式非法**不会**重投。硬造一个重投要么改生产代码加开关，要么手工往 broker 灌消息——前者为了测试污染设计，后者测的是 broker 不是我们。去重口径由 §8.1 的「同一 body 喂两次」与脚本的 `--selftest` 覆盖。
- **不模拟 broker 不可用**：那会触发 `dash.mq.enabled=true` 下已知的启动失败路径，属于「中间件整体不可用」——实施计划 §7.4 已排除，与本阶段无关。
- **不验证另外四个 topic**：本阶段不碰它们（§1）。

**IT 不登记 `BenchRun`**：`RiskEventIT` 不跑并发、不做超卖校验，与 `RiskGrabLinkIT` / `RiskFeatureIT` 同类。

### 8.3 离线脚本

`bench/scripts/analyze_risk_events.py`（Python 3，照 `analyze_s5_trace.py` 的形态：`argparse`、读日志文件、`print(json.dumps(...))`）。

**与既有脚本的关键差异**：`analyze_s5_trace.py` 读的是 JSON 行（靠 `{"event":"timeout_` 定位），而风控的日志行是 `key=value` 格式，需要一个小解析器（按空格切分、按第一个 `=` 拆名值）。这个解析器与 D13 是**同一条通路的另一端**：`LogField.safe` 保证值里没有空格，脚本才能安全地按空格切分。两处必须一起看——只改一边，切分立刻出错。

统计输出：

- `risk_event_publish_total` / `risk_event_suppressed_total` / `risk_event_dropped_total` / `risk_event_invalid_total`（按 `result` 分组的计数）；
- **`risk_event_duplicate_total`**：`risk_event_processed` 行按 **`requestId + operationType`** 去重后，`总行数 − 去重后条数`（蓝图 §5.3 的第三条验收）；
- `risk_event_consume_lag_ms` 的 P50/P95/P99/max（照 `analyze_s5_trace.py` 的 `pct()`：`math.ceil(len*p/100)-1` 取下标的**非插值**算法，保持一致）；
- **风险动作覆盖率**：按 `requestId` 去重后，`decisionAction` 的分布——即「聚合开启后，风险动作还能被统计到的比例」；
- `risk_review_pending` 计数。

**带 `--selftest`**：喂一段合成的日志文本（含成对的重复 `processed` 行、含空格污染行的反例），断言去重数与分组计数符合预期，退出码非 0 即失败。

**为什么给一个 Python 脚本做自检**：仓库对脚本没有测试设施（`analyze_s5_trace.py` 就没有），而本阶段的核心验收之一是「脚本能按 `requestId + operationType` 去重」。一个从来没被验证过的去重函数，与一个写错的去重函数，在报告里的表现完全一样——都给出一个数字。`--selftest` 是 15 行的代价换掉这个不确定性；归档里会记录它的实际输出。

### 8.4 不做什么

- **不给另外四个消费组补 `retryMaxTimes`**（D11）：它们承载资金与超时语义，改重试次数需要单独的评估与授权。
- **不重构那五份 `extractLong`**（§6.1）：它们的行为已经与各自消费者的语义绑在一起，统一它们是一次独立的、需要单独验证的改动。
- **不做「Worker 重启后继续处理」的自动化**：原写的理由是「没有进程编排」，这条**在任务 17 之后不再成立**（`WorkerSubprocess` 已经能停能起）。它仍然留给**手工实测 + 归档记录**（与 `实现期发现.md` F-18「无自动化守卫，已现场实测」同一处理方式），但理由换成了判据本身：要验的是「重启后继续消费得下去」，而判据必须在重启**之前**先把消费停住、把消息留在 broker 上，再证明它是在**之后**被消费的——现有证据链（同一个 `eventId` 的两行日志）分不出这两种情况。硬做就得在子进程日志上引入时序切分，那是一条独立的、要单独验证的机制。**所以现在不是做不了，是现有证据链证不了**；而一个证不了的用例比不做更糟——它会以「通过」的形式给出错误的安心。
- **不引入 JSON 库、不引入 Micrometer、不新增中间件或服务进程**。

**但有一件事本阶段躲不开：D-5。** 设计期的现场实验实测到 `dash-worker` **当前根本起不来**（完整失败输出与分析见 `预存缺陷与坑.md` D-5）：它的 `@ComponentScan` 含 `com.campusdash.infrastructure`，而 P9.1 交付的风控适配器都在那里、都需要 `RiskProperties`，后者靠 `@ConfigurationPropertiesScan` 注册——那个注解只在 `CampusDashApplication` 上。

**它为什么落到 P9.4 的范围内**：本阶段把风险事件消费者放进 worker，验收表里还有「Worker 重启后可以继续处理」。一个起不来的进程，这两件事都无从谈起——不是「相关」，是**前置**。

两个修法（细节与代价见 D-5）：

| 方案 | 一句话 | 本设计的态度 |
|---|---|---|
| **A** | 把 `*.risk.*` 与 `GrabErrandUseCase` 排除出 worker 的扫描 | ✅ **已拍板（2026-09-11）**。方向是「worker 不持有它用不到的东西」 |
| **B** | worker 也注册 `RiskProperties` | ✗ 否决：让 worker 满足它用不到的东西的校验，且 `dash.risk` 每加一个无默认值的项就要同步 worker yaml |

**方案 A 的确切范围**（设计期已核对过引用关系，不是估的）：

```java
@ComponentScan(basePackages = {
        "com.campusdash.worker",
        "com.campusdash.application",
        "com.campusdash.infrastructure"
}, excludeFilters = {
        @ComponentScan.Filter(type = FilterType.REGEX,
                pattern = "com\\.campusdash\\.(application|infrastructure)\\.risk\\..*"),
        @ComponentScan.Filter(type = FilterType.ASSIGNABLE_TYPE,
                classes = GrabErrandUseCase.class)
})
```

两处排除**缺一不可**，因为引用链是唯一的一条：`GrabErrandUseCase`（`application.usecase`，不能按包排除，同包里全是 worker 要用的用例）→ `RiskPreCheckUseCase`（`application.risk`）→ 三个 `RiskFeaturePort`/`RiskBlacklistPort`/`RiskLimitPort` 与 `RiskRules`/`RiskPolicy`，它们的实现和 `RiskConfig` 全在 `infrastructure.risk`。只排 `GrabErrandUseCase`：`RiskPreCheckUseCase` 会被扫进来，然后因为找不到三个端口而装配失败，报错换了个地方出现。只排两个 `risk` 包：`GrabErrandUseCase` 装配失败。排除按包级 REGEX 而不是逐个 `ASSIGNABLE_TYPE`，是为了今后风控再加 `@Service` 时不用再回来改这里——**这条是整个 D-5 的教训本身**。

**范围是静态核对出来的，所以 0a 的验收必须是真跑一次启动**：上面这条链条是从引用关系推出来的，而 D-5 的那次实验只证明了「风控这条链会炸」——Spring 在配置绑定期就中止了，**排在它后面的装配问题当时根本没有机会露头**。如果按方案 A 排干净之后又冒出第二个 unsatisfied dependency，那是一条**新的**既有缺陷（往下编号 D-6），不是回头去选方案 B 的理由。这也是任务 0 的验收写成「真的打印出 `Started WorkerApplication`」而不是「没报错」的原因。

按 §9 的 **0a / 0b / 0c** 做（**批次 1 的第一个动作**，先于配置基线），并在归档里记录复现命令的前后输出对照。

## 10. 验收标准

| 验收项（实施计划 §8.3 / 蓝图 §5.3） | 判定方式 |
|---|---|
| 风险事件可以正常发送和消费 | `RiskEventIT` 的两份独立证据：观察者消费者组收到载荷并逐字段比对（消息真的过了 broker）+ 真 worker 子进程写下**同一 `eventId`** 的 `risk_event_processed` 行（消费者真的执行过） |
| 重投递消息只产生重复日志，不产生重复业务状态 | 单测：同一 body 喂两次 → 两行 `processed`、零次存储调用（结构性断言，见 §8.1） |
| 离线脚本按 `requestId + operationType` 去重，重复可统计为 `risk_event_duplicate_total` | `analyze_risk_events.py --selftest` + 归档记录对真实日志的实测输出 |
| `REVIEW` 只产生 `risk_review_pending` 日志，不产生审核表记录 | 单测：`REVIEW` 决策 → 额外一行；全仓无审核表（本轮不建表，见 §8.4） |
| 事件聚合 Key 按用户/动作/实例与时间窗生效 | 单测：四个键名逐字 + TTL 等于窗口；`LIMIT` 用 `userId`、`DEGRADED` 用 `instanceId` |
| 聚合关闭/开启时同步风险动作结果一致 | 单测：同一组决策在两个开关下，`RiskPreCheckResult` 逐字段相同（适配器抛异常也不外溢） |
| 聚合开启后实际 MQ 发送量下降且风险动作覆盖率可统计 | `RiskEventIT` 的抑制用例（N 次只收到 1 条）+ 脚本的覆盖率输出 |
| MQ 发送失败不影响同步抢单 | 单测：假 `Producer` 的 `sendAsync` 返回失败 future → 抢单结果不变；闸门抛异常 → 抢单结果不变 |
| Worker 重启后可以继续处理 | **手工实测**（§8.4）：停 worker、发事件、起 worker、确认消费到 + 归档记录 |
| 异步延迟可以从结构化日志统计 | `lagMs` 字段 + 脚本的 P50/P95/P99 输出 |
| 新 Topic 和消费组已同步更新 `docker/init-mq.sh` | 脚本内容 + `getConsumerConfig` 回读记录 |
| **重试窗口已显式声明**（设计问题清单附录 D） | `getConsumerConfig` 回读 `retryMaxTimes` 与 `groupRetryPolicy`，归档记录 |
| **`dash-worker` 能启动**（D-5，本阶段前置） | 真跑一次，看到 `Started WorkerApplication`；归档记录修复前后两次输出 |

**验收时必须如实记录的三条限制**：

1. **事件在进程内队列里，进程退出会丢。** 队列上限 4096，关停时不 `awaitTermination`。这是 best-effort 的**边界**（蓝图 §3.9 定的是 best-effort，不是不丢），所以它必须出现在最终交付物里，而不是只在代码注释里。
2. **聚合不是全局限流，四类闸门互相独立。** 同一个用户在同一秒内可以同时产生 `LIMIT`、`REVIEW`、`BLOCK`、`DEGRADED` 各一条——四个键互不影响。「同一用户 10 秒最多 1 条」限定的是**同一类**事件。
3. **降级闸门是每实例一个键，因此发送量随实例数线性增长。** 蓝图 §3.9 就是这么定的（`{instanceId}`），但结论必须写出来：N 个 app 实例下，同一个降级原因在每 10 秒内最多产生 N 条事件，不是 1 条。P9.5 读抑制率时必须知道分母是什么。

**验收时不得出现的说法**：不得把 `SENT` 写成「已投递」——`SENT` 的含义是「已交给 `sendAsync`」，它到没到 broker 由 `risk_event_publish_failed` 的**缺席**间接说明，而缺席不是证明。要证明投递成功，只有 `RiskEventIT` 那条真的收到消息的用例。
