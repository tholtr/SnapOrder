## 1. 本阶段边界

**做**：请求上下文解析（deviceId / requestId / clientIp）、可信代理判定、设备与 IP 标识 HMAC、用户滑动窗口、设备多账号集合、IP 聚集集合与 IP 速率滑窗、黑名单键计算工具、结构化日志、对应单测与集成测试。

## 2. 已拍板的决策

| 编号 | 决策 | 落实位置 |
|---|---|---|
| D1 | 设备/IP 哈希放在 **infrastructure** 层 | §4.1、§4.3 |
| D2 | IP **需要哈希**；并交付黑名单键计算小工具 | §4.1、任务 11 |
| D3 | 阈值判断放在 **domain** 层，Lua 只返回计数 | §3.2、§4.2 |
| D4 | 脚本内使用 `redis.call('TIME')` 取时间 | §4.2、任务 0 |
| D5 | 窗口一律用 **ZSet 滑窗 + 成员上限截断** | §4.2、§4.4 |
| D6 | 只建 **一个** `RiskFeaturePort` | §3.2 |
| D7 | 配置用 `@ConfigurationProperties(prefix = "dash.risk")` | §8.1 |
| D8 | 黑名单小工具落点 **`dash-bench`**，并给它加 infra 依赖 | §8.5、任务 11 |
| D9 | IP 解析组件落 **presentation**（infra 对它不可见） | §5.2 |
| D10 | `device-hmac-secret` 用 `${VAR:}` + 构造器校验，不用无默认值 | §8.3 |

各决策的具体影响：

**D1 —— 哈希在 infrastructure。** `RiskContext` 携带原始 `deviceId` / `clientIp`，适配器写入 Redis 前哈希。与现有分层一致：`AuthInterceptor` 只解析，验证交给 `authPort`（infra 实现），哈希属于同一类技术机制。

配套硬约束：**任何日志都不得打印 `RiskContext` 的原始 `deviceId` / `clientIp`**，这条要写进 `RiskContext` 的 Javadoc 和 `RiskContextResolver` 的注释里，不只是口头约定。

**D2 —— IP 哈希 + 工具。** 与设备口径统一、键长度固定、不落原始 IP。代价是 Redis 里看不出是哪个 IP，排障需要工具，因此**键计算小工具是本阶段的正式交付物**而非可选补充：蓝图 §3.5 说的「通过初始化脚本、Redis CLI 或测试 fixture 写入黑名单」，没有这个工具在 P9.2 根本执行不了。

**D3 —— 阈值在 domain。** Lua 只做原子计数与裁剪并**返回计数**，阈值比较在 P9.2 的领域逻辑里。理由：蓝图 §3.6 要求多规则风险分累加，需要的是计数不是布尔值；阈值写死在 `.lua` 里既不可配置也无法被 domain 单测覆盖。

这满足蓝图 §3.2 的真实意图——那句话讲的是**原子性**（不能在 Java 里拆成检查与写入两次 Redis 请求），不是在规定阈值必须写在脚本里。蓝图 §3.2 的措辞已相应调整。

**D4 —— 脚本内 `redis.call('TIME')`。** 单一时钟源，多实例无偏差，比应用传参更干净。在 Redis 7.4.11 上验证通过。**精度只能用微秒**，理由是 Lua number 的 double 精度上限——见 [F-12](../实现期发现.md#f-12)，脚本注释里留了这条。

**D5 —— ZSet 滑窗 + 成员上限截断，五个键统一。** 相比固定窗口计数器，滑窗没有跨边界翻倍问题，`LIMIT` 判定更准；代价是 IP 速率键从单值计数器变成 ZSet，每键内存从几十字节涨到约 2KB（实测 2144 B，见 §4.4）。这个代价是固定的、有硬上界的，不随请求量增长。

**D6 —— 单端口 `RiskFeaturePort`。** 三类特征同属「实时特征采集」一个能力，共享同一份 `RiskContext` 与同一个 Redis；合并后 P9.2 的测试 fake 也只需要写一个。

**D7 —— 配置用 `@ConfigurationProperties`。** 仓库此前**零个** `@ConfigurationProperties`，全是 `@Value` 内联默认值（仅 infra 就有 20 处）。改变既有写法的理由是 11 个 key 同属一个前缀，沿用 `@Value` 会让适配器构造函数背 9–10 个参数，且单测里手搓适配器时顺序错了不报错。

**D8 —— 小工具落点 `dash-bench`。** 仓库所有 `main()` 都在 `dash-bench`（8 个 Load Client / Probe）或两个 Application 类上，infra 是纯库、没有 `main()`。`BlacklistKeyTool` 与 `DelayMessageProbe` 同类。代价是 bench 必须加 `dash-infrastructure` 依赖才能复用真哈希器——**不能复制一份 HMAC 逻辑**，否则会漂移，而漂移就是黑名单静默失效。

**D9 —— IP 解析组件落 presentation。** 原方案放在 infra，编译不过：presentation 只依赖 application，全仓 `presentation → infrastructure` 的 import 是 0 处、分层由 Maven 强制。这两个组件本就是纯 HTTP 请求层解析，不含 infra 技术；D1 的「哈希在 infra」未被绕开——解析产出的原始值正是要塞进 `RiskContext` 再交给 infra 哈希的。连带 `trusted-proxy-cidrs` / `test-context-enabled` 也走 `@Value`，与 `AuthInterceptor` 同型，最终归属是 **infra 6 个 key 走 properties，presentation 2 个 key 走 `@Value`**。

**D10 —— secret 用 `${VAR:}` + 构造器校验。** 比无默认值的 `${VAR}` 多挡一类情况：后者只要环境变量存在就通过，哪怕是空串或一个空格——那会变成一个所有实例共享的空密钥，比没有密钥更糟，因为它不报错。空串不构成蓝图 §3.10 意义上的「默认值」。

## 3. 领域层设计（`dash-domain`）

新增包 `com.campusdash.domain.risk`，结构沿用现有约定（只有 `model/` 与 `ports/`，无 `service/`）。

### 3.1 模型

`com.campusdash.domain.risk.model.RiskContext` —— record，不可变事实：

```text
RiskContext(
    long   userId,
    long   errandId,
    String requestId,     // 非空：客户端未传时由服务端生成
    String deviceId,      // 可空：老客户端不传，为空时跳过设备维度
    String clientIp       // 非空：至少能拿到 remoteAddr
)
```

设计要点：

- **`deviceId` 与 `clientIp` 不做「空字符串」与 `null` 的区分**——构造时统一归一化为 `null`，避免下游出现两种缺失形态
- `requestId` 必填，空白视为无效（与上述同一条归一化规则）
- 不提供静态工厂（不像 `Errand` 那样承载业务校验），直接用规范构造器；输入校验放在解析器里
- Javadoc 必须写明：**该 record 持有原始设备标识与 IP，禁止整体入日志**
- 这是 `..domain..model..`，按 ArchUnit 规则三**不得**依赖任何 `..ports..`

按蓝图 §3.10，风控决策结果（`riskScore` / `action` / `matchedRules` / `ruleVersion` / `degraded` / `decisionLatencyMs`）是 **P9.2** 的产物，本阶段不建。

### 3.2 端口

`com.campusdash.domain.risk.ports.RiskFeaturePort`：

```text
UserWindow trackUserWindow(long userId, String requestId)
Cluster    trackCluster(long userId, String deviceId, String clientIp)

record UserWindow(int count10s, int count60s, boolean duplicateRequest) {}
record Cluster(int deviceAccounts, int ipAccounts, int ipRequests) {
    static final Cluster EMPTY = new Cluster(0, 0, 0);
}
```

**端口只有两个方法，各自对应一次 Lua 脚本调用。** 集群的三个维度必须合并成一次写入——拆成三个方法会让 IP 请求数被静默记成三倍，且拆开做不出正确实现（推导见 [F-1](../实现期发现.md#f-1)）。

| 方法 | 脚本 | 返回 |
|---|---|---|
| `trackUserWindow(userId, requestId)` | `risk_user_window.lua` | 两个窗口的计数 + 是否重复请求 |
| `trackCluster(userId, deviceId, clientIp)` | `risk_cluster.lua` | 设备账号数 / IP 账号数 / IP 请求数 |

两个维度都缺失时 `trackCluster` 返回 `Cluster.EMPTY` 且**不调用脚本**——缺维度的请求不该在 Redis 里留下键。

约定对齐现有端口写法：

- 参数扁平标量，不传 `RiskContext` 整体（现有 `GrabSlotPort.tryAcquire(errandId, runnerId, requestId)` 就是这个风格）
- 嵌套 record 定义在接口内部，与 `ErrandQueryPort.CursorItem`、`WalletRepository.BalanceView` 一致
- 返回 `int` 计数而非布尔或决策——保持端口是「采集」而不是「判断」（D3）
- 不抛领域异常；Redis 故障由适配器按降级语义处理（本阶段异常直接向上抛，P9.3 才接 `fail-open`）

**命名注意**：ArchUnit 规则二要求接口名以 `Port` / `Repository` 结尾且落在 `..domain.risk.ports..`。不要命名为 `RiskFeatureGateway`，那样会绕过规则约束。

## 4. 基础设施层设计（`dash-infrastructure`）

新增包 `com.campusdash.infrastructure.risk`。

### 4.1 `DeviceHasher`

| 组件 | 职责 | 关键点 |
|---|---|---|
| `DeviceHasher` | HMAC-SHA256 + 十六进制编码，输出定长字符串 | 密钥由调用方从 `dash.risk.device-hmac-secret` 传入；设备与 IP **共用同一个哈希器**（D2），输出取前 32 hex 字符，兼顾碰撞率与内存 |

**硬约束：`DeviceHasher` 必须是没有任何 Spring 注解的普通类**，构造函数直接收密钥字符串。

理由见 §8.5：`dash-bench` 的 `BlacklistKeyTool` 要复用同一个哈希器（复制一份必然漂移，而漂移意味着黑名单静默失效），但 bench 不是 Spring 应用。只要 `DeviceHasher` 的签名里不出现 Spring 类型，工具就能 `new DeviceHasher(secret)` 直接用，不需要上下文；Spring 装配另放在 `@Bean` 方法里。

### 4.2 Lua 脚本

放 `dash-infrastructure/src/main/resources/lua/`，与 `grab.lua`、`rollback_slot.lua` 同级，在 `RedisLuaConfig` 里加 `RedisScript` bean。

脚本注释风格**必须对齐 `grab.lua`**：开头写清楚为什么必须用 Lua、逐个列出 `KEYS` / `ARGV`、结尾列出返回码含义。这是本仓库 Lua 的既定风格，新脚本不能例外。

#### `risk_user_window.lua` —— 一次往返处理用户的两个窗口

```text
KEYS[1] = risk:win:{userId}:10s    ZSet  成员=requestId 分值=时间戳
KEYS[2] = risk:win:{userId}:60s    ZSet
ARGV[1] = requestId
ARGV[2] = 10 秒窗口成员上限 (6)
ARGV[3] = 60 秒窗口成员上限 (31)
ARGV[4] = TTL 秒数（必须 ≥ 最长窗口秒数，即 60）
时间基准 = redis.call('TIME')
返回: {count10s, count60s, duplicateFlag}
```

四个设计点：

1. **两个窗口合并到一个脚本**。分两次调用就是两次 Redis 往返，与蓝图 §3.8 共享 10ms 总 deadline 的目标直接冲突。
2. **成员直接用 `requestId`，不额外开去重键**。去重键方案会让键数随 QPS×TTL 增长（S2 实测 12642 QPS 下 10 秒就是十几万键），而 `requestId` 作为成员后去重只需一次 `ZSCORE`——零额外键、零额外 TTL。窗口裁剪本来就会移走过期成员，不需要第二套生命周期。
3. **成员上限用 `ZREMRANGEBYRANK key 0 -(N+1)`**。当 `ZCARD <= N` 时该 rank 落在集合起点之外，天然不删任何东西；上限只保留「够判断阈值」的条数，与蓝图 §3.2「10 秒窗口最多保留 6 条、60 秒窗口最多保留 31 条」一致。
4. **顺序是先按时间裁剪、再查重**，不能反过来——反过来会把已滑出窗口的残留成员误判为重复请求。推导与实测见 [F-2](../实现期发现.md#f-2)。

去重语义：命中任一窗口的已有成员即视为重复，**两个窗口都不再加计数**。

**`TTL ≥ 最长窗口秒数` 的理由**：键若在窗口结束前整体过期，窗口内的成员会跟着一起消失，重放会被当成新请求，**计数偏小（漏报）**。这与查重顺序无关，是另一条独立的约束。

#### `risk_cluster.lua` —— 设备与 IP 维度

```text
KEYS[1] = risk:dev:{deviceHash}         Set    成员=userId
KEYS[2] = risk:ip:{ipHash}:users        Set    成员=userId
KEYS[3] = risk:ip:{ipHash}:rate         ZSet   成员=微秒时间戳 分值=同一时间戳
ARGV[1] = userId
ARGV[2] = 设备集合上限 (9)
ARGV[3] = IP 账号集合上限 (11)
ARGV[4] = IP 速率窗口成员上限 (101)
ARGV[5] = 设备集合的 TTL 秒数 (600)
ARGV[6] = IP 账号集合的 TTL 秒数 (600)
ARGV[7] = IP 速率 ZSet 的 TTL 秒数 (60)，同时是速率窗口长度
ARGV[8] = 是否存在设备维度 1/0
ARGV[9] = 是否存在 IP 维度 1/0
时间基准 = redis.call('TIME')
返回: {deviceCount, ipAccountCount, ipRequestCount}
```

**三个 TTL 必须是三个独立参数，不能合并成一个。** 根因是 Set 的性质：**成员是裸 `userId`，没有分值、没有时间信息，所以「窗口」这个语义完全由 TTL 承载**（配合「只在新增成员时才 `EXPIRE`」）。TTL 在这里不是无关紧要的过期时间，**它就是窗口长度本身**。合并的后果是某个配置项变成死键而毫无提示——见 [F-5](../实现期发现.md#f-5)。

**两个 Set 的上限只需要取「阈值 +1」**，这是本方案里最值得写进注释的一点：规则是「设备关联账号 > 8 → `BLOCK`」，集合封顶在 9 就足以表达「已越线」，9 和 900 对决策没有区别。同样，IP 账号数封顶 11 表达「> 10」。这样集合大小有硬上界，直接满足蓝图 §3.8「风控 Key 必须设置 TTL、成员上限和内存预算」。

**但「9 和 900 没有区别」这句话有边界**：Set 的编码悬崖在 512（见下），超过就走 hashtable、内存跳 18.5 倍。所以「阈值 +1」在 512 以内成立，超过就不成立——`RiskProperties` 会拦。

封顶方式是**拒绝继续 `SADD`**（不是随机剔除），因此集合达到上限后会一直保持到 TTL 到期——这正是期望行为：该设备在 10 分钟窗口内确实关联了超限账号。

**IP 速率 ZSet 的成员用微秒时间戳，不用 `requestId`**，这是与用户窗口唯一不同的处理（D5），因为两条规则的语义不同：

| | 用户窗口 | IP 速率窗口 |
|---|---|---|
| 规则目的 | 识别**脚本刷同一个人的抢单** | 识别**单个 IP 的异常请求量** |
| 成员 | `requestId` | 微秒时间戳 |
| 效果 | 隐式去重：同一 `requestId` 重放只计一次 | 计原始请求量：每次请求都算 |

用户窗口需要去重是因为它服务于重试幂等；IP 速率窗口若也去重，攻击者只要反复使用同一个 `requestId` 就能把计数压到 1，规则直接失效。用微秒时间戳作成员，同一微秒内的并发请求会合并成一条（低估），在单 IP 实际速率下可忽略；若该 IP 真能到百万 QPS 量级，这条规则本身也已无意义。

裁剪逻辑与 `risk_user_window.lua` 相同，两个脚本里各写一份并在注释里互相引用（Lua 脚本之间无法共享代码，除非用 `SCRIPT LOAD` 拼装，不值得为此增加复杂度）。

#### 两条编码硬约束

| 结构 | 上限 | 由谁决定 | 超过的后果 |
|---|---:|---|---|
| ZSet | **≤ 127** | `zset-max-listpack-entries`（默认 128），因脚本先写后裁有 `cap+1` 瞬时 | listpack → skiplist，单键 **7232 B → 17601 B（2.4×）** |
| Set | **≤ 512** | `set-max-intset-entries`（默认 512），无瞬间峰值问题 | intset → hashtable，单键 **1336 B → 24720 B（18.5×）** |

两者**都只升不降**（转过去就回不来，即使后来裁回小集合），**都不报错、不告警**，只会在压测里表现为 Redis 内存异常。

推导、实测数据与复现命令见 [F-3](../实现期发现.md#f-3) 与 [F-4](../实现期发现.md#f-4)。

这两条约束**已经落在代码里**而不是只写在文档里：`RiskProperties` 的构造器在启动时校验 `shortCap() / longCap() / ipRateWindow.cap() ≤ 127` 与两个 Set 的 `≤ 512`，配错则应用起不来。

### 4.3 适配器

`RedisRiskFeatureAdapter implements RiskFeaturePort`，注入 `StringRedisTemplate` + `RedisScript` bean，调用方式对齐 `RedisGrabSlotAdapter`（`redis.execute(script, keys, args)`）。

需要处理三点：

- `List` 返回值里的 `Long` 可能为 `nil`，取用前判空
- **设备缺失时不写任何设备键**：`deviceId` 为 `null` 或归一化后为空时，直接在 Java 层返回 0，不调用脚本、不产生 `risk:dev:*` 残留键（对应验收项「请求上下文缺失可安全降级」）
- Redis 不可用时**本阶段直接抛出**（P9.3 才引入 deadline 与 `fail-open`），但要保证异常类型可识别，便于 P9.3 的降级分支判断

哈希调用点：适配器内部对 `deviceId` / `clientIp` 调 `DeviceHasher` 后再拼键，**原始值不进入键名、不进入日志**（D1）。

### 4.4 键命名与内存预算

| 键 | 类型 | TTL | 基数上界 | 单键上限 | 实测单键内存 | 编码（悬崖） |
|---|---|---|---|---|---|---|
| `risk:win:{userId}:10s` | ZSet | 10s | 活跃用户数 | 6 成员 | 384 B | listpack（上界 127） |
| `risk:win:{userId}:60s` | ZSet | 60s | 活跃用户数 | 31 成员 | 1600 B | listpack（上界 127） |
| `risk:dev:{deviceHash}` | Set | 600s | 活跃设备数 | 9 成员 | 120 B | intset（上界 512） |
| `risk:ip:{ipHash}:users` | Set | 600s | 活跃 IP 数 | 11 成员 | 128 B | intset（上界 512） |
| `risk:ip:{ipHash}:rate` | ZSet | 60s | 活跃 IP 数 | 101 成员 | 2144 B | listpack（上界 127） |

**两个上界不同，不能混用**：ZSet 是 `zset-max-listpack-entries`（默认 128，因先写后裁取 127），Set 是 `set-max-intset-entries`（默认 512）。

（实测环境：Redis 7.4.11，**通过脚本真实写入**后读 `MEMORY USAGE`，键名与成员均按真实形态——`userId` 为四位数字、`deviceHash`/`ipHash` 为 32 位十六进制、`requestId` 为 36 字符 UUID、速率成员为 16 位微秒时间戳。空键基线 64 B。）

**上表两个 Set 的数字是按四位 `userId` 测的**，`intset` 会按集合内最大成员的值选择条目宽度，所以 `userId` 变长每个键都会变大（19 位雪花 id 时是 168 B / 192 B）。这只取决于将来注册功能怎么发号，不取决于风控——见 [F-6](../实现期发现.md#f-6)。

**全部键的基数都由活跃用户/设备/IP 数封顶，没有任何一个随请求量增长**——这是 P9.1 必须守住的不变式。成员上限截断在这里起的作用是：把「单键随请求量无上界增长」变成「单键固定成本」。没有截断时，一个 IP 打百万请求会生成百万成员的 ZSet；有了截断，打多少都是 2144 B 封顶。

**内存画像**：真实的计量单位是「一组活跃实体（一个用户 + 一个设备 + 一个 IP）占用全部五个键」，约：

```text
384 + 1600 + 120 + 128 + 2144 ≈ 4.4 KB
其中 IP 速率键占约 49%，用户 60s 窗口占约 37%
```

因此总画像为 `活跃实体数 × 4.4KB`：

| 活跃实体规模 | 内存量级 | 占 512MB 预算 |
|---|---:|---:|
| 1 千 | 约 4.4MB | 0.9% |
| 1 万 | 约 44MB | 8.6% |
| 5 万 | 约 220MB | 43% |
| 10 万 | 约 440MB | 86% |

两点要同时说清楚，只挑对自己有利的那个是不诚实的：

- **1 万活跃实体以内（约 44MB、8.6%）确实不构成压力**。S2 压测峰值 12642 QPS，对应的活跃实体量级在这一档。
- **10 万活跃实体就是 440MB、占预算 86%**，这是实打实的压力。这里的「活跃实体」指 10 分钟窗口内还有键存活（`risk:dev` / `risk:ip:*:users` 的 TTL 都是 600 秒）的用户+设备+IP 三元组，**不是 QPS，也不是累计用户数**。

IP 速率键虽然是单键最重的（约占总量的 49%），但即使把它换成计数器，总量也只减一半——因为用户 60s 窗口本身就占 1600 B。**所以 D5 的选型不必改。**

**这条约束的形态要说准：它随实体数线性增长，不是封顶的常量。** 所以 P9.5 的监控要看的是**活跃实体数**，而不是 QPS——单看 QPS 看不出问题，因为键数跟请求量无关。

## 5. 表现层设计（`dash-presentation`）

新增 `com.campusdash.presentation.risk` 包，与现有 `presentation.auth` 平级。

### 5.1 解析器

`RiskContextResolver` —— 输入 `RiskRequestSource`（一个记录，承载拦截器抠出来的原始字段）与 `userId`，输出 `RiskRequest`。纯逻辑，不依赖 Spring 上下文即可单测。

职责：

1. `requestId`：读 `X-Request-Id`，缺失/空白时由服务端生成 UUID
2. `deviceId`：读 `X-Device-Id`，缺失或空白置 `null`
3. `clientIp`：委托 `ClientIpResolver`（见 §5.2）
4. 测试上下文注入：见 §5.4

`userId` 由 `CurrentUser.get()` 提供（已由 `AuthInterceptor` 解析），解析器不重复解析身份。

解析器放在 presentation 层、只做解析不做哈希，是 D1 的直接结果：**原始设备标识与 IP 在这一层进入系统，随后由 infra 适配器负责哈希**。

**`requestIdOf` 是公开的静态入口**，因为抢单链路（`ErrandController.grab`）必须复用同一份空白归一化——同一个 `requestId` 在抢单链路里是幂等键、在风控链路里是窗口去重成员，两处各写一份判断迟早分叉。分叉的后果见 `预存缺陷与坑.md` 的 D-2。

### 5.2 IP 解析组件

| 组件 | 职责 | 关键点 |
|---|---|---|
| `ClientIpResolver` | 从 `remoteAddr` 与转发头解析真实客户端 IP | 见下方算法 |
| `CidrMatcher` | 判断 IP 是否落在可信代理网段 | 本轮**只支持 IPv4**；IPv6 一律判为「不可信」（安全默认），并写入注释 |
| `Ipv4` | 严格的点分十进制解析与格式化 | 见下方原因 |

**为什么需要 `Ipv4` 而不是 `InetAddress.getByName`**：`ClientIpResolver` 与 `CidrMatcher` 都要解析 IP，且**解析的输入是攻击者可控的字符串**，两处各写一份必然漂移。更关键的是绝不能用 `InetAddress.getByName`——它对非数字输入会走 **DNS 查询**，攻击者只要往 `X-Forwarded-For` 里塞一个主机名，就能让服务器替他做一次 DNS 解析，既是 SSRF 跳板也是放大攻击。因此 `Ipv4` 只认严格的点分十进制，并额外拒绝**前导零**：`"010.1.1.1"` 在 Java 里是十进制 10，而 C 的 `inet_aton` 与部分代理按八进制解析成 8，同一串字符在链路两端指向不同机器，正是绕过 IP 白名单的经典手法。

**为什么在 presentation 而不是 infra**：见 D9。

**`CidrMatcher` 的两个决定**：

- **网段格式错误直接抛异常让应用起不来**。静默忽略一个敲错的网段，表现是「代理突然不可信、全体用户挤在同一个 IP 桶里」，排查成本远高于启动失败。
- **`/0` 必须特殊处理**。Java 的移位是模 32 的：`0xFFFFFFFF << (32 - 0)` 就是 `<< 32`，等于不位移，掩码退化成全 1——`/0` 会变成 `/32`，语义正好相反（「信任全部」变成「只信任 0.0.0.0」）。`CidrMatcherTest` 里有专门的用例锁死它。

**`ClientIpResolver` 的算法必须是「从右向左」**：

```text
1. 取 remoteAddr；若它本身就不是合法 IPv4 -> 返回 null（IP 维度不可用）
2. 若 remoteAddr 不在可信代理网段 -> 直接返回 remoteAddr，忽略所有转发头
3. 若在可信网段 -> 取 X-Forwarded-For，从最右往左逐个检查：
   跳过可信代理，命中第一个不可信地址就立刻返回
4. 整条链都可信 -> 返回链中最左的地址
5. 链中途解析失败 -> 返回 remoteAddr（信任链已断，左边的值无法验证）
```

**第 1 步与第 5 步的返回结果不同，不能合并。** `remoteAddr` 由容器提供，正常情况永远是合法 IP；它解析不出来说明拿不到对端地址，此时不是「退回 `remoteAddr`」而是**根本没有可用的 IP**。`null` 与 `remoteAddr` 的区别有实际后果：退化成空串或某个固定值的话，所有这类请求会**共用一个风控桶**，既让限流误伤也可能让攻击者靠制造解析失败来稀释自己的计数。推导见 [F-7](../实现期发现.md#f-7)。

**从最右往左是关键**：取最左地址是典型的伪造漏洞——客户端自己发一个 `X-Forwarded-For: 1.2.3.4` 就能顶掉真实 IP。默认配置 `trusted-proxy-cidrs` 为空（即完全忽略转发头），但工具一旦被开启，算法正确性就是唯一防线。

**第 3 步「命中就立刻返回、不再继续往左看」同样是安全关键**：继续往左就进入了客户端完全可控的区域。对应的用例是「伪造值恰好写成内网地址」——实现若写成「看到可信就继续往左找」，攻击者用 `X-Forwarded-For: 10.9.9.9, <真实IP>` 就能把解析结果推到最左边的伪造值上。

**另外两点实现细节**：

- **多条转发头要拼接**：用 `getHeaders()` 而不是 `getHeader()`。攻击者发一条 `X-Forwarded-For`、代理不追加内容而是**再发一条头**，是转发头走私的经典手法；只读第一条就会读到伪造值。按出现顺序拼接后从右往左走，真实段始终在右侧。
- **端口要剥掉**：真实部署中代理常以 `IP:端口` 形式追加。不剥的话整条链因解析失败退回对端地址，表现是**一个代理后面的所有用户挤进同一个 IP 桶**。只在「恰好一个冒号且冒号后全为数字」时剥离，其余原样交给 `Ipv4.parse` 统一拒绝——只有一个拒绝出口，就不会出现两条路径判断不一致的漏洞。

### 5.3 拦截器

`RiskContextInterceptor implements HandlerInterceptor`，在 `com.campusdash.presentation.WebConfig.addInterceptors` 里注册到 `/api/**`（就是已注册 `AuthInterceptor` 的那个方法）。

**为什么不并入 `AuthInterceptor`**：`AuthInterceptor` 的职责是认证（守卫，鉴权失败直接 401 中断），风控上下文是附加信息，解析失败不应中断请求。两者混在一起会让「解析失败怎么办」的语义变含混。

注册顺序上 `AuthInterceptor` 在前（`userId` 是上下文的前置条件）。本阶段拦截器**只解析并存进 request attribute，不做任何风控调用**——特征采集的调用点在 P9.3 由 `GrabErrandUseCase` 触发。

**拦截器存的是 `RiskRequest`，不是 `RiskContext`。** `RiskContext` 有 `errandId` 字段，而拦截器挂在 `/api/**` 上，`preHandle` 阶段绝大多数路由根本没有任务 id。若塞一个 `0` 或 `-1` 顶替，这个「不存在」的值会一路流进采集日志行和 P9.4 的风险事件，**且没有任何地方会报错**。推导见 [F-8](../实现期发现.md#f-8)。

```text
RiskRequest(long userId, String requestId, String deviceId, String clientIp)
```

`RiskContext` 由知道 `errandId` 的一方（P9.3 的 `GrabErrandUseCase`）组装。

**`requestId` 的空白归一化在这里就做掉**：客户端传空串或纯空白时由服务端生成 UUID。这一条比看上去重要——`requestId` 是用户窗口的去重成员，空串若被原样放行，所有「带了空 `X-Request-Id`」的请求会共用一个去重成员，窗口计数恒为 1，风控规则**静默失效**且不报错。

### 5.4 测试上下文注入

| 测试头 | 覆盖字段 |
|---|---|
| `X-Test-Device-Id` | `deviceId` |
| `X-Test-Client-Ip` | `clientIp` |

生效条件**两个同时满足**：

```text
dash.risk.test-context-enabled = true
且 当前 profile 包含 test
```

生产配置 `test-context-enabled: false`，任何环境下测试头都被忽略。

**这一条要严格对齐现有 `dash.auth.allow-header-identity` 的教训**：那个开关是「后门优先于正门」——只要解析成功就跳过 token 校验。风控测试上下文必须避免同样的形态：测试头只在开关打开时生效，且**开关关闭时连读取都不发生**（而不是读了再忽略），减少被误用的可能。

## 6. 结构化日志

按蓝图 §3.10，日志字段 camelCase、离线指标 snake_case，两者由分析脚本映射。日志格式对齐仓库现有 SLF4J `key={}` 风格。

特征采集完成后输出一行：

```text
risk_feature userId=... errandId=... requestId=... count10s=... count60s=...
            deviceAccounts=... ipAccounts=... ipRequests=... degraded=false
```

**必须遵守**：这一行以及所有风控日志**不得包含原始 `deviceId` / `clientIp`**（D1）。若排障需要，只打印哈希后的值。

**落点：`com.campusdash.application.risk.RiskFeatureLog`（`dash-application`）。** 这一行不属于适配器——`errandId` 与 `degraded` 两个字段适配器都拿不到：端口签名里没有 `errandId`，而「本次采集是否降级」是调用方 catch 住异常才知道的事。硬塞进适配器要给端口加一个只为打日志存在的参数。

P9.1 只交付**格式**与它的单测（`RiskFeatureLogTest`，逐字断言整行 + 字段顺序 + 控制字符替换）；真正的调用点在 P9.3 的抢单用例。这样拆的好处是：字段名与顺序是给离线分析脚本的**跨系统契约**，现在就被测试锁住，P9.3 接入时不可能悄悄改动它。

**为什么 `format()` 收的是 `UserWindow` / `Cluster` 这种聚合值而不是原始字段**：让「日志泄露原始设备号/IP」在类型上不可能发生，而不是靠每次改代码时记得住。端口返回的记录里只有计数，这里也就无从打印。

## 7. 测试策略

### 7.1 单元测试（无中间件依赖）

| 目标 | 要覆盖的性质 |
|---|---|
| `DeviceHasher` | 同输入恒定输出；不同密钥输出不同；设备与 IP 走同一哈希器；空/超长输入不抛异常 |
| `CidrMatcher` | 网段边界（网络地址、广播地址、网段外相邻地址）；`/32` 与 `/0`；非法 CIDR 配置；IPv6 一律不可信 |
| `ClientIpResolver` | 无可信代理时忽略转发头；**伪造 `X-Forwarded-For` 不生效**；多级可信代理链从右向左跳过；整链可信的退化；XFF 含非法值时回落 `remoteAddr` |
| `Ipv4` | 前导零拒绝；边界值；非法输入 |
| `RiskContextResolver` | `deviceId` 缺失为 `null`；`requestId` 缺失或空白时生成；测试头在开关关闭时被忽略 |
| `RiskContextInterceptor` | 见 §7.4 |
| `RiskProperties` | 两条编码上界的边界（127 放行 / 128 拦截、511 放行 / 512 拦截）；secret 缺失或空白时构造失败 |

按仓库现约定：纯 JUnit 5 + `@DisplayName` 中文场景名，**不使用 Mockito**（全仓无 Mockito 依赖），需要的协作者手写 fake。

### 7.2 集成测试（`RiskFeatureIT`，`dash-bootstrap/src/test/java/com/campusdash/it/`）

按现有约定：

- `@BeforeAll` 用 `Assumptions.assumeTrue(MiddlewareAvailable.check(), ...)` 守卫（注意跳过看起来和全绿一样，见 `预存缺陷与坑.md` K-2）
- 用 `BenchRun` 登记轮次并 `run.track(...)`，**不自行清理数据**（交给 `cleanup.sh --keep-last`）
- `@BeforeEach` 只重置共享基线账号
- 直连真实 Redis（本仓库对 Redis 适配器的既有策略就是「连真实 Redis，缺了就跳过」，没有内嵌 Redis / Testcontainers / mock）

**必须覆盖的性质**：

| 性质 | 用例设计 |
|---|---|
| 用户窗口并发计数准确 | 参照 `GrabConcurrencyIT` 的 `CountDownLatch` 对齐释放 + 虚拟线程，同一用户 N 个**不同** `requestId` 并发 → 计数等于 min(N, 上限) |
| 同一 `requestId` 不重复计数 | N 个**相同** `requestId` 并发 → 计数恰好为 1，且 `duplicateRequest=true`。这条只有在 Lua 原子时才成立，是脚本正确性的核心证据 |
| 窗口外数据自动清理 | 手动 `ZADD` 一个过期分值 → 调用后该成员被移除 |
| 已滑出窗口的 `requestId` 不再算重复 | 同上手法再重放，断言 `duplicate=false`——这是 [F-2](../实现期发现.md#f-2) 的回归锁 |
| ZSet 成员上限生效 | 连续写入 > 上限条数 → `ZCARD` 恰好等于上限，且保留的是最新条目 |
| IP 速率与用户窗口语义相反 | 同一 `requestId` 重复调用 IP 速率**会累加**（D5 的关键差异点） |
| TTL 生效 | 断言各键 `TTL > 0` 且不超过配置窗口 |
| 两个 Set 各用自己的窗口秒数 | 把两个窗口配成**不同的值**，断言各自读到自己的——同值不具区分能力，见 [F-5](../实现期发现.md#f-5) |
| 设备和 IP 集合相互隔离 | 同 device 不同 IP、同 IP 不同 device 分别写入 → 计数互不污染 |
| 上下文缺失可安全降级 | `deviceId=null` 时设备维度返回 0，且**本次调用**不写任何设备键（用调用前后键集合差集断言，不要断言全局无此类键） |
| 各键编码未退化 | `OBJECT ENCODING` 断言：三个 ZSet 为 `listpack`、两个 Set 为 `intset` |
| ArchUnit 分层约束 | 无需新增测试——`ArchitectureRuleTest` 的 `@AnalyzeClasses(packages = "com.campusdash.domain")` 会自动纳入新 `risk` 包 |

**并发用例要注意的既有教训**：`SettleConcurrencyIT` 里记录过一次踩坑——若线程池大小小于并发数，前 N 个线程全阻塞在 `fire.await()`，`ready.await()` 永远等不齐。窗口并发用例直接照抄 `GrabConcurrencyIT` 的 `newVirtualThreadPerTaskExecutor()` 写法。

### 7.3 时间相关用例的处理

窗口类测试涉及时间推进。**不要用 `Thread.sleep` 等真实时间**——既慢又不稳定。直接在测试里操作 Redis 分值（`ZADD` 一个过期时间戳）来模拟「数据已滑出窗口」，这是确定性的做法，与现有 `CacheConsistencyIT` 直接用 `StringRedisTemplate` 构造脏缓存的思路一致。

### 7.4 后门关闭测试

验收范围里原本有「增加后门关闭集成测试」一条。但本阶段上下文没有消费者，请求头解析结果在 HTTP 层**不可观测**，写不出真正的端到端断言。

要证的性质是三条，它们全都在 `RiskContextInterceptor.preHandle` 里，**不需要 HTTP 端到端，也不需要为测试在生产代码里开接缝**：

1. 开关关闭时测试头不生效
2. 开关关闭时测试头**连读取都不发生**
3. profile 不含 test 时，即使开关打开也不生效

**实现方式**：`dash-presentation` 里的 `RiskContextInterceptorTest`——用 `StandardEnvironment`（spring-core 的普通类）构造拦截器，用手写的假请求调真实的 `preHandle`，再读 request attribute 断言。假请求记录**每一次 header 读取**，于是第 2 条从注释里的声明变成了可断言的事实。

**为什么不加 `spring-test` 依赖用 `MockHttpServletRequest`**：`dash-presentation` 的 pom 刻意只有三个依赖，为一个测试类引入不成比例。假请求只需覆盖拦截器会调的 5 个方法（`HttpServletRequestWrapper` 要求非空委托，塞一个占位动态代理即可）。

被否决的 `RiskContextSink` 方案及其原因见 [F-9](../实现期发现.md#f-9)。

**对应的验收项措辞**（见 §10）：「测试上下文开关的双闸门禁在 `RiskContextInterceptorTest` 中以单元测试断言，含『开关关闭时连读取都不发生』」。

## 8. 配置落地

### 8.1 绑定方式：`@ConfigurationProperties`

使用 `@ConfigurationProperties(prefix = "dash.risk")`。这是仓库里**第一个** `@ConfigurationProperties` 类——现有代码全部是 `@Value` 内联默认值（仅 infra 模块就有 20 处）。改变既有写法的理由是本阶段有 11 个 key 且逻辑上属于同一组：

- 沿用 `@Value` 会让 `RedisRiskFeatureAdapter` 的构造函数背 9–10 个 `@Value` 参数
- 单测与 IT 里手搓适配器要传一长串参数，且顺序错了不报错
- 后续 P9.2–P9.4 还会往同一前缀下加 `mode` / `fail-open` / `deadline-ms` / `limit-cooldown-ms` / `event-aggregation-enabled`

写法：

```java
@ConfigurationProperties(prefix = "dash.risk")
public record RiskProperties(
        @DefaultValue("true") boolean enabled,
        String deviceHmacSecret,
        @DefaultValue UserWindow userWindow,
        @DefaultValue DeviceWindow deviceWindow,
        @DefaultValue IpAccountWindow ipAccountWindow,
        @DefaultValue IpRateWindow ipRateWindow) {

    public RiskProperties {
        if (deviceHmacSecret == null || deviceHmacSecret.isBlank()) {
            throw new IllegalStateException("dash.risk.device-hmac-secret 未配置或为空白。...");
        }
        requireCompactEncoding(userWindow.shortCap(), "dash.risk.user-window.short-threshold");
        ...
    }
}
```

其余 key 一律用 `@DefaultValue`（Spring Boot 的 record 构造绑定写法），只有 `deviceHmacSecret` 必填，理由见 §8.3。

**校验用紧凑构造器，不用 `@Validated` + `@NotBlank`**——后者在本仓库会静默失效，原因见 [F-10](../实现期发现.md#f-10)。换成构造器后反而更好：校验逻辑是普通 Java，**不需要 Spring 上下文就能单测**，顺带把 §4.2 的两条编码约束也一并放进构造器——配置有错就让应用起不来，而不是运行到一半才发现编码退化了。

**`test-context-enabled` 与 `trusted-proxy-cidrs` 不在这个类里**：它们的使用方在 presentation，而 presentation 看不见 `dash-infrastructure`，由 §5.2/§5.4 用 `@Value` 各自读取，与 `AuthInterceptor` 现有写法同型。归属因此很干净——**infra 的 6 个 key 走 `@ConfigurationProperties`，presentation 的 2 个 key 走 `@Value`**，同一个 key 不会有两处绑定。

注册方式在 `CampusDashApplication` 上加一行 `@ConfigurationPropertiesScan`，不逐个 `@EnableConfigurationProperties`。

### 8.2 配置项

```yaml
dash:
  risk:
    enabled: true
    test-context-enabled: false
    trusted-proxy-cidrs: ""
    device-hmac-secret: ${DASH_RISK_DEVICE_HMAC_SECRET:}
    user-window:
      short-seconds: 10
      short-threshold: 5
      long-seconds: 60
      long-threshold: 30
    device-window:
      seconds: 600
      threshold: 8
    ip-account-window:
      seconds: 600
      threshold: 10
    ip-rate-window:
      seconds: 60
      threshold: 100
```

`test-context-enabled` 与 `trusted-proxy-cidrs` 由 presentation 用 `@Value` 读取，其余 6 个由 `RiskProperties` 绑定（§8.1）。

**五个 `cap` 不是配置项**，由 `threshold + 1` 派生——理由见 [F-11](../实现期发现.md#f-11)，核心是「cap 小于 `threshold + 1` 会让规则静默永不触发」，不该给它留一个配置入口。

`mode` / `fail-open` / `deadline-ms` / `limit-cooldown-ms` / `event-aggregation-enabled` 属于 P9.2–P9.4，本阶段不落配置项。

### 8.3 `device-hmac-secret`：必填，但默认值写成空串

`${DASH_RISK_DEVICE_HMAC_SECRET:}` + 构造器校验，而**不是** `${DASH_RISK_DEVICE_HMAC_SECRET}`（无默认值靠占位符解析失败）。

| | 无默认值 `${VAR}` | `${VAR:}` + 构造器校验 |
|---|---|---|
| 缺失时 | `Could not resolve placeholder 'DASH_RISK_DEVICE_HMAC_SECRET'` | `IllegalStateException: dash.risk.device-hmac-secret 未配置或为空白。...` |
| 报错指向 | 环境变量名 | **配置项全名**，并附带本地运行与测试环境的取值方式 |
| 空串 / 纯空白 | **放过** | 挡住 |

选后者的关键不是错误信息更好读，是**它多挡一类情况**：无默认值方案只要环境变量存在就通过，哪怕值是空串或一个空格——那会变成一个所有实例共享的空密钥，比没有密钥更糟，因为它不报错。空串不构成蓝图 §3.10 意义上的「默认值」，因此不违反「不提供默认值，不能提交到代码库」。

**本地开发**：仓库没有 CI、没有应用启动脚本，`docker-compose.yaml` 只起 mysql / redis / rmqnamesrv / rmqbroker 四个中间件、不跑应用。所以本地必须显式提供：

```bash
DASH_RISK_DEVICE_HMAC_SECRET=local-dev-secret mvn spring-boot:run
```

**不要**为了省这一步往 `application.yaml` 写死值，也不要建 `application-local.yaml`——两者都是把密钥写进代码库，正是蓝图 §3.10 禁止的。

**测试 yaml 必须显式写一个测试密钥**，否则全部 IT 打红。原因与注意事项见 `预存缺陷与坑.md` K-1。

### 8.4 密钥轮换会静默清空黑名单

设备/IP 黑名单的键是 `HMAC(device-hmac-secret, 标识)`。轮换密钥后**所有已写入的黑名单键立刻全部失配**：查询正常返回、不抛异常，就是再也命中不了。

窗口类键不受影响（TTL 最长 10 分钟，自己会过期），但黑名单是长期键。因此：轮换密钥与重建黑名单是**同一个操作的两步**，不能只做一半。

完整语义（含执行顺序）已写入蓝图 §3.5。

### 8.5 小工具：复用真哈希器 + 读同一个环境变量

`BlacklistKeyTool` 落在 `dash-bench`（决策见 §9 任务 11），它不是 Spring 应用，读不到 `@ConfigurationProperties`；现有 bench 客户端（如 `DelayMessageProbe`）的约定是 `args[0]` + 硬编码默认值。

**两条约束：**

**（1）必须给 `dash-bench` 加 `dash-infrastructure` 依赖，复用真的 `DeviceHasher`。**

`dash-bench` 原先只依赖 `dash-shared`，看不见 `com.campusdash.infrastructure.risk.DeviceHasher`。**不能在小工具里复制一份 HMAC 逻辑**——抄一份就有漂移风险，而漂移的后果正是下面这条：算出的键与应用实际查询的键不一致，**黑名单加了等于没加，且完全无感**（查询正常返回、不抛异常，只是永不命中）。共享代码是唯一能结构性排除它的办法。

无环：`dash-bench → dash-infrastructure → dash-domain → dash-shared`，而 `dash-bootstrap → dash-bench` 是 `test` scope，不构成回环。

配套要求见 §4.1：`DeviceHasher` 必须是无 Spring 注解的普通类。

**（2）默认读 `DASH_RISK_DEVICE_HMAC_SECRET`，`args` 只做显式覆盖。**

密钥全靠手敲的话，敲错一个字符就落进上一条的静默失败。读同一个环境变量则与应用天然同源。

> **安全约束**：工具**只从环境变量读密钥，绝不从 `argv` 读**——`ps` 与 shell 历史都会泄露命令行参数。

## 10. 验收标准

逐条给出判定方式：

| 验收项 | 判定方式 |
|---|---|
| 请求上下文缺失可安全降级 | `RiskContextResolver` 单测 + `deviceId=null` 时不写设备键的 IT |
| 用户窗口并发计数准确 | `RiskFeatureIT` 并发用例（不同 requestId） |
| 窗口外数据自动清理 | `RiskFeatureIT` 过期分值用例 |
| 同一 `requestId` 不重复计数 | `RiskFeatureIT` 并发同 requestId 用例 |
| **已滑出窗口的 `requestId` 不再算重复** | `RiskFeatureIT` 跨窗口重放用例。**这是 [F-2](../实现期发现.md#f-2) 的回归锁**，不见效就等于没修 |
| 设备和 IP 集合相互隔离 | `RiskFeatureIT` 交叉写入用例 |
| TTL、成员上限生效 | `RiskFeatureIT` TTL 断言 + 上限断言（用户窗口与 IP 速率各一组） |
| 用户窗口 ZSet 成员上限生效 | 同上，断言保留的是最新条目 |
| **各键编码未退化** | `OBJECT ENCODING` 断言：三个 ZSet 为 `listpack`、两个 Set 为 `intset` |
| 结构化日志包含 `requestId、userId、errandId、特征计数` | `RiskFeatureLogTest` 逐字断言整行 + 字段顺序 |
| **测试上下文后门默认关闭** | `RiskContextInterceptorTest`：开关关闭 / profile 不含 test 两种情形下测试头均不生效，且**连 header 读取都不发生**（见 §7.4） |
| **两个 Set 各用自己的窗口秒数** | `RiskFeatureIT.ipAccountCapEnforcedWithItsOwnWindow()`：把 `ip-account-window.seconds` 覆盖成 300、与设备窗口的 600 不等，断言读到的是 300。**这是 [F-5](../实现期发现.md#f-5) 的回归锁** |
| 新增风控 Domain 包通过 ArchUnit 分层约束 | `ArchitectureRuleTest` 自动纳入，`mvn test` 通过 |
| 原有测试全部通过 | `mvn test` 全绿（注意 K-1 的配置坑与 K-2 的跳过陷阱） |

**验收结果**：完整 `mvn test` = 276 用例全过 / 0 跳过 / 0 失败。上表每一项都有对应的自动化断言，没有一条依赖人工核对——**唯一例外是「结构化日志」那一行的实际输出**，它的格式锁在 `RiskFeatureLogTest` 里，但真实运行时的输出行要等 P9.3 接上调用点才能看到。
