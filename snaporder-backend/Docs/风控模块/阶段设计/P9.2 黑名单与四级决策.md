## 1. 本阶段边界

**做**：三类精确黑名单查询、风险分累加与四级动作映射、`LIMIT` 限频 Key 的读写语义、`SHADOW/ENFORCE` 模式、降级标记、决策日志行格式、独立风控错误码。

**不做**：不接入抢单主链路（P9.3）、不实现 RocketMQ 事件（P9.4）、不写永久黑名单、不实现动态规则、不使用 BloomFilter、不做黑名单管理 API。

**一个必须提前说明的范围细节**：本阶段交付的风控预检用例**在 P9.3 之前没有生产调用方**，只有测试调用它。这不是遗漏而是实施计划 §6.4 的明确要求。代价是它的真实调用形态要等 P9.3 才能被端到端验证——与 P9.1 的 `RiskFeatureLog` 是同一个情况（见 §7.4）。

## 2. 已拍板的决策

| 编号 | 决策 | 落实位置 |
|---|---|---|
| D1 | 决策模型是**分数驱动**：动作是总分的纯函数 | §3.2 |
| D2 | **同一个计数**上的多档阈值取最高；**不同计数**累加 | §3.2 |
| D3 | 黑名单是**分值等于 `BLOCK` 下界的规则**，不是旁路分支 | §3.2 |
| D4 | IP 账号聚集的分值**低于 `LIMIT` 下界**，实现「仅加分不单独定性」 | §3.2 |
| D5 | 限频冷却命中**走同一套分数模型**，不另开分支 | §3.2 |
| D6 | 档位边界与分值都是**领域常量**，只有阈值可配 | §3.2、§6.2 |
| D7 | 新增**三个**独立风控错误码，不复用一个 | §5.3 |
| D8 | 决策日志格式**现在定死**，`eventId` 留占位待 P9.4 填充 | §5.2 |
| D9 | 黑名单三类键用**一次 Lua 往返**查询 | §4.1 |
| D10 | 短路顺序：限频 → 黑名单 → 特征采集 → 决策 | §5.1 |
| D11 | 端口签名**不预埋** deadline 参数（P9.3 再改） | §3.5 |
| D12 | `UserWindow` / `Cluster` 从**端口移入模型** | §3.1 |

各决策的具体影响：

**D1 —— 分数驱动。** 每条规则贡献分值，动作 **只**由总分查表得出。蓝图 §3.2–§3.4 的规则表里那一列「输出信号」是**提示**（说明该规则单独命中时落在哪一档），不是第二条裁决路径。

选它而不是「每规则直接给动作、取最高」的理由：实施计划 §6.3 的验收项「单规则和多规则动作正确」在后一种模型下就是一行 `max()`，没有可验的内容；而蓝图 §5.5 要统计分数分布，那个数字在信号驱动下没有意义。

**D2 —— 同一计数取最高。** 「同维度取最高」这个说法**不成立**，必须精确到计数：

| 规则对 | 是否同一个计数 | 处理 |
|---|---|---|
| 设备 > 3 / > 8 | ✅ 都是 `deviceAccounts`，必然同时命中 | 取最高 |
| 用户 10s > 5 / 60s > 30 | ❌ 分别是 `count10s` / `count60s`，互不蕴含 | **累加** |

用户窗口的两条不是「同一事实的两档」——10 秒内爆发 6 次但 60 秒内总共只有 6 次（只中短窗口）与 60 秒内 31 次但分布均匀（只中长窗口）是**两种不同的行为模式**，都能独立发生。取最高会把「既爆发又持续」的画像压回 `REVIEW`。

**D3 —— 黑名单是规则不是旁路。** 蓝图 §3.6 写的是「黑名单等强规则直接 BLOCK」。实现上不写成 `if (黑名单) action = BLOCK`，而是给它一个**恰好等于 `BLOCK` 档下界**的分值。两者结果完全等价（≥ 下界即 `BLOCK`），区别在于：

- 旁路会产生 `action=BLOCK, riskScore=0` 的决策，往蓝图 §5.5 的分数分布里掺一个与分数无关的异常值；
- 分值方案让「分数 → 动作」保持为**纯函数**，全流程只有一条裁决路径。

**D4 —— IP 账号仅加分。** 蓝图 §3.4 原文是「风险加分**或** REVIEW」，自己没定。取前者的理由是误伤分析：「同一 IP 出现 > 10 个账号」在**校园网 NAT 出口下是常态**，给它 `REVIEW` 档意味着这些用户单独就被拒绝并记审核事件。蓝图 §5.4 自己列了「多账号同 IP | NAT 场景下的风险加分」，说明它知道这个场景会误伤。

实现方式是**给它一个低于 `LIMIT` 下界的分值**（20），于是它自然「只在总分里贡献、单独命中不产生任何动作」——**不需要特例分支，靠分值实现**。

**D5 —— 限频冷却也走分数。** 限频键命中时**不做任何采集**（D10），若直接返回 `LIMIT` 而不计分，就与 D3 要避免的旁路同型（`action=LIMIT, riskScore=0`）。给这条短路一个 `LIMIT` 档下界的分值即可。

**D6 —— 档位与分值是常量。** 蓝图 §3.6 的分数档表（0-29 / 30-59 / 60-79 / 80+）与每条规则的分值都硬编码为领域常量，**只有阈值可配**（沿用 `RiskProperties`）。理由是两者性质不同：

- **阈值是检测灵敏度**——调松调紧只改变规则触发的难易；
- **分值是档位归属**——改它等于改语义（`IP 账号 < LIMIT 下界` 正是「仅加分」这条语义的全部实现）。

把后者做成配置项等于给「IP 账号静默变回独立拦截」开了一个不报错的入口。D4 那条不变式因此由**行为单测**守住（断言「IP 账号单独命中 → `PASS`」），而不是配置校验。

**D7 —— 三个错误码。** 蓝图只要求「不能复用 Sentinel 的 `GRAB_RATE_LIMITED`」，没说几个。拆成三个的成本是零，而合成一个之后再拆要让日志、压测脚本和离线统计全部改口径——三种动作的处置语义完全不同（限频是「稍后再试」、审核是「人工介入」、封禁是「永久」）。

**D8 —— 日志格式现在定死。** 蓝图 §3.10 要求的决策日志字段含 `eventId`，而它是 P9.4 的产物。现在就把它写进格式、值留 `-`，P9.4 只填值不改字段。理由见 `RiskFeatureLog` 已经确立的那条原则：字段名与顺序是给离线分析脚本的**跨系统契约**，事后往中间插一个字段等于改协议。

**D9 —— 一次往返查三类黑名单。** 详见 §4.1。朴素实现是三次 `EXISTS`，加上限频读与两次特征采集共 6 次往返。

**D10 —— 短路顺序。** 每次短路都省下后续往返。语义后果要说清楚：**被 `LIMIT` 的用户在冷却期内不再累积任何窗口计数**，冷却结束后窗口是干净的。这是「冷却」语义，反过来（先采集）会让冷却期内的请求继续推高计数、冷却一结束立刻再越线。

**D11 —— 不预埋 deadline。** 10ms 预算贯穿四次 Redis 调用，是 P9.3 的事。现在预埋一个没人读的参数**比不加更危险**——P9.3 的实现者会以为超时已经被处理了。P9.1 的 `RiskFeaturePort` 已经确立过这条原则（明确反对「给端口加一个只为打日志存在的参数」）。代价是 P9.3 要改端口签名与相关测试，这个代价当时就是明账。

**D12 —— 两个特征记录移入模型。** 见 §3.1，起因是 ArchUnit 规则三。

## 3. 领域层设计（`dash-domain`）

沿用现有约定：包下**只有 `model/` 与 `ports/`**，没有 `service/`（全仓 `dash-domain` 的 11 个子包无一例外）。因此决策逻辑住在模型里，不新建服务包。

### 3.1 记录归位（D12）

`UserWindow` 与 `Cluster` 目前是 `RiskFeaturePort` 的嵌套记录。本阶段要把它们移进 `com.campusdash.domain.risk.model`，端口改为 import 模型。

**为什么必须动**：决策逻辑（模型层）要消费这两个记录，而 ArchUnit 规则三禁止 `..domain..model..` 依赖 `..domain..ports..`，构建会直接红。绕开它有三条路，都不如直接归位：

| 方案 | 问题 |
|---|---|
| 新建 `domain.risk.service` 包 | 打破全仓「模型即逻辑载体」的约定，为一个函数开出第十二个子包 |
| 决策函数收 7 个扁平 `int` | `deviceAccounts` 与 `ipAccounts` 都是 `int`，传反了不是编译错误——正是本项目最防的那类静默缺陷 |
| 新建 `RiskFeatures` 模型记录并在应用层做映射 | 同一份事实存在两套记录（`Cluster` 与 `RiskFeatures` 的设备/IP 部分），要靠人工保持同步 |

归位本身是机械改动，涉及端口、适配器、`RiskFeatureLog` 与相关测试的 import。**方向是对的**：端口依赖模型是允许的方向（规则三只禁反向），而且这两个记录本来就是领域值对象，作为端口嵌套只是 P9.1 当时的便利——那时它们没有第二个消费方。

### 3.2 模型

`com.campusdash.domain.risk.model` 新增：

```text
RiskMode          enum    SHADOW / ENFORCE
RiskAction        enum    PASS / LIMIT / REVIEW / BLOCK
RiskRuleId        enum    十条规则标识 + 各自的分数（见下）
DegradeReason     enum    五种降级原因（见 §3.4）
BlacklistHits     record  (user, device, ip)  三条布尔 + NONE 常量
RiskDecision      record  (riskScore, action, matchedRules, ruleVersion, degradeReasons)
RiskRules         record  (阈值 + ruleVersion) + evaluate(...)
```

`RiskMode` 必须在 `domain.risk.model` 而不是 `RiskProperties` 的嵌套类型里：消费它的用例在 `dash-application`，看不见 `dash-infrastructure`（与 §4.3 的 `RiskRules` 同一个理由）。它只有两个值，Spring 可以从配置字符串直接绑定到枚举。

**档位与分值**（D6，均为领域常量）：

```text
LIMIT_MIN  = 30
REVIEW_MIN = 60
BLOCK_MIN  = 80

actionOf(score):  >= 80 BLOCK | >= 60 REVIEW | >= 30 LIMIT | else PASS
```

| 规则（`RiskRuleId`） | 触发条件 | 分值 | 单独命中 |
|---|---|---:|---|
| `USER_WINDOW_SHORT` | `count10s > shortThreshold` | `LIMIT_MIN` | `LIMIT` |
| `USER_WINDOW_LONG` | `count60s > longThreshold` | `REVIEW_MIN` | `REVIEW` |
| `DEVICE_ACCOUNTS_LOW` | `deviceAccounts > lowThreshold` | `REVIEW_MIN` | `REVIEW` |
| `DEVICE_ACCOUNTS_HIGH` | `deviceAccounts > highThreshold` | `BLOCK_MIN` | `BLOCK` |
| `IP_ACCOUNTS` | `ipAccounts > ipAccountThreshold` | **20**（< `LIMIT_MIN`） | **`PASS`（仅加分）** |
| `IP_RATE` | `ipRequests > ipRateThreshold` | `LIMIT_MIN` | `LIMIT` |
| `BLACKLIST_USER` | 用户黑名单命中 | `BLOCK_MIN` | `BLOCK` |
| `BLACKLIST_DEVICE` | 设备黑名单命中 | `BLOCK_MIN` | `BLOCK` |
| `BLACKLIST_IP` | IP 黑名单命中 | `BLOCK_MIN` | `BLOCK` |
| `LIMIT_COOLDOWN` | 限频键存在 | `LIMIT_MIN` | `LIMIT` |

分值等于 `LIMIT_MIN` / `REVIEW_MIN` / `BLOCK_MIN` **而不是各写一个整数**，是为了让 D6 那条不变式在编译期就成立：档位边界一动，规则的分值跟着动，不会出现「`BLOCK` 下界调到 120 之后黑名单静默不再拦截」。`IP_ACCOUNTS` 的 20 是唯一一个字面量——它**故意不绑定任何档位**，因为它就不该单独定性。

**累加与取最高的实现形态**：设备两条阈值是**同一个计数**（D2），所以它们写成一个 `else if` 链，而不是「两条规则各判一次再取 `max`」：

```text
if (deviceAccounts > highThreshold)      命中 DEVICE_ACCOUNTS_HIGH
else if (deviceAccounts > lowThreshold)  命中 DEVICE_ACCOUNTS_LOW
```

`else if` **就是**「取最高」——高档命中时低档必然也命中，写成两条独立判断再聚合等于对同一件事重复计分。这个结构要配注释说明，并且由一条专门的行为单测守住：`deviceAccounts = 9` 必须产出**一条**命中、总分 80，而不是两条、140。

其余规则各自判定后**全部累加**（含用户窗口的两条，D2）。因此一个既在 10 秒内爆发 6 次、又在 60 秒内到 31 次的用户得 90 分 → `BLOCK`——这正是最像脚本的画像。

**`matchedRules` 的顺序必须固定**：它是日志行的一部分，顺序不稳定会让同一次决策在不同环境下产出不同文本，离线脚本去重时会把它们当成两条。实现上按 `RiskRuleId` 的**声明顺序**依次追加（枚举天然给出稳定序），并由单测断言一个多命中场景的完整序列。

**`degradeReasons` 不由 `evaluate` 产出**：规则层拿到的只有采集结果，它看不出
`count10s = 0` 究竟是「用户真的没请求过」还是「采集挂了所以记 0」。想让规则层区分，
就得把「哪些维度失败了」一起传下去——那等于让规则层理解 Redis 故障。
所以降级原因由**捕获异常的那一层**（用例）记录，事后用
`RiskDecision.withDegradeReasons(reasons)` 附到结果上；该方法只换原因列表，
**分数与动作原样保留**，这正是「降级不是放行」的实现形态（`实现期发现.md` F-14）。

**记录里不放 `decisionLatencyMs`**：蓝图 §3.6 把它列在结果字段里，但 §3.8 同时规定它「从风控用例入口计时」，即它属于**调用方测量的值**，不是决策的一部分。放在应用层的日志行里（§5.2）。

### 3.3 `RiskRules`

```text
RiskRules(
    int    shortThreshold, int longThreshold,
    int    deviceLowThreshold, int deviceHighThreshold,
    int    ipAccountThreshold, int ipRateThreshold,
    int    limitCooldownMs,
    String ruleVersion)

RiskDecision evaluate(UserWindow window, Cluster cluster,
                      BlacklistHits blacklist, boolean limitHit)
```

做成**值对象 + 纯方法**而不是一组静态常量，是为了让实施计划 §6.3 的边界值测试能直接构造一套自定义规则的 `RiskRules` 来跑，不必去改配置或起 Spring 上下文。

`ruleVersion` 是**配置项**而不是代码常量，因为它标识的是「本次决策用的哪套规则」，而规则阈值是配置的一部分——同一份代码、两套阈值就是两套规则。改任何风控阈值时必须同步升这个值，否则离线分析无法把两套规则下的指标分开。这条要写进配置项的注释里。

### 3.4 降级原因

```text
USER_WINDOW_FAILED     risk_user_window.lua 调用失败
CLUSTER_FAILED         risk_cluster.lua 调用失败
BLACKLIST_FAILED       黑名单查询失败
LIMIT_READ_FAILED      限频键读取失败
LIMIT_WRITE_FAILED     限频键写入失败
```

**五个而不是一个布尔**，因为蓝图 §3.9 的降级聚合是「同一实例、**同一原因** 10 秒最多 1 条」——没有原因就没法聚合。这个形状现在定死，否则 P9.4 要回头改接口。

**降级的语义是「少一个证据」，不是「放行」。** 这是蓝图 §3.8 那张表最容易被读错的地方：

| 情形 | 处理 |
|---|---|
| 黑名单查询失败 | 该维度记 `false`，**特征照采、决策照跑** |
| 某次特征采集失败 | 该维度计数记 0，**黑名单照查、决策照跑** |
| 两者都失败 | 分数为 0 → `PASS`，但两个原因都记进 `degradeReasons` |

只有「所有证据都拿不到」时才**事实性地**退化成 `PASS`——那是分数为 0 的自然结果，不是一个写着「失败就放行」的分支。区别在于：黑名单挂了但设备维度已经越线时，决策**仍然是 `BLOCK`**；写成 fail-open 分支就会漏掉它。

### 3.5 端口

```text
RiskBlacklistPort:
    BlacklistHits query(long userId, String deviceId, String clientIp)

RiskLimitPort:
    boolean isLimited(long userId)
    void    markLimited(long userId)
```

沿用 P9.1 已确立的三条约定：

- **参数扁平标量**，不传 `RiskContext` 整体（`RiskFeaturePort.trackCluster` 同型）
- **收原始 `deviceId` / `clientIp`，哈希在适配器内完成**——解析层不该知道哈希密钥，全仓「原始值 → 哈希」只有一个入口
- **不抛领域异常**；Redis 故障由调用方 catch 后转成 `DegradeReason`

`RiskBlacklistPort.query` 的两个字符串参数**可空**，缺失的维度不查那个键（`RiskKeys.blacklistDevice` 对非哈希值会抛异常，且缺失维度的键本来就不该存在），结果里对应字段恒为 `false`。

**端口不预埋 deadline 参数**（D11）。

**命名注意**：ArchUnit 规则二要求这两个接口以 `Port` 结尾且落在 `..domain.risk.ports..`。

## 4. 基础设施层设计（`dash-infrastructure`）

### 4.1 `risk_blacklist.lua` —— 一次往返查三类黑名单（D9）

```text
KEYS[1] = risk:bl:user:{userId}
KEYS[2] = risk:bl:device:{deviceHash}   缺失时为占位键
KEYS[3] = risk:bl:ip:{ipHash}           缺失时为占位键
ARGV[1] = 是否存在设备维度 1/0
ARGV[2] = 是否存在 IP 维度 1/0
返回: {blUser, blDevice, blIp}
```

三个设计点：

1. **用 `EXISTS` 而不是 `GET`**。黑名单的语义是「键存在即拉黑」，值是什么无所谓。`EXISTS` 对**任何类型**都返回 1、不做类型检查，因此不会因为运维误把键建成别的类型而 `WRONGTYPE` 失败；`GET` 则会。代价是蓝图 §3.8 表格里那条「键类型错误」的故障场景**在黑名单维度不适用**（它只适用于特征采集：`SADD`/`ZADD` 对错误类型会报错），这一点要在蓝图里注明。
2. **`EXISTS` 是只读的，占位键即使被误访问也不会被创建。** 这比 `risk_cluster.lua` 的情况更安全——那边占位键一旦漏进去就是真的 `SADD`/`ZADD` 建键。两个 `if` 守卫仍然保留，但它们在这里不是唯一防线。
3. **TTL 由写入方决定，脚本不管**。永久封禁就是不设 TTL，临时封禁就带 TTL——「黑名单失效后不再拦截」（§3.5）由 Redis 的过期语义天然满足，不需要应用侧判断。

`RiskKeys` 新增 `limitKey(long userId)` → `risk:limit:user:{userId}`（键名沿用蓝图 §3.6 的写法，`{}` 是 hash tag）。**黑名单三个键构造函数 P9.1 已交付**，本阶段只是第一个使用者。

### 4.2 适配器

```text
RedisRiskBlacklistAdapter implements RiskBlacklistPort
RedisRiskLimitAdapter     implements RiskLimitPort
```

`RedisRiskBlacklistAdapter` 注入 `StringRedisTemplate` + `DeviceHasher` + 脚本 bean，形状对齐 `RedisRiskFeatureAdapter`（`redis.execute(script, keys, args)`、`List<Long>` 按下标取值、元素可能为 `null`）。

**两个适配器各自注入 `DeviceHasher`**，这是 P9.1 的 D1 决定的既有形态（端口收原始值）。它看起来是「两处哈希」，但**不是**会漂移的重复：

- 两处拿到的是**同一个 Spring bean**，密钥同源；
- 键名统一由 `RiskKeys` 构造，格式不会分叉。

真正会漂移的是「复制一份 HMAC 逻辑」——那正是 `dash-bench` 必须给 `DeviceHasher` 加依赖而不是抄一份的原因（P9.1 §8.5）。

`RedisRiskLimitAdapter` 的 TTL 取 `RiskProperties.limitCooldownMs`。

**两个适配器对「按脚本下标取值拿不到」的处理刻意相反**，不要当成不一致去「统一」：
`RedisRiskFeatureAdapter.intAt` 拿不到返回 **0**（采集的定位，0 是中性值，不会让任何人被误判）；
`RedisRiskBlacklistAdapter.flagAt` 拿不到**抛异常**（安全判定，`false` 的含义是「不在黑名单里」，
等于放行——用一次故障换一次静默放行，比抛异常糟得多）。限频键的读同理：
`hasKey` 返回 `null` 时抛，而不是按「不在冷却期」处理。

**`markLimited` 只在 ENFORCE 模式且本次决策动作恰为 `LIMIT` 时调用**，判断在用例里（§5.1），适配器不做策略。

### 4.3 装配

`RiskConfig` 增加两个 `@Bean`：

```text
RiskRules riskRules(RiskProperties p)   // 把配置阈值 + ruleVersion 转成领域值对象
RiskMode  riskMode(RiskProperties p)
```

**为什么需要这一层转换**：`RiskProperties` 在 `dash-infrastructure`，而消费它的用例在 `dash-application`——application 看不见 infrastructure，两个模块之间只有 `dash-domain` 是公共词汇。所以配置类必须以**领域类型**的形式交给用例。这与 `DeviceHasher` 的装配是同一个模式（类保持纯净、装配集中一处）。

`RiskMode` 只有 `SHADOW` / `ENFORCE` 两个值，Spring 可以从字符串直接绑定到枚举。

**第三个开关 `enabled` 不走这里，而走 `@Value("${dash.risk.enabled:true}")`**（用例构造器参数）。它不是领域概念，只是「这一整套要不要跑」——做成第三个 `RiskMode` 值会把「关闭」和「只观察」混成一个轴，而这两件事的调用面完全不同（关闭时一个端口都不碰）。`@Value` 的默认值必须与 `RiskProperties.enabled` 的 `@DefaultValue("true")` 保持一致，否则同名的两处默认值会分叉。见 F-17。

> **P9.3 后续**：本段在 P9.3 被 `RiskPolicy` 覆盖——`enabled` / `mode` / `failOpen` / `deadlineMs` 收成一个领域 bean，`RiskMode` 那个独立 bean 随之撤销（P9.3 设计 D10、§3.1）。原文保留，因为被推翻的只是「做不成领域 bean」这一步：「`enabled` 不该是第三个 `RiskMode` 值」这条推理在 P9.3 仍然成立，`RiskPolicy` 用的是两个正交字段。

## 5. 应用层设计（`dash-application`）

### 5.1 `RiskPreCheckUseCase`

```text
RiskPreCheckResult preCheck(RiskContext context)

RiskPreCheckResult(RiskDecision decision, boolean enforced)
    RiskAction effectiveAction()   // enforced ? decision.action() : PASS
    ErrorCode  errorCode()         // effectiveAction 映射
```

`RiskContext` 直接复用 P9.1 的领域模型，不再造一个 `Command` 记录——它已经有 `userId / errandId / requestId / deviceId / clientIp` 五个字段，正是所需的全部输入。**这里是全仓第一个构造 `RiskContext` 的地方**（P9.1 的拦截器只交付 `RiskRequest`，因为它在 `preHandle` 阶段拿不到 `errandId`）。

执行顺序（D10）：

```text
0. !enabled            -> 直接返回 PASS，不做任何 I/O
1. ENFORCE 下读限频键   -> 命中：记 LIMIT_COOLDOWN，短路，不采集不查黑名单
2. 查三类黑名单         -> 查询失败：记 BLACKLIST_FAILED，three-false 继续
3. 采集用户窗口         -> 失败：记 USER_WINDOW_FAILED，计数记 0 继续
4. 采集设备/IP 维度     -> 失败：记 CLUSTER_FAILED，计数记 0 继续
5. RiskRules.evaluate  -> 得出 decision
6. ENFORCE 且 action==LIMIT -> 写限频键（失败记 LIMIT_WRITE_FAILED）
7. 写决策日志行
```

**第 0 步与 `SHADOW` 是两回事，不能合并**：

| | 采集 | 查黑名单 | 读限频键 | 写限频键 | 拦截 |
|---|---|---|---|---|---|
| `enabled=false` | ❌ | ❌ | ❌ | ❌ | ❌ |
| `mode=SHADOW` | ✅ | ✅ | ❌ | ❌ | ❌ |
| `mode=ENFORCE` | ✅ | ✅ | ✅ | ✅ | ✅ |

`SHADOW` 的定义是「计算并记录风险结果，但不拦截」（蓝图 §3.10），所以它必须完整地算——只是不生效。**限频键在 `SHADOW` 下连读取都不发生**（不是读了再忽略），与 P9.1 测试头开关的双闸门禁同型。

`effectiveAction()` 让「SHADOW 不拦截」这条性质在**本阶段就可断言**，不必等 P9.3 接入。

**「短路」的范围只有第 2~4 步**：第 1 步的括号逐条列了它省掉什么（不采集、不查黑名单），
第 6 步不在其中，所以短路路径上 `action == LIMIT` 仍然成立、限频键**仍然被续写**（TTL 刷新）。
后果是冷却期**滑动**的：持续请求的人不会在冷却期结束时挤进一次漏网请求。
两种读法都讲得通，选滑动是因为它更严——理由与实测见 `实现期发现.md` 的 F-16。

**`enabled` 从哪来**：它不在 §4.3 交出去的那两个领域 bean 里（不是阈值表的一部分，
也不该把 `enabled=false` 折叠成第三个 `RiskMode` 值——那会让「第 0 步与 SHADOW 是两回事」
在类型上重新合流）。用例走 `@Value("${dash.risk.enabled:true}")`，与同功能域的
`RiskContextInterceptor` 读法一致。见 F-17。

> **P9.3 后续**：`enabled` 改由 `RiskPolicy` bean 提供，`RiskContextInterceptor` 同步改成注入同一个 bean（P9.3 设计 D10）。本段对「不该折叠成第三个 `RiskMode` 值」的推理不变。

### 5.2 `RiskDecisionLog`

落点与形态对齐 `RiskFeatureLog`：纯函数 `format(...)` + `emit(...)`，日志格式可被逐字单测。
**入参是整条 `RiskDecision` 而不是拆开的 `action` / `riskScore` / `matchedRules`**——
那三个值在 `RiskDecision` 里有「动作是总分的纯函数」这条构造器不变式，
拆成平铺参数等于在日志这一侧把约束重新放开，而 `action=BLOCK riskScore=20` 的一行
与「一条被伪造的行」长得一模一样。

```text
risk_decision userId=... errandId=... requestId=... action=... riskScore=...
              matchedRules=USER_WINDOW_SHORT|USER_WINDOW_LONG ruleVersion=1
              degraded=false degradeReasons=- eventId=- decisionLatencyMs=3
```

- `eventId` 恒为 `-`，待 P9.4 填充（D8）。写死而不是开一个参数：开参数意味着每个调用点
  都要传一次 `null`，那是「一条默认关闭的线」——看起来接上了，实际永远拿不到值
- `matchedRules` / `degradeReasons` 按枚举声明序、以 `|` 连接，空时为 `-`。
  **渲染时重新排一遍序**：`evaluate` 本来就按声明序产出，但 P9.3/P9.4 会引入别的决策构造
  路径，日志行的稳定性不该依赖上游。是排序不是去重——真出现重复条目就该在日志里看见
- `degraded` 是 `degradeReasons` 非空的派生子，保留是为了让离线脚本不必解析空值语义
- **不记特征计数**。短路路径**没有采集**，此时记 `count10s=0` 是伪造数据——「未采集」与「采集到 0」是两回事，后者会让人以为用户真的没有请求过

`requestId` 沿用 `RiskFeatureLog.safe()` 的控制字符替换（它是本行里唯一来自客户端的字段）；`ruleVersion` 同样过一遍，因为它来自配置而不是代码，带换行的值会把一行日志劈成两行而污染离线指标。

**净化逻辑抽成了共用的 `LogField.safe()`**（`dash-application/.../risk/LogField.java`，包私有），
两条日志都调它。原来 `RiskFeatureLog.safe()` 是私有方法，「沿用」只能靠复制——而复制一份
**安全**方法迟早漂移，漂移的后果是其中一条日志重新变得可伪造，不报错、不告警。
其余字段（数字与枚举名）不需要净化：枚举名由代码定义，不含空白与控制字符。

**安全约束**：本行以及所有风控日志**不得包含原始 `deviceId` / `clientIp`**（P9.1 的 D1）。`RiskDecision` 里本来就没有这两个值，所以这条在类型层面就成立。

### 5.3 错误码

`ErrorCode` 新增三个（D7），错误码枚举在 `dash-shared`：

```text
RISK_LIMITED           "请求过于频繁，请稍后再试"
RISK_REVIEW_REQUIRED   "请求已被风控标记，等待审核"
RISK_BLOCKED           "请求已被风控拦截"
```

`PASS` 时返回 `OK`。不复用 Sentinel 的 `GRAB_RATE_LIMITED`（蓝图 §3.6）——两者语义不同：那是「当前任务过热」（按任务限流），这是「你的行为异常」（按用户风控）。

## 6. 配置落地

### 6.1 新增配置项

```yaml
dash:
  risk:
    mode: SHADOW                    # 新增
    limit-cooldown-ms: 10000        # 新增
    rule-version: "1"               # 新增
    device-window:
      seconds: 600
      threshold: 8                  # 高阈值（BLOCK），已存在
      low-threshold: 3              # 新增：低阈值（REVIEW）
```

`mode` / `limit-cooldown-ms` / `rule-version` 三项蓝图 §3.10 的配置示例里本来就有，P9.1 只是没落（那时用不上）。`lowThreshold` 是补蓝图 §3.3「> 3 → `REVIEW`」那条规则的位置——P9.1 的 `DeviceWindow` 只有单个阈值，装不下成对阈值。

### 6.2 校验

新增三条，落在 `RiskProperties` 的紧凑构造器里（与既有两条编码校验同处）：

| 校验 | 不校验的后果 |
|---|---|
| `deviceWindow.lowThreshold < deviceWindow.threshold` | 低阈值 ≥ 高阈值时 §3.2 的 `else if` 链**永远走不到低档**，高阈值那条规则的档位标注变成假的，且不报错 |
| `deviceWindow.lowThreshold >= 1` | 取 0 或 -1 会让「账号数 > 低阈值」**恒真**，每个带设备维度的请求都被判 `REVIEW`——不是规则失效而是**全站误判**。`0` / `-1` 恰是「想关掉这条规则」时最顺手的两种写法，必须把下一个念头堵在错误信息里（`实现期发现.md` F-13） |
| `limitCooldownMs > 0` | 0 或负数写进 Redis 会让限频键立刻过期，限频**静默失效** |

**分值不变式不在这里**（D6）：`IP_ACCOUNTS < LIMIT_MIN` 与黑名单分值 ≥ `BLOCK_MIN` 都是代码常量之间的关系，由 §7.1 的行为单测守住，不需要运行时校验。

测试 yaml 必须同步——**先改测试 yaml 建好启动基线再写代码**，反过来做会被一串启动失败淹没（`预存缺陷与坑.md` K-1）。

## 7. 测试策略

### 7.1 单元测试（无中间件依赖）

**这一批是本阶段最值钱的部分**：P9.1 的三个实现期缺陷（编码悬崖、TTL 耦合、查重顺序）全是靠手工跑真实 Redis 才抓到的，因为 Lua 没有单测抓手。决策逻辑恰恰**有**抓手——边界值、累加、取最高、档位映射全是纯输入输出，所以绝大多数复杂度压在这里，让后面的 I/O 部分尽量薄。

| 目标 | 要覆盖的性质 |
|---|---|
| `RiskRules.evaluate` —— **每条规则的单侧边界** | `5/6`、`30/31`、`3/4`、`8/9`、`10/11`、`100/101`：阈值**取不到**时不命中、**取到**时命中。注意 `30` 在这份清单里是**两个意思**（用户 60s 的阈值、`LIMIT` 档下界），用例命名必须带上下文 |
| `RiskRules.evaluate` —— **档位边界** | `29/30`、`59/60`、`79/80` 三组，断言跨过边界时动作恰好切换 |
| **同一计数取最高**（D2 的回归锁） | `deviceAccounts = 9` 产出**一条** `DEVICE_ACCOUNTS_HIGH`、总分 80；**不是**两条、140 |
| **不同计数累加**（D2 的另一半） | `count10s = 6` 且 `count60s = 31` → 30+60=90 → `BLOCK` |
| **IP 账号仅加分**（D4 的回归锁） | `ipAccounts = 11` 且其余全不命中 → 20 分 → **`PASS`**。这条断言是「`IP_ACCOUNTS` 不得被调过 `LIMIT_MIN`」的唯一守卫 |
| **黑名单恒为 `BLOCK`**（D3 的回归锁） | 三类黑名单各自单独命中 → `BLOCK`，且 `riskScore` 等于 `BLOCK_MIN` 而非 0 |
| **限频冷却走分数**（D5 的回归锁） | `limitHit = true` → `LIMIT`，`riskScore = LIMIT_MIN` |
| **降级不是放行** | 黑名单失败但设备维度越线 → 仍然 `BLOCK`，且 `degradeReasons` 含 `BLACKLIST_FAILED` |
| `matchedRules` 顺序稳定 | 多命中场景断言完整序列，锁住日志行的稳定性 |
| `RiskProperties` | 新增两条校验的边界（`lowThreshold == threshold` 拦截、`limitCooldownMs == 0` 拦截） |
| `RiskDecision` | 动作与分数必须自洽（构造器不变式）；`withDegradeReasons` 不改分数与动作 |
| `RiskPreCheckResult` | `effectiveAction()` 与 `errorCode()` 全部四种映射；`SHADOW` 下恒为 `PASS` / `OK` |
| `RiskDecisionLog` | 逐字断言整行 + 字段顺序 + 空值渲染为 `-` + 控制字符替换（`requestId` 与 `ruleVersion` 各一条）+ 不含特征计数 + 不记原始设备号/IP |
| `RiskPreCheckUseCase`（手写 fake 端口） | 短路顺序（**命中限频键时**不调用黑名单与特征端口；见 §5.1）；`enabled=false` 时**不调用任何端口**；`SHADOW` 下**不调用** `RiskLimitPort` 的读与写；`ENFORCE` 下 `LIMIT` 才写、`REVIEW`/`BLOCK` **不写**；五条降级路径各记一个原因且决策照常完成 |
| `RiskBlacklistPort` 契约 | 缺失维度不查对应键 |
| 装配 `RiskConfig` → `RiskRules` | 七个阈值**两两取不同的值**后逐个字段断言。`RiskRules` 的构造函数是一串挨着的位置参数，写反了编译器不报错；同值不具区分能力（P9.1 的 F-5） |
| `RiskKeys.limitKey` | 逐字断言 `risk:limit:user:{1001}`——花括号是**真字符**（hash tag），与蓝图 §3.6 一致；以及黑名单用户键**不带**花括号这处刻意的不对称 |
| `BlacklistKeyTool` 写入路径 | 两参数的旧写法**永远解析成只算键**（最危险的行为是「写」）；报告里出现的是**实际连的端点**；带 TTL 的键必须显眼报警；核验结果如实渲染；写入/解除报告里的键与 `RiskKeys` 同源 |

按仓库现约定：纯 JUnit 5 + `@DisplayName` 中文场景名，**不使用 Mockito**（全仓无该依赖），需要的协作者手写 fake——fake 记录**每一次调用**，于是「SHADOW 下不读限频键」这类断言从注释里的声明变成可断言的事实（与 P9.1 的 `RiskContextInterceptorTest` 同一手法）。

### 7.2 集成测试（`RiskPreCheckIT`）

沿用 `RiskFeatureIT` 的既有约定（`Assumptions.assumeTrue(MiddlewareAvailable.check())` 守卫、直连真实 Redis、每个用例开头 `purge` 自己那几个键）。

**必须覆盖的性质**：

| 性质 | 用例设计 |
|---|---|
| 三类黑名单各自命中 → `BLOCK` | 走 `RiskKeys.blacklistUser/Device/Ip` + `DeviceHasher` 算出键（**不手写键名字符串**，也不硬编码哈希值），直接写入真实 Redis 后走完整用例 |
| **黑名单删除后不再拦截** | `DEL` 键后再跑一次 → 不再 `BLOCK`（蓝图 §3.5「黑名单失效后不能继续拦截」） |
| 限频键在 `ENFORCE` 下读得到 | 用例直接写入限频键（走生产同一条写路径 `RiskLimitPort.markLimited`，**不手搓 `SET`**——手写的键形态可能与应用写的不是一回事）→ 短路返回 `LIMIT`，且**不产生任何特征键**（用调用前后的键集合差集断言） |
| 限频键的 TTL 正确 | 触发 `LIMIT` 后断言 `TTL` 落在 `limitCooldownMs` 附近（上界同时守着「TTL 不是某个写死的值」） |
| **短路路径仍然续写限频键**（F-16） | 把 TTL 压到 3 秒后再走一次短路 → `TTL` 被拉回冷却时长附近，两个读数数值上分得很开 |
| `SHADOW` 不读不写限频键 | 切换 `mode` 后跑同一场景，断言限频键**不存在**（用键集合差集） |
| 多规则累加 | 同时构造用户窗口越线与设备聚集，断言最终动作与分数 |
| 特征缺失维度不影响决策 | `deviceId = null` 时设备规则不命中，其余照常 |

IT 不通过 shell 调 `BlacklistKeyTool`（那是在测工具，不是在测用例），而是直接用工具内部那**同一个** `RiskKeys` / `DeviceHasher`——工具与 IT 于是共用一条键计算路径，「工具写进去的键应用能不能查到」这件事才有实证。`DeviceHasher` 走 `@Autowired` 拿，**不在测试里自己 new 一个**：自己造 hasher 就等于在测试侧复制了一份密钥来源，而那正是「工具算的键与应用的不一致」的测试版。测试上下文里的密钥来自 `dash-bootstrap/src/test/resources/application.yaml` 的明文常量 `test-only-not-a-secret`（主配置那份是环境变量占位符，没有默认值）。

**降级路径不进 IT**：诱发真实 Redis 故障需要 mock 或断连，两者都比单测脆。`BLACKLIST_FAILED` / `USER_WINDOW_FAILED` 等全部由 §7.1 的 fake 端口抛异常覆盖。顺带一提，黑名单用的是 `EXISTS`，对键类型不做检查，所以**没有**「把键建成错误类型来诱发降级」这条路径（§4.1）。

**类级配置取 `ENFORCE`，只起一个 Spring 上下文**：本 IT 主体验的是「真的拦下来了」，走的是 Spring 装配出来的那个用例 bean。对照 `AuthModeIT`——那边的 `mode` 决定 Spring 挑哪一套 `AuthPort` 实现，所以必须两个 `@Nested` 上下文；这里 `mode` 只是**同一个类的构造参数**，为它多起一个上下文不划算，而「配置 → 模式」这一段由 `RiskConfigTest` 断言。`SHADOW` 的场景因此在 IT 里手工构造用例（端口与规格仍是 Spring 里的真货）：它要证的性质是「哪些东西没被动过」，那与谁构造的用例无关。

**IT 不登记 `BenchRun`**：本类不写任何 DB 行（P9.2 的用例只碰 Redis），没有任务需要登记，与 `AuthModeIT` 的处理一致。同目录的 `RiskFeatureIT` 登记了，但它的 javadoc 自己也写着「无需 BenchRun 登记任务」——那是一处前后不一致，不要照着抄。

**黑名单键在用例收尾时删掉**：黑名单键没有 TTL（这是刻意保留的性质），而测试库是各 IT 共享的，不清就会永久留垃圾键。收尾清理放在 `@AfterEach` 而不是用例末尾——断言失败时后面的语句不会执行，而那正是最可能留下垃圾键的一次运行。用例开头另有一次 purge 兜底：上一轮崩溃留下的键只有「下次运行开头清掉」能救。

### 7.3 不做什么

- **不做并发 IT**：P9.2 新增的两次 Redis 调用都是**只读**（`EXISTS`）或**幂等写**（`SET` 限频键），没有 P9.1 那类「读取-判断-写入」的复合操作，并发正确性由 P9.1 已验证的 Lua 原子性覆盖。
- **不做 `UserWindow` / `Cluster` 归位的重复验证**：D12 是纯粹的记录搬家，P9.1 的 `RiskFeatureIT` 原样跑通即是证据。

### 7.4 无生产调用方的处理

本阶段的用例只有测试调用。这与 P9.1 的 `RiskFeatureLog` 情况相同（它的运行时输出行至今没被真实调用过）。

处理方式是**如实记入验收标准**（§9 的脚注），不为了「看起来端到端」而临时接线——那会违反 §6.4，而且接一条默认关闭的线等于没接。

批次 1 全部是单测（`mvn test`），批次 2、3 走 `mvn test` 全绿，批次 4 才跑 IT——沿用既有验证节奏。批次 1 的 6 个任务之间依赖很浅，可以并行开工。

注意「跑 IT」指的是**新增 IT**：本仓 surefire 的 includes 里有 `**/*IT.java`，所以 `mvn test` 本来就把全部 IT 跑一遍（这也是为什么必须盯 `skipped` 而不是失败数——中间件没起时 IT 会被 `assumeTrue` 整类跳过，而 `mvn test` 仍然 BUILD SUCCESS）。

**任务 12 的必要性**：P9.1 交付的 `BlacklistKeyTool` **只能算键、不能写**。运维拿到键还得自己拼 `redis-cli`，而这一步拼错（键名少个冒号、忘了 TTL）**不会报任何错**，只是黑名单不生效——正是 `RiskKeys` 要防的那类静默失效。把「算键 + 写入」收成一个动作，同时满足蓝图 §3.5「通过初始化脚本、Redis CLI 或测试 fixture 写入」与 P9.5 压测的批量种黑名单需求。

**写入必须是显式的动词**：`BlacklistKeyTool key|add|remove <维度> <标识>`。两参数的旧写法（`user 1001`）永远解析成 `key`，也就是**只算键、不写**。黑名单是生产数据，「以为只是算个键、结果写进去了」比「以为写进去了、结果只算了个键」危险得多——后者再跑一次就好，前者可能把一个正常用户永久封禁。这条性质靠 `parse` 这个纯函数被单测钉住，而不是只写在注释里。

**解除用 `DEL` 而不是 `SREM`**：查询侧 `RedisRiskBlacklistAdapter` 用类型无关的 `EXISTS`，所以一个被手工 `SET` 成字符串的键**同样算命中**；`SREM` 会在这种键上报 `WRONGTYPE`，也就是「看着像解除了，其实没有」。见 F-18。写入与解除各自在动作前后用**与查询侧同一条 `EXISTS`** 核验一次，并把读数如实渲染进报告（含端点、TTL 的三种读数），核验失败直接以退出码 3 结束——「跑完了」和「生效了」不是一回事。

落点沿用 `dash-bench`（P9.1 的 D8）。**安全约束不变：只从环境变量读密钥，绝不从 `argv` 读**——`ps` 与 shell 历史都会泄露命令行参数。

## 9. 验收标准

逐条给出判定方式：

| 验收项（实施计划 §6.3） | 判定方式 |
|---|---|
| 单规则和多规则动作正确 | `RiskRules` 单测：每条规则单独命中、以及多规则累加 |
| **黑名单覆盖普通风险分** | `RiskRules` 单测：黑名单单独命中 → `BLOCK` 且 `riskScore = BLOCK_MIN`。**注意措辞**：实现是「以最高分值参与累加」而非「覆盖分数」，两者动作结果相同 |
| 黑名单失效后不再拦截 | `RiskPreCheckIT` 的 `DEL` 用例 |
| Redis 查询异常产生可识别的降级结果 | 单测：fake 端口抛异常 → `degradeReasons` 含对应原因，且**决策照常完成** |
| 决策结果结构稳定 | `RiskDecisionLog` 逐字断言整行 + 字段顺序 |
| 边界值（5/6、30/31 等）测试通过 | `RiskRules` 单测的全套阈值边界 + 三组档位边界 |
| `ENFORCE` 能读取已有限频 Key 并直接返回 `LIMIT` | `RiskPreCheckIT` 手工写键用例 + 单测的短路顺序断言 |
| `SHADOW` 不读取、不写入限频 Key | 单测（fake 记录端口调用）+ `RiskPreCheckIT` 的键集合差集断言 |
| **短路路径续写限频键**（F-16 的回归锁） | `RiskPreCheckIT`：把 TTL 压到 3 秒后走一次短路，断言它被重新拉回冷却时长附近 |
| 三类黑名单的三个布尔各落对维度 | `RiskPreCheckIT`：三类各一例，断言 `matchedRules` 恰为对应的那一条 |
| 模式切换不会改变 SHADOW 下的业务结果 | 单测：`effectiveAction()` 在 `SHADOW` 下恒为 `PASS` |
| **IP 账号仅加分**（D4 的回归锁） | 单测：`ipAccounts = 11` 单独命中 → `PASS` |
| **同一计数取最高**（D2 的回归锁） | 单测：`deviceAccounts = 9` → 一条命中、80 分 |
| **降级不是放行** | 单测：黑名单失败 + 设备越线 → 仍然 `BLOCK` |
| 新增风控 Domain 包通过 ArchUnit 分层约束 | `ArchitectureRuleTest` 自动纳入，`mvn test` 通过 |
| 原有测试全部通过 | `mvn test` 全绿（注意 K-1 的配置坑与 K-2 的跳过陷阱，**看总用例数而不是失败数**） |

**验收时必须如实记录的一条限制**：本阶段交付用例**没有生产调用方**，端到端行为要等 P9.3 接入后才能在真实业务链路上观察（§7.4）。这不是缺陷，但必须写进结论，不能让「全部用例通过」读起来像已经端到端验证过。
