## 1. 本阶段边界

**做**：功能回归的执行与对照表、六项故障测试（含一个半自动重启用例）、八个攻击流量场景的 profile 与执行、两组 A/B 对照实验（风控开关、聚合开关）、同步侧与异步侧两份离线指标脚本、压测报告 / 故障报告 / 指标汇总三份交付物、阶段归档。

**不做**：**不改任何生产代码**。本阶段新增的代码全部落在 `dash-bench`（压测工具）、`bench/scripts/`（离线脚本）与测试源（两个 IT）里。一个「只做测试」的阶段如果顺手改了被测代码，它验的就不再是 P9.1–P9.4 验收过的那份东西——所以这条是本阶段的硬约束，不是习惯。若某个场景暴露出真实缺陷，处理方式是**登记进 `预存缺陷与坑.md`**（发现的当场就写），而不是在报告里顺手修掉。

**不做**（延续计划 §10 的范围边界）：动态规则管理、人工审核流程、前端改动、新中间件、引入 Micrometer/Prometheus（指标仍走结构化日志 + 离线脚本）、多机部署压测。

**一个必须提前说清的范围细节**：本阶段所有数字都是**同机（应用 + 中间件 + 发压端）**测出来的，历史报告里这一行一直写着「资源争抢，数字仅作基线」（`SpikeLoadClient` 的 `startRun` 描述就是这个）。所以：

- 报告的结论一律是**相对比较**（聚合开/关、风控开/关、同一 profile 的历史前后），不是容量承诺；
- **绝对数字不得跨机器引用**——`report-P4` 那次 TPS ≈64 与 `report-P3` 的 191 是同一套代码，差别来自同机的其它负载，这一条已经踩过一次。

**用例总数基线是 583**（P9.4 末：shared 9 / domain 100 / application 91 / infrastructure 124 / presentation 110 / bench 26 / bootstrap 94 / worker 29）。本阶段预计净增**个位数**用例，且全部在 `dash-bootstrap` 名下——这个阶段的产出主要是**证据与数字**，不是用例数量。跑完全量 `mvn test` 时要按 K-2 读总数与 `Skipped`，不是失败数。

各决策的具体影响：

**D1 —— 为什么新开一个客户端而不是给既有的加参数。** `SpikeLoadClient` 与 `GrabRampLoadClient` 产生的数字（S1 的 2240 req/s、S2 的 7735 qps、S3 的 2000→10000 阶梯）是**跨阶段对照的锚点**，历史报告逐字引用了它们。给它们加可选 header 意味着每次请求的构造路径变了（多几个 `if`、多几个 header），于是「这次 7434 与上次 7434 是不是同一个东西」变成一个需要论证的问题。新客户端把风险流量**全部**收在一处：它天然要发测试头、要按 scenario 决定用户/设备/IP 的组合，这些语义本来就不属于「稳态抢单」那个客户端。

代价是重复了一段 HTTP 客户端样板（约 60 行）。这个代价照 `DelayMessageLoadClient` 的先例付——它也没有去改 `SpikeLoadClient`。

**D2 —— 测试头是本阶段唯一的「后门」，必须同时证明它关得上。** 计划 §9.3 的四条测试注入验收里，前两条已经落地（头名独立、`test-context-enabled` 与 profile 相与），第三条「默认配置下测试头被忽略」目前只有 presentation 的单测（`RiskContextInterceptorTest`）。单测证明的是**这一段逻辑**，证明不了**装配起来之后默认配置真的不认它**——而这正是安全边界的形状：`test-context-enabled: false` 写错一个字母（比如写成 `test-context-enable`，历史笔记里就出现过这个笔误）时，单测全绿、线上认头。所以本阶段补一条 `RiskTestHeaderBoundaryIT`（§4.3），它是**唯一**一条为了让测试头能被压测使用而必须新增的安全用例。

**D3 —— `mode=ENFORCE` 是压测环境的必要条件。** 默认 `SHADOW` 下风控照常算、照常记日志，但**一律放行**：攻击流量的响应码全是 OK，于是「命中率」只能从日志里数出来，而「拦住了没有」一个字也证不了。计划 §9.3 的场景表里有「精确拦截率」「零超卖」「误伤率」三个只有真拦截才成立的口径，所以压测环境必须是 `ENFORCE`。

`SHADOW` 不是不做，而是**已经做过了**：`RiskGrabLinkIT` 的 SHADOW 上下文与「不改变业务结果」的断言就是它。本阶段不重复。

**D4 —— 黑名单种子用工具。** `BlacklistKeyTool` 自己的类注释已经论证过：它算出的键必须与应用查询的键逐字节相同，而 HMAC 逻辑复制一份必然漂移，漂移的后果是**黑名单静默失效**（查得到、不报错、永不命中）。手拼 `redis-cli SET risk:blacklist:device:<hash> 1` 时，`<hash>` 是我们自己算的——那条用例验的就变成了「我们能不能算对 HMAC」，而不是「应用会不会拦住黑名单用户」。工具的 `add` / `remove` 同时保证了收尾（黑名单键**没有 TTL**，共享测试 Redis 不能留垃圾）。

**D5 —— 重复投递用真 Producer 灌。** P9.4 §8.2 说不做「消费端重投」的自动化，理由是硬造一次重投要么改生产代码加开关、要么手工往 broker 灌消息。这里选后者，因为它**只测 broker 与消费端，不碰生产代码**——而 P9.4 那句话反对的是「为了测试污染设计」，不是「不许灌消息」。

要说清它与「重投」的区别：**重投**是 broker 因消费失败重发同一条消息，P9.5 不测它（要诱发消费失败得先让处理逻辑抛，而按 P9.4 的 D10 格式非法不重投，剩下的失败路径都要改代码）。P9.5 测的是**重复投递的后果口径**：同一条消息出现两次时，① 消费端写两行日志、零次业务写入；② 离线脚本去重后每个 `requestId + operationType` 只计一次。这两个判据都能被证，且与 P9.4 §6.2 的 D12 是同一条口径的两端。

**D6 —— 停 broker 与冻 Redis 是两种不同的故障。** `docker stop dash-rmqbroker` 验的是「发送失败不影响抢单」（蓝图 §3.8 / P9.4 D8、D9 的落点）；`docker pause dash-redis` 验的是「Redis 那一跳失败时降级原因被如实记下来」。后者要说清一件容易误解的事：

> **冻住 Redis 时抢单自身也会受影响**——风控与抢单共用同一个 Redis 实例（P9.3 §1 明文写了这一条）。所以这个场景的判据是 `degradeReasons` 里出现了哪几个原因、恢复后是否自动恢复，**不是**「抢单不受影响」。把「抢单不受影响」写进这个场景的判据，等于顺手推翻 P9.3 早就定下的边界。

`docker pause` 比 `docker stop curl` 更好用：`unpause` 之后连接与数据原样还在，不需要重新种子化；而 `DEBUG SLEEP` 需要算准「睡多久 > 客户端超时 2000ms」且期间整个实例不可用、时间一到自动恢复（可作为备选，写在这里是为了让执行的人知道还有第二条路）。

**D7 —— 不新开故障开关。** 三类杠杆都是**已交付行为的一部分**：`deadline-ms=0` 是 P9.3 D11 明文承认的合法值（语义就是「强制走降级」），键类型错误是 P9.3 §8.2 用过的手法（把 `RiskKeys.deviceCluster(hash)` 建成字符串即可），容器停/冻是环境动作。任何第四类都要动生产代码，而本阶段的硬约束是 §1 的第一句。

**D8 —— 重启用例的判据在 P9.4 之后才存在。** P9.4 §8.4 把「Worker 重启后继续处理」留给手工实测，理由是「现有证据链分不出这两种情况」——重启**前**发的事件与重启**后**发的事件在日志里长得一样。**那条理由现在不成立**：消费行上有 `lagMs`（消费时刻 − 事件时刻）与 `deliveryAttempt`，而 `lagMs` 恰好就是缺的那一段。于是判据可以写成：

```text
消费行.lagMs  ≥  第二个子进程的启动时刻 − 事件发生时刻
```

即在「停」与「起」之间，消息一直躺在 broker 上——这个不等式在「事件是重启后才发的」世界里不可能成立（那样 `lagMs` 只有毫秒级，而停止窗口是秒级）。这是对 P9.4 §8.4 那句话的**设计内修正**，不是推翻它的结论：它当时说「做不了」，现在有字段了，所以做得了。修正记在 §8.4 的对照表里。

停用 `kill -9` 是 D-6 的直接后果：`dash-worker` 收到 SIGTERM 后不退出（关停钩子卡在 RocketMQ `PushConsumer.close()` 的 `awaitTerminated`，六个消费者同一个形态），所以「优雅停」这件事**当前不可达**。用例里要写明这一点，并且**验收目标是「重启后能继续消费」，不是「优雅停」**——后者属于 D-6，等排期。

**D9 —— 聚合对照必须用攻击流量。** 聚合闸门的触发判据是「同用户 10 秒内第二条同类事件」，而**普通 PASS 不发事件**（P9.4 D2 的 `producesEvent()`）。正常用户的混合流量在 ENFORCE + 生产阈值下几乎不产生 `LIMIT`/`REVIEW`/`BLOCK`，也就是**几乎没有事件可供聚合**——在那种负载上做对照实验，抑制率会是一个由噪声决定的数字。计划 §9.4 写的是「同一攻击流量」，正是这个意思。

**D10 —— 解析器抽出来。** 同步侧的 `risk_feature` / `risk_decision` 行与 P9.4 的四个事件行是**同一套 `key=value` 格式**（`LogField.safe` 保证值里没有空格）。第二个脚本复制一份解析器，就等于把「值里没有空格」这条前提在两个地方各写一遍——而它一旦被破坏（D13 的空白中性化是唯一挡住它的东西），**两个脚本的失效方式还不一样**。抽成 `risklog.py`，两个脚本都 import，`--selftest` 各自保留。

它同时是 `LogField.safe` 这条通路的第二次落地：`risklog.py` 的注释要指回 P9.4 §8.3 那段「只改一边，切分立刻出错」。

**D11 —— `risk_rule_hit_total` 没有对应的日志行。** 已核实：全仓 `risk_rule_hit` 只出现在 `风控反作弊实现蓝图.md` 与 `风控模块实施计划.md` 里，**代码里一条都没有**。它作为指标名仍然成立，但口径必须写清：一次决策可以有**多条**命中规则（`matchedRules` 用 `|` 连接），所以它是「规则命中**次数**」而不是「命中规则的用户数」。读这个数字的人第一件想知道的事就是这个——而一个来源不明的指标名最容易让人按后一种意思去用。

**D12 —— 时长与轮次见 §6.5。** 那一节的量级参照全部引自**已有报告**，没有任何新增实测；预算已按 2026-09-12 的决定定稿，四处删减省下的是现场时间，不是判据。

**D13 —— 报告落点。** 压测报告进 `bench/reports/`（沿用 `report-<日期>-<主题>.md` 的命名与既有 7 份同级）；故障降级报告与指标汇总进 `Docs/风控模块/归档/`（它们是本模块的验收物，与阶段归档放在一起才有上下文）。三份都不改写既有报告。

**与计划 §9 的两处口径偏离**（2026-09-12 定，逐条留痕）：

| # | 计划原文 | 本阶段的处置 | 理由 |
|---|---|---|---|
| 1 | §9.3 场景表「风控路径异常」 | **不单独跑** | 与 §5.3 是同一个注入手段（`deadline-ms=0`），§5.3 已经记录降级比例与零超卖；再跑一轮只会得到同一批日志行 |
| 2 | §9.3 场景表「MQ 延迟或重复」 | **不单独一轮**，并入 §5.5 / §5.6 那次跑 | 停 broker 与灌重复消息本来就要在同一段窗口里做（broker 停着时消息灌不进去），单独一轮不产生新判据 |

两条都不是「不做」：第 2 条的全部指标照常在 §5.5 / §5.6 记录；第 1 条的判据由 §5.3 的故障记录与 §8 的零超卖轮次承接。

## 3. 测试环境与配置基线

### 3.1 环境配置（逐字记进报告）

```yaml
dash:
  risk:
    enabled: true              # 对照 B 里会关掉
    mode: ENFORCE              # D3：压测环境必须真拦截
    fail-open: true            # 攻击场景用默认值；故障场景 §5 单独覆盖
    deadline-ms: 10            # 同上
    test-context-enabled: true # 仅压测环境；D2 的边界用例证明默认 false 时不认头
    event-aggregation-enabled: true  # 对照 A 的自变量
    instance-id: bench-app     # 写死，便于算降级闸门键
    rule-version: "1"          # 阈值不改，所以不升版；改了阈值必须同步升
```

`rule-version` 保持 `"1"` 的理由要写在报告里：本阶段**一个阈值都不改**（5/30/3/8/10/100 与四个时间窗全是生产默认值）。指标跨 run 可比的前提是规则一致，而这条前提由「没动过配置」保证。

### 3.2 三个中间件与清理节奏

- MySQL `127.0.0.1:3307`、Redis `127.0.0.1:6380`、RocketMQ gRPC proxy `127.0.0.1:8081`（nameserver 9876 不探，理由见 P9.4 §8.2）。
- **Redis 是压测里最先坏的一环**：`maxmemory=512MB` + `noeviction`，而每个请求都会写一个 `errand:idem:*`。历史报告里已经踩过一次——反复几轮之后 Redis 开始回 `OOM command not allowed`，那一轮被标成 `FAIL` 并作废。所以**每个 run 之间必须跑 `bench/scripts/cleanup.sh`**（它按 `run_id` 精确清理，这也是 `BenchRunRecorder` 存在的理由）。清理不是可选项。
- 压测前后各记一次 `INFO memory` 的 `used_memory_human`，写进报告——这样「某轮数字异常」才有一个可归因的现场，而不是只能重跑。

### 3.3 隔离库仍然隔离

worker 子进程（`RiskEventIT` / `WorkerRestartIT`）的数据源钉在 `campus_dash_worker_it`，该库不自动创建，缺失时整类跳过（P9.4 §8.2、F-30）。本阶段不改这条，也不新增任何写共享 IT 表的路径。

**Redis 隔离不了**（6380 只有一份），所以用测试头与固定前缀的用户 ID 把压测流量与 IT 流量分开：压测用户 ID 全部落在 `2_000_000+`（这正是 `GrabRampLoadClient` 的 `runnerSeq` 起点），黑名单键用完即 `remove`，事件闸门键带用户前缀且有 TTL。

## 4. 功能回归（计划 §9.1）

计划 §9.1 的十条场景**绝大部分已经有承载它的用例**——P9.1–P9.4 四个阶段各自交付了 IT，本阶段不重写它们。这一节的产出是一张**对照表**：每条场景 → 承载用例（类名 + 用例名）→ 本次执行结果。缺的才补。

### 4.1 对照表（场景 → 承载）

| 计划 §9.1 场景 | 承载用例 |
|---|---|
| 正常用户抢单 | `RiskGrabLinkIT`（不越线的请求）+ 既有 `GrabConcurrencyIT` |
| 用户高频抢单 | `RiskGrabLinkIT.ENFORCE` 的 `shortThreshold + 1` 次连抢 |
| 同设备多账号 | `RiskGrabLinkIT.SHADOW` 的 `lowThreshold + 1` 个账号 + `RiskFeatureIT` 的设备维度 |
| 同 IP 多账号 | `RiskFeatureIT` 的 IP 账号维度 |
| 用户/设备/IP 黑名单 | `RiskPreCheckIT`/`RiskGrabLinkIT` 的黑名单用例 |
| 多规则同时命中 | `RiskPreCheckIT` 的多规则用例 + `RiskRulesTest` |
| `PASS/LIMIT/REVIEW/BLOCK` | `RiskPreCheckIT` + `RiskDecisionTest` |
| `SHADOW/ENFORCE` | `RiskGrabLinkIT` 的两个 `@Nested` 上下文 |
| 风控关闭 | `RiskGrabLinkIT`/`RiskConfigTest` 的 `enabled=false` |
| 风控拒绝后的后续调用为 0 | `RiskGrabLinkIT` 的幂等键断言 + `GrabErrandUseCaseTest` 的三个计数器断言 |

这张表要**逐行填执行结果**，不是列出来就算完成——「有承载用例」与「它这次通过了」是两件事。

### 4.2 回归怎么跑

分两层，两层都要留执行记录：

1. **全量 `mvn test`**：一次跑完，读总数 / `Skipped` / 失败数（K-2）。这一层是「原有测试全部通过」这条验收的判据。
2. **手工端到端抽查（两条）**：用**真实 HTTP** 走**多规则命中**与**风控关闭**两条，对着日志行逐字确认字段。这一层存在的理由是：IT 走的是测试 yaml 与测试头，而**报告要回答的是「真实流量下会怎样」**——`RiskGrabLinkIT` 的降级用例之所以必须用 `RANDOM_PORT` 走真 HTTP，就是这个道理（P9.3 §8.2）。

   **为什么只留这两条**（初稿是六条：黑名单三类各一次、高频越线、多规则命中、风控关闭）：黑名单三类由 §6.3 场景 5 的真 HTTP 流量覆盖（那里还多一个零误伤的对照组），高频越线由场景 2 覆盖，这四条的现场记录与压测报告里的数字是同一批东西。剩下的两条是**压测场景里没有对应物**的，所以留在这一层。

### 4.3 新增：测试头安全边界用例

**`RiskTestHeaderBoundaryIT`**（`dash-bootstrap`，`com.campusdash.it`）——计划 §9.3 第四条测试注入验收的自动化落点（D2）。

| 上下文 | 配置开关 | `test` profile | 预期 |
|---|---|---|---|
| 一、`DefaultOff` | `false`（yaml 默认） | 不激活 | 测试头被忽略 |
| 二、`SwitchOnWithoutTestProfile` | `true` | 不激活 | 测试头被忽略 |
| 三、`SwitchOnWithTestProfile` | `true` | `@ActiveProfiles("test")` | **测试头生效** |

**为什么是三个而不是两个**：闸门是「配置开关 **与** `test` profile 同时成立」（`RiskContextInterceptor:47`），所以「开关打开」单独一个上下文说明不了什么。更要紧的是**本仓库的 IT 里 `test` profile 从来不激活**——没有任何一处设置 `spring.profiles.active`，没有 `application-test.yaml`，测试 yaml 里也没有 `on-profile` 块，本类是**全仓第一个**用 `@ActiveProfiles` 的测试。于是上下文二同时是「profile 这一半在挡着」的证据，而反证（两半都成立时头真的生效）要上下文三。上下文二不能省：它是本地调试与压测环境里的**真实形态**，也是最容易被改成「只判开关」的那一处。

**判据落在 Redis 键上，不在 `risk_feature` 行上**（初稿写的是两条都断）：`risk_feature` 这一行整个没有生产者，见 `实现期发现.md` F-33 与 `预存缺陷与坑.md` D-7，本轮不改生产代码。留下来的 Redis 键判据本来就是更强的那一半——初稿并列两条的理由正是「没有第二条，`deviceAccounts=1` 可能是因为压根没采集」，而「键集合里有没有」直接就是那个「有没有采集」。四个键的分工：设备键与测试 IP 的两个键都是**本类专用**的（`TEST_DEVICE` / `TEST_IP` 只在那一个文件里出现），用户窗口键是**反证**（本次抢单真的走过采集，否则「没有键」可能只是整条链路没跑而绿），真实 IP `127.0.0.1` 的键**不作判据**（它与别的 IT 共用，断言它等于断言「Redis 干净不干净」）。

第三条是这条用例能不能被相信的关键：只在默认配置与「开关开着但 profile 没开」下断言「头被忽略」，在「测试头功能整个没实现」的世界里同样全绿。

`mode` 保持测试 yaml 的 `SHADOW`、并把 `deadline-ms` 覆盖成 1000ms：前者是因为本类断的是「采不采」、与拦不拦无关，`ENFORCE` 会把本机 `127.0.0.1` 上所有 IT 共用的 IP 速率窗口拉进判据；后者照 `RiskGrabLinkIT.Shadow` 的先例，默认 10ms 下新上下文的第一个请求光连接池冷启动就要 15ms，采集整段会被跳过。

这条用例**不登记 `BenchRun`**（不跑并发、不校验超卖），与 `RiskPreCheckIT`/`RiskFeatureIT` 同类。

## 5. 故障测试（计划 §9.2）

计划 §9.2 要求「每种故障记录请求结果、降级动作、抢单正确性、恢复结果和是否产生重复处理」——五个字段，逐条填。下表是六种故障的**注入手法与判据**（D6、D7）。

### 5.1 注入手段总表

| # | 故障 | 注入方式 | 类型 |
|---|---|---|---|
| 1 | 风控 Lua 异常 | 把 `RiskKeys.deviceCluster(hash)` 手工建成**字符串** → `SADD` 报 `WRONGTYPE` | 手工（`redis-cli`） |
| 2 | 风控查询超时 | `deadline-ms=0`（合法值，语义「一步都不许跑」） | 纯配置 |
| 3 | 黑名单精确查询失败 | `docker pause dash-redis` | 容器动作 |
| 4 | 风控事件发送失败 | `docker stop dash-rmqbroker` | 容器动作 |
| 5 | 风险事件重复投递 | `RiskEventDuplicateTool` 用真 Producer 灌同一条 body 两次 | 新工具 |
| 6 | Worker 停止后恢复 | `WorkerRestartIT`：`kill -9` 停 → 发事件 → 起 → 断言 | 半自动 IT（D8） |

`docker pause` / `docker stop` 两种动作都在**应用启动之后**执行，且执行前先确认容器名（`dash-redis` / `dash-rmqbroker`）。

### 5.2 风控 Lua 异常（键类型错误）

沿用 P9.3 §8.2 的手法：把设备聚集键建成字符串。期待 `degradeReasons=CLUSTER_FAILED`、**抢单照常成功**（这条注入不动共享 Redis 的其它键，所以「抢单不受影响」在这里是成立的判据，与 §5.4 不同）。收尾 `DEL` 该键。

### 5.3 风控查询超时（预算耗尽）

app 以 `deadline-ms=0` **重启**（不是热改——这是启动期配置）。两个方向都要跑：

- `fail-open=true` → `degraded=true` + `degradeReasons=DEADLINE_EXCEEDED` + 抢单成功；
- `fail-open=false` → 每次请求 `RISK_UNAVAILABLE`，且**不产生任何 `risk:win:*` 键**（P9.3 §8.2 的判据，这条是「降级真的发生了」的反证）。

### 5.4 黑名单精确查询失败（Redis 冻结）

`docker pause dash-redis` 保持**长于** `spring.data.redis.timeout`（2000ms），期间发若干请求，然后 `unpause`。要记录的是：

- `degradeReasons` 里出现了哪几个原因——**期待不止一个**：黑名单、用户窗口、聚集、限频读都会各自失败。这几个原因是每一个维度各写一条的，被一起记下来才说明「降级是按维度记的，不是一个总开关」；
- 恢复后**下一个请求**是否正常（`degraded=false`）——`unpause` 不需要重新连池；
- `docker pause` 期间抢单自身也失败或变慢，这一条**如实记录**，不算失败（§1 的边界与 D6）。

### 5.5 风控事件发送失败（broker 停）

`docker stop dash-rmqbroker` 之后继续打攻击流量（产生事件的那类），期待：

- `risk_event_publish_failed` 行出现（生产侧的失败留痕），或 `result=DROPPED`（队列满的留痕）——两者是不同原因，报告里要分开数；
- **抢单的成功率与 P99 不变**（与 broker 在时的同 profile 数字对照）——这是「MQ 发送失败不影响同步抢单」的端到端证据；
- `docker start dash-rmqbroker` 之后，事件重新开始发送、消费行重新出现。

注意这一场景期间**不要跑任何 IT**：`MiddlewareAvailable.mqReachable()` 探不到 8081 时整类跳过（K-2 的读法在这个场景里格外重要）。

**本场景同时承载计划 §9.3「MQ 延迟或重复」的压测部分**（§2 的偏离表第 2 条）：停 broker 期间照常打攻击流量，`lagMs`、发送失败数、抢单成功率都在同一段窗口里记录，不单独跑一轮。§5.6 紧接在这段之后——broker 停着时消息灌不进去，灌消息必须在 `docker start` 之后立刻做。

### 5.6 风险事件重复投递

**`RiskEventDuplicateTool`**（`dash-bench`，新增）：用真 producer 把一条**逐字节相同**的 body（同 `eventId` / `requestId` / `operationType` / `occurredAt`）向 `errand-risk-event` 发两次。工具的 payload 由参数拼出（`--event-id --request-id --operation-type --errand-id --runner-id --action`），默认值是一组自洽的样例，且**发完即打印它发了什么**——报告要能逐字复现。

实现期的四处定稿（都不改上面那句判据）：

- **参数加一个 `--endpoint`**（默认 `127.0.0.1:8081`），理由与 `BlacklistKeyTool` 的「端点必须可覆盖」同一条：只能连本机的工具在生产上没用。`--名字 值` 与 `--名字=值` 两种写法都收；**不认识的参数一律报错**，绝不用默认值继续跑——敲错一个字母会送出一条默认的 `LIMIT` 事件而报告里写着「灌了一条 `BLOCK`」，消息真的发出去了、消费行真的出现了，判据全绿。
- **payload 不手拼**：走 `RocketMqRiskEventAdapter.payloadOf`。手拼一份「看起来一样」的载荷，等生产端加字段或改转义之后仍旧送旧形态，而消费端与离线脚本都按名字取值——那样验的是另一条链路（F-26 那条规矩）。顺带白得生产端的 `requestId` 转义（D13）。
- **两次 send 共用同一个 `byte[]`**、各自同步 `send`、不加 tag：前者是「逐字节相同」唯一不依赖实现细节的写法（重新拼一次的话，`occurredAt` 这种取当前时间的字段会让两次 body 不同而**所有判据仍然全绿**）；同步是为了失败当场变成退出码；不加 tag 是因为生产端也不加。
- **纯逻辑有单测**（`RiskEventDuplicateToolTest`，16 个），网络部分不测（§8 的尺度）。盯得最紧的三处：参数写错必须报错、载荷必须来自生产端序列化器、两次取载荷逐字节相同。

判据两条：

1. worker 子进程日志里出现**两行** `risk_event_processed`，`eventId` 相同、`deliveryAttempt` 都是 1（不是重投，是两条独立投递）；
2. 离线脚本按 `requestId + operationType` 去重后 `risk_event_duplicate_total = 1`，且**业务表零写入**（`local_message` / `credit_*` 计数不变——消费端不落状态的判据）。

第 2 条的「业务表零写入」与 P9.4 §8.1 的单测是同一性质的两端：单测证明「同一 body 喂两次 → 两行日志、零次存储调用」，这里证明它在真 broker + 真 worker 下同样成立。

**这一段与 §5.5 是同一次现场**（§2 的偏离表第 2 条）：`docker start dash-rmqbroker` 之后立刻灌两条重复消息，于是「broker 刚恢复」与「重复投递」共用同一批日志与同一段窗口——单独跑一轮灌消息不会多出任何判据。

### 5.7 Worker 停止后恢复（半自动 IT）

**`WorkerRestartIT`**（`dash-bootstrap`）——D8 的落点，本阶段唯一新增的中间件 IT。

```text
① 起 worker 子进程（WorkerSubprocess，隔离库 + 守卫照 RiskEventIT）
② 停：kill -9（D-6：SIGTERM 后不退出，优雅停当前不可达）
③ 发事件：走真 HTTP 让某用户越线触发一条 LIMIT 事件（app 侧 publish 行拿到 eventId）
④ 起第二个 worker 子进程，记下它的启动时刻 T2
⑤ 断言：消费行 eventId 相同 ∧ 消费行 lagMs ≥ (T2 − 事件时刻)
   （初稿还写了 deliveryAttempt = 1，实测是 2，已删——见下面「实现期补上」的第 2 条）
```

判据的三种写法各有什么区别，写在这里免得被简化掉：

- 「消费行出现了」——**不够**。事件也可能是重启后才发的，那种情况下这条同样绿。
- 「`lagMs` 很大」——不够。`lagMs` 大也可能因为消费慢，而不因为停止窗口。
- 「`lagMs` ≥ T2 − 事件时刻」——**够**。它要求事件时刻早于第二个进程的启动时刻，也就是「消息在停止窗口里一直躺在 broker 上」。这是这条用例唯一能被证伪的地方。

`occurredAt` 由 app 写在载荷里，`lagMs` 由消费端算（P9.4 D14），两者相加即消费时刻——不需要新的日志字段。

**停用 `kill -9` 是必须写进用例注释的**：它不是因为用例懒得优雅停，而是 D-6 让优雅停当前不可达。用例的验收目标是「重启后能继续消费」，不是「优雅停」。等 D-6 修掉之后，把这一行换成 `kill -TERM` 即可升级（这条升级路径记在 D-6 的条目里）。

**守卫与前置沿用 `RiskEventIT`**：隔离库存在、worker 的 jar 是新的、broker 端口可探，三条缺一即整类**跳过**（不是失败）。本用例比 `RiskEventIT` 多一次「停」与一次「起」，所以 `READY_TIMEOUT` 要按两次启动各算一次。（隔离库与子进程守卫已搬到 `WorkerSubprocess.requireIsolatedDbAndWorker`，两个 IT 共用一份——不是这 20 行代码本身，而是那段跳过提示里的两条 docker 命令，两份一旦不一致，下一个人会照着一份错的命令去建库。）

实现期补上的七处：

- **停机窗口 3 秒是判据的一部分，不是等待**：没有它 `t重启 ≈ t事件`，那个不等式的下界就成了 0 毫秒，「`lagMs` ≥ 下界」变成一句恒真的话——用例照样绿而什么也没证明。
- **下界取「调用重启的时刻」而不是「新进程就绪的时刻」**：后者才是事件真正能被消费的最早时刻，但它在用例里拿不到（`ensureStarted()` 内部等就绪，40 毫秒级的 `lagMs` 与十几秒的冷启动之间差得太多）。取前者是**保守**的：下界偏小，所以判据偏弱而不是偏强——它只会漏报，不会误报。
- **「这一行是新进程写的」靠日志截断证明**：`WorkerSubprocess.start()` 每次都把日志文件截断（原本是为了让「本轮收到几条」算得对），于是重启后从文件里读到的消费行**只可能**来自第二个进程，不必再比时间戳或 PID。
- **先打一条预热事件**（初稿没有这一步）：一是给出起点（重启前这个 worker 到底消费过没有），二是**坐实消费组的位点**——本用例发布事件时消费组没有在线成员，而「一个从未提交过位点的消费组重新上线时从最早还是最新开始」本阶段没有独立验证（记进交付物的限制）。`RiskEventIT` 发布时 worker 已在线，碰不到这一条。
- **三个时刻分别来自 app（`occurredAt`）、worker（消费时刻）、测试侧（发布/重启时刻）**：同一台机器上它们是同一个时钟，这条不等式才成立——§1 的同机前提在这里也要说一句。`lagMs` 与下界都是用「测试侧记的时刻」相减的（事件时刻取投递行出现之后的那一刻，比真实 `occurredAt` 略晚），这一点让下界只会更小，方向同上。
- **等待时长按 150 秒，`deliveryAttempt` 只打印不断言**（F-34）：实测「停机期间发布的事件」要 **67.9 秒**才被新进程消费，`deliveryAttempt=2`——消息先被投给那个已死的成员，要等 broker 侧一个 60 秒量级的期限过去才回到新成员手上。于是 ① §5.7 ⑤ 里 `deliveryAttempt = 1` 那条判据是错的（断言 1 会**永远红**，断言 2 是把一次实测读数当不变式）；② 60 秒等待正好卡在那个期限上，第一次失败与成功只差 0.9 秒。顺带得到一条要进交付物限制的运维事实：**重启 worker 之后的一分钟量级内，停机期间产生的事件可能还没有消费行**——这是 D-6 的运行后果，不只是代码缺陷。
- **`properties` 里必须覆盖 `dash.risk.deadline-ms=1000`**（F-35）：本类走真 HTTP，yaml 的 10ms 会被第一个请求的连接池冷启动吃光，而那一次请求**不计进用户窗口**（`RiskPreCheckUseCase` 的检查点跳过第 3 步）——少一次计数，连抢 `shortThreshold+1` 次恰好只到阈值，事件压根不产生，失败信息却是 `ALREADY_GRABBED`（与风控无关）。`RiskEventIT.ProcessToProcess` 不覆盖也能过，是因为它直接调用例（微秒级）；**走真 HTTP 的越线用例一律要覆盖**。

## 6. 攻击流量压测（计划 §9.3）

### 6.1 `RiskTrafficClient`（新增，`dash-bench`）

```text
java -cp ... com.campusdash.bench.RiskTrafficClient \
     <scenario> [baseUrl] [concurrency] [durationSeconds] [taskPool] [seed]
```

| 参数 | 含义 |
|---|---|
| `scenario` | `normal` / `hot-user` / `same-device` / `same-ip` / `blacklist`，见 §6.3 |
| `concurrency` | 虚拟线程数 |
| `durationSeconds` | 正式测量时长（不含预热） |
| `taskPool` | 先发布的任务数（沿用 `GrabRampLoadClient` 的做法，避免全打到售罄任务上） |
| `seed` | 用户/设备/IP 的编号起点，让不同 run 的键互不重叠、也让对照实验能复现同一群体 |

它复用 `BenchRunRecorder`（`startRun` / `trackErrands` / `finishRun`）与 `bench/scripts/verify_run.sql`，登记的场景名是 `S5-RISK-<scenario>`（`bench_run` 表按 run 归类，历史报告与清理脚本都按这个走）。输出沿用既有客户端的形状：请求数 / 分类计数 / 错误分类 / QPS / P50/95/99/Max，**外加一行 JSON summary** 写进 `bench_run`。

**测试头只在需要它的 scenario 里发**：`normal` 与 `hot-user` 不带任何测试头（它们要反映真实前端流量），`same-device` / `same-ip` 带对应的那一个，`blacklist` 带被拉黑的那一个维度。`RiskTrafficClient` 的注释要写明这句话：**带上测试头意味着「这个请求不是真实前端能发出的」**，所以只在那几个场景里用。

### 6.2 压测环境的启动与收尾

```text
① docker compose up -d（三个容器）→ docker/init-mq.sh（topic 与消费组）
② 起 app：测试 profile + DASH_RISK_DEVICE_HMAC_SECRET=<bench-secret> + §3.1 的配置
③ 记 INFO memory：used_memory_human
④ 逐场景跑；每个 run 之间跑 bench/scripts/cleanup.sh
⑤ 两组 A/B（聚合、风控开关）各跑一对
⑥ 记 INFO memory + 收 app 日志（报告的原始材料）
⑦ 汇总：analyze_risk_events.py + analyze_risk_decisions.py + verify_run.sql
```

**app 日志是全部分析的原始来源**，所以第 ⑥ 步要把日志**整段落盘到 `bench/tmp/`**（历史报告的 `bench/tmp/grab-correctness/` 就是这个先例），报告里的每个数字都要能从那批文件里重新算出来。

### 6.3 压测场景（六个）

计划 §9.3 列了八个，其中两个按 §2 的偏离表处置：**「风控路径异常」不单独跑**（判据在 §5.3），**「MQ 延迟或重复」并入 §5.5 / §5.6**。下表是实际单跑的场景。

| # | 场景 | profile | 注入 / 前提 | 重点指标 |
|---|---|---|---|---|
| 1 | 正常用户混合流量 | `normal`：大范围互不重复的 userId，按 `uniform` 轮转任务 | — | 误伤率（§6.4 的配对）、抢单 P50/95/99、`decisionLatencyMs` P50/95/99 |
| 2 | 单用户脚本抢单 | `hot-user`：少量 userId 高并发猛打 | — | 窗口命中率（`LIMIT` 数 / 该用户请求数）、`risk:limit:user:{id}` 的写入与冷却生效、聚合抑制率 |
| 3 | 多账号同设备 | `same-device`：N 个 userId 共用一个设备号 | `X-Test-Device-Id` | 设备规则命中率（`deviceAccounts` 越过 `3` → REVIEW、越过 `8` → BLOCK）、命中与阈值的对应关系 |
| 4 | 多账号同 IP | `same-ip`：N 个 userId 共用一个 IP | `X-Test-Client-Ip` | IP 账号维度命中（**账号数要 ≥ 11 才越线**，阈值 10 且 cap 由阈值推导）、IP 速率维度（60 秒 100 次 → LIMIT） |
| 5 | 黑名单用户 | `blacklist`：用户/设备/IP 各一枚已拉黑的标识 + 同数量的干净标识作对照 | `BlacklistKeyTool add`（D4） | 精确拦截率（目标 `100%`）、**对照组的误伤为 0**、拒绝后零后续调用 |
| 6 | 聚合关闭/开启对照 | `hot-user`（D9） | `event-aggregation-enabled` 两个取值 | 尝试发送数、实际 SENT 数、抑制率、`lagMs` P50/95/99、最大堆积与恢复时间、覆盖率、抢单延迟与错误率 |

**计划 §9.3 里另外两个场景不在这张表里**（§2 的偏离表）：**「风控路径异常」不单独跑**——它与 §5.3 是同一个注入手段，判据在 §5.3 与 §8 的零超卖轮次里；**「MQ 延迟或重复」并入 §5.5 / §5.6** 那次跑——停 broker 与灌重复消息在同一段窗口里做，指标照常记录，只是不单独占一轮。

第 5 个场景的对照组是必须的：「拦截率 100%」在「所有请求都被拒绝」的世界里同样成立。对照组用**同数量的干净标识**跑同一 profile，断言全部正常放行。

### 6.4 两组对照实验

| 对照 | 自变量 | 固定量 | 负载 | 产出 |
|---|---|---|---|---|
| **A：聚合开关** | `event-aggregation-enabled` = `false` / `true` | 同一 profile、同一 seed、同一时长与并发、`rule-version` 不变 | `hot-user` | 抑制率、覆盖率、发送量、`lagMs`、堆积与恢复 |
| **B：风控开关**（误伤率） | `dash.risk.enabled` = `false` / `true` | 同上 | `normal` | 误伤率（定义见 §7.3） |

A 组的判据里有一条**必须单列**：**聚合不得改变同步风险决策结果**（蓝图 §3.9 的硬约束）。所以 A 组除了比 MQ 指标，还要比两次 run 的 `risk_decision` 行：`action` / `riskScore` / `matchedRules` 的**分布**应当一致（同一 seed 下不该有系统性差异）。只比发送量的话，一个「顺手把决策也改错了」的实现同样能让抑制率好看。

B 组是误伤率唯一的口径来源：分子分母都要求同一条流量跑两次，**关掉风控那次就是「本可成功」的基准**。所以 B 组不能省成一次 run 加推导。

## 7. 指标与离线脚本（计划 §9.4）

### 7.1 两份脚本

| 脚本 | 读什么 | 产出 |
|---|---|---|
| `bench/scripts/analyze_risk_events.py`（P9.4 已交付） | 四个事件行 | 事件侧指标 + 覆盖率 + `lagMs` 分位 + 去重（**不改输出口径**） |
| `bench/scripts/analyze_risk_decisions.py`（新增，D10） | `risk_decision` 行（初稿写的是「`risk_feature` / `risk_decision` 行」） | 同步侧指标：决策总数、动作分布、规则命中次数、降级原因分布、`decisionLatencyMs` 分位 |
| `bench/scripts/risklog.py`（新增，D10） | — | 共用的 `key=value` 解析器 + 非插值 `pct()`（算法**逐字**照 `analyze_s5_trace.py`，保持与历史报告一致） |

两个脚本都要带 `--selftest`（照 P9.4 的先例）：喂合成日志文本、断言计数与分位符合预期、退出码非 0 即失败。抽走解析器之后，`analyze_risk_events.py --selftest` 必须**继续通过**——这是 D10 那个改动唯一的验收。

**上面那一格为什么改了口径**：`risk_feature` 行没有生产者（F-33 / D-7），同步侧脚本因此只读 `risk_decision`。§7.2 的九个指标一个都没有落在那一行上，所以这次口径改动不影响任何一张表——但它必须写在这里，否则脚本读的文件列表与设计对不上，下一个人会以为漏读了一个文件。

### 7.2 指标来源对照（计划 §9.4 的九个名字 → 真实来源）

| 计划里的指标名 | 真实来源 | 备注 |
|---|---|---|
| `risk_decision_total` | `risk_decision` 行数 | 按 `requestId` 去重后计数 |
| `risk_decision_latency_ms` | `risk_decision` 行的 `decisionLatencyMs` | **风控自身的 P50/95/99 就是它**，不是接口延迟 |
| `risk_action_total` | `risk_decision` 行按 `action` 分组计数 | 即 `PASS/LIMIT/REVIEW/BLOCK` 分布 |
| `risk_rule_hit_total` | `risk_decision` 的 `matchedRules` 按 `\|` 拆开后计数 | **没有独立日志行**（D11） |
| `risk_event_publish_total` | `risk_event_publish` 行按 `result` 分组 | `SENT` / `SUPPRESSED` / `SENT_GATE_FAILED` / `DROPPED` |
| `risk_event_consume_lag_ms` | `risk_event_processed` 的 `lagMs` | 消费延迟分位 |
| `risk_event_duplicate_total` | `risk_event_processed` 按 `requestId + operationType` 去重后的差 | 去重只在离线做（P9.4 D12） |
| `risk_event_suppressed_total` | `result=SUPPRESSED` 计数 | 抑制率的分母见 §7.3 |
| `risk_degraded_total` | `risk_decision` 行 `degraded=true` 计数 | 按 `degradeReasons` 再分组一次 |

**报告必须分别给出的三条延迟**（计划 §9.4 的要求）：风控自身（`decisionLatencyMs`）、抢单接口整体（压测客户端）、RocketMQ 消费延迟（`lagMs`）。三者口径不同，**不得混在一张分位表里**——混起来的后果是「风控 P99 < 10ms」这条验收看起来轻松通过，而它其实说的是别的东西。

### 7.3 两个比率的定义（逐字照计划 §9.4）

```text
抑制率 = 被聚合抑制的事件数 / 风险事件尝试发送数
误伤率 = 关闭风控时本可成功、开启风控后被拒绝的请求数 / 关闭风控时本可成功的请求数
```

抑制率的分母是**尝试发送数**，不是「决策数」——两者在聚合关闭时相等，开启时不等，报告里要把两个分母都写出来。这一条与 P9.4 §10 的三条限制直接相关：**降级闸门是每实例一个键**，所以单实例压测下抑制率与多实例下的抑制率不是同一个数（P9.4 §10 限制 3 已经预告过）。

### 7.4 `SENT ≠ 已投递`

P9.4 §10 最后一段的规矩在本阶段**每个数字上都适用**：`SENT` 的含义是「已交给 `sendAsync`」，它到没到 broker 由 `risk_event_publish_failed` 的**缺席**间接说明，而缺席不是证明。报告里凡是写「发送成功」的地方，都要能指向 `RiskEventIT`/`WorkerRestartIT` 那条真的收到消息的证据，或者明确写成「已交出」。

2. **「Worker 重启后可以继续处理」是 `kill -9` 下的结论**——D-6 让优雅停当前不可达，所以「优雅停之后数据不丢」这件事本阶段**没有被验证**，它不是「已验证为真」。
3. **降级闸门按实例计数**，抑制率的解释随部署实例数变化（P9.4 §10 限制 3 在本阶段第一次被真正读成数字）。

## 11. 不做什么

- **不做 `SHADOW → ENFORCE` 的灰度演练**：那是运维按配置决定的动作，P9.3 已定。
- **不改任何阈值或时间窗**：改了就破坏了与历史数字的可比性，且必须同步升 `rule-version`；本阶段一个都不动。
- **不做多机/容器编排压测**：同机是全部历史数字的前提（§1）。
- **不做消费端幂等**：P9.4 D12 已定「去重只在离线」，本阶段只是把这条口径跑成数字。
- **不给前端加设备 ID**：计划 §9.4 的限制原文，必须写进最终交付物——本轮前端不发 `X-Device-Id`，真实流量的设备维度结论**全部来自测试注入**，这一条在报告里要写在设备/IP 那两个场景的表头上。
- **不引入 Micrometer/Prometheus**：指标仍走结构化日志 + 离线脚本。
