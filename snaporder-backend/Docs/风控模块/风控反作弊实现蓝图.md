# CampusDash 实时风控/反作弊实现蓝图

> 文档目的：明确本轮风控模块只实现的最小功能闭环、设计机制和验收指标。
>
> 适用项目：`campus-dash-backend`
>
> 修订日期：2026-09-11

## 1. 建设目标

针对校园跑腿中的脚本抢单、批量账号和异常网络行为，在抢单入口增加实时风控能力：

```text
行为特征采集 -> 风险判断 -> 分级处置 -> 异步记录 -> 压测验证
```

| 能力 | 主要职责 |
|---|---|
| Sentinel | 进程内热点参数限流，保护系统容量 |
| 信用分 | 描述用户长期履约信誉 |
| 风控 | 判断当前行为是否异常，并决定当前请求如何处置 |
| Redis Lua + MySQL CAS | 保证抢单名额守恒，是最终正确性防线 |

风控允许降级，但不能替代或绕过现有抢单正确性链路。

## 2. 本轮实现范围

本轮只实现：

1. 请求风险上下文；
2. Redis Lua 用户滑动窗口；
3. 设备多账号检测；
4. IP 聚集检测；
5. Redis 精确黑名单判断；
6. `PASS/LIMIT/REVIEW/BLOCK` 四级风险决策；
7. 抢单入口同步接入；
8. 风控路径超时和 `fail-open` 降级；
9. RocketMQ 风险事件与消费处理日志；
10. 结构化日志、攻击流量压测和最终指标测试。

本轮暂缓：

- Redis BloomFilter；
- “60 秒抢单失败超过 20 次”直接触发规则；
- 前端设备标识和 requestId 改造；
- 动态规则管理；
- 人工审核界面和复杂审核流程；
- 新的风控服务进程、新中间件；
- Prometheus、Grafana 等独立监控基础设施。

## 3. 功能与设计

### 3.1 请求风险上下文

抢单请求形成以下上下文：

```text
userId
errandId
requestId
deviceId（可选）
clientIp
```

要求：

- `requestId` 优先由客户端生成并在重试时复用，缺失时由服务端生成；
- `deviceId` 缺失时跳过设备维度，不拒绝老客户端；
- 设备标识使用配置密钥进行 HMAC/盐化哈希后再写入 Redis；
- 默认使用服务端 `remoteAddr` 获取 IP；
- 只有配置可信代理时，才解析 `X-Forwarded-For` 等转发头；
- 由独立请求上下文组件解析，Controller 只负责传入应用用例。

本轮不修改 `campus-dash-frontend`。因此当前前端请求不提供设备标识和 requestId
时，设备维度会跳过，服务端生成的 requestId 只保证本次请求内部可追踪，不能识别
客户端重试。设备维度和 requestId 去重通过测试客户端、压测客户端或后续接入的客户端验证。

### 3.2 Redis Lua 用户滑动窗口

| 规则 | 示例阈值 | 输出信号 |
|---|---:|---|
| 10 秒内抢单超过 5 次 | `> 5` | `LIMIT` |
| 60 秒内抢单超过 30 次 | `> 30` | `REVIEW` |

本轮不使用“60 秒失败超过 20 次”作为直接处置规则：热门任务下抢单失败本身是正常结果，容易误伤。

使用 Redis ZSet 保存行为时间戳。Lua 原子完成窗口清理、当前请求写入、计数、TTL 设置和同一 `requestId` 短期去重，并返回各窗口计数；不能在 Java 中拆成检查与写入两次 Redis 请求。

阈值比较不在 Lua 内，由领域层依据脚本返回的计数完成。原因是 §3.6 要求多规则风险分累加，需要的是计数而不是布尔值；阈值写死在脚本里既不可配置，也无法被领域单测覆盖。

每个窗口只保留判断阈值所需的最近记录：10 秒窗口最多保留 6 条，60 秒窗口最多保留 31 条，避免脚本刷请求导致 ZSet 无限增长。

### 3.3 设备多账号检测

| 规则 | 示例阈值 | 输出信号 |
|---|---:|---|
| 10 分钟内同一设备关联账号超过 3 个 | `> 3` | `REVIEW` |
| 10 分钟内同一设备关联账号超过 8 个 | `> 8` | `BLOCK` |

使用哈希后的设备标识和 Redis Set，设置 TTL 及最大成员数。设备缺失时不产生设备风险信号，设备信号不能单独作为永久封禁依据。

### 3.4 IP 聚集检测

| 规则 | 示例阈值 | 输出信号 |
|---|---:|---|
| 10 分钟内同一 IP 出现超过 10 个账号 | `> 10` | **仅风险加分**，不单独触发动作 |
| 60 秒内同一 IP 抢单超过 100 次 | `> 100` | `LIMIT` |

**「仅风险加分」的语义（P9.2 定稿）**：这条规则给一个**低于 `LIMIT` 档下界的分值**，于是它只在总分里贡献、单独命中不产生任何动作——把单条规则调过最低档下界，就实现了「仅加分」，不需要在裁决逻辑里为它开特例分支。

为什么它不能独立定性：「同一 IP 出现 > 10 个账号」在**校园网 NAT 出口下是常态**。给它 `REVIEW` 档等于让这些用户被单独拒绝并记审核事件，误伤面远大于它抓住的作弊面。它与另一条规则叠加时仍然有推动力（例如设备多账号 + IP 多账号正是批量账号攻击的画像）。

两类规则使用不同的窗口形态：

- **IP 账号聚集**：Redis Set，成员为 `userId`，上限取「阈值 +1」（封顶 11）——集合只要能表达「已越线」即可，11 和 1100 对决策没有区别，封顶后直接获得硬上界；
- **IP 速率**：Redis ZSet 滑动窗口，与 §3.2 用户窗口形态一致，避免固定窗口的跨边界计数翻倍。

IP 速率窗口的成员是原始请求时间戳，**不按 `requestId` 去重**——这是它与用户窗口唯一不同的语义。用户窗口去重是为了服务于重试幂等；IP 速率若也去重，攻击者只要反复复用同一个 `requestId` 就能把计数压到 1，规则直接失效。

同一 IP 不直接触发 `BLOCK`。IP 统计设置 TTL 和成员上限，默认只信任服务端真实连接地址。

### 3.5 Redis 精确黑名单判断

支持用户、设备、IP 三类黑名单。本轮只使用 Redis 精确键/集合判断，不引入 BloomFilter。

要求：

- 黑名单命中直接产生 `BLOCK`；
- 设备和 IP 使用与采集阶段一致的标准化/哈希方式；
- 读取端只依赖风控端口，不新增管理页面；
- 黑名单失效后不能继续拦截；
- Redis 查询失败按故障降级策略处理；
- 本轮通过初始化脚本、Redis CLI 或测试 fixture 写入黑名单；
- 本轮不提供黑名单管理 API，动态维护后续再做。

**密钥轮换语义（实现期补充）**：黑名单键是 `HMAC(device-hmac-secret, 标识)` 的结果，
标识被哈希后才落库/落 Redis，因此**轮换密钥会让已有黑名单键全部静默失配**——
查询不报错、不抛异常，只是永远不命中。这是最坏的一类失效：拦截能力归零而监控全绿。

所以：

- 轮换密钥与重建黑名单**是同一个操作的两步**，必须成对执行，顺序为「先按新密钥重建、再切密钥」；
- 切换期间新旧键并存会让重建过程本身被漏掉，因此重建必须以「快照 + 一次性重写」完成，
  不能靠「等它自己过期」；
- 本文档不规定轮换周期，也不提供轮换工具。本轮只要求任何执行轮换的人
  明确知道它等于「清空黑名单」，需要留出重建窗口。

### 3.6 四级风险决策

```text
PASS    继续原有抢单链路
LIMIT   拒绝当前请求，并写入用户级 10 秒限频 Key
REVIEW  拒绝当前请求，并记录审核事件
BLOCK   直接拒绝当前请求，并记录强拦截原因
```

| 风险分 | 默认动作 |
|---:|---|
| 0-29 | `PASS` |
| 30-59 | `LIMIT` |
| 60-79 | `REVIEW` |
| 80 以上 | `BLOCK` |

多条规则命中时风险分累加，**最终动作由总分查表得出**。本条与 §3.2–§3.4 规则表里那一列「输出信号」的关系是：**规则表只提示该规则单独命中时落在哪一档，不是第二条裁决路径**。每条规则的分值定义见 `阶段设计/P9.2 黑名单与四级决策.md` §3.2。

**黑名单不写成旁路分支。** 它取一个恰好等于 `BLOCK` 档下界的分值参与累加，动作结果与「直接 `BLOCK`」完全等价，但保持「分数 → 动作」是纯函数——否则会产生 `action=BLOCK, riskScore=0` 的决策，往 §5.5 的分数分布里掺入与分数无关的异常值。

**同一计数上的多档阈值取最高，不同计数累加。** 两者性质不同：设备窗口的 `> 3` 与 `> 8` 作用在同一个计数上（账号数 15 必然同时满足两条），是同一事实的两档强度，累加等于重复计分；而用户 10 秒与 60 秒窗口作用在**两个互不蕴含的计数**上，「10 秒内爆发」与「60 秒内持续」是两种可以独立发生的行为模式，必须累加。

本轮不把信用分重新查询并混入风控计算，信用分仍由原有 L2 资格校验负责。

`LIMIT` 使用以下最小语义：

```text
Key: risk:limit:user:{userId}
TTL: 10 秒
ENFORCE:
  预检开始时读取 Key，存在则直接返回 LIMIT
  新触发 LIMIT 时写入 Key，并拒绝当前请求
SHADOW:
  不读取、不写入 Key，只记录决策
```

`REVIEW` 和 `BLOCK` 本轮不自动写永久黑名单。

内部结果至少保留：

```text
riskScore
action
matchedRules
ruleVersion
degraded
decisionLatencyMs
```

风控动作必须使用独立错误码，不能复用 Sentinel 的 `GRAB_RATE_LIMITED`。

### 3.7 抢单入口同步接入

正确链路：

```text
请求进入 -> 解析风险上下文 -> Sentinel 热点限流 -> 风控预检
    -> 信用分与在途任务校验 -> Redis Lua 抢单 -> MySQL CAS 落库
```

风控结果处理：

```text
BLOCK  -> 立即拒绝
REVIEW -> 拒绝并记录审核事件
LIMIT  -> 拒绝并进入短期限频
PASS   -> 继续原有流程
```

要求：

- 风控调用落在 `GrabErrandUseCase` 内部；
- Sentinel 保持第一层内存限流；
- 风控拒绝后不得调用信用校验、抢单 Redis 和数据库 CAS；
- 风控关闭时恢复接入前行为；
- 不修改现有抢单 Lua、MySQL CAS、资金、信用和任务状态规则。

### 3.8 风控故障降级

风控与抢单共用 Redis 实例，不把“整个 Redis 宕机”视为可独立隔离的风控故障。

本轮验证风控路径的 Lua 报错、查询超时、键类型错误和适配器异常。**「键类型错误」只适用于特征采集**——黑名单查询用 Redis `EXISTS`，它对任何类型都返回 1、不做类型检查，因此不会因键被建成别的类型而失败；`SADD` / `ZADD` 才会对错误类型报错。

| 故障 | 降级方式 | 业务要求 |
|---|---|---|
| 风控 Lua 报错 | 记录原因并按配置放行 | 不绕过原有抢单正确性链路 |
| 风控查询超时 | 达到 deadline 后 `fail-open` | 不等待全局 2000ms |
| 黑名单查询失败 | 记录降级并跳过快速拦截 | 不产生误封 |
| 风控事件发送失败 | 记录失败并结束同步请求 | 不影响抢单结果 |

**「降级」不等于「放行」，这条必须说准。** 上表里的「跳过快速拦截」指的是**只少一个证据**，不是整次决策作废：

- 黑名单查询失败 → 该维度记「未命中」，**特征照采、决策照跑**；
- 某次特征采集失败 → 该维度计数记 0，**黑名单照查、决策照跑**；
- 两类都失败时分数自然为 0 → `PASS`，但降级原因必须记录。

区别在组合里才看得出来：**黑名单挂了但设备维度已经越线时，决策仍然是 `BLOCK`**。写成「任一步失败就整体放行」会漏掉它，且不报错。

降级原因必须是**可区分的枚举**而非一个布尔，否则 §3.9 的「同一实例、同一原因 10 秒最多 1 条」聚合规则无法实现。

风控预检使用一个共享的总 deadline，默认 10ms；底层单次 Redis 操作只能使用剩余时间，不能替代总 deadline。达到 deadline 后立即按配置 `fail-open`，`decisionLatencyMs` 从风控用例入口计时到决策完成或降级结束。

风控 Key 必须设置 TTL、成员上限和内存预算；不因风控修改 Redis `noeviction` 配置。

成员上限还必须保证键保持紧凑编码：**ZSet 成员数不得超过 127**（Redis `zset-max-listpack-entries` 默认值为 128）。超过后编码由 listpack 转为 skiplist，单键内存翻倍以上（实测 7232 B → 17601 B），且不会有任何报错或告警，只会在压测中表现为 Redis 内存异常。

上界是 127 而非 128 的原因：写入路径是「先 `ZADD`、再裁剪」，键在调用瞬间会达到「成员上限 +1」个成员；而 ZSet 的编码**只升不降**，cap 取 128 时瞬时到 129，当场转换且再也回不来。直接往 ZSet 塞恰好 128 个成员确实仍是 listpack，但那不是本项目的写入路径。该约束已在 `RiskProperties` 中落地为启动期校验。

**Set 型键另有一条悬崖，上界不同，不能混用**：设备与 IP 账号聚集用 Set，成员是整数 `userId`，走 intset 而非 listpack，悬崖由 `set-max-intset-entries`（默认 **512**）决定，超过即转 hashtable，同样只升不降。实测 512 个成员 1336 B → 513 个成员 24720 B，**跳涨 18.5 倍**，比 ZSet 那条更陡。Set 没有「先写后裁」的瞬时问题（脚本是 `SCARD < cap` 才 `SADD`），所以上界是干净的 512。该约束同样落在 `RiskProperties` 的启动期校验里。

**Set 型键的 TTL 就是窗口长度本身，因此每个 Set 必须有自己的 TTL 参数。** 这一点容易看漏：集合成员是裸 `userId`，没有分值、没有时间信息，所谓「10 分钟内关联了多少账号」**完全由 TTL 承载**（配合「只在新增成员时才 `EXPIRE`」那条规则）。所以 TTL 不是无关紧要的过期时间，写错它等于写错规则窗口。

对应的实现约束：设备集合与 IP 账号集合**不能共用一个 TTL 实参**。共用的后果有两个，都不会报错——一是 `dash.risk.ip-account-window.seconds` 变成一个读了也不生效的死配置项；二是改设备窗口会顺带改掉 IP 账号窗口，两条规则的窗口被静默耦合。P9.1 实现期正是踩了这一条（见 `实现期发现.md` F-5），现已拆成两个 ARGV，并由 `RiskFeatureIT` 用「把两个窗口配成不同值」的断言守住。

### 3.9 RocketMQ 风险事件与消费处理

抢单用例只为风险相关结果生成风险行为事件：

- `LIMIT/REVIEW/BLOCK`；
- 黑名单命中；
- 风控降级；
- MQ 发送失败或消费重复等异步异常只记录日志和指标，不再次发送风险事件。

普通 `PASS + SLOT_FULL` 请求不发送风险 MQ 事件，只做计数或采样日志，避免热门任务将大量正常失败放大到 MQ。

为避免攻击流量按请求量放大 MQ，风险事件发送前增加时间窗口聚合：

| 事件类型 | 聚合规则 |
|---|---|
| `LIMIT` | 同一用户 10 秒内最多发送 1 条 |
| `REVIEW` | 同一用户 60 秒内最多发送 1 条 |
| `BLOCK` | 同一用户、同一动作 60 秒内最多发送 1 条 |
| 风控降级 | 同一实例、同一原因 10 秒内最多发送 1 条 |

聚合 Key（**P9.4 的落地形态，已去掉时间桶**）：

```text
risk:event:gate:limit:{userId}
risk:event:gate:review:{userId}
risk:event:gate:block:{userId}
risk:event:gate:degraded:{instanceId}
```

窗口**不写在键里，而是这把键的 TTL**（`SET key 1 NX EX 10`）：抢到键才允许发，没抢到只增加
`risk_event_suppressed_total`。本节初稿的键名带一个时间桶段（`{userId}:{10sBucket}`），
P9.4 的决策 D4 把它去掉了——带桶会在**窗口边界**上泄漏（`t=9.9s` 与 `t=10.1s` 落进两个桶、
各自都抢到一次，实际间隔不到 10 秒却发了两条），而「距上次发送满 N 秒才允许下一次」
与上面那张规则表逐字对应。键名的构造与校验在 `RiskKeys`，理由见
`阶段设计/P9.4 异步事件与消费去重口径.md` 的 D4。

只有抢到聚合 Key 的请求才发送 MQ；被抑制的请求只增加
`risk_event_suppressed_total`，不丢失风险动作统计。

事件至少包含：

```text
eventId
requestId
operationType
errandId
runnerId
outcome
decisionAction
occurredAt
```

`operationType` 用于离线去重，必须随事件落日志。

风险事件使用 RocketMQ `sendAsync` 异步发送，不能阻塞抢单主链路。事件同时携带
`requestId` 和 `operationType`，两者共同标识一次业务操作；`eventId` 只是消息唯一标识。

发送失败不进入现有 `local_message` 可靠消息链路；风险事件不参与抢单正确性判断。

消费端处理定义为：

1. 校验事件格式；
2. 写一条 `risk_event_processed` 结构化日志；
3. `REVIEW` 额外写一条 `risk_review_pending` 日志；
4. 处理失败交给 RocketMQ 默认重试，重投递的消息会再次写日志。

消费端**不做运行时幂等，不写任何幂等 Key**。重复投递只产生重复日志，
不产生重复业务状态——因为消费端本来就不写业务状态。

去重职责下沉到离线分析：统计脚本按日志中的 `requestId + operationType` 去重后
再计算指标，`risk_event_duplicate_total` 由该步骤统计得出，并据此观察 MQ 重投递情况。

这样设计的原因：消费端不落表、不动资金、不碰抢单名额，全部产出物是结构化日志，
重复一条日志的代价远低于为此在共享 Redis 上维护一个无上界基数的幂等 Key。
风控与抢单共用同一个 Redis 实例，键被撑满会连带影响抢单 Lua 写入。

本轮不新增审核表、不提供审核查询接口。

### 3.10 Shadow 模式与指标承载

```text
SHADOW   计算并记录风险结果，但不拦截
ENFORCE  按风险动作实际处置
```

本轮使用结构化日志承载指标，不新增 Micrometer、Prometheus 或 Grafana。每次决策至少记录：

```text
requestId userId errandId action riskScore matchedRules
decisionLatencyMs degraded eventId
```

**字段名与顺序是给离线分析脚本的跨系统契约，从 P9.2 起就固定**，事后往中间插字段等于改协议。其中 `eventId` 是 P9.4 异步事件的产物，P9.2 先以占位值写进格式、P9.4 只填值不改字段。

`decisionLatencyMs` 由**调用方**测量（从风控用例入口计时到决策完成或降级结束），不属于决策本身的返回值。

消费端日志至少记录：

```text
requestId operationType outcome eventId
```

其中 `requestId + operationType` 是离线去重的依据，必须同时出现在日志中。

由现有压测记录和离线脚本统计 P50/P95/P99、命中率、误伤率和降级次数。

配置项至少包括：

```yaml
dash:
  risk:
    enabled: true
    mode: SHADOW
    fail-open: true
    deadline-ms: 10
    limit-cooldown-ms: 10000
    rule-version: "1"
    event-aggregation-enabled: true
    test-context-enabled: false
    trusted-proxy-cidrs: ""
    device-hmac-secret: ${DASH_RISK_DEVICE_HMAC_SECRET}
```

`rule-version` 标识「本次决策用的哪套规则」，会随决策日志落盘供离线分析区分口径。
它**必须是配置项而不是代码常量**：阈值是配置的一部分，同一份代码配两套阈值就是两套规则，
所以只有运维知道何时该升这个值——**改任何风控阈值时必须同步升它**，否则两套规则下的指标会混在一起。

`device-hmac-secret` 不提供默认值，不能写入代码库。日志字段使用 camelCase，
离线聚合指标使用 snake_case，两者通过分析脚本映射。

## 5. 测试与验收

### 5.1 功能测试

- 正常用户可以正常抢单；
- 高频用户触发 `LIMIT`；
- 同设备多账号触发 `REVIEW/BLOCK`；
- 同 IP 聚集增加风险但不无条件封禁；
- 黑名单用户、设备、IP 稳定触发 `BLOCK`；
- 多规则命中时风险分和动作正确；
- `ENFORCE` 能读取已有限频 Key 并直接返回 `LIMIT`；
- `SHADOW` 不读取、不写入限频 Key，模式切换不会改变 SHADOW 下的业务结果；
- `SHADOW` 模式只记录不拦截；
- 风控拒绝后不进入信用校验、抢单 Redis 和数据库 CAS。

### 5.2 并发和 Redis 测试

- 用户窗口并发计数准确；
- 窗口外数据会被清理；
- 同一 `requestId` 不重复计数；
- 不同用户、设备和 IP 的窗口互不影响；
- TTL 和成员上限生效；
- 风控 Lua 异常时按配置降级；
- 新增风控 Domain 包通过 ArchUnit 分层约束。

### 5.3 MQ 和 Worker 测试

- 风险事件正常发送和消费；
- 重投递消息只产生重复日志，不产生重复业务状态；
- 离线脚本能按 `requestId + operationType` 去重，重复投递可被统计为 `risk_event_duplicate_total`；
- `REVIEW` 只产生 `risk_review_pending` 日志，不产生审核表记录；
- 聚合关闭/开启时同步风险动作结果一致；
- 聚合开启后实际 MQ 发送量下降且风险动作覆盖率可统计；
- Worker 重启后可以继续处理；
- MQ 发送失败不影响同步抢单结果；
- 异步处理延迟可以从结构化日志统计。

### 5.4 攻击流量压测

| 场景 | 重点验证 |
|---|---|
| 正常用户混合流量 | 延迟和误伤率 |
| 单用户脚本抢单 | 用户滑动窗口和限频 |
| 多账号同设备 | 设备聚集识别 |
| 多账号同 IP | NAT 场景下的风险加分 |
| 黑名单用户 | 精确拦截稳定性 |
| 风控路径异常 | `fail-open` 和抢单正确性 |
| MQ 延迟或重复 | 异步处理和离线去重口径 |
| 聚合关闭/开启对照 | MQ 发送量、抑制率、消费延迟、堆积和风险覆盖率 |

多 IP、多设备 HTTP 压测只能使用测试环境专用上下文注入，生产默认不信任测试头。

测试注入要求：

- 使用独立测试头，例如 `X-Test-Device-Id`、`X-Test-Client-Ip`；
- 只有 `dash.risk.test-context-enabled=true` 且测试 profile 生效时才读取；
- 生产默认忽略测试头；
- 增加后门关闭集成测试，证明默认配置下测试头无效。

### 5.5 最终指标

至少统计：

```text
risk_decision_total
risk_decision_latency_ms
risk_action_total
risk_rule_hit_total
risk_event_publish_total
risk_event_consume_lag_ms
risk_event_duplicate_total
risk_event_suppressed_total
risk_degraded_total
```

误伤率定义为：

```text
关闭风控时本可成功、开启风控后被拒绝的请求数
/
关闭风控时本可成功的请求数
```

必须区分风控自身延迟、抢单接口整体延迟和 RocketMQ 异步消费延迟。

消费侧指标（`risk_event_processed`、`risk_event_duplicate_total`、`risk_review_pending`）
在统计前必须按 `requestId + operationType` 去重，避免 MQ 重投递导致重复计数。

### 5.6 最终验收目标

| 指标 | 目标 |
|---|---|
| 单次同步风控 P99 | `< 10ms` |
| 黑名单精确拦截率 | `100%` |
| 风控拒绝后的后续抢单 Redis/DB 调用 | `0` |
| 风控降级时新增超卖 | `0` |
| 重复风险事件 | 不产生重复业务状态；离线指标去重后每个请求操作最多 1 次 |
| 2000 并发抢 1 个名额 | 成功 1 个，零超卖 |
| 正常流量误伤率 | 通过配对对照压测实测 |
| 异步消息 | 无长期堆积；重复投递不影响指标口径 |

已知限制：本轮不修改前端，现有前端用户不会提供设备 ID，且服务端生成的 requestId
无法覆盖客户端重试去重；该限制必须写入最终交付物。

## 6. 实施顺序

1. 请求上下文和 Redis Key 约束；
2. 用户滑动窗口、设备多账号、IP 聚集；
3. 精确黑名单和四级风险决策；
4. Sentinel 后接入抢单链路、故障降级和 Shadow 模式；
5. RocketMQ 风险事件与消费处理、离线去重；
6. 总体回归、故障测试、攻击压测和指标报告。

本轮完成后不继续增加动态规则、人工审核、新风控维度、新中间件或新服务进程。

## 7. 面试表达

> 针对校园跑腿中的脚本抢单、批量账号和异常网络行为，在现有抢单链路中接入多维实时风控。通过 Redis Lua 滑动窗口完成用户频率、设备多账号和 IP 聚集判断，结合 Redis 精确黑名单输出 PASS、LIMIT、REVIEW、BLOCK 四级决策；风控放在 Sentinel 之后，并通过 RocketMQ 异步记录风险行为、结构化日志与离线去重完成验证。风控路径支持短超时和 fail-open，同时保留 Redis Lua + MySQL CAS 作为抢单最终正确性防线。
