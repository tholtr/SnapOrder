# 风控模块：预存缺陷与平台坑

> 分两类，**都是跨阶段的**——不属于任何单个阶段，因此不写在阶段设计文档里。
>
> - **缺陷（D-*）**：仓库里既有的、与风控无关但在风控开发中被撞见的 bug
> - **平台坑（K-*）**：仓库的构建/测试/环境特性，不知道就会误判或白查
>
> 维护方式：发现即写。**修好之后不要删**——保留现象与诊断过程，改成「已修」并记下修复方式，
> 因为同一个坑会以不同面貌再来一次。
> 判断一条改动是否该记在这里：**它是不是通过「在一次开发中顺手发现」才暴露的？** 是就记。

## D-1 预存缺陷：`docker/init.sql` 未种入跑腿钱包（已修）

**发现于**：P9.1 批次 1（跑完整 `mvn test` 时暴露）

**现象**：`docker/init.sql:120` 的注释写着「测试用户：1001 发单人（余额 1000 元），**2001-2100 跑腿**」，但紧随其后的 `INSERT` **只有 1001 一行**：

```sql
-- 测试用户：1001 发单人（余额 1000 元），2001-2100 跑腿
INSERT INTO wallet_account (id, owner_id, owner_type, available, frozen, version) VALUES
  (1001, 1001, 'USER', 100000, 0, 0)
ON DUPLICATE KEY UPDATE id = id;
```

仓库里也没有任何惰性建户逻辑（全仓搜不到 `ensureAccount` / `insertAccount` / `INSERT INTO wallet_account`）。于是以 2001 为跑腿的用例在结算时走到 `SettleErrandUseCase:171` 的跑腿钱包 `orElseThrow()`，抛 `NoSuchElementException`。

**影响的用例**：`SettlementIT`（2 个）、`CreditIT`（2 个）、`SettleConcurrencyIT`（2 个）、`ApiEndpointIT`（1 个），共 7 个。

**诊断过程**（避免误判成「改动引入」）：

1. 先把数据源指向一个**全新建的库**（`docker/init.sql` + `migrate-p6.sql`），失败形态完全不变 → 排除脏数据
2. 查新库的钱包表：只有 `ESCROW(-1)`、`COMMISSION(-2)`、发单人 `1001`，**没有 2001**
3. 补上 2001–2100 的钱包后重跑那四个类：**14 个用例全过，BUILD SUCCESS** → 诊断证实

**修复**（2026-09-11）：

```sql
INSERT INTO wallet_account (id, owner_id, owner_type, available, frozen, version)
WITH RECURSIVE seq(n) AS (
  SELECT 2001 UNION ALL SELECT n + 1 FROM seq WHERE n < 2100
)
SELECT n, n, 'USER', 0, 0, 0 FROM seq
ON DUPLICATE KEY UPDATE id = id;
```

余额为 0：跑腿只收钱不垫钱，初始余额没有意义。`ON DUPLICATE KEY UPDATE` 与原脚本一致，保持整个 `init.sql` 可重复执行（已实测跑两遍仍是 100 行）。

## D-2 预存缺陷：空 `X-Request-Id` 让两个跑腿共用幂等槽（已修）

**发现于**：P9.1 批次 3（写拦截器时注意到两处对 `requestId` 的判断口径不同）

**现象**：`ErrandController.grab` 原先只判空引用：

```java
requestId == null ? UUID.randomUUID().toString() : requestId
```

空串与纯空白会原样传下去，幂等键随之变成 `errand:idem:{errandId}:`（`RedisGrabSlotAdapter.idemKey`）。**该任务下所有带空头的请求共用同一个幂等键**，而 `grab.lua` 命中幂等键后只看存下来的值、**不看调用者是谁**：

```lua
local prev = redis.call('GET', KEYS[3])
if prev then
    if tonumber(prev) == 1 then return -2 else return 0 end
end
```

于是 300 秒 TTL 内：

| 时序 | 结果 |
|---|---|
| 跑腿 A 带空头发起 → 抢中，幂等键写 `1` | A 正常，任务归 A |
| 跑腿 B 带空头发起同一任务 | 命中幂等键 → `-2` → `GrabErrandUseCase` 返回 `Result.success()` |

**B 收到「抢单成功」，但任务实际是 A 的。** 一个假的成功响应，且不报任何错——与 [F-2](#f-2) 属于同一类：单看返回值每一处都说得通，矛盾只在跨调用的组合里出现。

**触发条件**：客户端发了一个空值的 `X-Request-Id` 头（例如 `X-Request-Id:`）。命中面窄，但一旦命中就是跨用户的错误成功。

**为什么必须在 P9.3 之前处理**：P9.3 会把 `RiskRequest.requestId` 接到 `RiskContext` 上，而 `RiskContextResolver` 对空白是当成「没传」并生成 UUID 的。两者对「这次请求是哪个请求」的判断不同，会让风控窗口的去重成员与抢单幂等键指向不同的值。

**修复**（2026-09-11）：复用解析器口径——`RiskContextResolver.requestIdOf` 从 `private static` 提为 `public static`，`ErrandController.grab` 改调它，不再自己判空。选复用的理由不是省两行，而是**同一个 `requestId` 在两条链路上必须给出同一个答案**。

**回归锁**：`RequestIdIdempotencyIT`（4 例，走真实 HTTP——缺陷整个活在 controller 那一行的空值判断里，直接调 use case 会跳过它）。三条是反例（空串、纯空白、空头重放），一条是正向对照（同一显式 id 重放仍返回首次成功，防止把幂等本身改坏）。

**这组用例能红，已实测**：把 controller 临时改回 `requestId == null ? UUID... : requestId` 复跑，4 条里 3 条转红，失败响应为 `{code=OK, data={code=OK, grabbed=true}}`——即 B 拿到了 A 所接任务的假成功。这条反证同时确认了**空值头真的穿透了 `TestRestTemplate` 到达 servlet**：若传输层把空头丢掉，服务端收到 `null`，旧代码会走生成 UUID 的分支，B 应拿到 `SLOT_FULL` 而非 `OK`。

> **验证测试本身是否有效，只能靠「让它红一次」。** 本仓库不是 git 仓库（见 [K-3](#k-3)），没有 stash 基线，所以这个动作要手动做，而且**做完要记下实测结果**——否则下次没人知道这组用例到底有没有判别力。

## D-3 `CreditCalibrationIT` 的断言仍与全库状态耦合（未修）

**发现于**：P9.1 批次 1（与 D-1 同一次全量跑，但根因不同）

**现象**：`CreditCalibrationIT.calibration_rebuilds_score_from_recent_window` 在主库上失败（`expected: <1> but was: <100>`），在**全新建的库上通过**。

**根因**：`JdbcCreditRepository.calibrateScores` 是**全局**扫描，不是按用户过滤：

```sql
FROM (SELECT user_id FROM credit_score
      UNION SELECT DISTINCT user_id FROM credit_event WHERE created_at >= ?)
...
HAVING old_score <> new_score
ORDER BY u.user_id
LIMIT ?
```

用例断言 `changed == 1`，而 `changed` 是全库范围内被修正的行数。该用例自己的 `@BeforeEach` 只清理 user 2001，管不到别的用户。所以当全库存在 ≥100 个漂移用户、且其中有 `user_id < 2001` 的，2001 会被 `ORDER BY user_id LIMIT 100` 挤出批次，`changed` 回到 100——**失败签名与 D-1 完全相同，但根因不同**。

**当前状态**：多轮全绿，说明当前库状态下是稳定的；但这条耦合没有被消除。

**两条修法**（属于 P7 信用模块，不在 P9 范围内）：

- 把 `calibrateScores` 的语义改成可指定用户范围
- 或者让用例改用「断言 2001 的分数被修正」而不是「断言全库只修正了 1 行」

**顺带印证的一条既有事实**：测试 yaml 里那句「测试库被各测试类共享，跑腿的在途任务会跨测试累积」——**这批 IT 不是幂等的**。

## D-4 预存缺陷：多名额任务从第 2 个名额起就再也抢不动（未修）

**发现于**：P9.3 批次 4（写 `RiskGrabLinkIT` 的 SHADOW 场景时——设计说「多名额任务 + 连续请求，断言每一次都成功抢到」，实测第 2 个人拿到 `GRAB_CONFLICT`）

**现象**：发一个 `slotTotal = 4` 的任务，四个不同跑腿各抢一次。第一个人正常抢中，**后面三人的每一次都是 `GRAB_CONFLICT`**，任务停在 `LOCKED`、`slot_taken = 1`，剩下三个名额谁也拿不到。全程没有异常日志。

**根因**：抢单的 CAS 自带矛盾条件（`JdbcErrandRepository.casLockForRunner`）：

```sql
UPDATE errand
   SET status = 'LOCKED', grabber_id = ?, slot_taken = slot_taken + 1, ...
 WHERE id = ? AND status = 'PUBLISHED'          -- ← 要求还是 PUBLISHED
   AND version = ? AND slot_taken < slot_total
```

`WHERE` 要 `status = 'PUBLISHED'`，而 `SET` 把它写成 `'LOCKED'`。于是**第一个人抢中之后任务就不再可抢**，`slot_taken < slot_total` 那个条件形同虚设——它永远等不到被求值的机会。

**为什么是全仓范围的死路，不是「另一个入口能走通」**：全仓搜遍了所有写 `status = 'PUBLISHED'` 的语句，只有两条——

| 语句 | 方向 | 能否救回第 2 个名额 |
|---|---|---|
| `casPublish` | `DRAFT -> PUBLISHED` | 不能，只用于发布 |
| `casRevertToPublished` | `LOCKED -> PUBLISHED` | 能，但它同时 `slot_taken = GREATEST(slot_taken - 1, 0)`、`grabber_id = NULL`，且只在**超时且候选队列为空**时触发 |

也就是说第 2 个名额要等到「第一个人超时未确认、且没有候选人」才会连同第 1 个名额一起重新开放。**任务一经抢单就退化成单名额任务。**

**为什么一直没被发现**：既有的 `GrabConcurrencyIT.same_user_cannot_take_two_slots` 用了 2 名额任务，但同一用户抢第二个名额在 **Lua 层**就被 `ALREADY_GRABBED` 挡掉了，**压根走不到 CAS**。全仓没有任何用例让两个不同用户成功抢到同一个任务的两个名额——`slot_taken` 从 1 涨到 2 的分支没有被任何测试覆盖过。

**影响面**：所有 `slotTotal > 1` 的任务。`slot_taken`、`slot_total`、`grab.lua` 的名额计数器、INV-1 不超卖校验都是为并行名额建的，但它们实际只在「1」这个值上运行。

**修法**（属于任务/名额模块，不在 P9 范围内，两个方向都不是纯改 SQL）：

- 把 `status` 拆成「是否有待确认的抢单」与「名额是否满」两件事——现状是一个字段同时承担了这两件事，这才是矛盾的来源；
- 或者给 `LOCKED` 补一条「名额未满时回到 `PUBLISHED`」的流转，但那会与「超时回退」那条路径争夺同一状态，需要一并设计。

**为什么记在这里**：它不是风控引入的，是**写风控 IT 时撞见的**——正好落在本文件开头那条判据上。P9.3 的 SHADOW 场景因此改成了「同一设备上 N 个账号各抢自己的单名额任务」，见 `归档/P9.3 交付记录.md`。

## D-5 预存缺陷：`dash-worker` 进程起不来（**已修**，方案 A，P9.4 批次 1）

**发现于**：P9.4 设计期的现场实验（准备给 worker 加风险事件消费者时，先验证「worker 现在能不能起来」）

**现象**：装上当前代码后启动 `dash-worker`，**启动失败**：

```text
APPLICATION FAILED TO START

Description:
Parameter 3 of constructor in com.campusdash.infrastructure.risk.RedisRiskFeatureAdapter
required a bean of type 'com.campusdash.infrastructure.risk.RiskProperties' that could not be found.

Action:
Consider defining a bean of type 'com.campusdash.infrastructure.risk.RiskProperties' in your configuration.
```

**根因**：`WorkerApplication` 的 `@ComponentScan` 里写着 `com.campusdash.infrastructure`，而 P9.1 交付的三个风控适配器（`RedisRiskFeatureAdapter` / `RedisRiskBlacklistAdapter` / `RedisRiskLimitAdapter`）与 `RiskConfig` 都在该包下、都是 `@Component`/`@Configuration`。它们构造时要 `RiskProperties`，而 `RiskProperties` 是一个 `@ConfigurationProperties` record，**靠 `@ConfigurationPropertiesScan` 注册**——那个注解在 `CampusDashApplication`（app 进程）上有，**`WorkerApplication` 上没有**。于是 worker 里没人提供这个 bean。

被牵连的还有应用层：`RiskPreCheckUseCase`（P9.3 起被 `GrabErrandUseCase` 依赖）同样在 worker 的扫描范围内，Spring 报的第一个失败 bean 就是它。

**为什么一直没被发现**（四条同时成立，缺一条都会暴露）：

1. **这个环境里没有任何进程在跑。** 容器只有 `dash-mysql` / `dash-redis` / `dash-rmqbroker` / `dash-rmqnamesrv`，**没有 app 容器、也没有 worker 容器**；本地起进程从来不是验证流程的一部分。
2. **IT 全在 `dash-bootstrap`**，而它的 `CampusDashApplication` 有 `@ConfigurationPropertiesScan`——同一个缺陷在 app 侧不存在。
3. **`dash-worker` 只有一个测试**（`AutoSettleConsumerTest`，纯反射调私有静态方法），**没有 `@SpringBootTest`**，不加载上下文。
4. **K-3：仓库不是 git 仓库、没有 CI**，`mvn test` 全绿是唯一的门禁，而它看不见这件事。

**引入时间**：P9.1（在那之前 `com.campusdash.infrastructure` 里没有需要 `RiskProperties` 的 bean）。**P9.1 / P9.2 / P9.3 三个阶段验收都通过了**，因为验收手段（`mvn test`）结构性地照不到这个面。

**影响面**：worker 进程承载超时流转扫描、自动结算、资金事件消费、缓存失效消费、对账、本地消息重发、信用校准。**这些功能在部署后一个都不会运行**——而 app 进程正常，所以从接口上看不出任何异常。

**两个修法**（都要先决定「worker 该不该有风控适配器」这个问题）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A：把风控 bean 排除出 worker 的扫描** | 给 `WorkerApplication` 的 `@ComponentScan` 加 `excludeFilters`，排掉 `com.campusdash.infrastructure.risk.*`、`com.campusdash.application.risk.*` 与 `GrabErrandUseCase`（worker 不跑在线抢单链路，这三个本来就不该在 worker 里） | 排除清单需要随新代码维护；但它是**一次性切断耦合**，不随配置项增长 |
| **B：给 worker 也注册 `RiskProperties`** | `WorkerApplication` 加 `@ConfigurationPropertiesScan`，worker yaml 补 `dash.risk.device-hmac-secret: ${DASH_RISK_DEVICE_HMAC_SECRET:}` | worker 从此**必须持有风控设备哈希密钥**（它永远用不到），且今后 `dash.risk` 每加一个**无默认值**的配置项，worker yaml 都要跟着补一条——正是 K-1 那一类「两份 yaml 必须人工保持一致」的陷阱 |

**已定方案 A**（2026-09-11 拍板）：它的方向是「让 worker 不再持有它用不到的东西」，而 B 的方向是「让 worker 满足它用不到的东西的校验」。风控与 worker 的耦合本来就是扫描范围过宽造成的，不是配置缺失造成的。A 的确切排除范围（两处缺一不可、为什么按包级 REGEX 而不是逐个列举）见 `阶段设计/P9.4 异步事件与消费去重口径.md` §8.4。

**它被 P9.4 选成前置后顺带翻出的第二件事**：修好之后得有人**看着它别回来**，而 `dash-worker` 现在连承载这件事的地基都没有——pom 里没有 `spring-boot-starter-test`，`src/test/resources` 整个不存在。更关键的是，**端到端用例不能只靠 `dash-bootstrap` 里的上下文**：消费者类在 `com.campusdash.worker` 包下，而 `dash-bootstrap` 的 pom 只依赖 `dash-presentation` + `dash-infrastructure`、**不依赖 `dash-worker`**——只断言「测试 JVM 收到消息」的用例会连上 broker、却永远看不到那个消费者，而收到消息并不等于有人消费。（这里原先的结论是「所以 `RiskEventIT` 只能住在 `dash-worker`」；P9.4 实现期改成了「把真 worker 当子进程跑、用例仍住 `dash-bootstrap`」，见 `实现期发现.md` F-30 与设计 §8.2。）这与上面第 2、3 条是同一个盲区。所以 P9.4 的任务 0 拆成三段：**0a** 修（本条目）、**0b** 建 worker 的测试脚手架、**0c** 写一个 `mq.enabled=false` 的上下文测试把它钉住。

**动手前要有的心理准备**：A 的排除范围是**静态读引用关系推出来的**，而这次实验只证明了「风控这条链会炸」——Spring 在配置绑定期就中止了，排在后面的装配问题**当时没有机会露头**。如果排干净风控之后又冒出第二个 unsatisfied dependency，那是一条**新缺陷**（往下编号 D-6），不是回头选 B 的理由。

**为什么记在这里**：它不是风控引入的功能缺陷，而是**写风控时撞见的既有装配缺陷**——正好落在本文件开头那条判据上。

**验证手法（做完必须复现一次）**：

```bash
mvn -o install -DskipTests -q                    # 不带 -am 的 -pl 会用到 ~/.m2 旧 jar（K-4）
timeout 60 mvn -o -pl dash-worker spring-boot:run \
  -Dspring-boot.run.arguments="--dash.mq.enabled=false --dash.ws.enabled=false"
# 看有没有 "Started WorkerApplication"
```

**顺带记一条手法**：直接调插件 goal（`spring-boot:run`）时**不能带 `-am`**——直接调用的 goal 会在 reactor 的**每一个**模块上执行，聚合根 pom 会先报 `Unable to find a suitable main class` 让整条命令失败。

**已修（2026-09-11，P9.4 批次 1 的 0a）**：`WorkerApplication` 的 `@ComponentScan` 加两处 `excludeFilters`（确切范围与「为什么按包级 REGEX 而不是逐个列举」见 `阶段设计/P9.4 异步事件与消费去重口径.md` §8.4）。用上面那条复现命令实测，输出从 `APPLICATION FAILED TO START` 变成：


全量 WARN/ERROR 为空，**没有第二条 unsatisfied dependency 浮出来**。前后两次输出的完整对照在 `归档/P9.4 交付记录.md`；回归网是 0c 的 `WorkerApplicationContextTest`（含 `schedulingIsDisabled()`），它同时是 F-20 的守卫。

<a id="d-6"></a>
## D-6 预存缺陷：worker 收到 SIGTERM 后不退出（未修）

**发现于**：P9.4 批次 5（手工实测「Worker 重启后继续处理」时，`kill -TERM` 之后进程不肯退出）

**现象**：给 worker 进程发 SIGTERM（`kill -TERM <pid>`），**它不会退出**。当次实测中进程在 **45 秒后仍然活着**，日志里连一行关停记录都没有，最后是用 `kill -9` 收的场。同一份现场的 `jstack` 显示 shutdown 线卡在 RocketMQ 客户端的关闭等待上。

**根因**（两层叠在一起）：Boot 注册的 shutdown hook 停在 `PushConsumer.close()` 里的 `awaitTerminated`——它在等 broker 那边确认退订/关停完成；而 SIGTERM 的处理路径**又在 join 这个 hook**。于是「等客户端关完」与「等 hook 返回」互相等，谁都不动。**哪一层是主因尚未用最小实验定位**（是 `PushConsumerImpl.close()` 自己等不到终止，还是我们 join 的位置不对），修之前必须先做那一步。

**影响面**：**六个消费者**是同一个写法（`consumer.close()` 一行）：

```text
FundEventConsumer:108      CacheEvictConsumer:84       RiskEventConsumer:109
AutoSettleConsumer:87      TimeoutTransferConsumer:100
FundEventPushConsumer:101（dash-infrastructure.realtime，app 侧）
```

**不是 P9.4 引入的**，仓库一直如此；`RiskEventConsumer` 只是照抄了既有形态。真实后果：

1. 滚动发布、重启 worker 时进程**不会优雅退出**，要等运维强杀（K8s 会到宽限期用 SIGKILL，能收场，但部署变慢）；
2. 强杀那一下**没处理完的本地消息重发与内存里的日志会被丢掉**；
3. **自动化看不出来**：`WorkerSubprocess.stop()` 先给 8 秒再 `destroyForcibly()`，强杀把这一条完全掩盖——所以它不会让任何测试变红（F-32 的「无自动化守卫」就是这个意思）。

**为什么记在这里**：写风控消费者时撞见的**既有**行为，符合本文件开头的判据（不是风控引入的功能缺陷，也不是风控范围内的设计问题）。

**要断言它得先有设施**：判据是「进程能在 N 秒内退出」，而现有测试基础设施里没有这条线。所以它现在的状态是「有现场、有根因方向、无自动化」。

**修法方向（未验证，不要照抄）**：最小实验先定位「卡在客户端还是卡在我们的 join」；方向上三选一——把关闭放到独立线程并给它一个超时（不再 join）、先停拉取再关（若客户端提供了对应的半步操作）、或把这段关闭从 Boot 的 shutdown hook 里挪出来。三条都要在**六个消费者**上一致落地，属于一次独立的、要单独验证的改动。

**本阶段（P9.4）不改**，理由记在 `归档/P9.4 交付记录.md` 与实施计划 §8；由此带出一条连带决定：P9.5 的「worker 停止后恢复」按**半自动用例**做，停下那一步用 `kill -9`，并在报告里如实标注「这一步验的是重启后能继续消费，不是优雅关停」。**若先修了 D-6，那条线可以升级成「优雅关停后恢复」。**

**P9.5 批次 1 补记一条实测的运行后果**（`实现期发现.md` F-34）：强杀之后，消费组里那个成员在 broker 侧**还活着**，于是停机期间产生的事件会**先被投给它**（算一次投递），要等一个 60 秒量级的期限过去、队列重新分给新成员才真正被消费——实测 `lagMs` 为 **67959ms / 67910ms** 两次，`deliveryAttempt=2`。这条比上面那三条后果更重：**强杀不只是「部署慢」，它还让重启后的一分钟量级内事件观测是断的**。修 D-6 的收益因此要一并写进那份排期（先做最小实验定位卡在哪一层，再决定三选一）。

**验证手法（修完必须复现一次）**：

```bash
# 用生产配置起 worker，另开一个终端：
kill -TERM <worker_pid>
for i in $(seq 1 8); do kill -0 <worker_pid> 2>/dev/null && sleep 1 || { echo "已退出（第 ${i} 秒）"; break; }; done
```

现状（2026-09-12 实测）：8 秒内不退出。修复后的目标：8 秒内退出（窗口与 `WorkerSubprocess.TERM_GRACE` 对齐）。

## D-7 预存缺陷：`risk_feature` 行没有生产者（未修）

**发现于**：P9.5 批次 1（写 `RiskTestHeaderBoundaryIT`，要断 `risk_feature` 行的 `deviceAccounts` 时）

**现象**：`risk_feature userId=... count10s=... deviceAccounts=...` 这一行**在系统里根本不会出现**。

1. **线上排障缺证据**：这是唯一带「窗口计数 / 聚集计数」的观测面。只剩决策行时，
   能看到 `action=LIMIT`，看不到当时窗口里有 6 次还是 60 次请求、这台设备上挂着几个账号。
   F-19（`deadline-ms: 10` 在真实并发下约等于全程空转）当天的现场就是靠决策行反推的。
2. **指标侧影响面为零**（已逐条核对）：P9.5 §7.2 的九个指标名全部落在 `risk_decision` 行或 P9.4 的四个事件行上，
   `风控反作弊实现蓝图.md` 与 `风控模块实施计划.md` 里搜 `count10s` / `deviceAccounts` / `ipRequests` 一个都没有。
   受影响的只有 P9.5 §4.3 与 §7.1 的两处口径，已在设计文档里就地改掉（改用 Redis 键集合差集 / 只读决策行）。
3. **不动生产行为**：它少打一行日志，多打一行不会改变任何决策、拒绝或事件。
   所以「先修再测」不会污染 P9.5 的判据——**但会让 P9.5 的整轮数字对应到另一棵树**，这是本轮不修的唯一理由。

**修法（未验证，不要照抄）**：`RiskPreCheckUseCase` 第 4 步之后加一行

```java
RiskFeatureLog.emit(context.userId(), context.errandId(), context.requestId(), window, cluster, degraded);
```

四个参数在第 5 步之前全部就位（`window` / `cluster` 是第 3、4 步的返回值，`degraded` 取当时的 `reasons` 非空）。

<a id="k-1"></a>
## K-1 `src/test/resources/application.yaml` 是整体替换，不是合并

Spring Boot **不会合并** `src/main` 与 `src/test` 的同名 `application.yaml`——测试资源目录里那份是整体替换。该文件开头注释已写明，并记录了「缺任何一段都会报 `Failed to determine a suitable driver class`」的实测踩坑。

后果：

1. `device-hmac-secret` 的生产值只能来自环境变量，而测试进程不会带这个环境变量，**所以测试 yaml 里必须显式写一个测试密钥**，否则构造器校验失败，`mvn test` 会把全部 IT 一起打红
2. 主配置里**只能**有 `${DASH_RISK_DEVICE_HMAC_SECRET:}` 这个空默认值，不得填任何可用值
3. 主配置其余的 key 都有 `@DefaultValue`，测试 yaml 不必逐个重复——只有 secret 一项是必须补的

**给后续阶段的建议**：**每加一个必填配置项，先改测试 yaml 建好启动基线，再往里填代码**。反过来做的话，第一次加 bean 时会被一串启动失败淹没，不容易定位。

<a id="k-2"></a>
## K-2 中间件没起时 IT 报 `Tests run: 0` 且构建通过

IT 类普遍用 `@BeforeAll` + `Assumptions.assumeTrue(MiddlewareAvailable.check(), "中间件未启动，跳过")` 守卫。

**后果**：中间件（MySQL 3307 / Redis 6380 / RocketMQ）没起时，这些类**整类被跳过**，输出是：

```
Tests run: 0, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

**`Skipped: 0` 是关键**——被 assumption 拦下的用例不计入 `Skipped`，所以「跳过」看起来和「全绿」一模一样，字数都不差。

**怎么避免误判**：看**总用例数**，不是看失败数。全量跑应该是 276（P9.1 结束时）；明显偏小就说明有 IT 整类没跑。

```bash
mvn -o test 2>&1 | grep -E "Tests run: [0-9]+, Failures" | grep -v -- "-- in" | sed 's/\x1b\[[0-9;]*m//g'
```

这条命令列出**逐模块的汇总行**（不带 `-- in` 的那些就是模块合计）。

<a id="k-3"></a>
## K-3 仓库不是 git 仓库，没有 stash 基线

`campus-dash-main` 及其子目录都不是 git 仓库。**没有 `git stash`、没有 `git diff`、没有可回退的基线。**

**影响**：IT 失败时，无法用「切回改动前跑一遍」判断是不是自己改出来的。

**替代手法：用新建的空库对跑。**

1. 建一个新库，用 `docker/init.sql` + `migrate-p6.sql` 初始化
2. 把数据源指向新库跑失败的那几个类
3. 新库上**仍然失败** → 是代码问题（自己改的或本来就有的）
4. 新库上**通过** → 是共享库的脏数据问题

D-1 与 D-3 都是靠这个手法区分的：D-1 在新库上复现（真缺陷），D-3 在新库上通过（脏数据耦合）。

**另一个用途：验证一个测试是否真的有判别力。** 把被测代码临时改回旧写法，复跑，**必须转红**；否则那条用例可能只是因为输入压根没送到而变绿。D-2 就是这么验的。

<a id="k-4"></a>
## K-4 `-pl <module>` 不带 `-am` 会用 `~/.m2` 里的旧 jar

`campus-dash-backend` 是 Maven 多模块，模块间靠 `~/.m2` 的已安装 jar 解析依赖。只跑 `mvn test -pl dash-application` 这类单模块命令时，上游模块**不会重新编译**，用的是上次 `mvn install` 留下的旧 jar。

**症状**：改了上游模块的接口（例如给 `dash-domain` 的某个类加了嵌套 record），下游编译报「程序包 xxx 不存在」「找不到符号」——看起来像自己写错了 import 或类名，实际上是被测模块的代码没问题，只是上游是旧的。

**正确写法**：

```bash
mvn -o test -pl dash-application -am -Dtest=RiskFeatureLogTest -DfailIfNoTests=false \
    -Dsurefire.failIfNoSpecifiedTests=false
```

`-DfailIfNoTests=false` 和 `-Dsurefire.failIfNoSpecifiedTests=false` 都要带上——`-am` 会把上游模块拉进 reactor，那些模块里没有匹配 `-Dtest` 的类，不带这两个参数会因「没有测试可跑」直接失败。

跑全量时不存在这个问题，直接 `mvn -o test` 即可。

**后续补充（P9.5 批次 1，同一个根因的第二个场面）：跑 `dash-bench` 的工具时也会撞上它。**
`mvn -o -pl dash-bench dependency:build-classpath` 输出的是**模块依赖树**，其中三个本仓库模块指向
`~/.m2` 里的 SNAPSHOT jar；那些 jar 只要不是刚 `install` 过的，就可能缺类。
实测：`RiskEventDuplicateTool` 用这份 classpath 起不来——
`NoClassDefFoundError: com/campusdash/domain/risk/model/RiskOperationType`（`dash-domain` 的 m2 jar 是旧的），
退出码 1、一条消息都没发出去。

正确写法：**四个本仓库模块一律用各自的 `target/classes`，只有第三方依赖用 m2 里的 jar**：

```bash
B=/workspace/Job/2026.9/campus-dash-main/campus-dash-backend
CJ=$(mvn -o -q -pl dash-bench dependency:build-classpath -Dmdep.outputFile=/tmp/cp.txt >/dev/null; \
     tr ':' '\n' < /tmp/cp.txt | grep -v campusdash | tr '\n' ':')
java -cp "$B/dash-bench/target/classes:$B/dash-domain/target/classes:$B/dash-shared/target/classes:$B/dash-infrastructure/target/classes:$CJ" \
     com.campusdash.bench.RiskEventDuplicateTool --action LIMIT
```

同样理由，**先用「参数写错」跑一次验 classpath**（退出码 2、不发消息）比直接发消息安全：
工具的参数校验在发送之前。
