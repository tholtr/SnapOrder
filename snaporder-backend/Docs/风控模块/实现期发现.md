<a id="f-1"></a>
## F-1 集群三个维度必须一次写入

**首次发现**：批次 2（端口定稿前）

**初稿形态**：把集群维度拆成 `trackDeviceAccount` / `trackIpAccount` / `trackIpRequest` 三个方法，理由是「按维度分开更清晰」。

**为什么错**：`risk_cluster.lua` 在一次调用里同时算这三个维度。每次调用脚本，脚本都会对 IP 速率 ZSet 执行一次 `ZADD`——这正是 IP 请求数递增的机制。于是：

- 「请求设备账号数」这一次调用顺手把 IP 请求数 +1
- 「请求 IP 账号数」再一次 +1
- 真正的 `trackIpRequest` 第三次 +1

**一次请求被记成三次**，计数被静默抬高 3 倍，不报任何错。

即便忽略计数，拆开也意味着三次 Redis 往返，直接违背蓝图 §3.8 的 10ms 总 deadline。

**定稿**：端口收敛为两个方法，各自对应一次脚本调用。

| 方法 | 脚本 | 返回 |
|---|---|---|
| `trackUserWindow(userId, requestId)` | `risk_user_window.lua` | 两个窗口的计数 + 是否重复请求 |
| `trackCluster(userId, deviceId, clientIp)` | `risk_cluster.lua` | 设备账号数 / IP 账号数 / IP 请求数 |

**为什么值得记**：「按维度拆开更清晰」是一个非常自然的重构冲动，而它造成的后果（计数 ×3）不会报错，只会在压测里表现为「阈值怎么调都不对」。看代码看不出来，因为拆开后的每个方法单独看都对。

<a id="f-2"></a>
## F-2 Lua 里必须先裁剪、后查重

**首次发现**：批次 2（手工验证脚本时）

**初稿形态**：计划初稿以及第一版脚本注释用一整段论证「**必须先查重、后裁剪**」，理由是「反过来写会漏去重：已被时间裁剪掉的 `requestId` 会被当成全新请求重新计数」。

**为什么错**：这个论证把「上次写入时刻」当成了「当前时刻」。成员在窗口内是**惰性清理**的——只在有写入时才裁剪。两次写入之间时间在走，一个已经滑出窗口的成员会一直留在集合里，直到下一次写入才被裁掉。「先查重」于是会把这种残留成员误判为重复。

而它担心的那件事本身是反的：滑出窗口的 `requestId` 本来就该当成新请求重新计数，这正是期望行为。窗口内的重复请求不会被裁掉（分数还在窗口里），查重照样命中，去重并没有被削弱。

**实测**（Redis 7.4.11，写入后静默 62 秒、键靠 TTL 存活，再重放同一 `requestId`）：

| 顺序 | 返回 `{10s计数, 60s计数, 是否重复}` |
|---|---|
| 先查重、后裁剪（初稿） | `{0, 0, 1}` ← **一边说「重复」，一边说窗口里一个成员都没有** |
| **先裁剪、后查重（现版本）** | `{1, 1, 0}` ✅ |

**定稿**：先按时间裁剪，再查重。

**发现手法值得单独记**：旧版本那种自相矛盾的返回值**不需要任何外部推理**就能看出不对——「说重复，但两个窗口计数都是 0」。手工验证时不能只看「值对不对」，还要看**返回值之间是否自洽**。

**影响面**：计数不受影响（滑出窗口本就不该计），错的是 `duplicateRequest` 标志位。它在当时还没有被任何规则消费，所以修在依赖产生之前。

**顺带修正的另一条**：`TTL ≥ 最长窗口秒数` 这个前提仍然成立，但理由与初稿不同——与查重顺序无关，而是因为键若在窗口结束前整体过期，窗口内的成员会跟着一起消失，重放会被当成新请求，**计数偏小（漏报）**。

## F-3 ZSet 成员上限是 127 不是 128

**首次发现**：批次 3（任务 10 复核编码时）

**初稿形态**：计划初稿写「不得超过 128」，依据是「128 个成员仍是 listpack」。

**为什么错**：这个依据本身没错（实测直接 `ZADD` 128 个成员确实是 listpack），**但它不是本项目的写入路径**。脚本是「先 `ZADD`、再裁剪」，键在调用瞬间会达到 `cap + 1` 个成员。cap 取 128 时瞬时到 129，当场触发转换。

Redis 7.4 的 ZSet 在成员数 ≤ `zset-max-listpack-entries`（默认 **128**）时用紧凑的 listpack 编码，超过即转换为 skiplist，**且编码只升不降**——转过去就再也回不来，即使后来裁剪回 100 个成员也不会变回 listpack。

**实测**（Redis 7.4.11，成员为真实形态，按真实写入路径）：

| 上限 | 编码 | 单键内存 |
|---:|---|---:|
| 101 | listpack | 5184 B |
| 110 | listpack | 6208 B |
| 120 | listpack | 6208 B |
| **127** | **listpack** | **7232 B** |
| **128** | **skiplist** | **17601 B** ⚠ |
| 129 | skiplist | 17304 B |
| 200 | skiplist | 26536 B |

（该组测量把 UUID 长度的 `requestId` 灌进**用户窗口键**，用于定位阈值。生产配置里用户窗口上限只有 6 / 31。）

**上限 127 → 128 之间单键内存翻 2.4 倍。** 当前 `ip-rate-cap = 101` 留了 26 的余量，是安全的。但任何人为了「更精确」把这个值调到 128 以上，内存画像会整体失控，且这种退化不会报错、不会告警，只会在压测里表现为 Redis 内存异常。

**定稿**：`ip-rate-cap` 及未来任何 ZSet 型上限**必须 ≤ 127**；确需更大窗口时，应改为降低窗口精度或换用其他结构，而不是直接调大 cap。已落地为 `RiskProperties` 构造器的启动期校验，配错则应用起不来。

**复现方法**（不要用估算值代替）：

```bash
docker run -d --rm --name risk-lua-verify -p 16399:6379 redis:7.4-alpine
docker cp dash-infrastructure/src/main/resources/lua/risk_user_window.lua risk-lua-verify:/tmp/uw.lua
docker exec risk-lua-verify redis-cli -p 6379 --eval /tmp/uw.lua \
    risk:win:1:10s risk:win:1:60s , <requestId> <cap10> <cap60> <ttl>
docker exec risk-lua-verify redis-cli -p 6379 OBJECT ENCODING risk:win:1:10s
docker exec risk-lua-verify redis-cli -p 6379 MEMORY USAGE risk:win:1:10s
```

两个坑：`--eval` **在容器内执行**，所以脚本路径必须是容器内的（宿主机路径会报 `Can't open file`，这正是 `docker cp` 那一步的原因）；`,` 是 `redis-cli` 分隔 `KEYS` 与 `ARGV` 的标记，漏了它参数会全被当成键名。**必须走脚本、不能手工 `ZADD`**——手工塞 128 个成员仍是 listpack，会得出与上表相反的结论。

<a id="f-4"></a>
## F-4 Set 成员上限是 512，且这条悬崖比 ZSet 陡得多

**首次发现**：批次 3（任务 10 复核编码时）

**初稿形态**：脚本注释与测试都声称两个 Set「成员是小整数，走 intset，**不存在编码跳变**」。

**为什么错**：前半句对，结论错——**intset 也有悬崖，只是位置不同、而且更陡**。

悬崖由 `set-max-intset-entries`（默认 **512**）决定，超过即转 hashtable，与 ZSet 一样**只升不降**。

**实测**（走 `risk_cluster.lua` 真实写入路径）：

| 上限 | 实际成员 | 编码 | 单键内存 |
|---:|---:|---|---:|
| 9（生产） | 9 | intset | 80 B |
| 11（生产） | 11 | intset | 80 B |
| 512 | 512 | intset | 1336 B |
| **513** | **513** | **hashtable** | **24720 B** ⚠ |

**跳涨 18.5 倍，比 ZSet 那条（2.4 倍）陡得多**，同样不报错、不告警。

上界是干净的 **512**（不是 511）：Set 没有 ZSet 那种「先写后裁」的瞬时 `cap + 1` 问题——脚本是 `if SCARD < cap then SADD`，最多正好到 cap。

**为什么危险**：那句错误注释**主动告诉后来人「Set 可以随便调」**，而「误报太多就把阈值调大」是本模块最自然的一次配置改动。原有用测试 `threshold=500` 断言「放行」，恰好卡在悬崖下沿 12 个身位，**看着像验过了，实际没碰到边界**。

**定稿**：已修正为 `requireCompactIntset(...)` 启动期校验，边界用例改为 511（放行）/ 512（拦截）。

<a id="f-5"></a>
## F-5 两个 Set 的 TTL 必须分成两个参数

**首次发现**：批次 3（写 `RiskFeatureIT` 时）

**初稿形态**：`risk_cluster.lua` 只有 `ARGV[5]` 一个 `setTtl`，同时用在设备集合和 IP 账号集合上，而适配器传的是 `deviceWindow.seconds()`。

**为什么错**：`dash.risk.ip-account-window.seconds` 成了**死配置项**——改它没有任何效果，且不报错；反过来改设备窗口还会顺带改掉 IP 账号窗口。

**根因是 Set 的性质**：成员是裸 `userId`，没有分值、没有时间信息，所以「窗口」这个语义完全由 TTL 承载（配合「只在新增成员时才 `EXPIRE`」）。**TTL 在这里不是无关紧要的过期时间，它就是窗口长度本身。** 这和 ZSet 完全不同——ZSet 的窗口由成员分值表达，TTL 只是个兜底的清理时间，配错了顶多多留一会儿数据。

**为什么这次能抓到**：编写 IT 时把两个窗口**配成了不同的值**（`ip-account-window.seconds` 覆盖成 300，设备窗口保持 600）。若两个窗口配成一样，这个缺陷永远看不出来——**这是一条通用的检测手法：要测「两个参数是否各自生效」，就必须让它们取不同的值。**

**定稿**：三个 TTL 拆成 `ARGV[5]` / `ARGV[6]` / `ARGV[7]`，用真实 `redis-cli` 验证拿到三个独立 TTL（600 / 300 / 60）。

**「TTL 即窗口长度」这条已提升进蓝图 §3.8**——它对 P9.2–P9.5 任何新增 Set 型键都成立，写在 P9.1 计划里对后续阶段没有约束力。

<a id="f-6"></a>
## F-6 Set 的内存随 `userId` 位数增长

**首次发现**：批次 3（任务 10 复核时）

内存预算表里两个 Set 的 120 B / 128 B 是按**四位 `userId`** 测的，也就是当前种子数据的形态（`owner_id` = 1001...2100）。但 `intset` 会按集合内**最大成员的值**选择条目宽度（2 / 4 / 8 字节），所以 `userId` 变长，每个键都会变大：

| `userId` 形态 | `risk:dev:*`（9 成员） | `risk:ip:*:users`（11 成员） |
|---|---:|---:|
| 四位（当前种子数据） | 120 B | 128 B |
| 19 位雪花 id | 168 B | 192 B |

本仓库**没有 `user` 表**，用户只以 `wallet_account.owner_id` 的形式存在，所以现在还够不到 19 位那一档。但这只取决于将来注册功能怎么发号，不取决于风控——要么给 `userId` 的长度定个上限，要么接受每个实体多 112 B。

112 B 相对单组 4.4 KB 是 +2.6%，**不改变任何结论**，所以不单列一条风险。但它说明内存预算表那些数字的成立条件：**它们是「当前 id 形态下」的测量值，不是「与 id 无关的常量」。**

<a id="f-7"></a>
## F-7 IP 解析的第 1 步与第 5 步语义相反

**首次发现**：批次 3（实现 `ClientIpResolver` 时）

**初稿形态**：把两种情况合并成「解析失败 → 返回 `remoteAddr`（不要返回 null）」。

**为什么错**：`remoteAddr` 由容器提供，**正常情况永远是合法 IP**；它解析不出来说明拿不到对端地址，此时不是「退回 remoteAddr」而是**根本没有可用的 IP**。

| 情况 | 返回 | 理由 |
|---|---|---|
| `remoteAddr` 非法 | `null` | IP 维度不可用，调用方直接跳过该维度 |
| 转发头中途某段非法 | `remoteAddr` | 对端地址是可信的，只是转发链断了 |

**后果的差别是实际的**：退化成空串或某个固定值的话，所有这类请求会**共用一个风控桶**——既让限流误伤，也可能让攻击者靠制造解析失败来稀释自己的计数。

<a id="f-8"></a>
## F-8 拦截器只能存 `RiskRequest`，不能存 `RiskContext`

**首次发现**：批次 3（实现 `RiskContextInterceptor` 时）

**初稿形态**：计划初稿写「拦截器解析后存入 `RiskContext`」。

**为什么做不到**：`RiskContext` 有 `errandId` 字段，而拦截器挂在 `/api/**` 上，`preHandle` 阶段绝大多数路由（用户列表、钱包、任务详情……）根本没有任务 id——`errandId` 是路径变量，只有抢单那几个端点才有，且要到 `handle` 阶段才拿到。

若在拦截器里塞一个 `0` 或 `-1` 顶替，这个「不存在」的值会一路流进采集日志行和 P9.4 的风险事件，**且没有任何地方会报错**。

**定稿**：拦截器交付它真正知道的东西——`RiskRequest(userId, requestId, deviceId, clientIp)`；`RiskContext` 由知道 `errandId` 的一方（P9.3 的 `GrabErrandUseCase`）组装。`RiskContext` 本身不变。

**为什么值得记**：这是「为不存在的值找个占位符」的典型诱惑。占位符的坏处不是它不准确，而是**它让一个缺失在类型上消失了**，于是没有一处代码有机会报错。

## F-9 后门测试不走 `RiskContextSink`

**首次发现**：批次 3（写 §7.4 的测试时）

**初稿形态**：计划 §7.4 推荐用一个 `@TestConfiguration` 提供的 `RiskContextSink` 接缝，在测试上下文里替换为空实现并记录每次解析结果，再通过 `TestRestTemplate` 发真实请求断言「开关关闭时测试头未生效」。仓库有先例（`CacheDoubleDeleteControlIT` 用 `@TestConfiguration` + `RecordingCacheEvictDelayPort` 做过同类验证）。

**为什么不采用**：这会为一个只服务于测试的接缝**在生产代码里加一个可注入的抽象**——多出来的生产抽象，等于给「后门」再开一个入口，与这条验收项想证明的事情方向相反。

**真正要证的性质是三条，它们全都在 `RiskContextInterceptor.preHandle` 里，不需要 HTTP 端到端**：

1. 开关关闭时测试头不生效
2. 开关关闭时测试头**连读取都不发生**
3. profile 不含 test 时，即使开关打开也不生效

**定稿**：改成 `dash-presentation` 里的 `RiskContextInterceptorTest`——用 `StandardEnvironment`（spring-core 的普通类）构造拦截器，用手写的假请求调真实的 `preHandle`，再读 request attribute 断言。

这样反而更强：

- 测的是真实的 `preHandle`，没有 `@TestConfiguration` 覆盖带来的「测的可能不是线上那套装配」问题
- 假请求记录**每一次 header 读取**，于是第 2 条从注释里的声明变成了可断言的事实
- 不需要起 Spring 上下文，留在秒级的单测里，不占用 IT 的时间

**为什么不为这个测试引入 `spring-test`**：`dash-presentation` 的 pom 刻意只有三个依赖，为一个测试类引入不成比例。假请求只需覆盖拦截器会调的 5 个方法（`HttpServletRequestWrapper` 要求非空委托，塞一个占位动态代理即可）。

<a id="f-10"></a>
## F-10 校验用紧凑构造器，不用 `@Validated` + `@NotBlank`

**首次发现**：批次 1（实现 `RiskProperties` 时）

**初稿形态**：`@Validated` + `@NotBlank`。

**为什么在本仓库会静默失效**：

- 仓库里**没有任何校验依赖**——`spring-boot-starter-validation` / `hibernate-validator` 都不在依赖树里，全仓也没有一处 `@Validated` 或 `jakarta.validation.*` 的 import
- 校验注解由 Hibernate Validator 提供实现。缺了它，注解本身能编译（如果依赖恰好被间接引入）或者根本引不进来；即使引进来，没有 `Validator` bean 时 `@Validated` 也不会触发校验，**配置缺失时应用照常启动**

**这比「报错信息不好看」严重得多**：一个看起来配了必填校验、实际完全不生效的类，比没有校验更让人放心地踩坑。

**定稿**：换成紧凑构造器。校验逻辑是普通 Java，**不需要 Spring 上下文就能单测**，`RiskPropertiesTest` 里 16 个用例直接 `new RiskProperties(...)` 即可。顺带把两条编码约束（ZSet `cap ≤ 127`、Set `cap ≤ 512`）也一并放进构造器——配置有错就让应用起不来，而不是运行到一半才发现编码退化了。

## F-11 五个 `cap` 不作为配置项

**首次发现**：批次 1（实现 `RiskProperties` 时）

**初稿形态**：`short-cap` / `long-cap` / `device-cap` / `ip-account-cap` / `ip-rate-cap` 都列为独立 key。

**为什么去掉**：

1. **初稿里这五个值本来就全部等于 `threshold + 1`**（6=5+1、31=30+1、9=8+1、11=10+1、101=100+1）。一个合法取值只有一个、且由另一个 key 决定的配置项，写出来只会让人误以为它可以随便调。
2. **cap 小于 `threshold + 1` 会让规则静默永不触发**：截断上限低于阈值，ZSet 永远攒不够触发所需的成员数，规则看起来配好了但一次都不会命中。
3. **cap 大于 127 会让内存翻 2.4 倍**（见 [F-3](#f-3)）。去掉配置项后这个约束由阈值唯一决定，构造器直接校验。

**顺带**：把 `device-window-seconds` / `ip-account-window-seconds` / `ip-rate-window-seconds` 三个扁平 key 改成嵌套结构（`device-window.seconds` 等），与 `user-window` 保持一致。

<a id="f-12"></a>
## F-12 Lua 时间戳只能用微秒

**首次发现**：任务 0（脚本可行性验证）

`redis.call('TIME')` 返回字符串，脚本里算出来是 Lua number，而 **Lua number 是 IEEE-754 double，只能精确表示到 2^53 ≈ 9.007e15**。

| 精度 | 当前量级 | 是否安全 |
|---|---:|---|
| 微秒 | 1.789e15 | ✅ 在安全区内（余量到 2255 年左右） |
| 纳秒 | 1.789e18 | ❌ 超出，不同请求会算出同一分值而被当成同一成员 |

**微秒不是随手选的，它是能安全使用的最高精度。** 这一行注释留在脚本里，避免后人「顺手改成纳秒提高精度」——那会让 IP 速率窗口在并发下静默合并成员，计数偏小。

**顺带验证的两条**（任务 0 一并做的，redis 7.4.11）：

- 脚本内 `TIME` 可用，**且其后继续执行写命令不报错**（历史上 3.2 之前禁止「非确定性命令后再写」，正是本场景）
- `ZREMRANGEBYRANK key 0 -(N+1)` 的截断正确：连打 10 次上限 6，`ZCARD` 恰好 6

<a id="f-13"></a>
## F-13 设备低阈值取 0 或 -1 会让低档规则恒真

**首次发现**：批次 1（实现 `RiskProperties` 的新校验时）

**设计只列了两条校验**（P9.2 设计 §6.2）：`lowThreshold < threshold` 与 `limitCooldownMs > 0`。
两者防的都是「规则静默失效」。实现期发现同一个字段还有**方向相反的第二类坑**——规则静默**恒真**：

```text
low-threshold: 0     deviceAccounts > 0    恒真（有设备维度的请求都满足）
low-threshold: -1    deviceAccounts > -1   恒真
```

`0` 和 `-1` 恰好是「想关掉这条规则」时最顺手的两种写法，而它们都**能通过** `lowThreshold < threshold`。
后果不是「低档规则失效」，而是**每个带设备维度的请求都加 60 分 → 全站 REVIEW**：
一次配置笔误就是全站拦截，日志里还显示「规则正常命中」，查不出所以然。

**定稿**：校验拆成一个取值域 `1 <= low < high`，由 `requireThresholdPair` 一处守住，
失败信息里明说「本阶段不提供关闭低档规则的开关，不要用 0/-1 表达关闭」——
把运维的下一个念头直接堵在错误信息里。

**顺带的收益**：这条下界让「限频短路路径」可以安全地传 `Cluster.EMPTY`（全 0）去跑
`evaluate`——若低阈值允许取 0，全 0 的输入会凭空命中一条 REVIEW，短路路径的
`action=LIMIT score=30` 就变成 90 分 BLOCK。两条设计互相咬合，不是巧合。

<a id="f-14"></a>
## F-14 降级原因不能进 `evaluate` 签名

**首次发现**：批次 1（实现 `RiskRules` 与 `RiskDecision` 时）

**设计给 `evaluate` 的签名**没有 `degradeReasons` 参数（P9.2 设计 §3.3），但也没说它们**怎么进到结果里**。
实现时有个很自然的冲动：加一个 `List<DegradeReason>` 参数传进去。

**为什么不能**：规则层拿到的只有采集结果——一堆 `int`。它**看不出** `count10s = 0` 究竟是
「用户这一个 10 秒窗口真的没请求过」还是「采集挂了所以记 0」。这两件事在同一个 `int` 上完全同形，
而它们的意义相反：前者是证据，后者是缺证据。想让规则层区分，就必须把「哪些维度失败了」
一起传下去——那就等于让规则层理解 Redis 故障与 try/catch 的结构。

**定稿**：降级原因由**捕获异常的那一层**（`RiskPreCheckUseCase`）记录，事后再附到结果上：

```java
rules.evaluate(window, cluster, blacklist, limitHit)
     .withDegradeReasons(reasons)
```

`withDegradeReasons` 只换原因列表，**分数与动作原样保留**——这就是「降级不是放行」的实现形态：
黑名单挂了但设备维度已经越线时，决策仍然是 `BLOCK`，只是在同一行日志里多出一个降级原因。
`RiskRulesTest.evaluateNeverInventsReasons()` 守着这条边界，防止后人「顺手」把这个参数加回去。

<a id="f-15"></a>
## F-15 设计文档内部对「短路」的口径不一致：只有限频键命中才短路

**首次发现**：批次 3（实现 `RiskPreCheckUseCase` 时）

设计 §5.1 给出的执行序里，只有**第 1 步（读限频键）**带短路：

```text
1. ENFORCE 下读限频键   -> 命中：记 LIMIT_COOLDOWN，短路，不采集不查黑名单
2. 查三类黑名单         -> 查询失败：记 BLACKLIST_FAILED，three-false 继续
3. 采集用户窗口         -> ...
```

而 §7.1 的测试表里写的却是另一回事：

| `RiskPreCheckUseCase`（手写 fake 端口） | 短路顺序（**黑名单命中时不调用特征端口**）；… |

两处不可能同时成立。按 §7.1 写，黑名单命中后就不该再采集特征；按 §5.1 写，黑名单
命中也只是加 80 分，第 3、4 步照常执行。

**判定依据是 §9 的验收项**，它把短路挂在限频键上：

| `ENFORCE` 能读取已有限频 Key 并直接返回 `LIMIT` | …单测的**短路顺序断言** |

加上 §5.1 的括号里逐条列了短路省掉什么（「不采集**不查黑名单**」——若短路条件是黑名单命中，
「不查黑名单」这句就无从谈起），可以确定 §7.1 那句是早期草稿的残留。

**定稿**：按 §5.1 实现，短路条件只有限频键命中；§7.1 那一行已改正。
单测把这个口径钉成了调用流水（`limitHitShortCircuits` 断言 journal 恰好是
`[limit.read, limit.write]`），黑名单命中时反而**必须**看到两次采集调用。

**为什么这条值得记**：两处不一致时，实现者很容易挑那句写得**更具体**的（§7.1 明确点名了
「不调用特征端口」），而正确的恰恰是看起来更啰嗦的执行序。设计文档里「算法」与「测试提示」
冲突时，算法优先——测试提示是算法的派生，不是它的补充。

## F-16 短路路径仍然续写限频键，冷却期是滑动的

**首次发现**：批次 3（实现预检用例第 6 步时）

设计 §5.1 只说了短路省掉第 2~4 步，**没说第 6 步（写限频键）走不走**：

```text
1. …命中：记 LIMIT_COOLDOWN，短路，不采集不查黑名单
6. ENFORCE 且 action==LIMIT -> 写限频键（失败记 LIMIT_WRITE_FAILED）
```

第 6 步的条件写的是 `(ENFORCE, action)` 的纯函数，而短路路径上 `action` 正是 `LIMIT`
（`evaluate` 拿着 `limitHit = true` 算出来的）。按字面读，写会发生；按「短路=提前返回」读，
不会。

**定稿：写。** 两个理由：

1. **短路省掉的是第 2~4 步**——第 1 步的括号把范围逐条列了出来（不采集、不查黑名单），
   没有第 6 步。把「短路」扩大解释成「直接返回」是在设计之外加动作。
2. 后果是**冷却期滑动**：持续请求的人不会在冷却期结束时挤进一次「漏网请求」。
   反过来（不写）则是固定冷却：10 秒一到放行一次，那一次请求大概率又越线被限，
   于是形成一个每 10 秒漏一个请求的缝。滑动的代价是每个被限频的请求多一次 `SET`。

这条属于「两种读法都讲得通、实现者必须先挑一个」的决定，它改变的是**安全行为**而不是风格，
所以必须写下来。

**顺带的收益**：`markLimited` 的端口注释本来就写了「幂等：重复写入只是刷新 TTL」——
这一点在短路路径上才真正被用上；若短路不写，那句话只覆盖并发重放一种场景。

## F-17 总开关 `enabled` 只能走 `@Value`，做不成领域 bean

**首次发现**：批次 3（给 `RiskPreCheckUseCase` 接 `enabled` 时）

设计 §4.3 说装配层只需要交两个 bean 出去，理由写得很清楚：`RiskProperties` 在
`dash-infrastructure`，而消费它的用例在 `dash-application`，两个模块之间只有
`dash-domain` 是公共词汇，所以配置必须以**领域类型**的形式过去。

```text
RiskRules riskRules(RiskProperties p)
RiskMode  riskMode(RiskProperties p)
```

但 §5.1 的第 0 步需要 `!enabled`，而 **`enabled` 不在那两个类型里**：它不是阈值表的一部分
（`RiskRules` 是纯阈值快照），也不该塞进 `RiskMode`（把 `enabled=false` 建模成第三个模式值
`OFF`，会让 §5.1 反复强调的「第 0 步与 SHADOW 是两回事」在类型上重新合流，
而且 `RiskMode` 会同时表达「算不算」与「拦不拦」两件事）。

**定稿**：`@Value("${dash.risk.enabled:true}")` 直接进构造器。这不是新发明——
**同一功能域的 `RiskContextInterceptor` 就是这么读的**（`dash.risk.test-context-enabled`
与 `dash.risk.enabled` 两个 key 都在 presentation 侧走 `@Value`），`dash-application` 里
也早有先例（`CacheEvictSupport` 的三个 `@Value`）。

**代价与守卫**：`@Value` 的默认值必须与 `RiskProperties` 的 `@DefaultValue("true")` 一致，
否则「配置里没写」这一个情形会有两种理解。两处默认值现在都是 `true`，靠注释互指维系——
这是本仓库里**唯一一处同 key 双读**，属于既有约定，不是本阶段引入的。

**后续（P9.3）——这条结论被推翻了一半。** P9.3 引入 `RiskPolicy(enabled, mode, failOpen, deadlineMs)`
领域 bean，`enabled` 不再走 `@Value`；`RiskContextInterceptor` 也改成注入同一个 bean。
于是上面那条「同 key 双读、两处默认值靠注释维系」的代价**整个消失了**，全仓只剩
`RiskProperties` 一个默认值来源。

被推翻的只是「做不成领域 bean」这一步。当时只为一个 `boolean` 新建领域类型不划算；
而 P9.3 要新增两个配置项，构造器会涨到 8 个参数——`RiskProperties` 这个类存在的理由原文就是
「若沿用 `@Value`，`RedisRiskFeatureAdapter` 的构造函数要背 9～10 个参数」。
**同一个理由在同一个模块里应当给出同一个结论**，这才是推翻它的依据，不是「后来想法变了」。

**不变的那一半**：`enabled` 仍然不该被建模成第三个 `RiskMode` 值——那会把「算不算」
与「拦不拦」压到一个轴上。`RiskPolicy` 用的是两个**正交字段**，P9.2 §5.1 的三态对照表一个字不用改。
见 P9.3 设计 §3.1、§4.2。

## F-18 黑名单写入工具必须能解封，且解除只能用 `DEL`

**首次发现**：批次 3（扩 `BlacklistKeyTool` 时）

设计 §8 任务 12 只要求「把算键 + 写入收成一个动作」。实现时发现**单向工具在现场不够用**，
而且解除动作有一个不看代码就想错的地方。

**为什么只能 `DEL`**：查询侧 `RedisRiskBlacklistAdapter` 用的是 `EXISTS`——**与键的类型无关**
（这是 P9.2 §4.1 一开始就定下的，也是 Lua 脚本注释里那条「蓝图 §3.8 的『键类型错误』在
黑名单维度不存在」）。所以一个被别的工具 `SET` 成字符串的键，**应用侧同样当成命中**。
此时：

```text
SREM key 1   ->  WRONGTYPE，解不掉   ← 应用还在拦，工具却报错
DEL  key     ->  清掉，两种形态都有效
```

已现场实测（Redis 7.4.11）：`SET risk:bl:user:8888 1` 之后 `EXISTS` 返回 1，
`add` 如实报 `WRONGTYPE` 并退出码 3（**不是**打印一份看着正常的报告），`remove` 正常清掉。
反过来说：写入路径必须让 `SADD` 的类型错误**浮出来**，因为那是唯一能发现
「键被别的工具建成了别的样子」的时刻。

**为什么 `remove` 是必要的而不是顺手加的**：试错成本不对称。算错键去 `SADD` 的后果是
**静默不生效**（本模块反复出现的那类故障）；算错键去 `DEL` 的后果是**静默不解除**——
用户还在被拦，而运维以为已经放行了。两个方向都需要工具把键算对，
所以「算键」这件事一个方向都不能少。此外 §7.2 的 IT 要断言「黑名单删除后不再拦截」，
P9.5 的压测也要反复种/撤黑名单。

**附带的两条**：
- `add` 前先算键、后连 Redis，维度写错、`userId` 不是数字都在**打开连接之前**报错；
- 报告里必须出现**实际连的那个端点**（`DASH_REDIS_HOST` / `DASH_REDIS_PORT` 可覆盖）。
  写死默认端口的话，一份照着复制的 `redis-cli` 命令在生产上会打到本机 Redis——
  语法合法、执行成功、只是黑名单没生效。

## F-19 `deadline-ms: 10` 在真实并发下约等于全程空转——它是覆盖率参数，不是延迟调优项

**首次发现**：批次 4（跑 `RiskDegradeConcurrencyIT` 与 `RiskGrabLinkIT` 的 SHADOW 上下文时）

`dash.risk.deadline-ms` 从 P9.3 起就是生产默认值 `10`，测试 yaml 与主 yaml 一致。它读起来像
一个延迟上限（「预检最多花 10ms」），**但它在真实负载下的实际效果是「一次采集都不做」**。

**第一次撞见：2000 并发下的每一行都是降级行。** `RiskDegradeConcurrencyIT` 用
`deadline-ms=0` 跑 2000 并发（那是显式配置），同一批日志里把默认值下的形态也照出来了：

```text
risk_decision userId=941936 ... action=PASS riskScore=0 matchedRules=- degraded=true degradeReasons=DEADLINE_EXCEEDED decisionLatencyMs=0
risk_decision userId=941937 ... action=PASS riskScore=0 matchedRules=- degraded=true degradeReasons=DEADLINE_EXCEEDED decisionLatencyMs=0
（… 2000 行，没有一行不是 degraded=true）
```

注意 `decisionLatencyMs=0`：**预检自己没花时间**，它是**一步都没走**就退出了。
不是「跑了 10ms 然后超时」，是「第一个检查点就没通过」。

**第二次撞见：一次冷启动请求吃了 15ms。** `RiskGrabLinkIT` 的 SHADOW 上下文里，四个账号
依次抢单，设备集合应当攒到 4 个成员，实测只有 3 个。查决策行：

```text
risk_decision userId=930100 ... action=PASS degraded=true degradeReasons=DEADLINE_EXCEEDED decisionLatencyMs=15   ← 第一个请求
risk_decision userId=930101 ... action=PASS degraded=false decisionLatencyMs=2
risk_decision userId=930102 ... action=PASS degraded=false decisionLatencyMs=0
risk_decision userId=930103 ... action=PASS degraded=false decisionLatencyMs=1
```

**新 Spring 上下文的第一个请求 15ms**（连接池冷启动），整段采集被跳过，集合少一个成员。
后面三个都是 0~2ms。

**为什么 10ms 不够**：预算是**协作式**的（D5），每步之前检查余额。一次 ENFORCE 预检的采集链
是「用户窗口 1 次 Lua 往返 + 集群 1 次 Lua 往返」，每次往返在共享 Redis 客户端上都要排连接；
而 2000 并发抢一个名额时连接池本身就在饱和。10ms 这个数字是按「正常负载下单次往返」估的，
没有把排队算进去。

**关键推论（这条才是要记的）**：`deadline-ms` 决定的是**采集覆盖率的量级**——
调它是在调「有多少比例的请求真的做了风控」，不是在调「快多少」。
取值必须对着**预期并发量**定，而不是对着单次往返的耗时定。

**对 P9.5 的直接影响**（蓝图 §3.10「先观察一段真实流量再切 ENFORCE」）：
如果观察窗口内绝大多数决策行都是 `degraded=true`，那么观察到的**风险分布是失真的**——
「没发现异常流量」可能只是因为压根没采集。所以 P9.5 的离线统计**必须**把
`degraded=true` 的行单独拆出来计入 `risk_degraded_total`，并在报告里先给出降级比例，
再给出风险动作分布；否则那份报告会读起来像「风控跑了且很干净」。
`degraded` 与 `degradeReasons` 本来就在 `risk_decision` 行里（P9.2 D8 定的字段契约），
现在多了一个非用不可的理由。

**顺带一条口径提醒**：`SHADOW` 下 `action` 恒为未生效值，但 `degraded` 是**照常记录**的
（降级与模式正交）。所以「SHADOW 观察期」里同样要先看降级比例。

**防回归**：
- `RiskDegradeConcurrencyIT` 用 `deadline-ms=0` 把这条钉成**确定性**行为——预算为 0 时
  `risk:win:*` 零新增，且抢中者本人的窗口键必须不存在（反证：他确实走完了整条链路）；
- `RiskGrabLinkIT` 的 SHADOW 上下文**显式放宽到 1000**，并在类注释里写明原因，
  免得后人以为那是「让用例更容易过」。

## F-20 worker 的定时任务在启动瞬间就跑第一次——单测会污染集成测试库

**首次发现**：P9.4 批次 1（跑 `mvn -o clean test` 做批次收尾时，5 个 IT 报 `CREDIT_TOO_LOW`）

`dash-worker` 的五个 `@Scheduled` 任务全部写成 `fixedDelayString` 或 `cron`，**没有一个带
`initialDelay`**。Spring 对 `fixedDelay` 的语义是「上一次结束到下一次开始之间隔这么久」，
它不推迟**第一次**——第一次在上下文启动的瞬间就执行。

于是「把间隔放大」这个最自然的配置层防御**完全无效**：

```yaml
# dash-worker/src/test/resources/application.yaml   ← 我先写成了这样，是错的
timeout:
  scan-interval-ms: 3600000   # 以为等于「启动后不再触发」
```

一小时只推迟第二次。第一次照跑。

**实测的污染量**（一次普通的 `mvn -o -pl dash-worker test`）：

```text
credit_score   0 → 1     行：user_id=930103, score=55
credit_event   0 → 1     行：GRAB_TIMEOUT_REVERT  delta=-5  ref=ERRAND 224164447676010496
local_message  PENDING 82 → 78
```

`TimeoutScanJob` 扫到了共享库里上一轮 IT 留下的超时任务，按 `GRAB_TIMEOUT_REVERT` 扣了
抢单人 5 分；`LocalMessageRetryJob` 处理掉 4 条 PENDING。**`930103` 落在 `RiskGrabLinkIT`
的 id 段（`USER_BASE = 930_000L`）里**——worker 扣的是别的测试类正在用的用户。

**为什么这次特别难查**：失败的表现与原因**不在同一个模块、也不在同一次运行里**。

```text
第 N 次  mvn test   →  单测绿（worker 扣分，没人断言）
第 N+1 次 mvn test   →  dash-bootstrap 里 RiskGrabLinkIT 抢单被 CREDIT_TOO_LOW 拦住
                        失败现场看不出任何与 worker 有关的东西
```

判断依据只能从执行顺序反推：出错的 `RiskGrabLinkIT$Enforce` 在日志第 700 行、
`TimeoutTransferIT` 在第 861 行，而唯一会洗 `credit_score` 整表的 `CreditIT`
（`@AfterEach` 里 `DELETE FROM credit_score`）在第 3067 行——**洗表发生在它们之后**，
所以那些低分是跑之前就躺在库里的残留。同一条命令重跑三次全绿，也说明它不是当次代码造成的。

**修法**：测试侧换掉调度器，不碰生产 wiring。`dash-worker` 测试源里新增
`NoScheduling`（`@TestConfiguration`），提供一个 `schedule*` 全部返回「一年后才完成的空
future」的 `TaskScheduler`。bean 名必须叫 `taskScheduler`——Spring Boot 的
`TaskSchedulingAutoConfiguration` 用 `@ConditionalOnMissingBean` 看着这个名字，见到就退让，
上下文里只剩这一个，`@EnableScheduling` 必然挑中它。

**它挡不住 `@PostConstruct`**，两个开关各管一段：

| 启动即执行的东西 | 挡它的是什么 |
|---|---|
| 五个 `@Scheduled` 任务 | `NoScheduling`（换调度器） |
| `BloomRebuildJob.rebuildOnStartup()` | 测试 yaml 的 `dash.cache.bloom-enabled: false` |
| 四个消费者的 `@PostConstruct` | 测试 yaml 的 `dash.mq.enabled: false` |

**为什么不在 `@ComponentScan` 上排除那五个 job**：它们是 `com.campusdash.worker` 包下的
`@Component`，测试要排除只能往 `WorkerApplication` 的扫描过滤上加——那是**改生产装配**。
D-5 的排除过滤是另一回事：那条在测试与生产里都成立，是设计本身要的。

**防回归**：`WorkerApplicationContextTest.schedulingIsDisabled()` 断言上下文里的
`taskScheduler` bean 就是 `NoScheduling.NeverFiresTaskScheduler`。谁把 `classes = {...}`
里的 `NoScheduling` 去掉，这条当场红，而不是等到某天别的 IT 莫名失败。**没有覆盖损失**：
`dash-worker` 的测试里没有任何一条用例调过这五个 job。

## F-21 三种**不换行**的 Unicode 空格穿过 `LogField.safe`，但 Python 的 `str.split()` 认它们是分隔符

**首次发现**：P9.4 批次 2（写 `LogFieldTest` 的 `U+2028` / `U+2029` 用例时，顺手把「Python 到底认哪些字符是分隔符」整张表跑了一遍）

D13 把净化范围定成 `Character.isISOControl(c) || Character.isWhitespace(c)`。这个谓词挡住了
`U+2028` / `U+2029`——它们不是 ISO 控制字符，但 Python 的 `splitlines()` 认它们是换行，
漏掉就能凭空多出一整行。**同一张表上有另外三个码点只当分隔符、不当换行**，于是从两个条件的
中间穿了过去：

| 码点 | 名字 | Java `isWhitespace` | Java `isISOControl` | Java `isSpaceChar` | Python `split()` 切开 | Python `splitlines()` 切开 |
|---|---|---|---|---|---|---|
| `U+00A0` | NBSP（不间断空格） | false | false | true | **true** | false |
| `U+2007` | FIGURE SPACE | false | false | true | **true** | false |
| `U+202F` | NNBSP（窄不间断空格） | false | false | true | **true** | false |
| `U+2028` | LINE SEPARATOR | true | false | true | true | true |
| `U+2029` | PARAGRAPH SEPARATOR | true | false | true | true | true |
| `U+3000` | IDEOGRAPHIC SPACE | true | false | true | true | false |
| `U+200B` | ZWSP（零宽空格） | false | false | **false** | false | false |

（表格是实测结果，不是查文档抄的：Java 侧逐码点打 `isWhitespace` / `isISOControl` / `isSpaceChar`，
Python 侧打 `len('aXb'.split()) > 1` 与 `len('aXb'.splitlines()) > 1`。`U+200B` 那行是**反面样本**：
它在 Java 三个谓词上全为 false、确实穿过了净化，但 Python 也不拿它当分隔符，所以它**不需要**补 ——
补谓词时不能顺手用「把 Unicode 空白全挡上」这种说法。）

**为什么这与 D13 要堵的东西完全同类**：D13 的威胁模型是「客户端可控的自由文本在日志行里
伪造出一个字段」。`X-Request-Id` 的值里塞一个 `U+00A0` 不需要任何特殊编码——HTTP 头按
Latin-1/UTF-8 传字节，`String` 里就是那个码点。渲染出来是这样：

```text
risk_decision ... requestId=x<NBSP>action=BLOCK ...
```

人眼看是「一串奇怪的空白」，而 Python 侧 `line.split()` 之后拿到的是一个**干净的
`action=BLOCK` token**——正是 `LogFieldTest.spacesAreNeutralizedToo()` 里那条
「客户端伪造不出一个字段」要防的事。反过来说，现在 `U+0020` 被挡而这个洞开着，
闸门的形状就是「挡得住普通空格、挡不住等价空格」，这种半开比全开更容易被当成已修好。

**为什么当时没顺手改**：设计 D13 只写了「空格一并替换为 `_`（控制字符的处理不变）」，
**没有点名谓词**——把范围写死的是 `LogField.isNeutralized` 的注释（「范围取
`Character#isWhitespace` 而不是字面的「ASCII 空格」，多出来的部分不是顺手扩大」），
而那句话是实现期自己写的。于是「`U+00A0` 算不算 D13 说的空格」成了一个**口径问题**：
口径取「ASCII 空格 + Python 认作换行的字符」，当时的实现就是对的（它正是这么写的）；
口径取 D13 自己写的威胁模型「指标不得被外部输入伪造」，就差这三个码点。
两种口径都能自圆其说，而选哪个会改变一条**已交付**日志的输出，所以按本仓库的规矩
（对已批准设计的偏离要明说）只记录、不动手。

**定稿**（2026-09-11 拍板）：**按威胁模型取齐，补上 `isSpaceChar`**。判据是 D13 的正文
写的正是「指标可被外部输入伪造」，而 NBSP 能达到同样的效果——留这个口子等于让这道闸
「挡得住普通空格、挡不住等价空格」，而这种半开比全开更容易被当成已修好。

```java
private static boolean isNeutralized(char c) {
    return Character.isISOControl(c)          // 换行、回车、制表……
            || Character.isWhitespace(c)      // ASCII 空格 + U+2028 / U+2029 / U+3000
            || Character.isSpaceChar(c);      // 补 U+00A0 / U+2007 / U+202F（不间断空格一类）
}
```

选 `isSpaceChar` 而不是「码点 ≤ 0x20 或自己维护一张表」：它恰好覆盖三个洞，且对
**真正切不开的 `U+200B`（ZWSP）为 false**——不会把造不出危害的字符一并换掉。
**改动只落在 `isNeutralized` 一处**（快慢两条路径都调它），不涉及任何调用点，
也不改日志格式与已冻结的字段顺序。

**防回归**：`LogFieldTest.nonBreakingSpacesAreNeutralized()` 逐码点断言三个值都被换成 `_`，
并留一条**反面样本**（`U+200B` 必须原样穿过）——谁把谓词改成「把 Unicode 空白全挡上」，
反面样本那条当场红。**这条洞此前不会自曝**：改前 8 条用例全绿，
`RiskEventPublishLogTest.requestIdWithSpacesIsNeutralized()` 也绿——它用的是普通空格。

**顺带一条写作坑**（本阶段第二次踩）：往测试里写这些不可见码点时，我原意是写转义序列
`\uXXXX`，实际落进文件的却是**原始字符**。两者在编辑器和 diff 里长得一模一样
（原始 NBSP 与普通空格也几乎一样），肉眼分不出来，而注释还写着「用转义写」——
注释本身成了假话，这是比测试失败更糟的失效方式，因为没有任何东西会红。
改法是拿 Python 按码点做字节替换（`chr(cp).encode('utf-8')` →
`('\\u%04X' % cp).encode('ascii')`），改完再数一遍剩余裸码点——六个全清零才算改完。
**唯一可靠的验收方式是按字节数，不是看屏幕。**

**⚠ 2026-09-12 第三次踩（P9.4 批次 4，`RiskEventPayloadTest`）**：往 `requestId` 夹具里写
「`U+2028` 与 `U+0001` 的转义序列」时，落进文件的又是两个**原始码点**（字节 `342 200 250`
与 `\001`），而 `javac` 与用例全绿、编辑器里也看不出区别。**这次是上面那条按字节验收的
方法逮住的**：扫描脚本报出两个裸码点，于是改成 `(char) 0x2028` / `(char) 0x0001` 两个纯 ASCII
常量，注释里也写清「为什么不写成转义写法」。结论比上一次更硬：**只要你打算写这些码点，
它就会再发生一次**——唯一稳的写法是用码点构造它们，而不是「这次小心点」。

## F-22 一个 `Producer` 拿到的是一条 gRPC 通道 + 一组线程池，不是「共享连接上的多路复用」

**首次发现**：P9.4 批次 3（写 `RocketMqConfig.riskEventProducer` 的注释时，用 `javap` 把 `rocketmq-client-java 5.2.0` 的持有关系逐层拆了一遍）

设计 §4.5 里那段话**一句话内部自相矛盾**：

> `RocketMqConfig` 不需要新 bean：生产者复用既有的 `timeoutProducer` 吗？**不。**……**给风险事件单独一个 `Producer` bean**：一个 topic 一个 producer 是仓库既有的做法（`RocketMqFundEventAdapter` 就为事务消息单独建了一个）。

前半句「不需要新 bean」，后半句「单独一个 `Producer` bean」。**结论取后者**（2026-09-11 已拍板：加新 bean + 给两个既有适配器补 `@Qualifier`），但**两条理由都要更正**：

**（1）「一个 topic 一个 producer」是错的归纳。** `timeoutProducer` 一个 producer 服务两个 topic：
`RocketMqDelayMessageAdapter`（`errand-confirm-timeout`）与 `RocketMqCacheEvictAdapter`
（`errand-cache-evict`），后者的类注释还专门写着「两者不能混用同一个 Producer 但可以共用普通 Producer」。
`RocketMqFundEventAdapter` 单独建 producer 也不是因为「一个 topic 一个」，而是
**事务消息的 `TransactionChecker` 只能在 `ProducerBuilder` 构建时注册**——那是硬需求，不是惯例。
仓库真实的惯例是「按**用途**分，不按 topic 分」。

**（2）真正的机制在客户端实现里。** `javap` 逐层拆 `rocketmq-client-java 5.2.0`：

```text
ProducerImpl   extends  ClientImpl                          // 字段 clientManager 是 final，每实例一个
ClientImpl     →  ClientManagerImpl(Client)                 // 构造参数就是宿主 client
ClientManagerImpl  →  Map<Endpoints, RpcClient> rpcClientTable   // 外加自己的 scheduler 与 asyncWorker
RpcClientImpl      →  ManagedChannel channel                // 一条 gRPC 通道
```

即**每个 `Producer` 自己持有一条 gRPC 通道与自己的回调线程池**，不存在「多个 producer 复用一条连接」
这回事。所以复用与不复用的差别是实打实的资源隔离，而不是「省一条连接」。取舍于是收成一句话：
让**允许丢的遥测**（风险事件自己带着队列满即丢、闸门抑制、发送失败只记日志三条衰减路径）
与**不可丢的正确性消息**（超时流转、延迟双删）共用一条通道和一组回调线程，值不值那一条连接。
答案是不值。

**顺带一个副作用（如实记，不当作缺陷）**：`RocketMqConfig` 在
`com.campusdash.infrastructure.config`，而 `WorkerApplication` 的 `excludeFilters` 只排了
`application.risk` 与 `infrastructure.risk` 两个包——所以 **worker 进程也会建出这个
`riskEventProducer`**，而它一个风险事件都不会发（`RocketMqRiskEventAdapter` 本身被排除了）。
代价是一个用不到的 Producer 与它那条连接。要消掉的话，把这个 `@Bean` 挪进
`infrastructure.risk` 下的一个 `@Configuration` 即可（那个包被 worker 排除），
代价是与 `NoopRiskEventAdapter` 放 `infrastructure.config`（设计 §4.5 定的）不对称。
**本阶段按拍板的形态保留**，这一条留作后续可选整理项。

**2026-09-12 首次真实启动（生产配置）的实测结果**：worker 正常启动（`Started WorkerApplication in 1.919 seconds`），
六个消费者全部就绪，23 条应用日志、**0 条 WARN/ERROR**；但**这个多用到的 `Producer` 在日志里完全不可观测**——
`org.apache.rocketmq` 客户端不输出 INFO 行、gRPC 通道也不打印。SIGTERM 后的线程转储里只剩 3 个客户端索引
（`RocketmqClientScheduler-N-*` / `RocketmqClientAsyncWorker-N-*`，此时关停钩子已关掉了别的消费者），
而客户端按创建顺序编号、与 bean 无法一一对应，**不构成「多了一个客户端」的证据**。所以这一条的性质没有变：
它仍是**代码事实**（`riskEventProducer` 在 `infrastructure.config`，不在 worker 排除的两个 `risk` 包里），
**没有运行时断言**，也没有日志旁证。

**防回归**：无——它是事实说明，不是一个能被断言的状态。真正需要它的地方是**下一个想
「顺手复用一个 Producer」的人**：那段 javadoc 与本节是唯一的拦阻。

## F-23 设计 §5.4 说 `outcome` 由 `denied()` 决定，§3.3 说它与 `decisionAction` 冗余——取 §3.3

**首次发现**：P9.4 批次 3（写 `RiskPreCheckResult.toEvent` 时，按 §5.4 逐字落笔会产出**自相矛盾的载荷**）

同一份设计文档里两处口径不一致：

- **§3.3（字段契约）**：`RiskOutcome` ……「本轮它与 `decisionAction` 之间**可由
  `decisionAction == PASS` 推出**，是一个冗余字段」。
- **§5.4（装配步骤）**：「`outcome` 由 `result.denied()` 决定（`DENIED`/`PASSED`）」。
- **§11 验收表**照 §5.4 写：「`denied()` 为真 → `DENIED`；`degraded` 但放行 → `PASSED` 且 `degraded=true`」。

`denied()` 的定义是 `unavailable || effectiveAction() != PASS`，而 `effectiveAction()`
在 `SHADOW` 下恒为 `PASS`。两条规则于是在两个场景上**给出相反的值**：

| 场景 | `denied()` | `decisionAction` | §5.4 给出 | §3.3 给出 |
|---|---|---|---|---|
| SHADOW 下算出 BLOCK | false | BLOCK | `PASSED` | **`DENIED`** |
| 预算耗尽 + `fail-open=false` + 决策 PASS | true | PASS | `DENIED` | **`PASSED`** |

两种口径都能自圆其说——「这次请求挡没挡住」对 `denied()`，「决策算出了什么」对
`decisionAction`——**取 §3.3**，四条理由：

1. §3.3 是**字段契约**那一节，直接说了这个字段与 `decisionAction` 冗余；§5.4 只是一句散文。
2. `RiskEvent` 的 `@param outcome` 也写着「本轮与 `decisionAction` 冗余」。两处对一处。
3. `SHADOW` 的**全部产出**就是这批事件（真实流量的决策分布），而 §5.4 的规则会让 SHADOW 期间
   每一条 BLOCK 载荷都长成 `decisionAction=BLOCK outcome=PASSED`——一份自相矛盾的载荷，
   且恰好出现在最不能出错的那一段时间。
4. `unavailable` 那格同理：「风控没给出结论」已经由 `risk_decision` 行的
   `degraded=true degradeReasons=DEADLINE_EXCEEDED` 与调用方拿到的 `RISK_UNAVAILABLE`
   表达清楚了，再让载荷里 `outcome=DENIED` 与 `decisionAction=PASS` 打架只是多造一处矛盾。

**实现**：`RiskPreCheckResult.toEvent` 里 `decision.action() == PASS ? PASSED : DENIED`。
连带 `RiskPreCheckResultTest` 里的两条断言，它们与既有那批「三态」用例并列。

**防回归**：`RiskPreCheckResultTest` 两条**成对**的反例——
`shadowEventIsDeniedEvenThoughTheRequestIsAllowed()`（`denied()==false` 但必须是 `DENIED`）
与 `unavailableEventIsPassedEvenThoughTheRequestIsDenied()`（`denied()==true` 但必须是 `PASSED`），
外加 `GrabErrandUseCaseTest.shadowGrabPublishesTheComputedBlock()` 在**接入点**上再钉一次。
**成对是刻意的**：只留一条的话，另一种写法（照直觉或照 §5.4 写）也可能碰巧通过。

## F-24 自纠：`RiskEventPublishLog` 注释里「本仓库没有日志捕获依赖」是错的

**首次发现**：P9.4 批次 3（写 `RocketMqRiskEventAdapterTest` 时，本打算沿用「格式做成纯函数」那条路，先核了一遍依赖树）

批次 2 写 `RiskEventPublishLog` 时留下过一句注释：

> `format` 单独拆出来是为了能在单测里断言整行文本——**本仓库没有日志捕获依赖**，把格式做成纯函数是唯一不引依赖的测法。

**这句是错的**，而且错得关键——它把一个「其实做得到」的测法说成了做不到。实测三件事：

```text
mvn dependency:tree -pl dash-infrastructure   →  ch.qos.logback:logback-classic:1.5.21  [compile]
                                                 ch.qos.logback:logback-core:1.5.21     [compile]
                                                 （经 spring-boot-starter-logging 传递）
javap ch.qos.logback.core.read.ListAppender   →  public java.util.List<E> list;        ← 可直接赋值
find . -name 'logback*.xml'                   →  （空）
```

合起来：`dash-infrastructure` 的 **compile** classpath 上就有 `ListAppender`，**不用加任何依赖**；
它的 `list` 字段是 `public` 的，可以直接换成 `CopyOnWriteArrayList`；而全仓没有任何
`logback*.xml`，所以 root logger 是默认的 DEBUG，INFO **一定**会到达挂上去的 appender。

**为什么这不只是「一句注释写错」**：`RiskEventPublishLog` 的四个取值里有两个
（`SENT` 与 `SENT_GATE_FAILED`）在假 `Producer` 上留下的痕迹**完全一样**——两者都真的调了
`sendAsync`——而它们的区别正是 D8 的全部内容；`publish_failed` 更是只在 `CompletableFuture`
的回调里产生，没有任何其他可观察副作用。也就是说**不捕获日志就测不了 D8**，
而那句注释会让下一个人以为只能不测。`RocketMqRiskEventAdapterTest` 因此改用 `ListAppender`
覆盖 §8.1 那五条性质。

**它带来两个新要求**（都写进了测试的类注释）：

1. **跨线程可见性**：默认的 `ArrayList` 在执行器线程写、测试线程读，没有 happens-before，
   必须换成 `CopyOnWriteArrayList`，否则表现为随机红。
2. **前置守卫**：`@BeforeEach` 里先 `assertTrue(publishLogger().isInfoEnabled(), "前提不成立：…")`。
   将来谁加了一个 `logback.xml` 把级别调高，本类会**安静地捕获到空列表**，然后每条断言都以
   「行数不符」的形式报出来——那个报错指向被测代码，而真正的原因是日志级别。

**防回归**：那条前置守卫本身就是。**注意这不是「测试写得不好」，是注释写错导致的选型错误**——
所以它进本文件而不是只留在测试注释里。**那句原注释已按本节更正**：`format` 仍然留着，
但理由改成了「让『格式』与『何时打这一行』两件事可以分别断言」，不再是「唯一不引依赖的测法」。

## F-25 我提的 `eventId` 不变式比设计更强，裁决为**只堵一个方向**

**首次发现**：P9.4 批次 3（汇报时提请裁决：设计没写这条不变式，是我加的）

设计**没有**要求 `eventId` 与 `producesEvent()` 同真同假。§5.4 那句
「若 `decision.producesEvent()` 则生成一个 `UUID.randomUUID().toString()`，否则为 `null`」
说的是**用例的行为**，不是值对象的约束。我把它写成了构造器里的一条不变式，
而且是**双向**的：`(eventId != null) != decision.producesEvent()` 就抛。

两个方向坏起来的样子确实不同（这是当初写双向的理由，仍然成立）：

- **为空而判据为真** —— 调用方拿 `null` 去建 `RiskEvent`，`RiskEvent` 的紧凑构造器当场抛。
  那次抛落在**投递点**上，也就是一次抢单请求的路径上；真正的错误却在分配那一刻。
- **非空而判据为假** —— 日志行报出一个**永远不会存在**的事件 id，P9.5 的关联对着它去找
  一条没有的载荷，而「找不到」只会被读成「投递丢了」：一个逻辑错误被记成一次传输故障。

**裁决：只堵前者。** 后者那种形态本身并不矛盾，而拦它等于把「**先分配 id 记 trace，
再决定不发**」一并禁掉——那是将来最可能想加的一种形态。这条方向上的守卫改放在
`toEvent`：不产生事件的决策，一个事件都交不出来。

**连带改了一处，是我的判断，如实记**：`toEvent` 的守卫从 `eventId == null` 改判
`!decision.producesEvent()`。两个方向必须由**同一条判据**说了算，否则被放行的那种形态
会**静默交出一个没人要的事件**，而 `toEvent` 的报错信息「`producesEvent()` 为假时调用方
不该走到这里」会变成一句假话。今天这个改动没有行为差别（分配本来就跟着判据走），
差别全在将来。

**影响面**（三处注释 + 两条用例）：`RiskPreCheckResult` 的 `@param eventId`、
紧凑构造器注释、`toEvent` 的 `@throws`；`GrabErrandUseCase.publishRiskEvent` 里
「两者由构造器不变式保证同真同假，写哪个都对」那句删掉（它已经不成立）；
`RiskPreCheckResultTest` 的 `eventIdMustBeNullWhenNoEventIsProduced` 改写成
`anIdWithoutAnEventIsAllowedButNotDeliverable`。

**防回归**：`anIdWithoutAnEventIsAllowedButNotDeliverable` 同时断两件事——
**构造不抛**（`id` 原样留着）与 **`toEvent` 抛**。前半条锁的是**不变式的边界本身**：
将来谁觉得「这个方向也该堵」，会在这一条上红，从而被引到本节的裁决。

## F-26 消费侧不建中间 record；生产端 `payloadOf` 改 `public`

给它一个公开入口，这条性质就由**构造**保证。

### 一、第五条行加 `reason=` 短码（设计只给了字段名）

§6.2 只给这条行定了 `error` 与 `deliveryAttempt` 两个字段，而 `error` 按同族的
`risk_event_publish_failed` 只能是**异常类名**。问题是解析失败时那个类名**恒为同一个**
（下面第二条就是它），于是「缺字段」「数字非法」「引号不配」「枚举名不认识」「内容自相矛盾」
五种完全不同的坏法在日志上一模一样——一条永远无法归因的 `risk_event_invalid`，
在 P9.5 的报告里只能表现为一个计数，而排查的人要知道的是「生产端改了格式」
还是「有人往 topic 里灌了别的东西」。

**裁决（2026-09-11）：加一个短码**，落在新的 `RiskEventInvalidReason` 上，五个值：
`MISSING_FIELD` / `BAD_NUMBER` / `MALFORMED_JSON` / `UNKNOWN_ENUM` / `INCONSISTENT_EVENT`。
（选项里我举的例子是 `unbalanced_quote`，实现时定名 `MALFORMED_JSON`：它还要覆盖
「对象没闭合」「对象之后还有内容」「出现了子集之外的记法」，按具体坏法命名会立刻不够用。
枚举名原样进日志，**是离线脚本要匹配的字面量，改名等于改协议**，新值只能追加在末尾。）

不用异常消息代替短码：解析器自己的消息里带着它正在解析的那段 JSON——`requestId` 就在里面。
§6.2 明确「不打印原始 body」，所以能进日志的只有**类型**与**这个枚举值**。

### 二、生产上那一行是 `error=Invalid`，不是 `error=IllegalArgumentException`

这条是实现期才看出来的，而且**第一次读日志的人多半会当成 bug**：解析器抛的是
`IllegalArgumentException` 的**子类** `RiskEventPayload.Invalid`（子类是这个短码的载体），
而日志取的是**实际异常的类名**。于是生产上跑出来的是：

```
risk_event_invalid error=Invalid reason=MALFORMED_JSON deliveryAttempt=1
```

`error=Invalid` 不含任何归因信息——**归因完全落在 `reason=` 上**，这反过来加强了上面那条
裁决：没有短码的话，这一行就只是一句「有东西坏了」。注意
`RiskEventConsumeLogTest.invalidLineMatchesSpecExactly` 里的 `error=IllegalArgumentException`
演示的是「随便一个 IAE 进来会渲染成什么」，**不是生产上的取值**；生产上的取值由
`RiskEventProcessorTest.malformedPayloadIsAckedWithAnInvalidLine` 逐字断言。

### 三、`lagMs` 为负时「保留原值」指的是 `occurredAt`

§6.2 第 2 步写的是「`lagMs = now - occurredAt`，负数按 `0` 记并保留原值」。歧义在
「保留原值」的宾语：是 `lagMs` 还是 `occurredAt`？实现按**后者**读——`lagMs` 夹到 `0`，
`occurredAt` 是数据、照原样打印，理由是「漂移了多少」必须留得下来：它就是
「事件时刻 vs 行自身的日志时间戳」，而 P9.5 的 P99 延迟要的正是这两个时间的关系。
夹取动作落在 `RiskEventConsumeLog.format` 里而不是调用点：调用点只该回答「现在几点」，
把「读哪个时钟」与「怎么呈现」分开，格式锁测试也就顺带把夹取一起锁住了。

**防回归**：`RiskEventConsumeLogTest` 的 `reasonValuesAreFrozen`（五个值与声明序）、
`everyReasonRendersDifferently`（五个值两两渲染不同）、`negativeLagIsClampedButOccurredAtIsKept`、
`zeroLagRendersAsZero`（零延迟渲染成 `0` 而不是 `-`——夹取最容易顺手写成「≤0 当缺失」）；
`RiskEventProcessorTest.malformedPayloadIsAckedWithAnInvalidLine`（逐字断 `error=Invalid`）。

## F-28 `RiskEventProcessor` 的两个 `try` 块不能合并，且补了一行设计没有的 `log.error`

**首次发现**：P9.4 批次 4

§6.2 的四步里，第 4 步是「捕获 `IllegalArgumentException` → 记 `risk_event_invalid` 行 +
`SUCCESS`（D10）；其余异常 → `FAILURE`」。按字面读，最省事的写法是把四步全放进一个
`try`、`catch (IllegalArgumentException)` 写在前面。那样有一个不好看见的坏处：
**判据是异常类型**，所以一次可重投的处理失败只要恰好也抛 IAE，就会被静默 ACK 掉——
比多写一行 invalid 日志严重得多。

所以实现成两块：**解析单独一块**（这一块里的 IAE = 消息本身坏了，丢弃），**解析之后的
任何异常**都当作「这次处理没成功」（交给 broker 重投）。代价是「解析之后抛出的 IAE」
会走重投而不是走 invalid 行——这是刻意的：那时坏的已经不在消息上了。

**第二件事：补了一行 `log.error`。** 设计只说「其余异常 → `FAILURE`」，没说这一路上要不要
留痕迹。不留痕迹的后果是：一次处理失败在日志上**完全没有**记录，只有 broker 的重试计数
会涨，而那个计数三次之后就不见了（D11）。它只带 `eventId` 与 `deliveryAttempt`，两者都是
应用自己生成／框架给的值；**不带 body**，与另外几条行同一条理由（`requestId` 在 body 里）。
这条日志**不是设计里的五条行之一**：§8.3 的脚本按 `risk_event_` 前缀定位，
所以它不会被计进任何指标。

**一个可注入接缝，顺带说明**：这个类的唯一依赖是时钟，而「时钟坏了」正是让 `FAILURE`
这条路可测的方式（本类没有别的可注入依赖，失败必须来自某处）。`reasonOf` 的兜底那一支
从 `process` **走不到**（解析器抛的每个 IAE 都是它自己的 `Invalid`），所以它被放开成
包级可见、由测试直接调——一段永远不会被执行的兜底代码等于没有兜底。

**防回归**：`processingFailureAsksForRedelivery`（`FAILURE` + **零条消费行**）、
`failureLogCarriesNoBody`、`unknownIllegalArgumentFallsBack`、`carriesNoStorageDependency`
（D12 的结构性断言，含**正对照**：判据真的认得出 `StringRedisTemplate` / `JdbcTemplate`，
否则一个恒为 false 的判据会让这条用例以全绿的形式失效）。

## F-30 端到端用例的归属：「测试 JVM 收到消息」不等于消费者跑过；真 worker 当子进程后，库必须隔离

**首次发现**：P9.4 批次 5（写 `RiskEventIT` 时）

设计稿写的是「`RiskEventIT` 必须住在 `dash-worker`」。前提成立（`dash-bootstrap` 的 pom 不依赖
`dash-worker`），但结论下早了：不必把用例搬去一个连 HTTP 脚手架都没有的模块。落地时先按
「住 bootstrap，只断言测试 JVM 里的观察者消费者收到消息」试了一版，那个判据有个洞——

**bootstrap 的上下文里没有 `RiskEventConsumer`**（它不在扫描路径里）。所以「收到消息」只证明
broker 上有一条消息，**不证明消费者执行过**；而这个阶段的验收项写的是「风险事件可以正常发送
**和消费**」。`local_message` 那次事故是同一形状、方向相反：那边是本地日志写了而消息没发出去；
这边是消息发了而消费者可能压根没跑。两者都能让一份「端到端」报告全绿。

**处理**：把真 worker 当**子进程**跑（`java -jar dash-worker/target/dash-worker-*.jar`），
消费行从子进程的日志文件里读，两个进程靠同一个 `eventId` 串起来。于是用例仍住 `dash-bootstrap`
（HTTP 脚手架与被测应用的上下文在那里），而「消费」这件事有了**另一个进程**作为观测面。
三条证据的分工（发布行 / broker 载荷 / 消费行）写在设计 §8.2。

**子进程翻出的第二件事**：它按**生产 yaml** 装配（只覆盖 `--spring.datasource.url` 一项），
所以五个 `@Scheduled` 任务启动即跑、四个 worker 消费者真连 broker。0c 的 `NoScheduling` 是
`@TestConfiguration`，只对**同 JVM** 的上下文生效，**管不到另一个进程**。于是落库的唯一防线是
**库隔离**：子进程被钉在 `campus_dash_worker_it`；库不存在 → 整类跳过并打印创建配方，
**不自动建库**——自动建会把「忘了建库」变成一条发生在别处的假绿。
这与 F-20 同源（真 worker 写共享 IT 库，实测扣掉 `RiskGrabLinkIT` 用户的信用分），
区别只在 F-20 是人在命令行拉的进程，这次是自动化用例自己拉的。

**Redis 隔离不了**：6380 只有一份，子进程与测试 JVM 共用。本用例涉及的键都带用户/实例前缀，
用例内也 `purgeUser` / `purgeEventGates` 清过，所以实际不冲突——但那是**互不重叠**，不是隔离。
边界写在这里，免得后来人据此以为「子进程碰不到我的键」。

**防回归**：`RiskEventIT` 的守卫里有两条本类独有的前置——隔离库存在、worker 的 jar 存在且不过期
（`WorkerSubprocess.jarReady()`），不满足即跳过；设计 §10 的验收表里对应「真 worker 进程（子进程）
也不写共享 IT 库」那一行。**自动化的部分到此为止**：「子进程真的没写共享库」仍靠一次手工比对
计数（`errand` / `grab_record` / `errand_status_log` 前后不变），记进归档。

## F-31 `risk_event_publish` 是异步写的；同一条红字来自两个都在测试侧的原因

**首次发现**：P9.4 批次 5（`RiskEventIT` 第一次跑红）

用例按「`grab()` 返回 → 立刻数投递行」写，两条红了，红字看起来都是**聚合失效**：

```
越线之后的每一次都必须被闸门吞掉并留下 SUPPRESSED 行；实际：[... result=SENT]
本次运行应当恰好投出一条事件（前几次 PASS 不发）；实际全部投递行：[...]
```

现场时间戳给出的却是另一个答案：`it-agg` 的三行投递落在 `.838/.839/.840`，而断言在 `.838`
就完成了——第 1 条 `SENT` 恰好被看到，后两条 `SUPPRESSED` **还没落盘**。
`risk_event_publish` 跑在 `risk-event-pub` 线程上（执行器投递，设计 §4.4），`grab()` 返回时
它还在队列里。**这是被测系统的性质，不是偶发。**

第一条（往返那条）另有原因，与时序无关：它的 matcher 拿 `requestId` 与**不带后缀的** `tag` 比
（`equals("it-roundtrip-<millis>")`），而每次 grab 的 `requestId` 是 `tag + "-" + i`，
于是**一条也匹配不上**——症状同样是「0 条投递」，看起来像事件没发出去，而那一行就在日志里。
两条红字一模一样，病因一个在系统时序、一个在断言认错了名字。

**处理**：断言改成「**等到第 N 条**」——等本用例不该出现的那条出现，或者超时；超时也返回手里
已有的行，让断言带着现场报错。N 由用例算出来（它知道自己该产生几条：往返 2、聚合 4），而不是
「等到不再新增」：静默窗口在「本来就只有一条」时纯属白等。落点是 `LogCapture.awaitLines(...)`，
它顺带解决了跨线程写 `ListAppender` 那个普通 `ArrayList` 的可见性问题（轮询重读，而不是读一次
就下结论）。三条用例各等几条写在设计 §8.2。

**防回归**：无自动化断言（这是测试侧的写法约定）。它留在这里的理由是**下一个人会先怀疑错东西**：
看到那两行红字的第一反应会是去查 `RedisRiskEventGate`，而两处修法都在测试侧。

## F-32 worker 收到 SIGTERM 后不会退出：卡在 RocketMQ `PushConsumer.close()`

**首次发现**：P9.4 批次 5（手工做「worker 重启后继续处理」时）

手工停 worker（`kill <pid>`，即 SIGTERM）：**45 秒后进程仍在**，日志里连一行关停记录都没有。
`jstack` 给出确切位置：

```
"SIGTERM handler" #326 ... WAITING (on object monitor)
	at java.lang.Thread.join
	at java.lang.ApplicationShutdownHooks.runHooks(ApplicationShutdownHooks.java:114)
	at java.lang.Shutdown.exit(Shutdown.java:167)
	- locked <...> (a java.lang.Class for java.lang.Shutdown)
	at java.lang.Terminator$1.handle(Terminator.java:51)

"SpringApplicationShutdownHook" #40 ... WAITING (parking)
	at ...AbstractService.awaitTerminated(AbstractService.java:339)
	at ...AbstractIdleService.awaitTerminated(AbstractIdleService.java:178)
	at org.apache.rocketmq.client.java.impl.consumer.PushConsumerImpl.close(PushConsumerImpl.java:482)
	at com.campusdash.worker.FundEventConsumer.stop(FundEventConsumer.java:108)
```

读法：SIGTERM 处理器在跑 shutdown hook；Boot 的 hook 在 `@PreDestroy` 里调
`PushConsumer.close()`，而 RocketMQ 客户端的 `awaitTerminated`（Guava `Monitor`）不返回；
处理器 `join` 这个 hook——**于是永远等下去**。同一份转储里 `DestroyJavaVM` 是 RUNNABLE
（非 web 应用，`main` 启动完就返回了，这是正常的），其余线程位置也都正常，
**唯一不动的是这一处 `close()`**。

三点：

1. **它不是本阶段引入的**：`FundEventConsumer`（`com.campusdash.worker`）本阶段没动过，
   而 `RiskEventConsumer` 是**同一个写法**（`@PreDestroy stop()` → `consumer.close()`，
   `RiskEventConsumer:109`）。所以这不是某一个消费者的问题，是「worker 的 MQ 消费者
   在关停时都可能卡住」。
2. **第一个踩到它的是手工动作，不是测试**：验收项「Worker 重启后可以继续处理」要求**先停再起**，
   而按设计稿那套（停 → 发 → 起）根本走不完——旧进程不退出，消费组一直有人占着，
   新起的 worker 与它同组抢队列，「重启后继续消费」就成了一句无法执行的话。
   实测最后是 `kill -9` 完成的。
3. **自动化里它被一个 8 秒兜底掩盖着**：`WorkerSubprocess.stop()` 是
   `destroy()`（SIGTERM）→ 等 8 秒 → `destroyForcibly()`（SIGKILL）。这条写法看着像防御性编程，
   实际每一步都会走到——本用例每次跑完都强杀一次子进程。谁把这个兜底删掉，
   就会在 CI 里留下常驻的僵尸 worker。

**本阶段不改它**（不在 P9.4 边界内，动 RocketMQ 客户端的关停语义要单独评估）。
归档里记的重启实测命令用 `kill -9`，并注明「SIGTERM 停不住」是现象、不是操作失误。

**2026-09-12 已登记为 `预存缺陷与坑.md` 的 D-6**（编号取自 D-5 复盘里预留的那个）：现象、六个消费者的
影响面、三个未验证的修法方向与复现命令都记在那边，本文件不重复。连带决定：P9.5 的「worker 停止后恢复」
按**半自动用例**做，停下那一步用 `kill -9` 并在报告里标注——**若先修了 D-6，这条线可以升级成「优雅关停后恢复」**。

**防回归**：无（要断言它得有「进程能在 N 秒内退出」这条判据，那属于「重启/部署」那条线的设施）。

## F-34 停机期间发布的事件要 60 秒量级才被新进程消费，且 `deliveryAttempt=2`

**首次发现**：P9.5 批次 1（`WorkerRestartIT` 第一次跑，断言在 60 秒处超时）

**现象（两次运行的原始读数，都是这条用例、同一台机器）**：

```text
第一次（断言超时，消费行在超时后 0.9 秒才落盘）
  事件 occurredAt=1789214505924（20:01:45.924）
  消费行 2026-09-12T20:02:53.886  lagMs=67959  deliveryAttempt=2
第二次（把等待放到 150 秒之后，通过）
  [IT-RESTART] 停机耗时=8016ms 停机窗口=3000ms 下界=3000ms 实际lagMs=67910ms deliveryAttempt=2
```

**机制（推断，标注清楚哪些是读数、哪些是解释）**：读数是「`lagMs` 68 秒量级、`deliveryAttempt=2`、消息最终
被新进程消费」。解释是——`stop()` 走的是 SIGKILL（D-6 让优雅停不可达），消费组里那个成员在 broker 侧
**还活着**，消息先被投给它（那算一次投递，所以新进程拿到手时 `deliveryAttempt` 已经是 2），
要等一个 **60 秒量级的期限**（5.x 客户端的 `invisibleDuration` / 成员存活判定，客户端字节码里有一个
`60l` 常量）过去、队列重新分给新成员，消息才回到新进程手上。**本阶段没有把这个旋钮追到底**——
验证的是现象与量级，不是那个配置项的取值。

**影响面**：

- **设计 §5.7 ⑤ 的判据错了一条**：原文写「消费行 `eventId` 相同 ∧ `lagMs ≥ (T2 − 事件时刻)` ∧
  `deliveryAttempt = 1`」。第三条被实测推翻（是 2）。断言 1 会让用例**永远红**；断言 2 则是把一次
  实测读数当不变式，它会随 broker 期限与新进程启动快慢的关系在 1/2/3 之间跳。已改为**只打印不断言**。
- **等待预算**：`AWAIT_CONSUME` 从 60 秒改成 150 秒。60 秒正好卡在那个期限上——第一次运行失败与
  成功的差别只有 0.9 秒，那是「时灵时不灵」的典型。
- **这条是 D-6 的运行后果，不只是代码缺陷**：重启 worker 之后的一分钟量级内，停机期间产生的事件
  可能还没有消费行。要原样进交付物的限制小节（设计 §5.7 与 §8 都指到这一条）。
- **`lagMs` 那条不等式不受影响**，而且这次拿到了一个很强的读数：下界 3000ms、实际 67910ms，
  差了两个数量级——「消息在停机窗口里一直躺在 broker 上」这件事没有含糊的余地。

**防回归**：`WorkerRestartIT` 通过时打印 `[IT-RESTART] 停机耗时=… 停机窗口=… 下界=… 实际lagMs=… deliveryAttempt=…`。
没有断言盯着 `deliveryAttempt`（理由见上），但那一行让**下一次这个数字变了**的时候有人能看见。

## F-35 F-19 的第二次现身：走真 HTTP 的越线用例必须覆盖 `deadline-ms`

**首次发现**：P9.5 批次 1（`WorkerRestartIT` 第二次跑，改成 150 秒等待之后换了个错）

**现象**：`最后一次必须在风控这一层被拦下 ==> expected: <RISK_LIMITED> but was: <ALREADY_GRABBED>`。

**根因**：本类走真 HTTP（`RANDOM_PORT`），而测试 yaml 的 `dash.risk.deadline-ms: 10` 会被第一个请求的
连接池冷启动吃光（15ms 量级）。`RiskPreCheckUseCase` 的四个检查点在预算耗尽后**跳过第 2~4 步**
（`:180-193`），其中第 3 步就是 `trackUserWindow`——于是那一次请求**不计进用户窗口**。
少一次计数，连抢 `shortThreshold + 1` 次恰好只到阈值、不越线，于是：不产生事件 → 最后那次抢单
走到名额裁决 → 返回 `ALREADY_GRABBED`。

**为什么失败信息误导**：`ALREADY_GRABBED` 是「这个任务已经被人抢了」，与风控毫无关系。
看到它的人会去查名额/幂等键，而真正的原因是配置里那个 10ms。

**F-19 已经记过同一个预算的覆盖率后果**（「在真实并发下约等于全程空转」），这里补的是**另一面**：
它还会让「越线」这条判据**少一次计数**，而两个形态的差别是决定性的——

| 形态 | 例子 | 进程内调用 | 结论 |
|---|---|---|---|
| 直接调用例 | `RiskEventIT.ProcessToProcess`（`deadline-ms` 保持 10） | 微秒级，预算够用 | 稳定 |
| 走真 HTTP | `WorkerRestartIT`（冷连接池） | 毫秒级，预算被吃光 | **必须覆盖 `deadline-ms`** |

**修法**：`WorkerRestartIT` 的 `properties` 加 `dash.risk.deadline-ms=1000`，与 `RiskGrabLinkIT.Shadow`、
`RiskTestHeaderBoundaryIT` 同一个写法、同一个理由。三处注释都指向本条目。

## F-36 F-35 的第三次现身（现场流量侧）：档位起点取决于有没有预热

**首次发现**：P9.5 批次 1（对照 §4.1 的第 3 行「同设备多账号」时，两次现场的数字对不上）

**现象**：同一条攻击流量——12 个账号共用一台设备与一个 IP、各抢一次——两次现场的档位起点**差一个账号**：

| 现场 | 3 个 `PASS` | 5 个 `REVIEW`/60 `DEVICE_ACCOUNTS_LOW` | `BLOCK`/80 `DEVICE_ACCOUNTS_HIGH` | `BLOCK`/100 `+IP_ACCOUNTS` |
|---|---|---|---|---|
| `09-故障-broker停.txt` 批次 A 攻击组（app-9，**先打过一条预热请求**） | #1–#3 | **#4**–#8 | #9–#10 | #11–#12 |
| `03-抽查-多规则命中.txt`（app-1，**冷启动**） | #1–#4 | **#5**–#9 | #10–#11 | #12 |

**根因（已定位到条目，不是猜测）**：`03` 的第 1 个账号（2100001）的决策行是
`degraded=true degradeReasons=DEADLINE_EXCEEDED decisionLatencyMs=21`——新进程的第一个请求
（连接池冷启动，与 F-35 同因），10 ms 预算在第一步就耗尽，**该请求的采集体写入被跳过**。
于是设备集合在每个后续账号上都少一个成员：规则在「集合已有 4 个成员」时给出 `REVIEW`，
少一个成员意味着整条阶梯后移一位；集合上限 `cap = threshold + 1 = 9` 的饱和点同样后移一位
（所以 `BLOCK` 从 #9 变成 #10）。分数模型两侧**完全一致**（60 → 80 → 100，`IP_ACCOUNTS` 都在最后一个账号加入）。

**这不是缺陷**：采集写入本来就是「预算内尽力而为」（`RiskGrabLinkIT$Shadow` 的注释里记着同一个现象）。
它是一条**复现条件**：报告里照抄现场命令的人，如果不先热身一条请求，会得到与自己记录不同的档位起点，
然后去怀疑规则实现。

**防回归**：`run-5.5.sh` 把预热做成独立的一步（并写明理由）；本条目给出一条可核对的判据——
「两次现场的逐账号档位表要么完全相同、要么能指出是哪一次请求被跳过了采集」。

## F-37 Redis 冻结时，先 500 的是鉴权，不是风控

**首次发现**：P9.5 批次 1（§5.4 第一次现场全废，见 `07-故障-Redis冻结-作废第一次.txt`）

**现象**：`docker pause dash-redis` 之后，带 token 的请求在 **2.0 秒左右**（即
`spring.data.redis.timeout` 的取值，实测 2010 / 2011 ms）返回 `500 INTERNAL_ERROR`，
而应用日志里**一行 `risk_decision` 都没有**——风控预检根本没被执行（该场记录里
「冻结期间的 `degradeReasons` 去重」是空的）。
<!-- 记录里另有两处 10 ms / 16 ms 的 500，那是当时脚本的另一个 bug（errandId 为空、请求被 Spring
     归一成静态资源），与鉴权无关，不计入本条。 -->

**根因**：身份是 **Redis session**（`RedisAuthAdapter`，键 `auth:token:{token}` → userId，TTL 2h），
在 `AuthInterceptor.preHandle` 里每个已鉴权请求都要读一次，**失败没有降级路径**（不像风控预检有
fail-open / 降级原因）。Redis 一冻结，`QueryTimeoutException` 先在这里抛出，请求在到达风控之前就结束了。

**影响面**：

- **§5.4 的观测必须换身份**：改用测试后门头 `X-User-Id`（`--dash.auth.allow-header-identity=true`），
  这样一次请求里除了风控自己的 Redis 调用再没有别的 Redis 调用，降级原因才记在风控头上。
  这是**测试专用做法**，生产配置该项为 `false`。
- **这条本身就是一条对报告有用的结论**：Redis 故障时，全站鉴权会比风控**更早**失败；
  风控的降级设计挡不住这个（也不该挡，那是鉴权层的事）。写进报告的限制小节。

## F-38 客户端超时 ≠ 服务端未执行

**首次发现**：P9.5 批次 1（§5.4 第二段现场核对 Redis 键时发现）

**现象**：`08-故障-Redis冻结.txt` 的哈希对照表显示——10 ms 预算那一段（2100060~2100063）的设备/IP 键
**一个都没有**（第 2~4 步被检查点跳过，**调用根本没发起**）；而 30 s 预算那一段（2100065）的四个写命令
（`risk:dev:bfa86b4a…`、`risk:ip:414114ee…:users`、`risk:win:{2100065}:10s` / `:60s`）在 `unpause` 之后
**全部存在**——客户端 2 秒就超时放弃了，但字节早已进了服务端缓冲，Redis 恢复后照常执行。

**结论**：判成降级的那一次预检，其写命令**仍可能在恢复后落地**。把「降级 = 什么都没写」当不变式会错。
两处机制必须分清，不要当成一回事：

| 场景 | 机制 | Redis 侧的后果 |
|---|---|---|
| §5.3 `deadline-ms=0` | 预算在第一步之前耗尽，**调用没发出去** | 一个键都不产生 |
| §5.4 冻结 + 大预算 | 调用发出去了，**客户端超时**，服务端稍后执行 | 键在恢复后出现 |

**影响面**：报告的限制小节；也解释了为什么 §5.4 的判据只能落在 `degradeReasons` 与恢复后的
`degraded=false` 上，不能落在「有没有键」上。

## F-42 抢单是**单赢家**：任务池容量 = 任务数，`slotTotal` 在抢单路径上根本不被读

**首次发现**：P9.5 批次 2（烟测的闸门第一次拦住正式五轮）

**现象**：`RiskTrafficClient normal` 在 200 个任务、64 并发、30 秒下打出 233618 次请求，
`OK=131`、`GRAB_CONFLICT=233487`（99.9%）。同参数的第一版（任务号被用户号完全决定时）
是 `OK=131 / GRAB_CONFLICT=231359`——**两版 OK 都是 131**，说明它不是分配算法的问题。

**根因**：`JdbcErrandRepository.casLockForRunner` 的 SQL 是
`SET status='LOCKED', version=version+1 WHERE id=? AND status='PUBLISHED' AND version=?`。
任务被抢中一次就离开 `PUBLISHED`，**之后每一次抢单都在 CAS 上失败**
（`GrabErrandUseCase:311` → 回滚 Redis 名额 → `GRAB_CONFLICT`）。
数据库侧的读数对得上：1092 条 `grab_record` 每任务只有一条，而 `errand` 里
`slot_total=2000` 的任务全部停在 `slot_taken=1 / LOCKED`，最高 `slot_taken` 就是 1。

**单赢家的边界要写准：它是「每（任务，轮次）一次」，不是「每任务一次」。** 库里唯一那条
同任务两条记录的行是 `(round=0, seq=1, runner=2011)` 与 `(round=1, seq=1, runner=2012)`，
相差 40 毫秒——唯一索引是 `(errand_id, round, seq)` 与 `(errand_id, round, runner_id)`，
两条落在不同 round 上，都不冲突。这是**轮次流转**（确认窗口超时后转给候选人）开了新一轮，
与本条的批量冲突不是同一个机制。批次 2 不跑 worker，超时扫描不发生，所以那些任务
在本批里永远停在 LOCKED、不会再开新轮。

**这条推翻了设计 §6.1 的一个假设**：那里写「先发布一批任务，避免全打到售罄任务上」，
隐含容量 = `taskPool × slotTotal`（500 × 2000 = 100 万个名额）。真实容量 = `taskPool`。
`slotTotal` 只写给发布接口看，抢单路径不读它——所以也**不会**返回 `SLOT_FULL`：
Redis 的 Lua 名额数是 2000，拦不住，失败一律发生在数据库那一步。

**影响面**：
- **风控侧指标一个都不受影响**。决策发生在抢单之前（`GrabErrandUseCase` 的 L1.5），
  每个请求都写一行 `risk_decision`：拦截率、命中率、误伤率、`decisionLatencyMs` 全都照常有效。
- **只有「抢单分位」这一项的读法变了**：它主要由冲突路径决定。报告必须带一句口径注记
  （2026-09-12 用户决定：直接跑，报告里注明口径，不为它再加一轮改动）。
- 尖峰（`SpikeLoadClient 2000 1`，§8 验收那一行）**不受影响**：`slotTotal=1` 时
  Redis 名额先耗尽 → 1999 个 `SLOT_FULL`，正是历史 S1 的形态。

**同一场烟测里客户端自己的三个缺陷**（都已在工具里修掉，一并留证）：
1. 登录段一次放出 20000 个并发 → 10711 个失败，**应用日志零 ERROR**（Tomcat
   `maxConnections` 默认 8192，超出的连接在内核 accept 队列被丢）→ 登录在途数封顶 256。
2. `taskPool` 整除 `userPool` 时，用户号完全决定任务号 → 同一用户永远打同一条任务 →
   撞 `uk_errand_round_user` → 回滚 → 再撞。**这是「压测端自己造出来的 99.9% 冲突」**，
   与第 3 条的真冲突叠在同一份读数里，是本条发现被推迟一小时才判明的原因。
3. 黑名单车道的身份来自 token，而它用的是池里干净用户的 token → 该车道永远不可能被拦，
   `黑名单种子自检失败` 只是把「种错了车道」暴露成了「种子没生效」。

## F-43 `deadline-ms: 10` 的预算耗尽会**跳过黑名单查询**：降级放行让黑名单漏过 16 条

**首次发现**：P9.5 批次 2（黑名单场，五份应用日志逐条对账时定位）

**现象**：黑名单场（200 并发 / 60 秒 / 6 万用户池 / 500 任务）测量窗内，三个被拉黑车道
共 378318 条请求：**378302 条 `RISK_BLOCKED`，16 条进了抢单链路**（三车道 5 / 5 / 6；
客户端把它们记成 `GRAB_CONFLICT`——它们到了抢单那一步、只是没抢中）。
对照组 378318 条全部 PASS，**零误伤**（这一半是达成的）。

这 16 条的决策行是 `action=PASS degraded=true degradeReasons=DEADLINE_EXCEEDED`：
bl-user 车道的 5 条可按 `userId=2190006` 直接确认；另 11 条由两件事推定——
本场出现过的降级原因**只有** `DEADLINE_EXCEEDED` 一种，且 15 次探针（三维度各 5 次，
自检要求「命中黑名单只可能是 RISK_BLOCKED」）与 126101 次拦截证明匹配逻辑本身正常。

**同一份日志里的第二个数字**：测量窗内 **82%（623069 / 756656）** 的决策是降级的；
`normal` 场是 **65%（337791 / 519937）**。降级不是偶发。

**根因**（三段，都是既有代码与配置，不是缺陷）：
1. `dash-bootstrap/src/main/resources/application.yaml:77` → `deadline-ms: 10`。
   预检的四步采集（限频键 → 黑名单 → 用户窗口 → 聚集）必须在这个**墙钟**预算内跑完。
   它算的是墙钟，所以**应用内的线程排队也算进去**——200 并发下单实例与本机压测端抢 CPU，
   10 毫秒极易耗尽。这跟「Redis 慢」是两回事。
2. `RiskPreCheckUseCase:180-193` 在每次采集**之前**比较预算，耗尽后不再发起后续采集调用，
   决策照常用已有证据给出（第 5 步）。若预算在黑名单查询之前就没了 → 黑名单**没被查** →
   `BlacklistHits.NONE` → 分数 0 → PASS。
3. `policy.failOpen()` 默认 true，于是第 8 步的 `unavailable` 判定（四条件里有一条 `!failOpen`）
   不成立 → 这次预检**不算「风控不可用」**，请求按普通 PASS 继续走到抢单。

**这条推翻的是「降级不是放行」的适用范围**，不是它本身：那条不变式成立的前提是
「证据不全，但已有证据里有拒绝依据」。黑名单压根没查时，没有任何证据可依据，
fail-open 下它就是放行——**降级的放行与拒绝对称性，取决于哪一步被跳过**。
顺序上黑名单排在最前（第 2 步），所以被跳过时后果最重。

**补记（2026-09-14）· 为什么 82% 的降级只漏了 16 条——死在第几个检查点决定后果。**

四个检查点分别卡在第 1/2/3/4 步**之前**（`RiskPreCheckUseCase:157/181/185/189`）。
只有在**第 181 行**（第 2 步「查黑名单」之前）就断气的请求才会丢掉拦截，而它之前的
全部工作只有一次 Redis 往返（读限频键）。实测三个数把这条钉死：

- 378317 条 BLOCK 里有 **311142 条带降级标记** → 它们**查到了**黑名单、拿到了 BLOCK，
  之后才在 185/189 行耗尽预算——处置已经成立，后面跳过不影响结论；
- 三个黑名单车道共 378333 条请求，只有 **16 条**死在 181 行之前（≈ 0.004%）；
- 对照组同样比例的降级（311927/378318 = 82.5%）落在同一个死亡点分布上，但干净身份
  死在哪一步都是 PASS，**从结果上看不出差别**——两车道的死亡点分布相同，差别只在身份。

所以「降级率 82%」与「漏 0.004%」不矛盾：降级率高是因为**第 2 步之后预算普遍不够**
（压测环境下一次 Redis 往返要几毫秒，两次就贴到 10 ms 线），而黑名单是最早被问到的那一个。
换言之，**要漏必须在第一步就超时**——那是极端尾巴；报告里若只写「降级 82%」而不写
这条死亡点分布，读者会以为漏的是 82%。

**影响面**：
- 设计 §6.3 场景 5 的两条硬口径都要按实测写：**「精确拦截率（目标 100%）」= 99.9958%**；
  **「拒绝后零后续调用」有 16 次后续调用**。验收表这两行不能写「达成」。
- **报告的口径要求**：凡引用「拦截率」必须同时给出**降级率**。
  同理，`normal` 场的「误伤率 0」要写成「在 65% 的请求根本没跑到窗口/聚集规则的条件下的 0」——
  降级会**掩盖**误伤，两个数字必须一起出现，否则读者会把它读成「规则很准」。
- 尖峰场（`slotTotal=1`）不受影响：那里 `RISK_UNAVAILABLE`/放行与否都不改变
  「1 个成功、其余名额已满」的结论，`verify_run.sql` 的四项校验照常 PASS。
- **处置方向属于设计层决定，本阶段不改生产代码**（P9.5 §1）：
  黑名单规则要不要单独的「不可降级」待遇，或者让 `deadline` 只覆盖「可选」规则、
  把黑名单移出预算——两条路都要动配置与语义，不是实现期的顺手改动。
  已作为待议项写入 `验收报告/P9.5 §6.3 场景取数（批次 2）.md` 的「待决定」。

**顺带留一条对数口径**（批次 3 的分析脚本会踩到）：应用日志里的 `risk_decision` 行
**包含预热流量**。预热是单用户 `30300xx` + `192.0.2.250`，它把 IP 速率打爆后全部记
`LIMIT`，一场约 16–21 万行（黑名单场 211542 行，占该场日志的 21.9%）。
分析脚本必须按 `userId >= 3000000` 剔除，否则拦截率的分母里会混进 21% 的预热。
剔除后，五场的测量窗决策行数与客户端请求数**逐场精确相等**
（519937 / 3177381 / 579082 / 2352548 / 756636+20 条探针），这是一条很强的互验。

## F-44 对照 B（误伤率）在「单赢家抢单 + 关档预热吃池」下退化成 `0/0`

**首次发现**：P9.5 批次 2 的对照 B 补充取数（2026-09-14，同 seed `2130011` 背靠背两轮）

**现象**（两轮都是 normal / 200 并发 / 60 秒 / 500 任务 / 6 万用户池）：

| | 风控 `enabled=false` | 风控 `enabled=true` |
|---|---|---|
| 测量窗请求 / 抢中 | 629860 / **0** | 539400 / 431 |
| 测量窗被风控拒绝 | —（无风控） | **0** |
| 预热抢中的任务数 | **500**（全池） | 69 |
| 预热 2 秒内发出的请求 | 63487（全 PASS） | 223946（223877 被限流） |

预热用户在关档那一轮把**整个任务池吃光**：DB 里 500 条 `grab_record` 全部出自预热用户
3030011，时间跨度 13:53:03.805–13:53:05.023（1.2 秒）。测量窗因此一条都抢不中。

**根因（两层，缺一不成）**：
1. **单赢家抢单**（F-42）让「成功」只有 431/500 条量级；
2. **关掉风控后预热不再被限流**——开着风控时预热的第 100 条之后被 IP 速率规则限流
   （只抢到 69 个），关掉风控后它一路抢满 500 个。

**影响面**：设计 §7.3 逐字定义的误伤率
（`关闭风控时本可成功、开启风控后被拒绝的请求数 / 关闭风控时本可成功的请求数`）
在这套系统里**分母为 0** → `0/0`，比率未定义。把预热算进去则更荒谬：预热在开档被限流
223877 条、在关档「本可成功」，会算出 99% 量级的「误伤率」。

**采用的口径**（报告与 `analyze_risk_decisions.py` 都按这个写，两个口径都要出现在报告里）：

```text
误伤率 = 开启风控时被拒绝的测量请求数 / 同一轮测量请求数
       = 0 / 539400 = 0%
```

它不依赖「本可成功」这个在抢单系统里退化的概念；分子为 0 时最稳。
**预热一律排除**——它是客户端为预热 JIT 造的流量（单用户 192.0.2.250 猛打），
不是被测流量；把它算进去等于拿「故意的高频流量被限流」当误伤。

**顺带的收获（可直接写进报告）**：关闭档**逐条记日志**，693347 行 = 63487 预热 + 629860 测量，
形态是 `action=PASS riskScore=0 matchedRules=- ruleVersion=1 degraded=false
degradeReasons=- eventId=- decisionLatencyMs=0`——`ruleVersion` 保留、`degraded=false`、
无 `eventId`，所以离线分析能把「风控关闭期间」与「开着但全 PASS」分开，与
`RiskPreCheckUseCase` 第 0 步的注释一致。

## F-45 `deadline-ms` **不是延迟上界**：降级组按定义是最慢的一批

**首次发现**：P9.5 批次 2 的指标汇总（2026-09-14，同一批日志上做延迟分组的二次提取）

**现象**（normal 场，测量窗 519937 条决策行，按 `degraded` 拆开）：

| 组 | n | min | 均值 | P50 | P95 | P99 | Max |
|---|---:|---:|---:|---:|---:|---:|---:|
| `degraded=true` | 337791 | **10** | 15.7 | 16 | 21 | 24 | 42 |
| `degraded=false` | 182146 | 0 | 5.5 | 5 | 11 | 16 | 31 |

**机制**：`RiskPreCheckUseCase` 的四个预算检查点都在「**发起下一次采集调用之前**」
（`157/181/185/189`）。所以

- 判出「预算耗尽」的前提是**已经**过了 10 ms → 降级组的 `decisionLatencyMs` 按定义 ≥ 10（实测 min 恰为 10）；
- 反过来，**在途的那次调用不会被截断** → 未降级组也能超过 10 ms（P95=11、Max=31）。

**影响面**：设计 §8 的「单次同步风控 P99 < 10 ms」按实测**未达成**（normal 24 ms、
same-device 26、blacklist 25、same-ip 21；只有 hot-user 是 1，因为那里 92%+ 的请求在第 1 步
`LIMIT_COOLDOWN` 上短路、根本不采集）。「P99 超标」的成因是
**预算只拦发起、不拦在途** + 单实例与本机压测端共抢 CPU（后者占比见 D-b），
**不是「风控逻辑慢」**。

**读数的更正（同日）**：本批的 `bench/tmp/p95-batch2/batch2-run/06-指标-决策延迟与规则命中.txt`
初稿把这条读反了，写成「降级会**压低**分位」。实际的因果相反：降级是**慢**的结果而不是原因。
hot-user / same-ip 的 `P50=0` 与降级无关（那两场降级率 0.0011% / 5.4%），它的成因是
`LIMIT_COOLDOWN` 在第一步短路。文件已当场改正，结论以本条目为准。

**处置方向**：属设计层（两条都在 D-b 里）——要么承认 10 ms 是「发起预算」而非延迟 SLO，
把 §8 那一行改成别的口径（如「跑完规则的请求 P99 < 10 ms」，实测未降级组 P99=16 也仍不满足），
要么把这 10 ms 调大并在独立压测机上复测。**本阶段不改代码、不下结论。**
