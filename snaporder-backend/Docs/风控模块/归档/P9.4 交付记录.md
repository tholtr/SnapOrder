## 与设计的偏离

| # | 设计里怎么写的 | 实际怎么做 | 为什么 |
|---|---|---|---|
| 1 | `RiskEventIT` **必须住在 `dash-worker`**（模块边界：消费者类在 worker；`dash-bootstrap` 不依赖 worker） | 住在 `dash-bootstrap`（`com.campusdash.it`），**worker 以子进程参与** | 那个模块边界的理由成立，但结论下早了：不必把用例搬去一个连 HTTP 脚手架都没有的模块——拉起子进程后 bootstrap 同时握着两端。设计 §8.2 已就地改写（F-30） |
| 2 | （原计划）新增 `WorkerMiddleware` 探针类 | **取消** | 它存在的唯一理由是「用例住在 worker，而 `MiddlewareAvailable` 是 bootstrap 测试源的包级私有类」；用例搬回 bootstrap 后理由消失，再添一个同型的类是重复 |
| 3 | — | `MiddlewareAvailable.mqReachable()` 探 `127.0.0.1:8081`（gRPC proxy），**不探 9876** | 应用连的是 8081；探 nameserver 会给出「9876 通但应用连不上」的假绿 |
| 4 | 端到端用例跑在受控配置下 | 子进程**只覆盖一个配置项**（`--spring.datasource.url` → 隔离库），其余全走**生产 yaml** | 生产 yaml 下五个 `@Scheduled` **启动即跑第一次**（`fixedDelayString` / `cron` 都不带 `initialDelay`），`NoScheduling` 只对同 JVM 生效、管不到子进程。所以**库隔离是唯一防线**；Redis 隔离不了（6380 只有一份），只能靠键不重叠（F-20、F-30） |
| 5 | — | 隔离库 `campus_dash_worker_it` **不自动创建**：缺库整类跳过并打印创建配方 | 自动建库会把「忘了建库」变成一条发生在别处的静默假绿 |
| 6 | `LogField.safe` 挡住空白（D13） | 白名单式转义 + 补 `Character.isSpaceChar` | `U+00A0` / `U+2007` / `U+202F` 三种**不换行**空格会被 Python 的 `str.split()` 认成分隔符，漏一个字符离线脚本就多切一段（F-21） |
| 7 | `RiskEvent` 的 `outcome` 由 `denied()` 决定（§5.4） | 取 §3.3（与 `decisionAction` 冗余的那个），`RiskEvent` 外部不可直接构造 | 按 §5.4 逐字落笔会产出**自相矛盾**的载荷（`decisionAction=PASS` 配 `outcome=DENIED`）（F-23） |
| 8 | `eventId` 不变式写成「非空 ⟺ `producesEvent()`」 | **只堵一个方向**：有事件必有 `eventId`；允许「有 id 无事件」 | 更严的那半条会挡住 SHADOW 下的正常流；`toEvent` 的守卫也随之从 `eventId == null` 改判 `!producesEvent()`（F-25） |
| 9 | 消费侧解析出一个中间 record | **不建中间 record**，解析直接产出领域 `RiskEvent`；生产端 `payloadOf` 相应改 `public` | 「生产端序列化 ↔ 消费端解析」的往返必须由**构造**保证，不能靠两份手抄的字面量碰巧一致（F-26） |
| 10 | 消费侧日志五条行 | 第五条加 `reason=` 短码（`RiskEventInvalidReason`） | 生产上那行只写 `error=Invalid`，**归因全在 reason 上**；没有它，四种非法载荷在日志里长得一样（F-27） |
| 11 | 调用点自己夹 `lagMs` | 负数夹取落在 `RiskEventConsumeLog` 的格式化方法里 | 任何调用点都不该自己记得夹一次（F-27） |
| 12 | `RiskEventProcessor` 一个 `try` 包住解析与处理 | **两个** `try` 块不合并；补一行设计没有的 `log.error`（**不许带 body**）；`process` 包级可见 | 合并会让一次**可重投**的 `IllegalArgumentException` 被静默 ACK；错误行带 body 等于把未信任的载荷抄进日志（F-28） |
| 13 | 设计 §4.5：「不需要新 bean」与「单独一个 `Producer` bean」自相矛盾 | 取后者：新增 `riskEventProducer`，并给两个既有适配器补 `@Qualifier("timeoutProducer")` | 同一类型两个候选 bean，参数名回退救不了注入点。设计 §4.5 的两条理由（「一个 topic 一个 producer」「省一条连接」）**都被更正**（F-22） |
| 14 | `NoopRiskEventAdapter` 与生产者 bean 都在 `infrastructure.config` | 一致照做 | 副作用如实记在 F-22：worker 的过滤器按包排除、只排 `*.risk.*`，所以 **worker 进程也会建出这个用不到的生产者**。本阶段保留，记作后续可选整理项 |
| 15 | — | IT 观察者另起消费组 **`dash-risk-event-it`**，写进 `docker/init-mq.sh` | 与 worker 同组会**抢消息**，「worker 收到了吗」就成了一条概率性断言；写在脚本里而不是只在测试代码里，是为了不变成「在别人机器上跑才失败」的隐藏依赖 |
| 16 | （原计划）IT 需要复用 `RiskGrabLinkIT` 的助手 | 从 `RiskGrabLinkIT` **提取**到新的 `ItFixtures`（`idemKey` / `publishSlots` / `resetPublisherBalance` / `login` / `grabRequest` / `purgeUser` / `purgeEventGates`），原类改用它们 | 直接复制会让同一条规则有两个版本，而两处都是 IT 夹具——夹具分叉的代价是「改了一处，另一处静默失效」 |

### 文档类更正（四处）

1. **设计 §8.2**：「`RiskEventIT` 必须住在 `dash-worker`」改为「住 `dash-bootstrap`、worker 以子进程参与」，并保留原理由作为「为什么不只看测试 JVM」的论据。**已就地改写**。
2. **设计 §8.4**（本阶段不做）：「不做 Worker 重启自动化」的理由从「没有进程编排」改为「**现有证据链证不了**」——任务 17 之后前一条理由已不成立（子进程能停能起），而判据本身要求「重启前停住消费、证明消息是在之后被消费的」，现有证据（同一个 `eventId` 的两行日志）分不出这两种情况。
3. **设计 §10**（验收表）：「真 worker 进程也不写共享 IT 库」那一行的**手工部分写错了比对对象**。初稿让比对共享库的 `errand` / `grab_record` / `errand_status_log`，而这三张表正是**测试 JVM 自己**走 HTTP 抢单时写的（实测 +3 / +3 / +6），它们的变化分不出是谁写的；那一行另一处还指向不存在的「§8.4 的手工项」。已改为按 F-20 的签名（`credit_score` / `credit_event` / `local_message`）比对，并指向本文件的手工实测一节。
4. **实施计划 §8 的任务 17 范围条目**按最终形态改写（bootstrap + 子进程 + 四个脚手架类）。

**唯一待同步项**：`风控反作弊实现蓝图.md` §3.9 的聚合键示例仍是设计 D4 推翻前的带时间桶写法（`risk:event:gate:limit:{userId}:{10sBucket}`）。蓝图按「阶段末统一同步」处理，**本阶段未改**。

## 验收结果

设计 §10 的二十行，逐条判定：

| # | 验收项 | 判定 | 证据 |
|---|---|---|---|
| 1 | 风险事件可以正常发送和消费 | ✅ | `RiskEventIT` 两份**独立**证据：观察者组收到载荷逐字段比对（消息过了 broker）+ 子进程写下**同一 `eventId`** 的 `risk_event_processed` 行（消费者真的执行过） |
| 2 | 重投递只产生重复日志，不产生重复业务状态 | ✅ | 单测：同一 body 喂两次 → 两行 `processed`、零次存储调用（结构性断言） |
| 3 | 离线脚本按 `requestId + operationType` 去重 | ✅ | `--selftest` 通过 + 对真实日志的实测输出（见下） |
| 4 | `REVIEW` 只产生 `risk_review_pending`，不产生审核表记录 | ✅ | 单测：`REVIEW` 决策 → 额外一行；全仓无审核表（本轮不建表） |
| 5 | 事件聚合 Key 按用户/实例/动作与时间窗生效 | ✅ | `RiskKeysTest` 四个键名逐字 + `RedisRiskEventGateTest` 的 TTL 断言；`LIMIT` 用 `userId`、`DEGRADED` 用 `instanceId` |

### 必须随交付物一起给出的三条限制（设计 §10 逐字）

1. **事件在进程内队列里，进程退出会丢。** 队列上限 4096，关停时不 `awaitTermination`。这是 best-effort 的**边界**（蓝图 §3.9 定的是 best-effort，不是不丢），所以它必须出现在最终交付物里，而不是只在代码注释里。
2. **聚合不是全局限流，四类闸门互相独立。** 同一个用户在同一秒内可以同时产生 `LIMIT`、`REVIEW`、`BLOCK`、`DEGRADED` 各一条——四个键互不影响。「同一用户 10 秒最多 1 条」限定的是**同一类**事件。
3. **降级闸门是每实例一个键，因此发送量随实例数线性增长。** 蓝图 §3.9 就是这么定的（`{instanceId}`），但结论必须写出来：N 个 app 实例下，同一个降级原因在每 10 秒内最多产生 N 条事件，不是 1 条。P9.5 读抑制率时必须知道分母是什么。

### 不得出现的说法

**不得把 `SENT` 写成「已投递」。** `SENT` 的含义是「已交给 `sendAsync`」，它到没到 broker 由 `risk_event_publish_failed` 的**缺席**间接说明，而**缺席不是证明**。要证明投递成功，只有 `RiskEventIT` 那条真的收到消息的用例。
