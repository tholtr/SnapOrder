批次 2 单测结果：`dash-domain` 36、`dash-infrastructure` 34，全部通过。

**批次 2 靠手工验证抓出三个缺陷**，都不是靠单测能发现的——两个 Lua 脚本没有单测抓手，只能靠真实 Redis 跑出来：

**一、`cap ≤ 127`，不是 128。** 计划初稿与蓝图 §3.8 都写的 128，依据是「128 个成员仍是 listpack」——这个依据本身没错，但**它不是本项目的写入路径**。脚本是「先 `ZADD`、再裁剪」，键在调用瞬间会达到 `cap + 1` 个成员，而 ZSet 的**编码只升不降**，cap 取 128 时瞬时到 129 就当场转成 skiplist 且再也回不来。实测：

| 路径 | 127 个成员 | 128 个成员 | 129 个成员 |
|---|---|---|---|
| 直接 `ZADD` | listpack 1080 B | listpack 1080 B | skiplist 13580 B |
| **经脚本（真实路径）** | listpack 7232 B | **skiplist 17601 B** | skiplist 17304 B |

**二、Set 也有一条悬崖，而且更陡。** 脚本注释和 `RiskPropertiesTest` 都声称 Set「不存在编码跳变」，于是**没有任何守卫**。实测走 `risk_cluster.lua` 真实路径：512 个成员 intset 1336 B，513 个成员 hashtable 24720 B，**跳涨 18.5 倍**。那句错误注释会主动告诉后来人「Set 可以随便调」，比没有注释更危险。

**三、查重与裁剪的顺序写反了。** 初稿用一整段论证「必须先查重后裁剪」，论证是错的；实测静默 62 秒后重放，旧顺序返回自相矛盾的 `{0,0,1}`。详见 §5.1 的专节。

三条都已修复并同步到 `RiskProperties`（两处启动期校验）、`RiskPropertiesTest`（8 个编码边界用例）、两个 Lua 脚本注释、蓝图 §3.8、实施计划 §5.2，以及本计划 §4.2/§4.4/§5.1/§11。

**批次 3 又抓出一个静默失效类缺陷（与批次 2 三条同类）：两个 Set 共用一个 TTL。**

`risk_cluster.lua` 早期版本只从调用方拿一个 `setTtl`（`ARGV[5]`），同时用在设备集合和 IP 账号集合上；而适配器传的是 `deviceWindow.seconds()`。后果：

- `dash.risk.ip-account-window.seconds` 是一个**读了也不生效的死配置项**——改它没有任何效果，且不报错
- 把设备窗口从 600 调到 300 会**顺手把 IP 账号窗口也改成 300**，两条规则的窗口被静默耦合

这一条比看上去严重：**Set 的成员上没有时间信息，「窗口」这个语义完全由 TTL 承载**，所以 TTL 不是无关紧要的过期时间，它就是窗口长度本身。

修法是给 IP 账号集合单开一个 ARGV（现在 `ARGV[5]`=设备集合 TTL、`ARGV[6]`=IP 账号集合 TTL、`ARGV[7]`=IP 速率 TTL，原 `ARGV[7]/[8]` 两个维度开关顺延到 `ARGV[8]/[9]`）。已用真实 Redis 验证三个键拿到三个独立的 TTL（600 / 300 / 60）。

**这个缺陷单测抓不到，是写 `RiskFeatureIT` 时被逼出来的**：要断言「IP 账号集合用自己的窗口秒数」，主配置里两个窗口恰好都是 600，根本区分不开。于是把 `ip-account-window.seconds` 在测试里覆盖成 300——**只有刻意让两个配置值不相等，才写得出这条断言，也才发现代码里根本就没有第二个 TTL 参数**。守卫现在就固化在 `ipAccountCapEnforcedWithItsOwnWindow()` 里。
