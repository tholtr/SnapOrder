## 与设计的偏离（五处）

阶段设计 §8.2 的两行测试规格**已按最终形态改正**（设计文档只写最终形态，见实施计划 §0）；下面记的是「为什么最终形态是这样」。

| # | 偏离 | 原因 |
|---|---|---|
| 1 | `Enforce` 上下文用 `webEnvironment = RANDOM_PORT`（设计只说「与 `AuthModeIT` 同型」） | D4 那条必须走真实 HTTP：`requestId` 的解析缺陷整个活在 controller 与拦截器之间，直接调用例会绕过它 |
| 2 | D4 用例**刻意不带 `X-Request-Id` 头**（设计说要带一个显式的） | 带显式头时新旧代码**本来就同值**，那条用例在 P9.3 之前也是绿的——**测不出任何东西**。只有头缺失时两个调用点才会各生成一个 UUID；而按实施计划 §9.4，本轮前端压根不发这个头，所以这条分支覆盖的正是全部真实流量。改法是：从 `errand:idem:{errandId}:*` 里取出服务端生成的值，再去风控窗口 ZSet 里找它 |
| 3 | `SHADOW` 场景改成「同一设备上 `lowThreshold + 1` 个账号，**各抢自己的单名额任务**」（设计说「多名额任务 + 连续请求」） | 多名额任务的第 2 个名额在正常路径上永远拿不到，实测 `GRAB_CONFLICT`——见 `预存缺陷与坑.md` D-4。因此设计里那句「对照 `ENFORCE` 上下文里同一场景的拒绝」**没有对应的 ENFORCE 用例**，`SHADOW` 那三条断言的第三条（确实算出了非 `PASS` 的动作）由设备集合越线来撑 |
| 4 | `SHADOW` 上下文把 `deadline-ms` 从默认 10 **放宽到 1000** | 实测新 Spring 上下文的第一个请求耗时 15ms（连接池冷启动），整段采集被预算跳过，设备集合少一个成员。那次失败与 `SHADOW` 的语义毫无关系——预算行为有专门用例，不该在这里被顺带检验。见 F-19 |
| 5 | 新增 Logback `ListAppender` 测试手法 | 设计要求断言 `risk_decision` 行，而结构化日志是那条断言的**唯一观测面**，仓库原本没有任何日志捕获设施。appender 挂在 `RiskDecisionLog` 的 logger 上，抓到的是真实应用写出来的行；行格式本身仍由 `RiskDecisionLogTest` 逐字锁着，这里只读 `action` 字段 |

第 2 条是唯一一处**比设计更严**的偏离：设计给的那个写法会得到一条永远为真的断言。

第 3 条还带出一个连带影响：`SHADOW` 用例的「每一次都成功抢到」现在**不再与 `ENFORCE` 形成对照**——它对照的是「同一设备第 4 个账号会被判 `REVIEW`」。三个断言（全部抢中 / 设备集合越线 / 存在非 `PASS` 行）缺一不可，只留第一条的话，「`SHADOW` 全放行」与「风控关掉」在行为上无法区分。

**验收时必须如实记录的两条限制**（设计 §10 已定，不得在后续文档里被磨掉）：

1. **10ms 不是硬上界**。预算耗尽后不再发起新命令，但一条已在途的命令由共享 Redis 客户端的 `commandTimeout`（当前 2000ms）兜底。**不得出现「预检一定在 10ms 内返回」这类说法。**
2. **不承诺共享 Redis 完全不可用时抢单仍成功**（实施计划 §7.4）。风控与抢单共用一个实例，本阶段验证的只是风控路径自身的异常。

3. **另加一条本阶段实测出来的**：生产默认的 `deadline-ms: 10` 在 2000 并发下**一次采集都做不成**（F-19）。所以「风控已接入」与「风控真的在算」在默认配置下是两件事——P9.5 的报告必须先给降级比例。
