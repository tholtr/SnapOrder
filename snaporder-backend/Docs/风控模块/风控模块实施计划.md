## 0. 文档结构

本目录下的文档**按寿命分工**，不是按主题分工。写新内容前先判断它属于哪一类，放错地方就是将来的臃肿。

| 文件 | 寿命 | 放什么 |
|---|---|---|
| `风控反作弊实现蓝图.md` | 长命 | 主文档。**只在产生跨阶段约束时才改**，改动要记出处 |
| `风控模块实施计划.md`（本文件） | 长命 | 五阶段总览与导航。**未完成阶段**写详细范围；**已完成阶段**收缩成一段结论 + 链接 |
| `阶段设计/P9.x *.md` | 长命 | 单阶段的设计。只写**最终形态**——决策、模型、端口、配置、验收标准 |
| `实现期发现.md` | 长命 | 实现期被推翻的初稿结论、实测硬约束、绕坑决定。**发现即写，不要攒** |
| `预存缺陷与坑.md` | 长命 | 仓库既有缺陷 + 构建/测试/环境特性。修好不删，改成「已修」 |

两条通用规则：

1. **设计文档不写变更日志。** 「初稿写了 X，后来改成 Y」属于发现账本；设计文档只写 Y，并在需要防止后人重新踩坑时附一句「为什么不能是 X」。
2. **已完成的记录只进归档。** 交付清单、测试数、同步记录都属于「当时交付了什么」，不是「设计是什么」。

## 2. 实施原则

- 只实现蓝图明确列出的最小功能。
- 风控调用放在 `GrabErrandUseCase` 内部，Controller 只负责传递请求上下文。
- Sentinel 先于风控，风控通过后才进入信用校验、Redis Lua 和 MySQL CAS。
- 本轮不修改 `campus-dash-frontend`；设备维度和客户端重试去重仅对提供相应请求头的测试/压测客户端生效。
- 风控不能修改现有抢单 Lua、MySQL CAS、资金、信用、任务状态和分片规则。
- 风控故障只降低安全能力，不能绕过现有交易正确性防线。
- 复用已有 Redis、RocketMQ、Worker、Sentinel、`dash-bench` 和离线分析脚本。
- 不引入 BloomFilter、Kafka、Flink、Neo4j、Drools、新服务进程或监控平台。
- 每阶段完成后先通过阶段验收，再进入下一阶段。

## 3. 配置约束

```yaml
dash:
  risk:
    enabled: true
    mode: SHADOW
    fail-open: true
    deadline-ms: 10
    limit-cooldown-ms: 10000
    event-aggregation-enabled: true
    test-context-enabled: false
    trusted-proxy-cidrs: ""
    device-hmac-secret: ${DASH_RISK_DEVICE_HMAC_SECRET}
```

`device-hmac-secret` 必须通过部署环境注入，不提供默认值，也不能提交到代码库。
测试上下文开关默认关闭，并要求测试 profile 才能启用。

日志字段使用 camelCase，离线脚本输出的指标名使用 snake_case，例如：

```text
decisionLatencyMs -> risk_decision_latency_ms
```

四大动作的语义（`PASS` 放行 / `LIMIT` 拒绝并写 10 秒限频键 / `REVIEW` 拒绝并记审核事件 / `BLOCK` 直接拒绝并记强拦截原因）与档位分值表以设计文档 §3.2 为准，本节不再重复。

**本阶段带出的跨阶段约束**——P9.3 起一律适用：

- **黑名单命中以「最高分值参与累加」实现，不是覆盖分数**：动作恒为 `BLOCK`，而总分可以被其他规则继续抬高
- **短路只由「限频键命中」触发**，且短路路径**仍然续写**限频键 → 冷却期是**滑动的**（F-15、F-16）
- **`SHADOW` 不读取也不写入限频键**，模式切换不改变 `SHADOW` 下的业务结果
- **`RiskMode` 不建模 `OFF`**：`enabled`（算不算）与 `mode`（拦不拦）是两个正交字段（F-17）
- **三类黑名单查询必须一次往返**，且查询侧用类型无关的 `EXISTS`；因此审计/运维工具**解除黑名单只能用 `DEL`**，`SREM` 会在字符串键上报 `WRONGTYPE`（F-18）
- **风险动作与降级原因一律由 `evaluate` 的入参决定**，降级原因只能事后附加，不能在规则层凭空生成（F-14）

- **验收必须看总用例数与 `Skipped`，不是失败数**（K-2）

**唯一待同步项**：`风控反作弊实现蓝图.md` §3.9 的聚合键示例仍是设计 D4 推翻前的带时间桶写法（`risk:event:gate:limit:{userId}:{10sBucket}`）。蓝图按「阶段末统一同步」处理，**本阶段未改**。

**本阶段不做**（设计 §8.4）：不给另外四个消费组补 `retryMaxTimes`（D11 只声明风险事件那个组的重试窗口）；不重构那五份 `extractLong`；不做「Worker 重启后继续处理」的自动化——**不是做不了，是现有证据链证不了**（判据要在重启前停住消费、证明消息是在之后被消费的，而「同一个 `eventId` 的两行日志」分不出这两种情况），仍走手工实测 + 归档；不引入 JSON 库、Micrometer、新中间件或新进程；不在 IT 里造重投、不模拟 broker 不可用、不验证另外四个 topic。

**本阶段带出的跨阶段约束**——P9.5 一律适用：

- **`SENT` 不是「已投递」**，它只表示「已交给 `sendAsync`」。`risk_event_publish_failed` 的**缺席不是投递成功的证明**；能证明投递的只有 `RiskEventIT` 那条真从 broker 收到消息的用例。报告里不得把 `SENT` 写成「已投递」
- **三条限制必须进最终交付物**（设计 §10 末尾逐字给出）：事件在**进程内队列**里（上限 4096，关停时不 `awaitTermination`，进程退出会丢）；聚合**不是全局限流**，四类闸门互相独立；**降级闸门每实例一个键**，发送量随实例数线性增长——P9.5 读抑制率时必须知道分母是什么
- **`key=value` 日志与 `LogField.safe` 是同一条通路的两端**：离线脚本按空格切分的前提是值里没有空格。P9.5 若要扩脚本，先看 `实现期发现.md` F-21（三种不换行的 Unicode 空格曾穿过去）
- **消费端不做运行时幂等**，重投递只产生**重复日志**、不产生重复业务状态；去重口径在离线脚本（按 `requestId + operationType`），不在消费端。`requestId` 仍是两条链路之间唯一的关联键（P9.3 D4 的延续）
- **IT 的守卫不成立时是「跳过」不是「失败」**（隔离库缺失 / worker 的 jar 过期 / broker 探不通三条），所以读 IT 数据前先看 `Skipped` 与总用例数（K-2）

### 9.3 攻击流量压测

复用现有 `SpikeLoadClient`、`GrabRampLoadClient`、`BenchRunRecorder` 和 verify SQL，只新增必要的风险流量 profile：

| 场景 | 重点指标 |
|---|---|
| 正常用户混合流量 | 延迟、误伤率 |
| 单用户脚本抢单 | 窗口命中率、`LIMIT` 数量 |
| 多账号同设备 | 设备规则命中率 |
| 多账号同 IP | 风险加分、误封率 |
| 黑名单用户 | 精确拦截率 |
| 风控路径异常 | 降级比例、零超卖 |
| MQ 延迟或重复 | 消费延迟、离线去重后的重复投递数 |
| 聚合关闭/开启对照 | MQ 发送量、抑制率、消费延迟、堆积和风险覆盖率 |

多 IP、多设备 HTTP 场景使用测试环境专用上下文注入，生产默认不信任测试头。

测试注入验收：

- 使用 `X-Test-Device-Id`、`X-Test-Client-Ip` 等独立测试头；
- 仅测试 profile 且 `dash.risk.test-context-enabled=true` 时生效；
- 默认配置下测试头被忽略；
- 通过后门关闭集成测试验证生产默认安全边界。

### 9.4 指标和验收目标

通过结构化日志和离线脚本统计：

```text

risk_decision_latency_ms
risk_action_total
risk_rule_hit_total
risk_event_publish_total
risk_event_consume_lag_ms

```

消费侧指标（`risk_event_processed`、`risk_event_duplicate_total`、`risk_review_pending`）
在统计前必须按 `requestId + operationType` 去重，避免 MQ 重投递导致重复计数。
消费端不写幂等 Key，去重只发生在离线统计阶段。

聚合前后对照实验固定使用同一攻击流量、同一用户分布和同一运行时长，分别执行：

```text
event-aggregation-enabled=false
event-aggregation-enabled=true
```

至少比较以下指标：

- 风险事件尝试发送数；
- 实际 MQ 发送数；
- `risk_event_suppressed_total` 与抑制率；
- RocketMQ 消费延迟 P50/P95/P99；
- 最大消息堆积量和恢复时间；
- 风险动作覆盖率（聚合后仍被记录的用户/动作比例）；
- 抢单接口整体延迟和错误率。

抑制率定义为：

```text
被聚合抑制的事件数 / 风险事件尝试发送数
```

聚合不得改变同步风险决策结果，只允许减少异步代表事件数量。

| 指标 | 目标 |
|---|---|
| 单次同步风控 P99 | `< 10ms` |
| 黑名单精确拦截率 | `100%` |
| 风控拒绝后的抢单 Redis/DB 调用 | `0` |
| 风控降级时新增超卖 | `0` |
| 2000 并发抢 1 个名额 | 成功 1 个，零超卖 |
| 重复风险事件 | 不产生重复业务状态；离线指标去重后每个请求操作最多 1 次 |
| 正常流量误伤率 | 通过关闭/开启风控配对压测实测 |
| 异步消息 | 无长期堆积；重复投递不影响指标口径 |

误伤率定义：

```text
关闭风控时本可成功、开启风控后被拒绝的请求数
/
关闭风控时本可成功的请求数
```

必须分别报告风控自身 P50/P95/P99、抢单接口整体 P50/P95/P99 和 RocketMQ 消费延迟。

本轮不修改前端，现有前端用户不会提供设备 ID，且服务端生成的 requestId
无法覆盖客户端重试去重；该限制必须写入最终交付物。

### 9.5 最终交付物

- 全量测试执行记录；
- 攻击流量压测报告；
- 风控路径故障降级报告；
- 结构化日志指标汇总；
- 原有抢单正确性校验结果；
- 实现范围和未变更范围说明。

## 10. 最终范围边界

完成 P9.5 后，本轮风控模块即视为完成。除非重新确认范围，否则不继续增加：

- 动态规则管理；
- 人工审核流程；
- 新的风控维度；
- 新中间件；
- 新服务进程；
- 与风控无关的代码重构。
